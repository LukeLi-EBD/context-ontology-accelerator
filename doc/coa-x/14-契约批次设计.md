# 14 · 契约批次设计（P5 / P7 / P8 / P9）

> 范围：契约设计 + 卡点 1 的 schema 迁移（`V47`）。不写 `.smithy`、不跑生成、不改业务代码。
> 依据：`09-platform整合评估.md` §5、`12-剩余51条批量排期.md`、`07-研发台账.md`、现有 `.smithy`、8099 桥接 `tools/coa_api_local.py`、`platform_core` 实现。

## 0. 结论

- **17 是候选清单数，不是最终新增数。** 逐条核对后：新增 7 个 op，字段扩展 1 处，剔除/并入 9 项。
- 11 个功能点（P5 4 个、P7 2 个、P8 2 个、P9 3 个）没有一个是“已有 op 够用”，都要落契约；缩的是 op 数，不是功能。
- **P9 不是 0 新 op。** `PublishOntology` / `RollbackOntology` 在 `.smithy` 里不存在，只有 8099 无类型路由。按契约口径算 **新增 2 个**。
- 两批模型都能独立生成，**都不依赖 P3 的 `facts.smithy`**；第二批要挂上网关，得先有 OntologyService。
- 三个实现差异已处理：manifest/card 数据源（§6 仍开放）、`import_batch` 命名空间（§4.4，已落 `V47` 并在克隆库实测）、rollback/publish 桥接缺口（§5.1 / §5.2 已取证，未改代码）。

## 1. 17 个候选的逐条去向

“17”按 09 §5 + 12 排期能对上的候选如下。去向只有三种：新增、扩展、剔除/并入。

| # | 候选 op | 去向 | 说明 |
|---|---|---|---|
| 1 | `ListMetricFamilies` | 剔除 | 族清单可由 manifest 行 + `GetMetricCard.variantOf` 本地归组；没有独立族索引页就不加 op。 |
| 2 | `GetMetricFamily` | 新增 | 族详情含变体并排与差异，无法由单品推导。 |
| 3 | `GetMetricReportManifest` | 新增 | 行级对外状态、执行预检、汇总计数需要服务端单源判定。 |
| 4 | `GetMetricCard` | 新增 | 口径卡详情（绑定列 + 对外状态）。见 §2 的替换理由。 |
| 5 | `GetMetric` 补 `externalStatus` | 并入 4 | OSI `GetMetric` 与口径卡不同源；硬补会把平台判定耦合进 metric-service。 |
| 6 | `GetMetric` 补 `fieldBindings` | 并入 4 | 同上，绑定数据在 `platform.metric_field_binding`。 |
| 7 | `ListMetrics` 补 `metricId` | 扩展 | 成员已存在，服务端补值即可，用于详情页跳口径卡。 |
| 8 | `CheckAnswerable` | 新增 | 本地已有实现与稳定响应形状，契约缺。 |
| 9 | `GetAnswerQuality` | 剔除 | F76/F79 只读预检结果，不需要质量分。 |
| 10 | `ListIngestionRuns` | 新增 | 批次列表与失败明细一次返回，F17/F18 共用。 |
| 11 | `GetIngestionRun` | 剔除 | 失败明细随列表内联（最多 20 条），不单开详情 op。 |
| 12 | `PublishOntology` | 新增 | 契约缺；8099 已有 `/publish`。 |
| 13 | `RollbackOntology` | 新增 | 契约缺；8099 已有 `/rollback`。 |
| 14 | `ListOntologyVersions` | 不在本批 | F111 已落位，走既有无类型路由；本批不新增，留 M2 统一收口。 |

| 17 | `RollbackOntology` 的 `planOnly/newVersion` | 并入 13 | 同上。 |

合计：**7 新增 + 1 扩展 + 9 剔除/并入 = 17**。

## 2. 关键判断：为什么口径卡要单开 op

`GetMetric` 契约上挂 `ControlPlaneService`，由 metric-service 实现，按 **name** 寻址，返回 OSI 指标定义。
F54/F56 要的字段（`metricId`、`fieldBindings`、`externalStatus`）在 `platform.metric_definition` / `metric_field_binding`，属 platform 内核，按 **metricId** 寻址。

两条路：

- **A（采纳）**：`ControlPlaneService` 新增 `GetMetricCard`，按 metricId 读平台口径卡。判定逻辑与 manifest 共用同一函数。
- **B（否决）**：给 `GetMetric` 加字段。代价是 metric-service 要读平台库、复制对外资格判定，两份状态迟早漂移。

代价：多 1 个 op。收益：单一数据源，无跨服务复制。
`ListMetrics` 只补 `metricId`，解决“详情页怎么拿到 metricId”的前置，不改判定。

## 3. 通用约定

| 项 | 约定 |
|---|---|
| 命名空间 | 路径统一 `Uuid`，36 位。平台口径表没有 namespace 列，契约仍保留该段；这是既有多租户差异，不是本批引入，实施卡点单列在 §6。 |
| 路径 | `/namespaces/{namespaceId}/...`；资源段用复数名词，动作段只用动词（`publish` / `rollback`）。 |
| 分页 | `maxResults` + `nextToken`；默认值写在成员文档里，不用 Smithy 默认值语法。小集合 op 可不分页，但要在文档里写明理由。 |
| 时间 | `String`，ISO 8601 UTC，例：`2026-11-10T08:00:00Z`。 |
| 错误 | 只复用既有形状，不新增。`ValidationError`(400)、`AccessDeniedError`(403)、`NotFoundError`(404)、`ConflictError`(409)、`ServiceUnavailableError`(503)。业务码放 `message` 的 `E_` 前缀，和现状一致。 |
| `E_` 语义 | `E_*_NOT_FOUND` → 404；`E_*_REQUIRED` / `E_*_BAD_FIELD` / `E_*_QUERY_*` → 400；`E_*_BREAKING` / `E_*_STATUS` / `E_*_CONFLICT` → 409；`E_*_UNAVAILABLE` → 503。 |
| Cedar | 读用 `readMetric` / `viewNamespace` / `query`；写用 `manageOntology`。读写不共用 action。 |
| 示例 | 每个 op 都要 `@examples`，放独立的 `*-examples.smithy`，用 `apply <Op> @examples([...])`。缺一个，`OperationMissingExamples` 让四个 job 全挂。 |
| 文档 | op、领域结构、枚举、枚举值都要 `///`；成员目标类型已有文档可豁免。 |
| 输入约束 | 字符串必须有 `@length`；数字必须 `min` + `max` 双侧 `@range`；list 必须有 `@length`；输入侧禁止裸 `Document`。 |

**HTTP**：`GET /namespaces/{namespaceId}/metrics/report/manifest`

**输入**

| 成员 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `namespaceId` | `Uuid` | 是 | 路径 | 命名空间。 |

**落地前提（已定：加列 + 回填）**：`platform.import_batch` 原本没有 `namespace_id`（V12 建表只有 `batch_id/root_path/status/options/created_at/updated_at/finished_at`），批次是全局表。已拍板走加列方案，不降级成全局 op——多命名空间是 COA 第一原则，不能因为表没跟上就退回管理员专用。

迁移 `V47__import_batch_namespace.sql`（V46 属 P4，本线用 47）：

- 加列：`namespace_id uuid`，可空；索引 `import_batch_namespace_updated_idx (namespace_id, updated_at DESC, batch_id)`。
- 新写入硬约束用 `BEFORE INSERT` 触发器 `import_batch_require_namespace`，**不用** `CHECK (namespace_id IS NOT NULL) NOT VALID`：`NOT VALID` 只跳过首次全表校验，之后每次 UPDATE 仍会检查，历史批次连 `status`/`updated_at` 都改不了（导入恢复和收尾都会失败）。触发器只拦新建行，历史行照常可更新；同 `root_path` 的 `INSERT ... ON CONFLICT DO UPDATE`（`importer._get_or_create_batch` 的恢复路径）放行，因为不会产生无 namespace 的新行。
- 回填策略（不瞎填）：
  1. 只有行内 `options->>'namespaceId'` 是合法 uuid 时才回填——那是调用方自己写的值，不算推断。
  2. 其余一律留 NULL，迁移里 `RAISE NOTICE` 报数，不写任何默认命名空间。
  3. 推不出的原因：`root_path` 是文件系统目录、`import_item` 没有 namespace 列、`platform.document.metadata` 只有 `batchId/relPath`；命名空间注册表在控制面 DynamoDB，不在本库，路径也不等于命名空间。
  4. 遗留 NULL 的处理：这些批次对命名空间过滤不可见，但恢复/收尾仍可用；需要归属时由运维按 `root_path` 手工 `UPDATE ... SET namespace_id='<uuid>'`，不做猜测式批量回填。

克隆库实测（`platform_v47_check`，从 5432 只读复制 `import_batch/import_item/schema_version`，现网 5432 未改）：

- 迁移前：18 个批次、18 个不同 `root_path`、`options ? 'namespaceId'` = 0；`options` 只有 `parseConcurrency/embedConcurrency/retryFailed/staleAfterMinutes/staleReason`。
- 真实 runner（`MetadataPg.migrate()`，不是手跑 psql）返回 `{'to': '47', 'applied': ['V47']}`，`platform.schema_version` 记到 47。
- 迁移输出 `NOTICE: V47: 18 of 18 import_batch row(s) have no derivable namespace and stay NULL (no default applied)`，回填 `UPDATE 0`。
- `\d` 确认：`namespace_id uuid` 可空、索引 `(namespace_id, updated_at DESC, batch_id)`、触发器 `import_batch_require_namespace BEFORE INSERT`。
- 行为：历史批次 resume upsert 通过（`namespace_id` 仍为 NULL）；历史批次普通 UPDATE（`status='completed'`）通过；新建批次不带 namespace 被拒（SQLSTATE `23502` / `E_IMPORT_NAMESPACE_REQUIRED`）；带 namespace 新建成功。
- 迁移幂等：同一文件重跑只出 `already exists, skipping`，无副作用。

配套与顺序：

- 写入侧：`importer._get_or_create_batch` 目前只写 `batch_id/root_path/status/options`，触发器生效后**新建批次必须带 namespace**，所以 `StartIngestion` 落契约时要同时改 insert 参数，否则 CLI `platform import` 新目录会直接失败。这条与 F17/F18 同批上线，不能只落迁移。
- 合并顺序：本线只有 47，合并后注册表必须是 45 → 46 → 47。任何共享环境不要在 V46 落库前跑本线 `migrate()`，否则高水位跳到 47，`migration_gap_versions()` 会让合并后的构建拒绝启动（这是既有保护，不是新问题）。

### 5.2 `RollbackOntology`（F115 / F117，兼 F116）

**归属**：`OntologyService`。理由同 5.1。

**HTTP**：`POST /namespaces/{namespaceId}/ontologies/{ontologyId}/rollback`

**输入**

| 成员 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `namespaceId` | `Uuid` | 是 | 路径 | 命名空间。 |
| `ontologyId` | `OntologyId` | 是 | 路径 | 本体 id。 |
| `targetVersionId` | `String` | 是 | `@length(1,128)` | 回退目标。 |
| `mode` | `RollbackMode` | 是 | 枚举 | `POINTER_ONLY`（F116）/ `NEW_VERSION`（F117）。必填，不给默认，避免误建版本。 |
| `expectedVersionId` | `String` | 否 | `@length(1,128)` | 乐观并发：当前指针必须等于它。 |
| `dryRun` | `Boolean` | 否 | — | `true` 只返回计划（F115 预览）；默认 `false`。 |
| `reason` | `String` | 否 | `@length(1,1024)` | 回退原因，进审计。 |
| `actor` | `String` | 否 | `@length(1,256)` | 操作人。 |

`RollbackMode` 两个值都要文档：`POINTER_ONLY` 只挪指针；`NEW_VERSION` 复制目标内容建新版本再挪指针。

**输出**

| 成员 | 类型 | 说明 |
|---|---|---|
| `dryRun` | `Boolean` | 是否预检。 |
| `mode` | `RollbackMode` | 回显。 |
| `targetVersionId` | `String` | 目标版本。 |
| `targetTriples` | `Integer` | 目标三元组数。 |
| `replacedVersionId` | `String` | 被替换的当前版本，可空。 |
| `publishedVersionId` | `String` | 生效版本：`POINTER_ONLY` 等于目标；`NEW_VERSION` 是新 id。 |
| `rollbackOf` | `String` | 新版本的来源目标，仅 `NEW_VERSION`。 |
| `semver` | `String` | 生效版本语义版本；新版本为 `目标版本+rollback.N`。 |
| `graph` | `String` | 图 IRI。 |
| `contentHash` | `String` | 内容哈希，仅 `NEW_VERSION`。 |
| `wouldChangePointer` | `Boolean` | 预检：指针会不会变。 |
| `unchanged` | `Boolean` | 目标已是当前指针。 |
| `rolledBackAt` | `String` | 生效时间。 |
| `rolledBackBy` | `String` | 操作人。 |
| `blockers` | `RollbackBlockerList` | 预检阻断项，结构同 `PublishBlocker`。 |

契约名与平台字段映射：预检 `targetVersionId`←`versionId`、`targetTriples`←`triples`、`replacedVersionId`←`currentVersionId`；真实回退 `publishedVersionId`←`id`、`rollbackOf`←`rollbackOf`。

**错误**：
- `ValidationError`（400）：缺 `targetVersionId`、缺 `mode`。
- `NotFoundError`（404）：目标版本不存在。
- `ConflictError`（409）：目标为 `draft` / `deprecated`（`E_ONTOLOGY_STATUS`）、目标已是当前指针、并发指针冲突。
- `ServiceUnavailableError`（503）：图不可装载。

**Cedar**：`manageOntology`，资源 `Ontology`，id = `ontologyId`。预检同 action。

**示例**：

```json
{
  "input": { "namespaceId": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
    "ontologyId": "urn:ontology:fsldm-tbox", "targetVersionId": "ont-f413054a0c72",
    "mode": "NEW_VERSION", "dryRun": true },
  "output": {
    "dryRun": true, "mode": "NEW_VERSION", "targetVersionId": "ont-f413054a0c72",
    "targetTriples": 234, "replacedVersionId": "ont-4d9c2a1b7e3f",
    "wouldChangePointer": true, "unchanged": false,
    "rolledBackAt": "2026-11-10T08:10:00Z", "rolledBackBy": "operator",
    "blockers": []
  }
}
```

**落地缺口（取证结论）**：

平台侧两个入口语义不同，都已核对代码：

- `rollback_to` = **切指针，不建版本**：[ontology_pg.py](file:///D:/agentABC/wt/contract-design/packages/platform-core/src/platform_core/adapters/ontology_pg.py#L3717-L3800)（`def rollback_to`，第 3717 行）。目标版本改 `published`、原指针版本改 `superseded`，再 `UPDATE platform.graph_pointer` 指到目标；`draft` 拒绝（`E_ONTOLOGY_STATUS`），`deprecated` 拒绝（`E_ONTOLOGY_READONLY`）。指针没变时返回 `unchanged: true`。
- `rollback` = **复制目标内容建新版本再切指针**：[ontology_pg.py](file:///D:/agentABC/wt/contract-design/packages/platform-core/src/platform_core/adapters/ontology_pg.py#L4231-L4297)（`def rollback`，第 4231 行）。新 id `ont-<hex12>`，semver `目标semver+rollback.N`，写 `rollback_of`，指针指新 id。
- `packages/context-manager` 没有 rollback 实现，全包只有 [defaults.py](file:///D:/agentABC/wt/contract-design/packages/context-manager/src/coa_serve/tier3/agentic/defaults.py#L13) 一句注释提到 rollback，因此语义完全由 platform-core 定义。
- 两条路径并存的原因写在 [OPEN-QUESTIONS.md](file:///D:/agentABC/wt/contract-design/packages/platform-core/OPEN-QUESTIONS.md#L55) OQ-48：S11 明确 `rollbackTo(version)` 只回切指针，S1 的旧 `rollback` 按 OQ-14 建新版本；两者都不删版本与图。

桥接侧（`doc/coa-x/tools/coa_api_local.py:1004-1016`）：`planOnly=true` → `GET /governance/rollback/plan`；否则固定 `POST /governance/rollback-to`。平台已有的 `POST /governance/rollback`（[api.py](file:///D:/agentABC/wt/contract-design/packages/platform-core/src/platform_core/api.py#L3310-L3333)）没有被暴露。所以：

- `mode=NEW_VERSION` 必须补一条桥接映射，否则 F117 无处落地。
- 桥接读 `planOnly`，契约用 `dryRun`，必须做一次参数映射。
- `expectedVersionId` 桥接已支持。

**本批结论**：模型能独立编译，但**当前网关挂不上**——`OntologyService` 尚未落地，且 `NEW_VERSION` 桥接缺失；不依赖 `facts.smithy`。示例放 `ontology-lifecycle-examples.smithy`。若 P9 必须在 M2 前上线，临时挂 `ControlPlaneService`（路径不变），M2 再迁；本文默认按 OntologyService 设计。

## 2. Q1 · 候选排序

### 2.1 判据

「能跑起来」在本机拆成两条，缺一不可，所以两条都给出：

- **轴 A（起进程）**：能否在本机起一个监听 HTTP 的长期进程。
- **轴 B（跑逻辑）**：能否在不连 AWS 的前提下执行真实业务逻辑。

「依赖能备齐」按**启动时是否真的需要新装包**算，不算 `uv lock` 能不能解析。

排序的**第一判据是轴 B**：因为「真正跑起来」的字面含义是「跑出真结果」，只有轴 A、轴 B 都为空的组合不算。若只看轴 A，排序会变成 `ontology-engine` → `vkg` → `mcp-server`（见 §2.4 末尾的对照）。

### 2.2 排序结果

| 排名 | 服务 | 形态 | import 实测 | 轴 A 起进程 | 启动新增依赖 | 轴 B 跑逻辑 | 断点性质 |
|---|---|---|---|---|---|---|---|

**① `metric-service`**

### 2.4 与计划的冲突（需要决策）

`00-总计划.md:112` 写「阶段 2 · `data-layer`：……替换它仅有的 3 个 AWS 点……本机起服务，逐条调 5 个契约操作」。

**对照：如果只按「能起监听进程」排序**（不看能否跑出结果），顺序变为：

| 只看轴 A | 服务 | 起进程代价 |

## 6. Q5 · `vkg` 单独评

**原判断「唯一接近能算的」不再准确，应改为「唯一接近能起的」。**

### 6.1 `smithy-generated` 入库对它没有影响（可证）

- `packages/vkg/pyproject.toml` 的 dependencies 只有 `coa-common` + `sqlglot` + `rdflib` + `certifi`。
- `translate-server.py` 全文只 `import sqlglot`（`:52`），`rdflib` 还是 `_load_table_routing` 里的函数内可选导入（`:151`）。
- `packages/vkg/src/coa_vkg/__init__.py` 为空。

即：`translate-server.py` 运行期**既不 import `coa_common`，也不 import 任何 smithy 生成物**（`coa-common` 只是写在 pyproject 里、这条入口没用到）。生成物齐了、`uv lock` 通过，对 vkg 的启动能力**没有任何变化**——它本来就不缺这些。

### 6.2 真正的卡点是三件非 pip 的东西

| 条件 | 现状 | 依据 |
|---|---|---|
| Ontop 5.x 可执行体 | **无**。全盘搜索 `ontop*.jar` 为空 | `Get-ChildItem D:\agentABC -Recurse -Filter "ontop*.jar"` 无结果 |
| Java 17 | **不满足**。本机 `java version "1.8.0_341"` | `java -version` |
| 本体 + R2RML 映射文件 | **无本机副本**。容器内从 S3 下载后一次性加载 | `translate-server.py:18-21` 注释；`:753` `MAPPINGS_FILE` 默认空，`:148-149` 空文件直接返回 `{}` |

三件缺任何一件，`/health` 都恒 503：`_probe_health`（`:242-257`）要求 actuator UP **且** 探针 SPARQL 能重写成 SQL（`:221-239`）。

### 6.3 结论

| 维度 | 判断 |
|---|---|
| 能起进程 | ✅ 是，且是七条里唯一「0 依赖、现在就起」的 |
| 能算 | ❌ 否。没有 Ontop 就没有任何一次 SPARQL→SQL 重写 |
| 之前为什么被当成「接近能算」 | 因为它是唯一一个不依赖 AWS 语义的组件；但这个「不依赖 AWS」来自它把全部复杂度外包给了 Ontop 二进制，不等于本机可算 |
| 阶段 2 是否应从它开始 | **不建议**。它的阻塞项（下载 jar + 装 JDK17 + 准备映射）都在外网/二进制侧，与「COA 服务本地化」这条主线正交；把它做成只能得到一个恒 503 的空壳 |

**未验证**：装上 Ontop 5.x + JDK17 后 `/ontop/reformulate` 是否能在本机返回可用 SQL（无二进制，无法验证）。本机 Ontop 版本、mapping 语法兼容性亦未验证。

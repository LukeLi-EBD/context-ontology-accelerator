### 1.2 接口读数

```
GET  /namespaces/{ns}/ontologies/ont-demo/versions      → total=1911, count(本页)=613
GET  /namespaces/{ns}/ontologies/ont-demo/proposals     → count=1315, items=50
POST /namespaces/{ns}/ontologies/ont-53fb5cb43f5b/verify
     → {"ok":true,"checked":10141,"prov":{"ok":true,"checked":0,...}}
GET  /namespaces/{ns}/ontologies/ont-53fb5cb43f5b/events?limit=1|50|1000
     → count=1|50|1000（= 本页条数，恒等于 items 数）
```

`verify.checked` 的口径：`verify_events()` 无 `LIMIT` 全量读取 `platform.ontology_event ORDER BY event_id`，逐行校验 `prevEvent` 与 `hash`，返回 `checked = len(records)`（[ontology_pg.py:1852-1875](file:///d:/agentABC/wt/luke-p115/packages/platform-core/src/platform_core/adapters/ontology_pg.py#L1852-L1875)）。因此 `checked=10141` 就是哈希链里的**事件总行数**，不是分页条数。

注意：`verify` 会先跑 `ensure_chain()`；它只在 `prev_event`/`hash` 缺失时执行 `UPDATE`。本次调用前后 `ontology_event` 行数一致（10141→10141），未观察到写入。

`GET .../events` 的 `count` 是**本页条数**，单次上限 1000，不能用来读总数。

### 1.3 页面上"一行"是什么

| 页面 | 取数 | 一行代表 | 上限 |
| --- | --- | --- | --- |
| 本体版本页的审计面板 | `listOntologyEvents(ns, oid, {versionId, limit: 50})` | 该版本的 1 条治理事件：`eventId / action / actor / reason / payload / hash / prevEvent` | 50 行/版本 |
| 治理页 | `listOntologyEvents(..., {limit: 100})` | 同上，跨版本的事件明细 | 100 行 |

代码位置：[OntologyVersions.tsx:242-246](file:///d:/agentABC/wt/luke-p115/packages/web-app/src/pages/ontology/OntologyVersions.tsx#L242-L246)、[GovernancePage.tsx](file:///d:/agentABC/wt/luke-p115/packages/web-app/src/pages/governance/GovernancePage.tsx)。

结论：10,141 是**审计事件明细表的行数**（哈希链长度），不是任何页面上的聚合指标；页面只渲染前 50/100 行，**不显示总数**。所以"页面上可读到 10,141"这一验收口径不成立，只能改成"接口 `verify.checked` 可复核"。

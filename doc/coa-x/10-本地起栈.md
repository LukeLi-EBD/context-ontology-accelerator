# 10 · COA 原版本地栈一键盘

一条命令拉起上游 COA 后端（不是 `platform-core` 8080/8082 那套）：

```powershell
powershell -ExecutionPolicy Bypass -File .\10-本地起栈.ps1          # 起栈
powershell -ExecutionPolicy Bypass -File .\10-本地起栈.ps1 -Seed     # 起栈前重灌本体
powershell -ExecutionPolicy Bypass -File .\10-本地起栈.ps1 -Stop     # 停进程 + 停容器
```

## 管什么、不管什么

| 角色 | 地址 | 形态 | 由脚本管理 |
| --- | --- | --- | --- |
| API 桥 | `127.0.0.1:8099` | 进程 `tools/coa_api_local.py` | 起/停 |
| ontology-engine | `127.0.0.1:8101` | 进程 `tools/coa_ontology_local.py` | 起/停 |
| context-manager | `127.0.0.1:8091` | 进程 `run_local.py context-manager` | 起/停（`/query`、`/kb/search` 在此执行） |
| PostgreSQL（pgvector） | `127.0.0.1:5444` | 容器 `coa-local-pg` | 起/停（数据卷 `coa-local-pg-data`） |
| Oxigraph | `127.0.0.1:7878` | 容器 `coa-local-oxigraph` | 起/停（数据卷 `coa-local-oxigraph-data`） |
| 前端 dev server | `127.0.0.1:5173` | 本地 vite（未跟踪配置） | **不管**，单独起 |
| 验收栈 | `8080` / `8082` | 既有平台栈 | **不碰** |

`-Stop` 只停「端口 + 命令行」都对得上的三个进程；容器用 `docker stop`，命名卷保留，
再次启动数据原样回来。`-KeepContainers` 可只停进程。

## serve 库一次性初始化

`8091` 的 context-manager 读 `serve_local` 库（平台元数据 + 真实 BGE chunk）。
这个库不在容器初始化里，需要在**第一次**起栈前跑一次（幂等，可重复跑）：

```powershell
$dsn = "postgresql://platform:platform_dev@127.0.0.1:5444/serve_local"
& .\.venv-coa-local\Scripts\python.exe doc/coa-x/tools/local_bootstrap.py migrate --dsn $dsn
& .\.venv-coa-local\Scripts\python.exe doc/coa-x/tools/local_bootstrap.py seed    --dsn $dsn
```

`migrate` 跑 platform-core 的真实迁移（68 张表），`seed` 写入 3 条 FS-LDM chunk 及其
BGE 向量（依赖 8081 的嵌入服务）。没初始化时 `10-本地起栈.ps1` 只 `warn` 不炸栈，
但 `/query`、`/kb/search` 会返回 500。

## 数据

- 本体：`doc/_fsldm/fsldm-merged.ttl`（2675 三元组 / 156 个 `owl:Class` /
  84 个 `owl:ObjectProperty` / 45 个 `owl:DatatypeProperty`）。`-Seed` 用 GSP PUT
  覆盖写入**独立命名图**
  `https://coa.local/graph/<namespace>/<quote(ontology_id)>`，与 metric 的
  `urn:coa-metrics:` 图完全分开。
- 注册表：与 API 桥共用 `public.coa_local_items`（逻辑表 `coa-local-ontologies`），
  读路径由 `coa_local_providers.ontology_registry_pg` 接管。
- 默认演示命名空间：`ed70a15c-2d42-4dc9-8c61-33b2584f05fd`（`-Namespace` 可改）。

## 替换口径

每处 AWS 依赖都由显式 provider 键选择，**无默认值，缺键拒绝启动**：

| 键 | 值 | 缺失时 |
| --- | --- | --- |
| `COA_PROVIDER_ONTOLOGY_GRAPH` | `oxigraph` / `neptune` | 启动即报错 |
| `COA_ONTOLOGY_OXIGRAPH_URL` | `http://127.0.0.1:7878` | `oxigraph` 分支启动即报错 |
| `COA_PROVIDER_ONTOLOGY_REGISTRY` | `postgres` / `dynamodb` | 启动即报错 |
| `COA_CONTROL_PLANE_PG_DSN` | 本地 5444 的 DSN | `postgres` 分支启动即报错 |

## 对账：开发只告警，验收必须阻断

起栈第 4.5 步会跑 **只读**对账（`tools/reconcile_fact_ledger.py`），核对
`platform.fact_assertion` / 候选状态 / A-Box 投影三方是否一致。两种模式：

| 模式 | 触发方式 | 有差异时 |
| --- | --- | --- |
| 开发/日常起栈 | 直接 `.\10-本地起栈.ps1`，或 `-Stop`（不跑到 4.5） | `[warn]` 一行，栈照常可用 |
| **验收模式** | `.\10-本地起栈.ps1 -StrictReconcile` 或环境变量 `COA_RECONCILE_STRICT=1` | 直接 `exit 1`，不起后面的服务；对账根本没跑成也算失败 |

```powershell
# 8 步验收 / 功能点核对 / M3 闸门：干净起栈
$env:COA_RECONCILE_STRICT = "1"
powershell -ExecutionPolicy Bypass -File .\10-本地起栈.ps1
# 等价写法
powershell -ExecutionPolicy Bypass -File .\10-本地起栈.ps1 -StrictReconcile
```

为什么分两种：验收的价值在于「干净」。带着已知不一致跑出来的通过没有意义，所以
验收路径必须 fail-closed；开发期若一次对账就把栈卡住，会逼人跳过它。

修复永远是显式动作，不在起栈里做：先看六桶明细，再决定
`reconcile_fact_ledger.py --fix --actor <who>`（会写 `reconciled` 审计事件）。

## 已知窟窿（验收必看）

1. **ontology 502 的来龙去脉**：此前 8101 未启动，8099 的 `/namespaces/{ns}/*`
   按路由表转发到 `ONTOLOGY_ENGINE_ENDPOINT`，连接被拒即 502（不是 404，也不是空数据）。
   本轮起 8101 后**读路径**已 200：`/ontologies`、`/graph/search`、`/graph/schema`、
   `/graph/ontology-overview`、`/graph/vertex` 都是真读 Oxigraph / PG。
   **写/归纳链路仍是上游 AWS**：DynamoDB 的 job/proposal、S3 产物、Bedrock 嵌入、
   OpenSearch 向量都没有本地实现；`POST /ontologies/{id}/upload`、induction 等会失败。
2. **数据库源只能靠本地目录快照注入，UI 无法新建**：新建数据库源要走
   Glue / DataZone / Secrets Manager；本地没有这些，桥用
   `COA_PROVIDER_METADATA_CATALOG=json-snapshot` + `POST /local/seed-catalog`
   把 `tools/local-catalog.json` 里的 APPROVED 快照写进去。
   **验收陷阱**：在 UI 里点「新建数据库源」不会成功，这是数据源契约缺口，不是前端 bug；
   UI 新建 DOCUMENTS 源是真实可用的。
3. **metric 向量索引 best-effort**：`platform-pg` 索引缺少
   `platform.metric_definition` schema，嵌入失败只告警、不阻断；指标真身在 Oxigraph
   `urn:coa-metrics:` 图里。判定指标是否落地要看图，不要看向量条数。
4. **类实例缺口（数据面 + 契约双缺）**：`fsldm-merged.ttl` 没有 `owl:NamedIndividual`，
   也没有任何领域类的 ABox 实例；95 个 `skos:Concept` 只是词表概念。
   COA 的 `GraphVertexKind` 只定义 class / object-property / datatype-property，
   前端也没有实例浏览入口。因此「某个类下的实例」在本地数据与契约里都没有来源，
   本轮不造假数据补齐。
5. **PowerShell 上传中文标题会乱码**：`Invoke-RestMethod` / `Invoke-WebRequest`
   发 JSON 时默认不声明 UTF-8 charset，Windows PowerShell 5 会按本地代码页编码请求体，
   服务端收到的 `title` 变成 `??????`。用 Python（httpx/requests，`json=`）或
   浏览器页面上传不受影响。历史那份乱码文档不用回填，下次 `-Seed` 会自然覆盖。
6. **Node 版本偏差**：仓库 `.mise.toml` 钉 `node = "22.23.4"`，`package.json`
   `engines.node` 是 `>=22.23.4`；本机实际是 `v22.23.2`，不满足 engines。
   本轮 `pnpm run build`、`tsc --noEmit`、`prettier` 都能跑，但 `pnpm install`
   会按 engines 报不满足；换机器或重装依赖前先 `mise install`（或升级 Node），
   别把「本机能跑」当成版本已对齐。
7. **本机 JDK 是 1.8，CI 的 Gradle 路径只能在 JDK 17 容器里跑**：CI 是
   `cd models && ./gradlew clean build`（Gradle 9.4.1）。本机跑不了的原状是
   `java -version` = `1.8.0_341`，且 `services.gradle.org` 指向 GitHub 不可达 →
   `Downloading …/gradle-9.4.1-bin.zip` 后 `Read timed out`（10 秒）。
   2026-11-10 已跑通，做法是从腾讯镜像取
   `https://mirrors.cloud.tencent.com/gradle/gradle-9.4.1-bin.zip`（137,878,901 字节），
   在 `eclipse-temurin:17-jdk` 容器里解压成 `gradle` 二进制（`chmod +x`）后直接
   `gradle clean build`，绕开 wrapper 的下载与 CRLF 问题。产物在
   `models/build/smithyprojections/models/`。
   **两条路验证的 shape 数不同，别混用结论**：Gradle 路径 `Validated 2467 shapes`
   （依赖模型不在验证范围）；本地 Docker 把手解出来的依赖模型当 `sources` 时是
   `2918 shapes`。后者是离线绕法的副产物，不是 CI 的行为。
   离线（无 Gradle）时的备用路径是 Docker + `smithy-jars` 下的 Maven 坐标 jar：
   `java -cp '/jars/*' software.amazon.smithy.cli.SmithyCli build --config /cfg/openapi.json`
   （TS 用 `--config /cfg/ts.json`），产物写 `models/build`。Python 模型另用
   `openapi-generator-cli-7.12.0.jar`（生成前需去掉 `format: password`）。
   指纹脚本是 CRLF 的 bash 脚本，PowerShell 下的 `bash` 是 WSL，需按
   `/mnt/d/agentABC/coa` 路径跑并先 `tr -d '\r'`。`scripts/smithy-generate.sh`
   未改，**复跑时别指望 `make generate`**。
8. **查询链路已本地化，但合成依赖外部 LLM**：`POST /namespaces/{ns}/query` 与
   `/kb/search` 经 8091 的 context-manager 执行，图（Oxigraph）、向量（pgvector）、
   元数据、嵌入（8081 BGE）都是本地 provider；T3 的答案合成走 `openai-http`，
   key/base/model 从 `packages/platform-core/.env` 的 `PLATFORM__LLM__*` 读取。
   没有 key 时 `/query` 会 500，不会静默降级成空答案。
9. **生成产物被 Windows 编码工具改写会带 BOM**：`smithy-generated/data-layer-python-server/
   coa_data_layer_server/__init__.py` 曾以 `EF BB BF` 开头（文件首字符变成 `\ufeff#`）。
   这是 Windows 侧写入的复发坑——`Set-Content -Encoding UTF8` / `Out-File` 在
   PowerShell 5.1 下会补 BOM，而生成脚本里的 bash `echo` 不会。Python 3 能容忍源码
   BOM，所以本地 import 不一定报错，**真正代价是漂移闸门必红**（生成器输出无 BOM），
   而且带 BOM 就说明有人用 Windows 的写法手改过生成文件——手改本身就是漂移源。
   回灌产物一律整目录复制或用生成脚本，不要用 `>` / `Set-Content` 写 `smithy-generated/`。
10. **本地 `cdk synth` 卡在资产打包的 Docker → PyPI 下载**：`infra/lib/utils/python-bundling.ts:204`
   在 Windows 上一律退回 Docker 打包（本地 `uv` 路径只给 Linux 用），所以 synth 必然要跑
   `public.ecr.aws/sam/build-python3.12` 容器里的 `pip install`。2026-11-10 实跑三次，全部在
   `app.synth()` 的资产打包阶段失败，构造期（含 `api-stack.ts` 的接线守卫）没有报错：

   | 次 | 现象 | 原始错误 |
   | --- | --- | --- |
   | 1 | 容器内 pip 25 分钟停在 928 文件 / 3 MB、CPU 0.00%，手动 kill | `docker exited with status 137`（`coa-dev-namespace/NamespaceApiFn`） |
   | 2 | 同上位置超时 | `ReadTimeoutError: HTTPSConnectionPool(host='files.pythonhosted.org', port=443): Read timed out.` → `docker exited with status 2` |
   | 3 | 先报解析失败 | `Could not find a version that satisfies the requirement cedarpy==4.12.2 (from versions: none)` → `docker exited with status 1` |

   第 3 次容易误判成「包不存在」，实测是网络：同一镜像内 `curl` 取
   `cedarpy-4.12.2-cp312-cp312-manylinux_2_17_x86_64.manylinux2014_x86_64.whl`（1.13 MB）
   `--max-time 60` 只下到 1.13 MB 边界、耗时 60 s（约 19 KB/s）；宿主机对同一 URL `HEAD` 200，
   清华镜像 `simple/cedarpy/` 0.59 s。**Docker NAT 到 PyPI CDN 被限速**，pip 的默认 15 s 读超时
   先把它变成 `Read timed out`，`-q` 下又表现为 `from versions: none`。

   本机绕过（只为取证，不是仓库改动）：给该镜像加 `/etc/pip.conf` 指清华源
   （`index-url = https://pypi.tuna.tsinghua.edu.cn/simple`、`timeout = 60`），`docker tag` 回原 tag。
   lock 是 `--require-hashes`，换源只能拿到同哈希字节，拿错会直接失败而不是静默通过。
   换源后同一 wheel 2.3 s 下完。原始镜像 id 为 `sha256:09821e36135d…`，需要时 `docker tag` 回去。

   **定性：本地环境阻塞，不是合成逻辑失败。** CI 的 `cdk-synth` 跑在 GitHub runner（Linux，
   走本地 `uv` 路径），是否同样慢未验证——按未验证记，别把本机结论外推成 CI 结论。

## 生成产物漂移闸门

`smithy-generated/` 是**已提交**的目录（本轮回灌后 1024 个文件），而生成器每轮都
`rm -rf` 整目录重建。两者一旦不一致，仓库就带着旧契约发布，而 CI 只会拿「刚生成的
产物」去跑测试，永远发现不了。所以生成之后必须比一次：

```bash
changed="$(git status --porcelain -- smithy-generated \
  ':(exclude)smithy-generated/.inputs.sha256' \
  ':(exclude)smithy-generated/openapi/build-info')"
[ -z "$changed" ] || { echo "$changed"; git --no-pager diff --stat -- smithy-generated; exit 1; }
```

判据：**生成产物目录与已提交内容逐字节一致**，不为空即失败。用 `git status` 而不是
`git diff`，因为后者只看已跟踪文件，会漏掉「生成器新产出、仓库里没有」的文件——
本轮回灌就碰到 6 个（`graph_statement.py` / `list_statements_response_content.py`
及其 docs / test）。客户端自带的 `.gitignore` 已排除 `dist-*` / `node_modules` /
`*.tsbuildinfo`，比的是契约源码，不是构建缓存。

两处必须排除。它们记录的是**生成环境**，不是契约，留在判据里会让闸门每轮假红：

| 排除项 | 为什么排除 | 实测 |
| --- | --- | --- |
| `.inputs.sha256` | 指纹脚本对输入文件的**原始字节**求哈希；仓库 `core.autocrlf=true`，CI 检出 LF、本地检出 CRLF | 同一棵树：LF `afc3a2e0fb04fc523f05132248fd1705accce8c19c5ec37aa9f420be2fa2b565`，CRLF `1e3bc93b18a5799a0395c4c214894790536b31fdd563faa50c2cbf91ff85883d` |
| `openapi/build-info/smithy-build-info.json` | `validationEvents[].filename` 是绝对路径，仓库里是 `/work/src/…`，CI 是 `/home/runner/…` | 逐文件比对时唯一不一致的 OpenAPI 产物 |

### 一致性前提已验证（2026-11-10）

闸门只有在「本地提交的产物 == CI 生成的产物」时才不是假门。本轮按 CI 同一条路
（Gradle 9.4.1 + JDK 17，`gradle clean build`）实跑，再与提交产物逐文件比
（CRLF→LF 归一后取 SHA256）：

| 产物 | 结果 |
| --- | --- |
| `control-plane-typescript-client` 137 个文件 | 全同（`package.json` 的 `build` 脚本经生成脚本 `sed` 改写，与仓库一致） |
| `data-layer-typescript-client` 33 个文件 | 全同 |
| `openapi/openapi/*.json`、`model/model.json`、`sources/model.json`、`sources/manifest` | 全同 |
| `openapi/python-codegen/*.json` | 已按脚本的 `json.dump(indent=4)`（`ensure_ascii=True`）重写 |
| 两个 `*-python-server` | 已用同版本 `openapi-generator-cli-7.12.0` 重生成 |

顺带证明闸门不是空转：回灌前仓库里的产物已经落后于模型——`*-python-server` 缺
`domain` / `evidenceBasis` / `publishable` 三个字段、缺 `GraphStatement` 与
`ListStatementsResponseContent` 两个 schema，`data-layer` 的 `__init__.py` 还带
UTF-8 BOM，`openapi/` 里连 `/graph/statements` 这条路由都没有。这些都会被闸门判红，
本轮按生成结果一并回灌。

落在 CI：`.github/workflows/pr.yml` → `smithy-generate` job → **Check generated
artifacts are committed**（在生成之后、上传 artifact 之前，失败即整个 job 失败）。

为什么不做成提交前脚本：

- 本机能跑 CI 同款 Gradle，但要「腾讯镜像 + JDK 17 容器 + 手动解压分发」（见上面
  窟窿 7），不是一条 `make generate` 就完事的常规动作；本地 Docker 路径又与 CI
  不同源，拿它的产物当基准会「本地绿、CI 红」。
- 提交前钩子可以被跳过；CI 这一步与下游 `needs` 串联，跳不过。

失败时怎么做：按 CI 同一条路重跑生成，把 `smithy-generated/` 的 diff 和模型改动
放进**同一个提交**。不要手改生成文件——手改的下一步就是漂移。取证记录见
`11-D组缺口评审.md`「CI 的 smithy build 是红的」。

回到离线生成（窟窿 7 的 Docker + Maven 坐标 jar 路径）时必须多做一步：**把
`linters.smithy` 保留在 `sources` 里跑一次 validate**，只删它生成第二遍。因为删掉
linter 的绕法会把仓库自己的 DANGER 一起吞掉——本轮 `ListStatements` 缺
`@examples` 就是这么漏过本地检查、直到 CI 才发现的。

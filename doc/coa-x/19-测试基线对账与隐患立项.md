## 2. 立项：data-layer 的同源 502（只写不改）

### 2.1 触发路径

**前置条件（两条同时成立才会挂）：**

1. 环境变量 `COA_PROVIDER_CONTEXT_MANAGER` 有值（如 `local-http`）；
2. Lambda bundle 里没有 `coa-runtime` / `coa-ports`。

当前 `infra/lib/stacks/services/data-layer-stack.ts:85-91` 的 `environment` **没有设置** `COA_PROVIDER_CONTEXT_MANAGER`，所以今天部署走的是 AgentCore 分支。这条隐患的准确性质是：**配置一开就 502**，不是「线上正在 502」。也正因为如此，本地与测试都碰不到它。

**分叉点**在 `packages/data-layer/src/coa_data_layer/handler.py:105`：

```python
if os.environ.get("COA_PROVIDER_CONTEXT_MANAGER", "").strip():
    return _invoke_context_manager_via_port(payload, token)
return _invoke_context_manager_via_agentcore(payload, token)
```

**会走到的路由**（`handler.py:800-807` 的 `_ROUTE_MAP`，全部在请求期调用 `_invoke_context_manager`）：

| 方法 | 路由 | 调用点 |
|---|---|---|
| POST | `/namespaces/{namespaceId}/query` | `handler.py:480` |
| POST | `/namespaces/{namespaceId}/translate` | `handler.py:510` |
| POST | `/namespaces/{namespaceId}/kb/search` | `handler.py:545` |
| POST | `/namespaces/{namespaceId}/sparql` | `handler.py:574` |
| POST | `/namespaces/{namespaceId}/graph/traverse` | `handler.py:622` |
| GET | `/namespaces/{namespaceId}/schema` | **不经过**（直接代理 ontology-api-proxy，`handler.py:638`） |

**惰性导入发生在 `handler.py:147-153`**（函数体内，不是模块级）：

```python
import asyncio
from coa_ports import ContextAction, ContextRequest, PortError, Principal
from coa_runtime.registry import resolve
from coa_runtime.settings import Settings
```

再往下：`resolve("ContextManagerPort", ...)`（`handler.py:176`）→ catalog 工厂 `_context_manager_local_http`（`packages/coa-runtime/src/coa_runtime/catalog.py:357-367`）→ `from coa_local_providers.context_manager_http import LocalHttpContextManager`。该模块模块级 `import httpx`（`context_manager_http.py:39`）。

**bundle 现状**（`data-layer-stack.ts:69-72`）：

```python
bundlePython({
  srcDirs: [fromRoot("packages/data-layer/src"), Paths.commonLib],
  requirementsFile: fromRoot("packages/data-layer/requirements.lock.txt"),

```

`Paths.commonLib` = `libs/common/src`（`infra/lib/paths.ts:82`）。`requirements.txt` 只有 `pydantic` / `pydantic-settings` / `structlog` / `certifi`（`packages/data-layer/requirements.txt`）。即：**bundle 里没有 `coa_ports`、没有 `coa_runtime`、没有 `coa_local_providers`、没有 `httpx`。**

现有守卫看不见这条链：`tests/unit/test_lambda_bundle_deps.py:188` 只遍历 `ast.parse(...).body`，即**模块级语句**；`handler.py:149-153` 的 import 在函数体内，不会被收集。所以这个缺口在单测里是绿的，不是守卫失效，是扫描范围到不了函数内部。

补充一个比「少两个包」更麻烦的事实：即使只补 `coa-runtime` + `coa-ports`，导入仍会失败。因为 `coa_local_providers/__init__.py` 在包初始化时 eager 导入 `json_lookup`，而 `json_lookup.py:17` 导入 `coa_metrics.lookups`；`coa_metrics` 位于 `packages/metric-service/src`，不在任何 data-layer 的 `srcDirs` 里。`coa_metrics.lookups.py:22-26` 又继续导入 `coa_common.metadata_store.reader` → `smus`。所以完整导入链是：

```
handler.py:147-153
├─ coa_ports                      ← 缺
├─ coa_runtime (registry/settings/catalog/contexts/env_config)   ← 缺
└─ coa_local_providers.context_manager_http
   └─ coa_local_providers/__init__  (eager)
      ├─ win_compat                ← 在 local-providers 内
      └─ json_lookup → coa_metrics.lookups  ← 缺（metric-service/src）
         └─ coa_common.metadata_store.reader → smus (boto3，Lambda 运行时自带)
   └─ httpx                        ← 缺（pip）
```

### 2.2 影响

- **线上表现**：`ModuleNotFoundError` 在 `handler()` 的兜底分支被捕获（`handler.py:854-856`），返回：

  ```json
  {"statusCode": 502, "body": "{\"message\": \"Context Manager invocation failed: ModuleNotFoundError\"}"}
  ```

  API Gateway 侧就是 502。
- **错误信息能否看出缺模块**：**不能**。响应体只带异常类名 `ModuleNotFoundError`，不带模块名。真正的 `No module named 'coa_runtime'` 只在 CloudWatch 的 `logger.exception("context_manager_invocation_failed")` 堆栈里（`handler.py:855`）。对调用方而言，它长得像「上游 context-manager 挂了」或「网络不通」，会被引向错误的排查方向。
- **为什么「晚触发」更危险**：导入在函数体内，Lambda 冷启动、健康检查、`GET /schema`、以及没有业务流量的环境全部正常。只有命中上面 5 条 POST 路由时才 100% 失败——每个请求都挂，但部署后的冒烟很容易只打 `/schema` 或只看 Lambda `State=Active`，得到「部署成功」的假象。
- **影响面**：Query 是本地链路唯一真跑通的操作（台账 §2.1），一旦切到端口传输而 bundle 没补，最核心的问答链先挂。

### 2.3 修它要做什么

| 要加的东西 | 加到哪 | 为什么 | 证据 |
|---|---|---|---|
| `packages/coa-ports/src` | `data-layer-stack.ts` 的 `srcDirs` | `from coa_ports import ...` | `handler.py:151` |
| `packages/coa-runtime/src` | 同上 | `from coa_runtime.registry import resolve` / `settings` | `handler.py:152-153` |
| `packages/metric-service/src`（`coa_metrics`） | 同上 | `coa_local_providers/__init__` eager → `json_lookup` → `coa_metrics.lookups` | `local-providers/src/coa_local_providers/__init__.py:14`、`json_lookup.py:17` |
| `httpx` | `packages/data-layer/requirements.txt`，再跑 `scripts/relock-python-requirements.sh` | `context_manager_http.py` 模块级 `import httpx` | `context_manager_http.py:39` |

**pip 侧的新增闭包**（按 `uv.lock` 实测）：`httpx 0.28.1` → `anyio 4.14.2` / `certifi` / `httpcore 1.0.9` / `idna 3.16`；`httpcore` → `h11 0.16.0`；`anyio` → `idna` / `typing-extensions`（<3.13）。`certifi`、`typing-extensions`、`pydantic`、`structlog` 已在现有 lock 里，所以**净新增是 httpx + anyio + httpcore + h11 + idna 五个分发**。

**`psycopg` 那条链有多长**（回答「要不要整包带 local-providers」）：

| 分发 | 版本 | 依赖 / 备注 |
|---|---|---|
| `psycopg` | 3.3.8 | `typing-extensions`（python < 3.13）、`tzdata`（仅 win32） |
| `psycopg[binary]` → `psycopg-binary` | 3.3.8 | manylinux x86_64 wheel ≈ 5.0 MiB（`uv.lock` 5,241,603 B） |
| `psycopg[pool]` → `psycopg-pool` | 3.3.3 | `typing-extensions` |

即整包照搬 pyproject 声明会多 4 个分发、约 5 MB 二进制，**且这条路径完全用不到**：`context_manager_http` 只用 `httpx`，`psycopg` 只在 `query_pg` / `metric_index_pg` / `control_plane_pg` 等 PG 实现里。同理 `boto3` 由 Lambda 运行时提供，无需打包。

**能不能只带必需的部分：能，而且应当。** 做法与 `namespace-stack.ts:651-657` 已修过的那份保持一致——只把三个 `srcDirs`（`coaRuntimeSrc` / `coaPortsSrc` / `metric-service/src`）加进 bundle，`requirements.txt` 只加 `httpx`。这样不带 `psycopg`、不带整包 local-providers，也不改任何 Python 代码。

另一条路是改代码：把 `coa_local_providers/__init__.py` 的 eager 导入改惰性，从而不必带 `coa_metrics`。**本轮不做**，且要注意 `ensure_resource_module()` 必须早于 `coa_metrics`/`coa_common` 导入（`__init__.py` 注释），改错顺序会把 Windows 兼容 shim 弄失效。

### 3.2 为什么没人发现

先回答「它在不在 CI 里」：**在**。`.github/workflows/pr.yml` 有两处显式执行 repo-level suite：

- `pr.yml:184`（`unit-test` job）：`uv run pytest tests/unit -q`
- `pr.yml:250`（`full-test-suite` / merge_group job）：`uv run pytest tests/unit -q`

守卫测试就在 `tests/unit/test_unit_marker_coverage.py`，所以「CI 跑过就会红」。

真正的原因是**这棵树从来没跑过那两步**，四条同时成立：

1. **CI 只跑在 GitHub 镜像，不跑在内部仓库**：`pr.yml:3-6` 原文 `Runs on GitHub (the public mirror repo), NOT internally.`。
2. **本分支从未建 PR**：台账 §7.3 R1（`07-研发台账.md:1137`）记录 `lint` / `unit-test` / `cdk-synth` / `full-test-suite` 四个 job **无结果**，「CI 侧机器证据为零」。
3. **镜像树还是绿的**：最后一次 Mirror sync 是 `bc185642`（2026-11-06 00:08 UTC，即 08:08 +0800），早于全部违规提交（11-09 起）。镜像上没有违规文件，自然不会红。
4. **包级闸门看不见它**：各包 `project.json` 的 test target 全部带 `-m unit`（`context-manager/project.json:10`、`control-plane/project.json:11`、`metric-service/project.json:11`、`ontology-engine/project.json:11`），违规用例被静默 deselect，所以 `nx affected -t test` 是绿的；而 `tests/unit` 当时没有 `project.json`，不属于任何 Nx project，`nx affected` **永远选不到它**（`pr.yml:180-183` 的注释也这么写）。

结论：**守卫不是「不存在」，也不是「逻辑无效」，而是它唯一的执行入口（repo-level suite）在本仓库的历史里没人跑。** 包级 `-m unit` 静默 deselect 与守卫的缺口是同一枚硬币的两面——守卫负责发现，但没人执行守卫。

### 3.4 什么条件下才会被发现（同类假绿的判据样本）

**会被发现的条件**（满足任一）：

1. 有人在这棵树上跑 repo-level suite（`uv run pytest tests/unit`）——本轮是第一次；
2. 镜像收到含违规提交的同步，且有人在 GitHub 开 PR（`pr.yml:184`）；
3. merge queue 跑 `full-test-suite`（`pr.yml:250`）；
4. 2026-11-10 起，任何一次 `nx affected -t test` / `nx run-many -t test` 且改动落在 `packages/` 或 `libs/`（`unit-guards` 的 `implicitDependencies: ["*"]`，见 §3.5）。

**不会发现它的条件**（本轮五条全中，所以静默 32 小时）：只跑包级 target；只跑带 `-m unit` 的命令；CI 未触发；镜像未同步到违规提交；改动落在守卫自己看不到的位置。

```json
  "targets": {
    "test": {
      "dependsOn": [],
      "cache": true,
      "command": "uv run pytest tests/unit/test_unit_marker_coverage.py -q",
      "inputs": [
        "{workspaceRoot}/tests/unit/**/*.py",

```

三个取舍：

| 取舍 | 选择 | 理由 |
|---|---|---|
| 跑整个 `tests/unit` 还是只跑守卫文件 | 只跑守卫文件 | 本机全量实测 **307 failed / 311 passed**，绝大多数是 Windows 缺 bash/sh 的环境失败；塞进 Nx 会把 307 条无关红拖进门槛。repo-level 全量仍由 `pr.yml:184` / `250` 负责 |
| 命令带不带 `-m unit` | 不带 | 带上会把 `unit-guards` 自己纳入守卫的扫描范围（`tests/unit` 下多数文件无 marker），等于让守卫检查自己；它本质是 repo-level suite，不是包级 unit |
| 怎么让 `affected` 选中它 | `implicitDependencies: ["*"]` + 覆盖 packages/libs 的 `inputs` | Nx 的 affected 由文件归属驱动，`tests/unit` 不在任何包根下；`["*"]` 让它依赖所有 project，`inputs` 防止命中旧缓存再次假绿 |

实测（2026-11-10，本 worktree）：

```
$ nx show projects --affected --base=ef358de8~1 --head=ef358de8
context-manager
mcp-server
unit-guards          ← 正是当初让守卫变红的那次 control-plane 提交
control-plane

$ nx run unit-guards:test

# 负对照：临时新增无 marker 的 packages/ontology-engine/tests/unit/test_zzz_entry_probe.py

```

CI 不需要改 workflow：PR job 的 `nx affected -t test`（`pr.yml:178`）从此会带上 `unit-guards`；merge queue 的 `nx run-many -t test`（`pr.yml:245`）也会；repo-level 全量仍由 `184` / `250` 兜底。代价是每个受影响 PR 多约 3.5 秒。

环境说明：本 worktree 没有 `node_modules`，上述验证用 `pnpm dlx nx@22.7.10` 加一个空的 `node_modules/.modules.yaml` 占位（nx 解析 pnpm lockfile 的前置），验证后已删除；CI 有正常的 `pnpm install`，不需要占位。日常入口：`pnpm install` 后 `pnpm nx run unit-guards:test`，或直接 `uv run pytest tests/unit/test_unit_marker_coverage.py -q`。

## 2026-11-11 · 台账 §8 编号两次撞号案例

**事实**：§8 系列编号在并行线之间重复发号两次，均在同一合并窗口内暴露——两条线各自「看过几个树」后选了同一个号，说明「发号前多看几个树」是概率规则，不是结构规则。

**证据**：
- `doc/coa-x/07-研发台账.md` 在每条并行线上各有一份，§8 编号由人工分配，无中央分配点。
- 本树（`feat/statements-route-authz`）该文件仅到 §8.3（`Select-String '^#{2,4} '` 末段为 `8.1 各包实测` / `8.2 脚本与工具` / `8.3 环境限制`）；§8.4、§8.11 存在于并行线各自的树中，这也是分叉的直接证据。
- §8.4 内容在两条线上分别是：canvas 5 条红测试登记 / 8080 记录；§8.11 分别是：8080 记录 / checksum（`.inputs.sha256`）方案。

**结论**：编号是共享可变状态，靠「看树」无法保证互斥；改为「追加区 + 日期分节 + 只追加」后，编号不再由人分配，撞号这一类问题从根上消失。

### 案例 1 · §8.4 被两侧同时占用（canvas 红 / 8080 记录）

- **怎么发现的**：合并时同一文件同一位置出现两段 §8.4，一段是 canvas 5 条红测试，一段是 8080 记录；两段互相覆盖，`git diff` 里表现为同号不同题。
- **当时怎么处理的**：人工判定先后，后来者顺延改号，两段内容都保留。
- **留下什么**：只解决了这一次的冲突，没有改发号方式，同类问题可再次发生（见案例 2）。

### 案例 2 · §8.11 被两侧同时占用（8080 记录 / checksum 方案）

- **怎么发现的**：§8.11 再次出现两段内容，一段是 8080 记录，一段是 checksum（`.inputs.sha256`）方案；此时距案例 1 不久，判定为同一类问题复发，而非偶发。

- **留下什么**：约定仍然依赖人的记忆。两次撞号后改为结构解法：§8 系列冻结，新记录只进本追加区。

## 2026-11-11 · 待办登记：版本按 namespace 过滤当前失效

**事实**：`platform.ontology_version` 有 `namespace_id` 列，但 `platform_core` 的所有插入语句都不写它；现网 1911 行全部为 NULL，包括刚通过正常 publish 产生的新行。列表接口 `GET /namespaces/{ns}/ontologies/{id}/versions` 忽略 `namespaceId`/`ontologyId`，返回的是全表非 deprecated 行（发布前 612 条、分属 532 个 `ont-*` ontology_id；发布后 613 条、533 个）。

**证据**

- 插入位置共 4 处，均在 `packages/platform-core/src/platform_core/adapters/ontology_pg.py`，逐处都没有 `namespace_id`：
  - L1366：`(version_id, semver, status, content_hash, triple_count, source_format, source_key, graph_iri, label)`
  - L2006：`(version_id, semver, status, content_hash, triple_count, source_format, source_key, graph_iri, label)`
  - L2303：`(version_id, semver, status, content_hash, triple_count, source_format, source_key, graph_iri, label)`
  - L4249：`(version_id, semver, status, content_hash, triple_count, source_format, source_key, graph_iri, rollback_of, label, published_at)`
- 自证 SQL（应返回 0）：`select count(*) from platform.ontology_version where namespace_id is not null;`
- 旁证：发布前 46 个 `graph_pointer` 行全是 `tbox/ont-<id>/current`，没有全局 `tbox/current`，说明指针层同样按 ontology_id 组织，不按 namespace；本次发布新增的 `tbox/current` 也只有一个全局名，不带 namespace 维度。

## 2026-11-11 · 治理口子：收编 `.p1-evidence` 的写库脚本，禁止再有无痕写入

### 现象

- 2026-11-11 05:50 左右，5944 的 `platform` 库三张本体表被一次性盖上 `attribution_source='legacy_unmapped'`：`ontology_version` 1908 行、`ontology_proposal` 1313 行、`ontology_event` 10134 行。
- `ontology_event` 里查不到任何对应记录；库未开语句日志；执行脚本 `D:\agentABC\.p1-evidence\backfill_ownership.py` 不在 git 里。
- 同目录还有 `migrate_six_rows.py`、`mark_legacy_fixtures.py` 这类同样会写生产数据的脚本。

### 查实过程

- 逐份读 `.p1-evidence` 下的脚本，按「是否对数据库执行 INSERT / UPDATE / DELETE / DDL」分类：
  - 会写业务数据：`backfill_ownership.py`、`mark_legacy_fixtures.py`、`migrate_six_rows.py`、`migrate_ontology.py`、`write_pointers.py`。
  - 只读：`build_event_id_map.py`（只读库、写本地 CSV）、`reconcile_rows.py`、`inventory_serve_local.py`、`serve_local_disposition.py`、`probe_pointer_and_coverage.sql`、`embed_stub.py`（HTTP 桩，不碰库）、`measure_peak.py`（只测 RSS/耗时）。
  - `apply_v52_v53.py` 是 DDL 迁移执行器，不是数据修复，不收录；它的审计事件还会占用迁移源的真实 `event_id`，与 `migrate_ontology.py` 的主键保留策略冲突。
  - `run-real*.ps1` 是压测驱动，目标是临时库 `realcorpus`，不涉及 5944 的 `platform`。
- `backfill_ownership.py` 的三条 UPDATE 在同一个事务里：version 按 `ontology_id IS NULL` + `graph_iri` 正则派生，proposal/event 按 `version_id` 回填；脚本没有任何事件写入或日志。
- `ontology_event` 的 `action` / `version_id` 没有约束区分「业务事件」和「运维事件」；事件表虽有 `prev_event` / `hash` 链，但缺事件时链不会报错，只会静默少一段。
- 尝试从 `ontology_event`、PG 语句日志、shell 历史反查执行者：事件表无记录；语句日志未开；脚本不在 git；本机没有可核对的执行账号痕迹。**查不到是谁执行的**，不推测。

### 结论

- 这不是「某条数据写错」，而是「写入路径没有强制留痕」：任何能连 5944 的一次性脚本都可以在不留事件的情况下改生产数据。
- 已把 5 个会写业务数据的脚本收进 `scripts/data-fix/`，统一经 `audit.py` 执行：
  - 默认 dry-run，只打印「哪些表、会改多少行」；带 `--apply` 才写。
  - 数据改动和审计事件在同一个事务；事件写不进去就整体回滚，脚本非零退出。
  - 事件写 `platform.ontology_event`，`action='data-fix'`，`version_id='data-fix:<batch_id>'`；payload 含脚本名、批次 id、影响行数、参数摘要、执行前后行数、脱敏 DSN、host / pid / 时间。
  - `prev_event` / `hash` 按 `platform_core` 的链式规则衔接。
- 自检脚本 `scripts/data-fix/selfcheck_rollback.py` 在一次性 Postgres 上验证了「事件写失败 → 数据整体回滚」：给 `ontology_event` 装必然报错的 BEFORE INSERT 触发器后，3 行 UPDATE 一行未留、事件 0 行；移除触发器后重跑，3 行更新 + 1 条事件，payload 字段齐全且 hash 与规则一致。

### 是谁查不到

- **执行者查不到**：`ontology_event` 无对应记录，库未开语句日志，脚本不在 git，无法归因到具体人或会话。
- 只能确认「不是通过已入库的代码路径写的」：代码路径都会走 `_append_event`，而这次没有事件。
- 受影响行数是事后按 `attribution_source='legacy_unmapped'` 统计出来的，不是脚本自报的。

### 今后怎么防

1. 所有一次性写库脚本只从 `scripts/data-fix/` 发起；`.p1-evidence` 只保留证据与只读脚本。
2. 默认 dry-run；执行必须带 `--apply` 和显式 `--batch-id`，先打印计划。
3. 审计事件与数据同事务，写不进事件即失败回滚；禁止捕获 `AuditWriteError` 后继续提交。
4. 任何绕过 `audit.py` 的直连 UPDATE / INSERT 视为违规；发现后按本条格式补记，不修改历史节。
5. 定期在一次性测试库跑 `selfcheck_rollback.py`，确认回滚约束仍成立。

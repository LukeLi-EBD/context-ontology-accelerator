## 2026-11-11 · 台账 §8 编号两次撞号案例

**事实**：§8 系列编号在并行线之间重复发号两次，均在同一合并窗口内暴露——两条线各自「看过几个树」后选了同一个号，说明「发号前多看几个树」是概率规则，不是结构规则。

**证据**：
- `doc/coa-x/07-研发台账.md` 在每条并行线上各有一份，§8 编号由人工分配，无中央分配点。
- 本树（`feat/statements-route-authz`）该文件仅到 §8.3（`Select-String '^#{2,4} '` 末段为 `8.1 各包实测` / `8.2 脚本与工具` / `8.3 环境限制`）；§8.4、§8.11 存在于并行线各自的树中，这也是分叉的直接证据。
- §8.4 内容在两条线上分别是：canvas 5 条红测试登记 / 8080 记录；§8.11 分别是：8080 记录 / checksum（`.inputs.sha256`）方案。

**结论**：编号是共享可变状态，靠「看树」无法保证互斥；改为「追加区 + 日期分节 + 只追加」后，编号不再由人分配，撞号这一类问题从根上消失。

### 案例 1 · §8.4 被两侧同时占用（canvas 红 / 8080 记录）

- **怎么发现的**：合并时同一文件同一位置出现两段 §8.4，一段是 canvas 5 条红测试，一段是 8080 记录；两段互相覆盖，`git diff` 里表现为同号不同题。
- **当时怎么处理的**：人工判定先后，后来者顺延改号，两段内容都保留。
- **留下什么**：只解决了这一次的冲突，没有改发号方式，同类问题可再次发生（见案例 2）。

### 案例 2 · §8.11 被两侧同时占用（8080 记录 / checksum 方案）

- **怎么发现的**：§8.11 再次出现两段内容，一段是 8080 记录，一段是 checksum（`.inputs.sha256`）方案；此时距案例 1 不久，判定为同一类问题复发，而非偶发。
- **当时怎么处理的**：同样人工顺延改号；同时在计划文档里补了「发号前多看几个树」的约定。
- **留下什么**：约定仍然依赖人的记忆。两次撞号后改为结构解法：§8 系列冻结，新记录只进本追加区。

## 2026-11-11 · feat/readonly-freeze（8080 只读冻结上线记录，原拟 §8.11）

**事实**：

- **8080 已冻结**：镜像 `agent-platform:0.1-s6-readonly`（sha256 `f954e40c0c36744f3c8ecc24890c98ba876624affb280c7f29f85cd77c3431f8`），149 op = 原 148 + `GET /readonly`，schema 49 未迁移（启动 `migrate` → `to: []`），哨兵 `D:\agentABC\data\READONLY` 存在。
- **拦 38 / 放 12**：50 条写方法逐条实测，38 条 409 `E_PLATFORM_READ_ONLY`，12 条按设计放行；8090 临时实例与 8080 切换后两轮结果一致。
- **解冻耗时**：删哨兵后写恢复 8090 为 350.2 ms、8080 为 351.1 ms，均无需重启（`RestartCount=0`）。
- **回滚物两件**：容器快照 tag `agent-platform:rollback-8080-20261111-052322`；库备份 `D:\agentABC\backups\platform-8080-pre-readonly-20261111.dump`（162,389,945 B）。
- **提醒**：8080 跑的是热补丁运行态而非镜像代码，任何「回滚到 `agent-platform:0.1-s5`」的说法都不成立。

**证据**：镜像 sha256、149 op、50 条写方法两轮结果、解冻耗时与 `RestartCount=0` 均为 `feat/readonly-freeze` 分支（tip `6b24978b`）实跑记录；`GET /readonly` 是新增的第 149 个 op。

**结论**：8080 只读冻结上线完成，写口由哨兵控制、解冻即时生效，回滚物两件齐备。原拟发 §8.11，因 §8 冻结改记本追加区。

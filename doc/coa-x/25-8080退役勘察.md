## 0. 一页结论

1. **8080 是「旧 Platform Kernel」，也是唯一完整数据实例。**
   运行态 138 条路径 / 148 个操作；容器 `agent-platform-api` 从 `D:\agentABC\coa`
   这个 checkout 起出来（分支 `feat/statements-route-authz`，HEAD `9b1e793c`），
   **不是本 worktree**。3,066 份文档、6 万级实例断言、610 个已发布版本都在它后面（数据量引自 `09` §2）。
2. **8082 不是独立的「验收 API」。** 它就是同一镜像 `agent-platform:0.1-s5` 在
   `platform-acceptance` 项目里的第二个平台实例；验收判据在脚本里，不在 API 里。
   更关键：**从宿主访问 8082 现在就是坏的**（连接被重置），容器内 `/healthz` 却 200、
   healthcheck 连续 9 小时 healthy。也就是说，今天宿主上没有任何消费者真正用得到它。
3. **路径级能直接对上的只有 14 条**，桥的 138 条里 126 条挂在 `/namespaces/{id}/` 下（多租户），
   旧栈是单租户（`/documents`、`/metrics`、`/ontology/versions`）。语义等价要靠 `09` §4 的
   operation 映射，不能靠路径名对齐。
4. **不能直接停 8080**：先坏的是 web-app 开发代理（`/ws`）、旧 UI（`/ui/`、`web/*.js`）、
   7 个运维脚本和 `stack-verify` 的 AS-8080 基线，最后才是数据。8082 可以直停，
   影响面只有能重跑的验收脚本与证据链。
5. 建议顺序：**8082 先退 → 8080 冻结写入 → 回填 + T1–T8 → 双跑 14 天 → 补 38 条缺口 → 停 8080**。
   详见 §6。

## 4. 8082 的验收 API 是什么

### 4.1 它不是一个独立服务

- 镜像与 8080 完全相同：`agent-platform:0.1-s5`；容器内也监听 8080，宿主映射到 8082。
- 差异只在 **compose 项目 + 数据根 + 端口**：`platform-acceptance` / `D:\agentABC\data-acceptance` /
  PG 5433 / reasoner 7882 / embedding 8083。
- 因此「退役 8082」= 退役一个**可重建的临时实例**，不涉及代码删除。

### 4.2 判据、调用方、报告

| 项 | 事实 | 出处 |
|---|---|---|
| 判据 | `skipped > 0` 即不通过（退出码 2）；锁被占中止（75）；每个 smoke suite 必须 `passed == total`，否则即使退出 0 也判 FAIL | `packages/platform-core/tests/acceptance.ps1:9-11` |
| S14 判据 | 0 全过；1 失败/错误/跳过；2 覆盖自检失败（discovered != executed）；3 显式排除 | `packages/platform-core/scripts/acceptance-s14.ps1:25-26` |
| 调用方 | 只有验收脚本：`tests/acceptance.ps1`、`scripts/acceptance-s14.ps1`；没有人从代码或前端调它 | §3.3 |
| 报告 | `doc/evidence/acceptance-s0s13-<project>-<时间戳>-<git sha>.log`、`doc/evidence/acceptance-s14-*.log`（git 跟踪） | `tests/acceptance.ps1:12,47-55`、`acceptance-s14.ps1:17-18,43` |
| 数据根 | `D:\agentABC\data-acceptance`（对象存储、导出目录、`platform.yaml`） | `tests/acceptance.ps1:23,27-28` |

### 4.3 当前宿主 8082 不可达（实测，未修）

| 探测 | 结果 |
|---|---|
| `curl http://127.0.0.1:8082/healthz` | `000`，`curl` 退出码 52（Empty reply from server） |
| `Test-NetConnection 127.0.0.1 -Port 8082` | `True`（Docker 端口代理在听） |
| 容器内 `urllib ... 127.0.0.1:8080/healthz` | `200` |

结论：**容器是健康的，宿主 → 容器的端口转发坏了**。根因未定位（Docker Desktop 代理状态、
容器网络、还是别的），列入 §8。对退役的影响：**没有宿主消费者会被 8082 的停止打断**；
但也不能把「8082 现在坏着」当成「可以立刻删」的理由——验收脚本仍以它为默认目标，
证据链仍依赖它跑出来的 transcript。

## 5. 三种退役走法

### 5.1 直接停

**8082：可行，代价最低。**

- 谁先坏：`tests/acceptance.ps1` / `acceptance-s14.ps1` 的默认目标失败（fail-fast，不会污染数据）；
  `acceptance-stack.ps1 down` 可替代手工停。
- 代价：验收证据链暂停；需要时 `docker start platform-acceptance-api` 即可恢复。
- 前置：确认没有正在跑的验收（`platform-acceptance.heavy.lock` / 进程）。

**8080：不可行。**

- 谁先坏（按时间顺序）：web-app dev 的 `/ws` → 旧 UI 页面 → `scripts/{up,seed,bulk-index,burst,stack-verify}` →
  `tests/acceptance.ps1` 的共享栈模式 → `doc/_design/knowledge-gap` 分析脚本。
- 真正的问题：**数据没有第二个副本**。停 = 唯一完整实例下线，`09` §8.2 的冻结/回填/双跑一步都没做。

### 5.2 影子迁移（两套并行，比结果）

- 做法：8080 **冻结写入** → 一次性回填 → 同一批请求双打（旧 8080 / 新 COA）→ 比对。
- 判据：`09` §8.3 T1–T8；黄金查询 20 条（10 指标 / 5 SPARQL / 5 问答）双方规范化 JSON 的 SHA-256 相等；
  双跑 ≥14 天零差异。
- 代价：14 天窗口 + 比对脚本 + 回填脚本；最大风险是**冻结不彻底**——旧 UI 和 7 个脚本都能写 8080，
  一边回填一边写入，差异永远不收敛。
- 前置（当前不存在）：8080 的只读模式。`api.py` 没有 read-only 开关，compose 也没有；
  需要单独设计（网关只放行 GET、或停写路由），属执行轮工作项。

### 5.3 先补独有功能，再停

- 做法：按 §2.3 的 38 条缺口，逐条补 Smithy operation + 桥路由 + 测试，再切出口。
- 代价：会改 `models/`（本轮明令不碰），需要独立分支与契约评审；按域分批，不能一口吞。
- 风险：如果先补功能、不动数据，最后仍会卡在「8080 有数据、COA 没数据」。

### 5.4 建议组合

```text
8082：先走 5.1（直停，可随时恢复）
8080：5.2 冻结+回填+T1–T8 先行，5.3 的 P0 缺口并行补，最后才走 5.1 停 8080
```

理由：8082 不影响数据与运行时消费者，先拿掉可以减少一个需要盯的实例；
8080 的瓶颈是数据与写入冻结，而不是路由数量，所以顺序必须是「冻结 → 回填 → 双跑 → 补缺口 → 停」。

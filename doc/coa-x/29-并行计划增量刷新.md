- **未过时**：该任务退回分支不计入出口；P0 出口判为未达成；**不允许「先打 tag 后补」**。
- **串行举证（P0-17 → P0-18）**：冲突证据 = 两者改同一批提交历史与 tag 指向；为什么无法隔离 = tag 是单一引用，不能指向两个 commit；最小串行集与耗时 = 1.0 + 0.5 = 1.5 人日；并行替代方案 = 先打 `p0-rc1` 预 tag 再打正式 tag（代价是多一次 tag 维护、且预 tag 会被误当出口），**不采用**。

### 4.3 两个 Oxigraph 残余缺口排在哪（关键判断）

| 缺口 | 定级 | 排在哪 | 依据 |
|---|---|---|---|
| **取消时返回 `200` + chunked 非法 JSON，消费方把取消当成功** | **P0** | **B-P0c，第 3 位，tag 之前** | ① 它是「静默成功」，违反 07 号 §1.3 硬规则「禁止把异常降级成正常结果」，与 P0-10 的读空同类；② 取消是 P0-12 引入的能力，其语义错属于**本次改动直接引入的缺陷**，不该留给 P2 追账；③ 成本低（消费侧识别解析失败），1.0 人日可闭环 |
| **≥3 个未绑定 `GRAPH` 的交叉积不响应取消**（`--timeout-s 5` 下 40s、15 下 180s 不返回） | **P2** | **B-P2，P2-08** | ① 后果是「慢」不是「挂」：CPU 看门狗兜底、自动恢复、**无需人工重启**（与改造前「必须重启」有本质差别）；② 修复要动查询规划/改写，不属「低成本优化」，按 P2 定义排后；③ 不阻塞 P0 演示（演示查询形状可控）；④ 触发升级条件见 §5.2 说明与 §5.4 |

### 4.4 「打 tag」排在哪

- **位置**：`B-P0c` 最后一步（P0-18），不是独立批次，也不进 P1。
- **为什么不能更早**：tag 必须包含 P0-17，否则出口带着一个 fail-open 缺陷；也必须包含 P0-14 的跨租户用例，否则无法回答「合进来的 37 条映射没回归」。
- **为什么不能更晚**：tag 是 M1 出口的唯一缺口；P1 的导入校验需要一条可解析的对照基线（当前只能靠 commit hash，评审时无法保证「导入前后同一版本」）。
- **附带要求**：tag 说明必须写两条已知限制（未做外网鉴权验证、statements p95 4.8–10s @100k），避免被当作「全绿发布」使用。

### 0.1 最严重的三条不一致

1. **`error` 这个键在三种类型之间摇摆，前端只能看见 `UNKNOWN_ERROR`。**
   - 改前：`POST /ontology/publish`（含破坏性变更、未确认）→ `409`，体为 `{"error":{"code":"Conflict","providerCode":"E_ONTOLOGY_BREAKING","message":…,"retryable":false,"details":{…}}}`（`packages/platform-core/src/platform_core/api.py:1775-1787`、`adapters/ontology_pg.py:3216-3220`）。
   - 前端：`ApiClientProvider` 读 `parsed.code`，取不到 → `ApiError{status:409, code:"UNKNOWN_ERROR", message:'API POST … failed (409): {"error":…}'}`（`ApiClientProvider/index.tsx:86,124`）。
   - 于是业务代码只能靠正则匹配原始 JSON：`/E_ONTOLOGY_BREAKING|breaking changes/i.test(`${err.code} ${err.message}`)`（`packages/web-app/src/pages/ontology/OntologyVersions.tsx:306-315`，注释直说 "The bridge wraps platform errors as {"error":{"providerCode":...}}, so ApiError.code may be UNKNOWN_ERROR"）。
   - 应返回：统一信封 `{"error":{"code":"E_ONTOLOGY_BREAKING","message":"…","details":{"breakingItems":[…]},"requestId":"…","retryable":false}}`，前端只读 `error.code`。

2. **同一个「图不在白名单」有 4 个码、2 个状态、3 种字段名。**
   - `E_GRAPH_GRAPH_NOT_ALLOWED` → `403`，`details.allowedPrefixes/allowedGraphs/graph`（`adapters/graph_fuseki.py:87-100`）。
   - `E_CANVAS_GRAPH_FORBIDDEN` → `403`，`details.allowed`（`adapters/canvas_full.py:569`）。
   - `E_SPARQL_GRAPH_FORBIDDEN` → **`400`**（`coa_serve/tier2/sparql/console.py:501-515`，`GRAPH_SCOPE` 分支）。
   - `E_SPARQL_FORBIDDEN` → `403`（同上，`GRANT` 分支）。
   - 改前：同一个 IRI，`POST /namespaces/{namespaceId}/sparql` 带 `FROM <g>` 返回 `400 E_SPARQL_GRAPH_FORBIDDEN`；`/browse/canvas/full?graph=<g>` 返回 `403 E_CANVAS_GRAPH_FORBIDDEN`。
   - 应返回：一个码 `E_GRAPH_NOT_ALLOWED` + `403` + `details.allowedGraphs`（写操作另用 `E_GRAPH_NOT_WRITABLE` + 403/409）。

3. **一个码两种语义、两种状态。**
   - `E_ONTOLOGY_LIFECYCLE_INVALID`：未知实体类型 → `code="InvalidArgument"` → `400`；非法状态迁移 → `code="Conflict"` → `409`（`packages/platform-core/src/platform_core/ontology_lifecycle.py`，两处 raise 共用同一 `provider_code`）。
   - 同类还有 4 个（§3.2）。契约里一个 `code` 只能对应一个 `@httpError`，这 5 个码现在无法落 `errors`。

- **Lambda（ONTOLOGY / SOURCES / METRICS / GRANTS / NAMESPACE / ROLES / PLATFORM_ROLES）**：`control-plane`、`ontology-engine`、`coa-gateway` 等，各自的信封又不一样。
- 本地壳自己的错误：`JSONResponse({"error": "<人话>"}, 400/404/405/500)`（`coa_api_local.py:1409,1987,1979`）。

## 2. 现状：5 套词表 × 4 种键位

| 层 | 响应体（真实键位） | code 在哪 | 词表 | 证据 |
|---|---|---|---|---|
| platform-core（PortError） | `{"error":{"code","provider","providerCode","message","retryable","details"}}` | `error.code` + `error.providerCode` | PortErrorCode + `E_*` | `platform_core/api.py:99,1775-1787` |
| platform-core（dictionary） | `{"code","message",…}` | 顶层 `code` | `E_*` **或** `ValidationError`/`NotFoundError`/`Conflict`/`InternalServerError` | `platform_core/dictionary_api.py:90` 及各 `_error` 调用 |
| platform-core（RequestValidationError） | `{"detail":[{type,loc,msg,…}]}` | 无 | 无 | `platform_core/api.py:1789-1815`；仅 `/metrics/*` 特判成 400 + PortError 信封 |
| control-plane | `{"message": …}` | 无 | 无 | 例：`control_plane/grants/create_handler.py:91` |
| coa-gateway | `{"message": …}` | 无 | 无 | `coa_gateway/http_api.py` 各 `HTTPException(detail=…)` |
| ontology-engine | `{"detail":"…"}` / `{"detail":{"code","message"}}` | `detail.code`（少数） | `UNSUPPORTED_SOURCE`/`CONFIGURATION_ERROR`（无 `E_` 前缀） | `coa_ontology/main.py:95-153`、`induce_catalog.py:1283-1297` |
| context-manager（serve） | `{"message","requestId","statusCode"}`，部分 `{"error":"<异常类名>",…}` | `error`（类名） | `AccessDeniedError`/`NoResultError`/`TimeoutError`/`InternalError`… | `coa_serve/main.py` `_error()`、`coa_serve/exceptions.py` |
| context-manager（SPARQL） | `{"statusCode","error","message","providerCode"?}` | `error` = `E_SPARQL_*` | `E_*` | `tier2/sparql/console.py:94-120` |
| data-layer | `{"message","code"?,"providerCode"?,"statusCode"?}`；未捕获只有 `{"message"}` | `code` | `E_*` | `coa_data_layer/handler.py:198` |
| coa_api_local（壳） | `{"error":"<人话>"}` | 无 | 无 | `coa_api_local.py:1409,1987,1979` |
| web-app | 只读顶层 `code`/`message`/`detail`/`errors` | — | 兜底 `UNKNOWN_ERROR` / `FORBIDDEN` | `ApiClientProvider/index.tsx:81-126` |

由此产生三个硬事实：

1. **`error` 一个键，三种类型**：对象（platform-core）、码字符串（data-layer、SPARQL）、人话字符串（coa_api_local）。契约层无法给 `error` 绑定一个结构。
2. **同一个 `code` 键，两套词表**：`dictionary_api` 里既可能是 `E_DICTIONARY_SOURCE_NOT_FOUND`，也可能是 `NotFoundError`（`dictionary_api.py:90` 与各处 `_error(...)`）。
3. **前端拿不到任何 `E_*` 码**：平台错误码都在 `error.providerCode`，而前端不读 `error.*`；`data-layer` 的 `error` 是码、`message` 是人话，前端只读到人话。最终 `ApiError.code` 恒为 `UNKNOWN_ERROR`（403 除外，恒为 `FORBIDDEN`）。

## 3. 四类问题

### 3.1 同一个 HTTP 状态用了多个不同 code

按「码 → 状态」严格统计（多状态码在各状态各计一次）：

| HTTP | code 数 | 说明 |
|---|---:|---|
| 400 | 91 | 参数缺失、IRI 非法、枚举非法、超限、解析失败、功能未开启、上游拒绝，全部挤在 400 |
| 409 | 23 | 状态机冲突、版本冲突、并发锁、重复导入、门禁阻塞 |
| 503 | 17 | 依赖不可用、未配置、读不到资产、只读模式 |
| 404 | 18 | 版本/命名空间/事实/候选/字典源不存在 |
| 500 | 17 | `Internal` / `DataLoss` 两档都落 500 |
| 504 | 7 | 超时 |
| 403 | 7 | 权限/白名单/上游鉴权/磁盘写失败（见 §3.4） |
| 413 | 7 | 请求过大、结果过大、**限流**、**磁盘不足**（见 §3.4） |
| 422 | 5 | 只有 dictionary 用 422 |
| 502 | 1 | `E_SPARQL_PROVIDER_ERROR` |

问题不在「多」，而在**同一状态里语义不可区分**。典型三簇：

- **400 里混了「客户端错」和「服务端拒绝」**：`E_SPARQL_PROVIDER_REJECTED`（上游 4xx 折成 400）、`E_GRAPH_BAD_REQUEST`（Fuseki 返回非 2xx，含 500，折成 400，`adapters/graph_fuseki.py:123`）、`E_CONSISTENCY_BAD_REQUEST`（reasoner HTTP 失败折成 400，`adapters/reasoner_hermit.py:117`）。
- **409 里混了「用户没确认」和「并发抢锁」**：`E_ONTOLOGY_BREAKING`（需人确认）与 `E_INGESTION_*`/锁冲突（重试即可）都返回 409。
- **404 与 503 混用**：同一个「没有暂存版本」既能 404 也能 503（详见 §3.2）。

### 3.2 同一个 code 在不同路径含义不同（逐条）

| code | 状态 | 含义 A | 含义 B | 证据 |

| `E_SHACL_SHAPES_MISSING` | 400 / 503 | 该 namespace 没有 shapes（`Unsupported`） | shapes 目录读不到（`Unavailable`） | `platform_core/api.py:3689`、`validation.py:130-140` |

**同义不同码**（同名不同拼法，契约期必须先合并）：

| 语义 | 现有码 |
|---|---|
| namespaceId 非法 | `E_NAMESPACE_ID`（`api.py:2049`）、`E_NAMESPACE_ID_INVALID`（`importer.py:1033`） |

| 上游鉴权失败 | `E_EMBED_AUTH`（403）、`E_LLM_AUTH`（403）——服务端自己的密钥被上游拒绝 |

### 3.4 本该 4xx 却写成 5xx（以及反向）

**确凿的 4xx→5xx（3 条）**

| # | code | 现状 | 触发 | 应返回 |
|---:|---|---|---|---|
| 1 | `E_VALIDATE_BAD_DATA` | 500（`DataLoss`） | 解析待校验的 data graph 失败（内容来自调用链的 A-Box） | `400 E_VALIDATE_BAD_DATA` + `details.graph` |
| 2 | `E_ONTOLOGY_STAGE_MISSING` | 503（`Unavailable`） | 暂存图为空，用户没暂存任何东西 | `409 E_ONTOLOGY_STAGE_MISSING` |
| 3 | `E_SPARQL_SCOPE_EMPTY` | 503（`console.py:494`） | 该 namespace 没配 data graph | `409 E_SPARQL_SCOPE_EMPTY` + `details.namespace` |

**边界项（2 条，需产品口径确认）**

| code | 现状 | 为什么不合适 |
|---|---|---|
| `E_GRAPH_READONLY` | 503 | 「图处于只读模式」是服务能力受限，客户端可换写目标；应 `403` 或 `409` |
| `E_GRAPH_WRITE_PROBE` | 500 | 写入前的 `ASK {}` 探针失败，属依赖不可用；应 `503` |

**反向问题更严重：5xx 写成 4xx（5 条）**

| code | 现状 | 实际原因 | 后果 |
|---|---|---|---|
| `E_GRAPH_BAD_REQUEST` | 400 | Fuseki 返回非 2xx（可能是 500），`graph_fuseki.py:123` | 上游故障被当成用户查询错误，客户端不会重试 |
| `E_CONSISTENCY_BAD_REQUEST` | 400 | reasoner HTTP 调用失败，`reasoner_hermit.py:117` | 同上 |
| `E_EMBED_AUTH` | 403 | **平台自己的** embedding 密钥被上游拒绝，`adapters/embedding.py:420` | 用户被误导为「无权限」 |
| `E_LLM_AUTH` | 403 | 同上，`adapters/llm_openai.py:193` | 同上 |
| `E_STORAGE_WRITE` / `E_STORAGE_RENAME` | 403 | 服务端磁盘/ObjectStore 写失败，`adapters/object_fs.py:50,87` | 运维故障被当成用户越权 |

**状态选错的 3 条**

| code | 现状 | 应返回 |
|---|---|---|
| `E_LLM_RATE` / `E_EMBED_RATE` | 413（`ResourceExhausted`） | `429` + `Retry-After` |
| `E_DISK_LOW` | 413 | `503` 或 `507` |
| `E_SPARQL_RESULT_TOO_LARGE` | 413 | `413` 是「请求体过大」；响应过大应 `507` 或 `502` |

### 3.5 附：warning 与 error 共用命名空间

以下 `E_*` 只出现在 200 响应的 `warnings` / `degraded` / `reasons` 里，但与致命错误共用 `E_` 前缀，客户端无法靠前缀区分：

`E_NO_PUBLISHED_ONTOLOGY`、`E_PUBLISHED_ONTOLOGY_NO_PROPERTIES`、`E_MAPPABLE_PAIRS_EMPTY`、`E_REFRESH_REPLAYED`、`E_CANVAS_PATHS_TRUNCATED`、`E_NO_VECTOR_INDEX`、`E_LLM_BAD_RESPONSE`、`E_EMBED_UNAVAILABLE`、`E_SOURCE_CATALOG_UNAVAILABLE`、`E_DOC_METADATA`。

另外 `E_ONTOLOGY_BREAKING` 在 dry-run 里是 **200 响应里的 blocker**（`api.py:1690-1712`），在真实 publish 里是 **409 错误**（`ontology_pg.py:3216`）。同一码既表示「业务结论」又表示「HTTP 错误」，契约必须显式区分：前者放 `200.blockers[]`，后者放 `errors`。

## 4. 契约层可直接用的建议

### 4.1 code 命名规则

```text
E_<DOMAIN>_<CONDITION>
```

- `DOMAIN` 取白名单（避免同义前缀）：`AUTH`、`NAMESPACE`、`GRAPH`、`SPARQL`、`ONTOLOGY`、`BUNDLE`、`DOC`、`EMBED`、`LLM`、`METRIC`、`FACT`、`DICT`、`CONTEXT`、`STORAGE`、`CONFIG`、`INTERNAL`。
- `CONDITION` 用名词短语，不复用实现细节：`NOT_FOUND`、`INVALID`、`NOT_ALLOWED`、`CONFLICT`、`LIMIT_EXCEEDED`、`NOT_CONFIGURED`、`UNAVAILABLE`、`TIMEOUT`、`UPSTREAM_FAILED`、`BREAKING`。
- **一码一义一状态**；码里不写 HTTP 状态（`E_NOT_FOUND_404` 这种禁止）。
- **一语义一码**：同一语义不允许按模块起名（`E_GRAPH_BAD_IRI`/`E_CANVAS_BAD_IRI` 合并为 `E_GRAPH_IRI_INVALID`）。
- **warning 独立命名空间**：`W_<DOMAIN>_<CONDITION>`；blocker 用 `B_<DOMAIN>_<CONDITION>`，都只出现在 200 响应，不进 `errors`。
- `E_*` 一旦发布不复用；废弃用 `deprecated` 标注，不重用字符串。

### 4.2 建议的 code → HTTP 映射

| HTTP | 语义 | 建议 code（示例） |
|---:|---|---|
| 400 | 请求格式/参数/语法错误 | `E_REQUEST_INVALID`、`E_IRI_INVALID`、`E_ENUM_INVALID`、`E_SPARQL_SYNTAX`、`E_SPARQL_STATEMENT_NOT_ALLOWED` |
| 401 | 未认证 | `E_UNAUTHENTICATED` |
| 403 | 已认证但无权 / 图不在白名单 | `E_FORBIDDEN`、`E_GRAPH_NOT_ALLOWED`、`E_GRAPH_NOT_WRITABLE`、`E_SPARQL_GRANT_DENIED` |
| 404 | 资源不存在 | `E_NAMESPACE_NOT_FOUND`、`E_VERSION_NOT_FOUND`、`E_FACT_NOT_FOUND`、`E_STAGE_MISSING` |
| 409 | 状态冲突（可重试或需确认） | `E_CONFLICT`、`E_TRANSITION_INVALID`、`E_ONTOLOGY_BREAKING`、`E_LOCK_HELD` |
| 412 | 前置条件不满足 | `E_PRECONDITION_FAILED` |
| 413 | 请求体/上传超限 | `E_REQUEST_TOO_LARGE` |
| 422 | 语法合法但语义不可处理 | `E_UNPROCESSABLE`（dictionary 的 5 个码并入） |
| 429 | 限流 | `E_RATE_LIMITED`（带 `Retry-After`） |
| 500 | 服务端自身缺陷 | `E_INTERNAL` |
| 502 | 上游失败/上游鉴权失败 | `E_UPSTREAM_FAILED`、`E_UPSTREAM_REJECTED`（原 `E_*_AUTH`、`E_GRAPH_BAD_REQUEST`） |
| 503 | 依赖不可用/未配置/只读 | `E_UNAVAILABLE`、`E_NOT_CONFIGURED`、`E_GRAPH_READONLY` |
| 504 | 超时 | `E_TIMEOUT`（旧的各 `*_TIMEOUT` 并入） |

其中与现状差异最大的三处**已拍板**（§4.6）：限流从 413 改 429；上游鉴权从 403 改 502；图白名单从 400 统一到 403。

> 本表是示意；每个旧码的最终归属以 §4.7 为准。已合并的例子：`E_SPARQL_GRANT_DENIED` → `E_GRAPH_NOT_ALLOWED`，`E_SPARQL_TIMEOUT` → `E_TIMEOUT`，`E_LOCK_HELD` → `E_OPERATION_BUSY`，`E_STAGE_MISSING` 拆成 `E_ONTOLOGY_STAGE_NOT_FOUND` / `E_ONTOLOGY_STAGE_UNAVAILABLE`。

### 4.4 `errors` 在 Smithy 里怎么定义（建议，不写 `.smithy`）

现状（只读核对）：`models/src/main/smithy/common.smithy` 已有 16 个 `@error` 结构（`AccessDeniedError`、`NamespaceNotFoundError`、`NoResultError`、`TimeoutError`……），但成员只有 `message`，既没有 `code`，也没有 `details`；线上真正的码在 `providerCode` 里。两套词表没有交点——这就是写 `errors` 会卡住的直接原因。

建议采用「一个信封 + 少量按状态段的结构」，而不是 449 个错误结构：

```smithy
// 建议草案（未落地，合并时由契约 owner 决定文件位置）
@error("client")
@httpError(400)
structure BadRequestError {
    @required code: String        // ^E_[A-Z]+(_[A-Z0-9]+)+$
    @required message: String
    details: ErrorDetails
    requestId: String
    retryable: Boolean
}
```

配套建议：

1. **信封只保留一种**：`{"error":{ code, message, details, requestId, retryable }}`。`providerCode` 作为过渡字段保留一个版本，值等于旧 `E_*`，迁移结束删除。
2. **按状态段定义 7 个结构**（400/401/403/404/409/429/5xx），不要按 code 定义；code 是字符串字段，不是 Smithy 类型。
3. `ErrorDetails` 用 `document` 或按域的少量结构（`GraphNotAllowedDetails`、`BreakingDetails`、`ValidationDetails`），避免 449 个 details 结构。
4. **每个 operation 显式列 `errors`**，至少 `BadRequestError`、`ForbiddenError`、`NotFoundError`、`ConflictError`、`InternalError`；不要靠全局默认。
5. **现有 16 个错误结构不要删**：加 `code: String` 成员，映射到新码，作为 `providerCode` 的兼容层。
6. **HTTP 状态由 `@httpError` 固定**，不允许同一 structure 在不同 operation 用不同状态；这样 §3.2 的 5 个码必须先拆。

### 4.6 三条已拍板（2026-11-10）

三处理由如下；本轮只进文档，不改代码。

| # | 决定 | 改前 | 改后 | 理由 | 涉及旧码 | 前端 |
|---:|---|---|---|---|---|---|
| 1 | 限流 | `413` | **`429` + `Retry-After`** | 413 是「请求体太大」，客户端会去改请求内容，改多少次都没用；限流必须让客户端知道「等一会儿再来」 | `E_LLM_RATE`、`E_EMBED_RATE` | 前端没有 429 分支，不会误判 |
| 2 | 上游鉴权失败 | `403` | **`502` `E_UPSTREAM_REJECTED`** | 403 是「你没有权限」，真实是我们的上游凭证坏了；把服务端问题伪装成调用方问题，是最误导人的一类错误 | `E_EMBED_AUTH`、`E_LLM_AUTH` | 会退出 `ApiClientProvider` 的 403 分支 |
| 3 | 图白名单 | `400` / `403`，4 个码 | **`403` `E_GRAPH_NOT_ALLOWED` + `details.allowedGraphs[]`** | 不是参数格式错，是作用域决策，403 才对 | `E_GRAPH_GRAPH_NOT_ALLOWED`、`E_CANVAS_GRAPH_FORBIDDEN`、`E_SPARQL_GRAPH_FORBIDDEN`、`E_SPARQL_FORBIDDEN` | `E_SPARQL_GRAPH_FORBIDDEN` 由 400 变 403，会进入 `FORBIDDEN` 兜底分支 |

命名规则随之落定：`E_GRAPH_GRAPH_NOT_ALLOWED` 的 `GRAPH` 重复，新码统一为 `E_GRAPH_NOT_ALLOWED`，一次说清。

`E_UNAUTHENTICATED`（`401`）与 `E_FORBIDDEN`（`403`，带 `action`）**不是本轮待建码**：鉴权线 worktree `wt/authz-close` 已在用，以那条线为准；合并后主线会出现这两个码，本表直接接上，不另造同义词。

### 4.9 什么时候执行

前置条件（全部满足才动手）：

1. 五条 worktree 全部合并，主线只剩一个 head；
2. 主线 `tsc && vite build` 变绿（现在构建是红的，此时换码等于在正在锯的树上再砍一刀）；
3. 8099 起栈 smoke 绿（至少 `/system-health` + 一条 SPARQL + 一次 publish）。

执行方式：**一次性改，不零散改**，分四个批次，每批单独提交并引用 §4.7 行号：

| 批次 | 内容 | 为什么必须这个顺序 |
|---|---|---|
| B1 | 前端先读 `error.code`，服务端在 `error.code` 与 `error.providerCode` 双写 | 不改可见行为，但让后续换码不丢信息 |

| B3 | 只落 §4.6 三条状态变更（429 / 502 / 403）+ `Retry-After` | 唯一会改前端分支的一批，单独回滚 |
| B4 | 按 §4.4 写 `errors`，生成客户端类型 | 让契约与代码同源 |

禁止：合并窗口中途改；跳过 B1 直接做 B2/B3；把 B3 和 B2 混在一个提交里。

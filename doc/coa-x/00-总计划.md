## 1. 定位（校准后）

一句话：**coa-x 是在 COA 代码库内部做二次开发，让 COA 自己在本机跑起来。**

三条边界，写死，后续不再讨论：

1. **宿主是 COA 本身。** 运行时承载体是 `packages/data-layer`、`metric-service`、`context-manager`、`ontology-engine`、`vkg`、`mcp-server`、`control-plane`、`sources`。不是 `packages/platform-core`，也不是 `packages/coa-gateway`。
2. **替换点在 COA 自己的代码里。** AWS 构造点改成「先有接口、再由配置注入」，实现放在 provider 包里被 COA 引用。不新起一套并列系统，不把 COA 挂到 platform 网关后面跑。
3. **`platform_core` 是实现库，不是宿主。** 它的适配器（图、向量、Embedding、LLM、SQL、对象存储、会话、记忆）以库形态进入 COA 的端口实现；它多出来的特性做迁入，不重造。

`coa-gateway` 的定位：P1–M2 的验证跑道（harness），不是交付物。阶段 2 起对外的是 COA 服务本身，网关退为可选。

## 2. 终态与完成定义

终态三句话：

1. 本机一条命令起 COA，不依赖任何 AWS 账号或外网。
2. 功能不低于现有 platform（指标、本体、术语、问答、溯源、画布、健康看板等）。
3. 每个接口一个配置键，可在 **AWS 原生 / 本地 / 第三方** 之间逐接口混搭（例如 graph 用 AWS、llm 用本地），切换不改调用代码。只承诺配置矩阵里标「已验证」的组合。

## 3. 五条原则

1. **接口先行**：每个替换点先有接口（方法签名、输入输出、错误语义），再谈实现。
2. **只依赖接口**：业务代码禁止 import 具体实现；实现类只出现在组合根与 provider 包。
3. **组合根注入**：构造与装配集中在一处，按配置键选实现；业务类构造参数只接收接口实例。
4. **只换插头**：允许改 COA 上游代码，但只做「写死改可注入」，不重写业务逻辑；能复用 `platform_core` 已有实现的不重造。
5. **功能优先、单机优先、易用优先**：先让功能在本机真跑起来，再谈等价性与性能；不为「像 AWS」牺牲可运行性。
6. **按 DDD 组织，扬长避短**：领域模型、统一语言、限界上下文必须真正落地（见 §11）；只在需要不变量与跨上下文边界的地方用重武器，基础设施适配、纯 CRUD、转发网关、一次性脚本不套 DDD。**本条优先于「先出代码」**：端口名与 DTO 先对齐统一语言，再写签名。

缺配置必须明确报错，禁止静默 fallback 到任何实现。

### 4.1 验收档位（全篇统一，2026-11-09 起）

凡涉及代码能力的结论，**必须标下列三档之一**。未标档位的「已回填 / 已实现 / 已通过」一律按未验证处理。

| 档位 | 定义 | 可接受的证据 | 不算 |
|---|---|---|---|
| **真跑通** | 有一次真实调用跑过：真实 provider + 真实后端（本地 PG / Oxigraph / TEI / 文件系统等）或真实请求路径，调用栈里没有替身 | 命令 + 原始输出、服务日志、可复现脚本 | 只跑 `python -m coa_runtime matrix`；只跑 mock/fake 单测 |
| **只编译** | 代码路径已改、可导入、类型检查通过；或仅有替身单测通过；**没有任何一次真实调用** | 单测输出（含 mock）、import 成功记录 | — |
| **未验证** | 代码未改；或改了但从未运行；或依赖缺失（如 `graphrag_toolkit` / `sqlalchemy`）无法运行 | 缺依赖报错、当前代码现状 | — |

两条硬规则：

1. **编译通过不算通，mock 通过不算通。**「薄壳有单测覆盖真实调用」中的「真实调用」只认**真跑通**档。
2. **判据必须当阶段能判完。**禁止把「全仓 grep 0 命中」「11 类全部清零」这类跨阶段才成立的表述写进单阶段判据；跨阶段事项一律写进 §5.1 归属表，按阶段分摊。

文档、结构、命名类判据不标档位，只给文件/章节证据；只要结论涉及运行期行为，就必须标档位。

### 为什么重排（避免前面白干）

原计划把「`platform_core` 迁入」放在阶段 6，结果是阶段 2–5 先写一份本地实现，阶段 6 再换成 `platform_core` 另一份，等于同一能力做两遍。修订后：

- **阶段 1 就把 `platform_core` 已有适配器经薄壳登记为端口实现**，阶段 2–5 只消费端口，不再自写第二份。薄壳是必要成本，不是重复实现：它只做签名/结构/错误码转换，不含业务逻辑。
- 原阶段 6 拆成两块：已实现能力的「登记与去重」并入阶段 1；尚未实现的新特性放进阶段 5/6。
- `coa-gateway` 不再作为阶段 6 的宿主；阶段 2 起由 COA 服务自身对外。

### 各阶段工作项

**阶段 1 · 端口层与组合根**（本轮开工）

- **先定边界与语言**：按 §11.1 划清上下文、按 §11.2 落统一语言表与术语裁定，再写任何端口签名；端口名/DTO 名与表不一致即返工。
- 新建 `packages/coa-ports`：13 个端口中的 11 个跨服务端口 Protocol + DTO + 错误类型，纯 typing、零第三方依赖。DTO 只使用统一语言里的值对象（`NamespaceId`/`Iri`/`GraphUri`/`ChunkId`/`MetricName`/`DataSourceId`），禁止把领域对象或平台模型放进签名。
- 例外两个端口落消费方包：`ControlPlaneStore` 留 `control-plane`（阶段 7 才实现，先定义后落位）；`OcrPort` 留 `context-manager`（只有文档摄入用）。
- 新建 `packages/coa-runtime`：组合根 + 配置解析。理由：组合根不属于任何业务服务；放 `libs/common` 会让公共库反向依赖所有实现包，破坏依赖方向。
- **薄壳层（新补的工作量）**：`platform_core` 的适配器不能直接当端口实现，两边签名不一致——同步/异步、方法名、参数形态、返回结构、错误码都可能有差。每个复用接口要一层薄壳做四件事：签名转换（sync→async 用 `to_thread`）、参数形状转换、返回结构映射、错误码映射（`PortError` → COA 端口错误）。清点结果见 `02-薄壳清点.md`：**实测 11 个壳**。截至 2026-11-09：S1–S6 已有；S8 `ObjectStorePort`、S9 `MetadataStorePort`、S10 `GraphStorePort` 已落地并由 catalog 登记 provider（S10 接 oxigraph，真跑通），S7 `LLMClient` 壳已写但用例为替身，记**只编译**。行数与测试数见 §4 薄壳行。其余 12 个端口平台无对应物，属新建实现，不算壳。
- 薄壳必须有单测，且单测跑真实调用（本地 PG / Oxigraph / TEI），不允许只测 mock。
- 部署形态在阶段 1 收尾定稿并落进本计划：**交付形态用 docker compose，裸进程只作单服务调试**。理由：一条命令要同时拉起 PG、Oxigraph、TEI、MinIO、dynamodb-local、OpenSearch、Trino 七个依赖件，裸进程无法统一编排；compose profiles 用来开关可选件。风险：Windows 依赖 Docker Desktop，首次拉镜像受网络限制；镜像体积需控制在单机可接受范围。定稿前不改 D1 验收方式。
- 11 类违规**不在阶段 1 处理**，按 §5.1 归属表分流到阶段 2/3/4/7；阶段 1 只保证新增代码（`coa-ports` / `coa-runtime` / 薄壳）不引入新的违规站点。
- 只写接口与装配，不启动服务。

**阶段 2 · `metric-service`**（首选由 `data-layer` 改为本服务，依据见 `04-阶段2启动勘察.md` 与 `06-阶段2首发清单.md`）：`data-layer` 的 3 个 AWS 点就是它的全部逻辑，本机没有 `ContextManagerPort` 的本地对端，替换完只剩转发，作阶段 2 首选不成立；`metric-service` 的 `validate` 路由已在现有 venv 零下载跑通并产出确定性 findings，是七条里离「真跑」最近的。前置 `smithy-generated`（codegen 或手写最小替代模块并标注「替代物，非上游生成」）；指标仓库/执行器/目录三处换 PG + 本地目录；`validator` 保持唯一校验入口；补 `DataSourceLookup` / `OntologyLookup` 两个壳（`sources` 审批门禁用已有的 `ALLOW_PERMISSIVE_SOURCE_LOOKUP` 开关，不算壳）；把 Lambda handler 起成本机可调的服务形态（方案见 `06-阶段2首发清单.md`）。

**阶段 3 · `context-manager` + `data-layer`**：`context-manager` 加 Neptune 免签开关，DynamoDB 会话存储换 SQLite/PG。`data-layer` 顺延到此，**等 `ContextManagerPort` 的本地实现落地**——`catalog.py` 的 `local-http` 当前为 `_todo`——再替换它仅有的 3 个 AWS 点（AgentCore Runtime ARN、AgentCore HTTP、`DescribeSchema` 的 Lambda），本机起服务，逐条调 5 个契约操作。

**阶段 4 · 检索与本体**：`ontology-engine` 的 `dynamo_store` 换 PG，接口不动；`vkg` 接 Postgres；`mcp-server` 的 `use_fuseki` 接上或删除，S3 换本地件。

**阶段 5 · 特性第一批**：指标观测、健康看板、值级溯源。每项写清落哪个包、依赖哪些端口、怎么验。

**阶段 6 · 特性第二批**：A-Box 断言账本、画布、影响分析、合成数据、迁移 bundle。

**阶段 7 · 硬骨头 + 回归**：`control-plane` 做 DynamoDB 语义适配层（分页游标、条件写、乐观锁逐条对齐）；`sources` 用「目录快照 + 本地 SQL/Trino」降级并列能力缺失清单；全量回归 + 配置矩阵 + 一条命令起栈。

## 6. AWS → 本地映射

替换点细化到文件/行号见 doc/_design/86 §4–§5，本表只给包级落点。

| AWS 组件 | COA 内替换点（包） | 本地实现 | 等价程度 |
|---|---|---|---|
| Neptune | `context-manager`、`ontology-engine`、`vkg` | Oxigraph / Fuseki（SPARQL 1.1） | **等价**（查询能力）；不保证 Neptune 专有语义 |
| AOSS / OpenSearch | 检索类包（`context-manager`、`vkg`、`mcp-server`） | 本地 OpenSearch（k-NN 索引与查询）/ pgvector（降级） | **形状等价**（k-NN 有，SigV4、托管扩缩容无）；pgvector 为降级 |
| Bedrock（LLM） | `context-manager` 等调用 LLM 的包 | llama.cpp + 小模型 | **链路等价，能力不对等**（0.5B 仅证链路） |
| Bedrock（Embedding） | 同上 | TEI + `BAAI/bge-m3`（1024 维）/ 外部 HTTP | **等价**（OpenAI 兼容形状）；第三方端点未验 |
| DynamoDB | `control-plane`、`context-manager`、`ontology-engine` | dynamodb-local（API 形状）/ SQLite·PG（降级） | **API 形状等价、语义子集**；分页/条件写/乐观锁需逐条对齐 |
| S3 | `mcp-server`、`data-layer`、`context-manager` | MinIO（S3 API）/ 本地 fs | **等价**（基础对象语义）；fs 无预签名 |
| Athena | `sources`、`metric-service` | 本地 Trino（Presto 协议，提交—轮询—取结果）/ PG 执行器 | **部分等价**；无 Glue 联邦、方言与配额差异 |
| Glue / DataZone | `sources` | 目录快照 | **降级**（仅元数据，无血缘与治理） |
| AgentCore Runtime | `data-layer`、`context-manager` | 本地 HTTP 服务 | **等价物，非 AWS 行为** |
| SQS | 编排类包 | SQLite 队列 | **等价物，非 AWS 行为** |
| StepFunctions | 编排类包 | 本地状态机 | **等价物，非 AWS 行为** |
| EventBridge | 编排类包 | 进程内事件总线 | **等价物，非 AWS 行为** |
| ECS / Cloud Map | 部署层 | docker compose + DNS 别名 | **等价物，非 AWS 行为** |

口径：「等价」= 同协议同语义，调用代码不改；「部分等价/降级」= 协议或能力缺项，必须写进能力缺失清单；「等价物，非 AWS 行为」= 只保证接口可用，不与 AWS 行为做等价性对比。

## 11. 领域组织（DDD：扬长避短）

> **优先级高于「先出代码」**。阶段 1 先落 §11.1 边界与 §11.2 语言，再写端口签名；端口名、DTO 名、错误码与本节不一致即返工。

### 11.1 限界上下文

上下文不等于目录：`sources` 一个包承载「文档摄入」与「数据源接入」两个上下文，模块边界就是上下文边界；`ontology-engine` 同时承载「本体」与「知识图」，以 catalog/validation 与 graph store 为界。拆分的唯一依据是不变量、事务边界与变更原因，不按目录切。

| # | 上下文 | 承载包（模块） | 职责（一句话） | 聚合根 / 主要实体 | 对外只暴露 | 为什么不能与相邻上下文合并 |
|---|---|---|---|---|---|---|
| R | 问答与检索 | `context-manager`（`coa_serve`） | 把自然语言请求变成受控计划，产出答案与引用。 | **`QueryRun`**；实体 `RetrievalPlan`、`Answer`、`Citation`；值对象 `Confidence`、`QueryOptions` | `Query` / `Translate` / `KBSearch` / `GraphTraverse` + `GetAnswer` | 有会话状态、超时预算与置信度，变更由回答质量驱动；知识图只保证图的不变量，两者事务与变更原因不同。 |
| M | 指标 | `metric-service` | 定义指标口径，并在窗口内产出或读取观测值。 | **`MetricDefinition`**；实体 `MetricObservation`、`MetricComputation`；值对象 `MetricName`、`Period`、`Grain` | 指标管理 operation + `GetMetricObservations` / `ComputeMetric` | 定义是不可变口径，观测是事实记录；数据源接入只管连接与目录，不能因换连接而改口径。 |
| O | 本体 | `ontology-engine`（catalog / validation） | 管理 namespace 内 T-Box、映射、约束、校验与发布版本。 | **`Ontology`**；实体 `OntologyClass`、`OntologyProperty`、`Mapping`、`OntologyProposal`；值对象 `OntologyId`、`OntologyVersion` | schema / registry / 提案校验 + `GetOntologyVersion` | schema 级不变量与不可变发布快照；知识图是实例级断言，可持续增长。合并后「发布版本」无法定义。 |
| D | 文档摄入 | `sources`（documents） | 把外部文件变成不可变版本与可检索切片，并抽取事实候选。 | **`Document`**；实体 `DocumentVersion`、`Chunk`、`IngestionRun`；值对象 `DocumentId`、`ChunkId`、`PageRange` | 文档上传/查询/删除、摄入状态；下游只见 `Chunk` 与 `DocumentVersionRef` | 文档有原始字节、解析失败、重试与版本；知识图只有断言。chunk 是检索单位，不是图节点。 |
| C | 控制面 | `control-plane` | 管理 namespace 生命周期、授权、角色与配额。 | **`Namespace`**；实体 `Grant`、`Role`、`PrincipalBinding`；值对象 `NamespaceId`、`NamespaceStatus` | namespace / 角色 / 授权管理 + 鉴权判定 | 横切治理，失效模式是越权与误删租户；放进业务上下文会让每个上下文都依赖管理模型。 |
| S | 数据源接入 | `sources`（database） | 登记数据库连接、发现目录资产、提供跨源联邦能力。 | **`DataSource`**；实体 `ConnectionProfile`、`TableAsset`、`FederationPlan`；值对象 `DataSourceId`、`SecretRef` | 连接登记/探测、目录资产、`DataSourceLookup` | 连接与凭据的生命周期（轮换、撤销、探测）与文档生命周期完全不同，二者只是同包不同上下文。 |
| G | 知识图 | `ontology-engine`（graph store）+ `vkg` | 承载 A-Box 实例断言、图查询与虚拟图到关系源的翻译。 | **`Graph`**；实体 `Entity`、`Statement`；值对象 `Iri`、`GraphUri` | `GraphClient.query/ask`、`GraphTraverse`、`GetEntity`、`OntologyLookup` | 断言集合要幂等、可重放（A-Box 账本）；本体要发布不可变。聚合根与事务边界不同。 |

非领域层（不建聚合、不建领域事件、不设仓储）：

| 层 | 包 | 定位 | 禁止 |
|---|---|---|---|
| 契约网关 | `data-layer`、`mcp-server` | Smithy/HTTP 契约校验、协议转换、鉴权透传 | 不做聚合、不做业务编排、不持有领域状态 |
| 基础设施端口 | `packages/coa-ports` | 出站端口的 Protocol / DTO / 错误，属于基础设施边界 | **不是领域模型**，不承载业务规则，不反向依赖任何领域包 |
| 组合与适配 | `packages/coa-runtime`、`packages/local-providers`、`packages/platform-core` | 组合根、ACL 薄壳、本地实现库 | 领域包不得 import 它们；它们只被组合根 import |
| 验证跑道 | `packages/coa-gateway` | P1–M2 harness | 不进交付路径，不被领域包 import |

### 11.2 统一语言

四条规则：

1. 一个词只有一个权威定义、一个 owner 上下文；其他上下文引用时必须显式翻译，禁止同名不同义。
2. 契约 wire 字段可以沿用上游名字，但进入端口签名前必须映射到本表术语。
3. 值对象用显式别名（`NamespaceId`、`Iri`、`GraphUri`、`ChunkId`、`MetricName`、`DataSourceId`），禁止裸 `str` 跨上下文混用。
4. 新代码不得引入本表之外的近义词；发现冲突先改本表并记录裁定，再改代码。

| 术语 | 中文 | 权威上下文 | 唯一权威定义 | 跨上下文规则 |
|---|---|---|---|---|
| `Namespace` / `namespaceId` | 命名空间 | 控制面 | 租户与隔离边界，UUID v4 | 其他上下文只读引用；RDF 命名图一律叫 `GraphUri`，禁止叫 namespace |
| `Principal` / `principalId` | 主体 | 控制面 | 调用者身份与所属组/全局角色 | 问答上下文的 `profile` 是 Principal 的投影，不得另造 user 模型 |
| `Metric` / `MetricName` | 指标（定义） | 指标 | namespace 内按名唯一的指标口径，含表达式方言、数据源、时间粒度 | 数值不叫 metric；平台 registry 条目是 `MetricDefinition` 的投影 |
| `Observation` / `MetricObservation` | 观测值 | 指标 | 已落库的期间值：`periodStart`、`periodEnd`、`value`、`unit`、`dimensions`、`synthetic`、`dataSourceId` | 其他上下文引用必须写 `MetricObservation`；SQL 执行回显、日志、trace 都不得叫 observation |
| `MetricComputation` | 指标计算 | 指标 | 一次只读计算，不落库 | 与 `Observation` 区分；需要落库走平台既有写路径 |
| `Ontology` / `OntologyId` | 本体 | 本体 | namespace 内 schema、映射、约束的集合 | 不指实例数据；实例数据归 `Graph` |
| `OntologyVersion` | 本体版本 | 本体 | 不可变标识：`contentHash` + `publishedAt` + `graphUri` | 空串只表示「无已发布版本」，禁止用 `updatedAt` 冒充 |
| `Graph` / `GraphUri` | 知识图 | 知识图 | namespace 内的命名图 | 禁止与 `Ontology` 混用；图标识不叫 namespace |
| `Entity` / `EntityRef` | 实体 | 知识图 | 一个主语（IRI 或 bnode）及其陈述；`EntityRef` = (`namespaceId`, `iri`) | 禁止用 entity 指表或行；表和行分别叫 `TableAsset` / `Row` |
| `Statement` | 陈述 | 知识图 | 断言 (s, p, o, g) | wire 可保留 triple 字样，跨上下文 DTO 用 statement |
| `Document` / `DocumentVersion` / `DocumentId` | 文档 / 文档版本 | 文档摄入 | 原始文件与不可变版本 | 禁止把 chunk 当 document |
| `Chunk` / `ChunkId` | 切片 | 文档摄入 | `DocumentVersion` 的最小可检索文本单元，`chunkId` 稳定 | 引用链节点是 `Citation` 包装 Chunk，不是 Chunk 子类；禁止 passage / fragment |
| `DataSource` / `DataSourceId` | 数据源 | 数据源接入 | 数据库连接 + 凭据引用 + 目录绑定 | 文档来源用 `documentId`，不叫 source |
| `SourceFilter` | 来源过滤 | 契约字段（跨文档摄入/数据源接入） | 只表示 chunk 的 originRef（`documentId` 或 `dataSourceId`） | 不是 `DataSource` 聚合；禁止据此建领域模型 |
| `QueryRun` / `Answer` / `Citation` | 问答运行 / 答案 / 引用 | 问答与检索 | 一次问答的完整生命周期 / 答案 / 引用元数据 | 指标值不是 answer；答案必须带 citations 或显式空 |
| `TraceStep` | 追踪步骤 | 问答与检索 | 一次执行的步骤记录 | 不是 `Observation`，不参与指标口径 |

#### 11.2.1 术语冲突裁定（逐条）

| 词 | 冲突在哪 | 裁定 | 落地动作 |
|---|---|---|---|
| `metric` | `metric-service` 的 `MetricDefinition`；`platform_core` 的 `metric_observation` 与 `outputType: observation`；口语里「指标值」也叫 metric | **Metric 只指定义**；值一律叫 `Observation`；契约 `metricName` 永远指定义名 | 阶段 1 新 DTO 用 `MetricDefinition` / `MetricObservation`；阶段 3 清理 metric-service 内混用 |
| `observation` | `platform_core` 的 `metric_observation`（观测值）与 `context-manager` 的 `sql_agent.py` 把 SQL 执行回显叫 observation（喂给模型） | **Observation 专属指标观测值**；模型反馈改名 `ExecutionFeedback`；`TraceStep` 不得叫 observation | 阶段 3 只改 `sql_agent` 的局部命名与注释，不改行为；跨上下文 DTO 先按新名 |
| `ontology version` | `ontology-engine/stores/base.py:481` 与 `neptune_db_graph.py:2076` 返回 `ontologyVersion: ""`；`control-plane` 的 `OntologyRecord` 只有 `updatedAt`；doc 85 要求不可变 `contentHash` | **OntologyVersion = contentHash + publishedAt + graphUri 的不可变标识**；`""` 只表示无已发布版本，读取方按 503/404 处理，不得回退 `updatedAt`；跨上下文 DTO 把 `updatedAt` 改称 `modifiedAt` | 阶段 4 接版本源；阶段 2 前不改返回形状 |
| `namespace` | 契约 `namespaceId` 是 UUID 租户边界；`ontology-engine` 把命名图与 RDF namespace 也叫 namespace（`na_store` 的 `namespaced graph ID`） | **Namespace 只指租户边界**；图标识一律 `GraphUri`；局部变量在阶段 4 改名为 `graph_uri` | 阶段 4 只改跨边界签名与新增代码，不强制重命名所有局部变量 |
| `entity` | `GraphTraverse` 的 `entities` 是图节点；平台 `GetEntity` 是一个主语的全部陈述；`sources` 里 entity 有时指表资产或行 | **Entity = 图主语（IRI/bnode）+ 陈述**；`EntityRef` = (`namespaceId`, `iri`)；表 / 行分别叫 `TableAsset` / `Row` | 阶段 4 在 sources 对外字段做映射，不改存储 |
| `chunk` | `VectorHit` 的 text 叫 chunk；MCP `KBSearch` 返回 `chunks`；doc 85 的 `CitationNode` 也含 `chunkId`；平台 `supportingContent` 是平铺 chunk | **Chunk = DocumentVersion 的最小可检索单元，chunkId 稳定**；`Citation` = Chunk + 引用元数据（不是 Chunk 子类）；`SupportingContent` = Citation 列表；禁止 passage / fragment | 阶段 5 值级溯源统一用 `Citation` |
| `source` | `DataSource`（数据库连接）、文档来源、契约 `sourceFilter` 三义 | **DataSource 专属数据源接入**；文档来源用 `documentId`；`sourceFilter` 只是 chunk originRef 过滤，不是聚合 | 阶段 4 只在新 DTO 与文档字符串说明，不改契约字段名 |
| `ontology` vs `graph` | `ontology-engine` 一个包同时存 schema 与实例图，外部常把两者都叫 ontology | **Ontology 只指 schema / 映射 / 版本**；A-Box 断言归 `Graph`；`OntologyLookup` 查 schema，`GraphClient` 查实例 | 阶段 4 在端口与 DTO 注释中写死，包内实现不动 |

### 11.3 上下文映射与防腐层

依赖方向（只允许从左到右）：

| 依赖方 | 被依赖方 | 交互方式 | 过 ACL | 说明 |
|---|---|---|---|---|
| 契约网关 `data-layer` / `mcp-server` | 问答与检索、本体、指标 | 端口调用 + HTTP 契约 | 是 | 只做协议校验与透传，不持有领域状态 |
| 问答与检索 | 本体 | `SchemaProvider` | 是 | 只取 schema 快照与版本标识 |
| 问答与检索 | 知识图 | `GraphClient`、`GraphTraverse` | 是 | 图结果映射为 `Entity` / `Statement` |
| 问答与检索 | 指标 | `GetMetricObservations` / `ComputeMetric` | 是 | 只消费观测值与计算结果 |
| 问答与检索 | 文档摄入 | 向量检索 + `Chunk` DTO | 是 | 不直接读文档库 |
| 指标 | 本体 | `GraphClient`（指标定义存 ontology 图） | 是 | 指标不解析 RDF，只经端口读写定义 |
| 指标 | 数据源接入 | `DataSourceLookup` | 是 | 只查数据源元数据，不拿凭据明文 |
| 本体 ↔ 知识图 | 双向 | `GraphStorePort` | 是 | 本体发布写 schema 图、读图校验；不共享内核 |
| 文档摄入 | 知识图 | `EventBusPort` / `ComputePort` 发布抽取事实 | 是 | 文档上下文不直接写图 |
| 所有上下文 | 控制面 | `IdentityPort` + 鉴权判定 | 是 | 单向；控制面不依赖任何业务上下文 |

ACL 规则（写死）：

1. 跨上下文只允许三种交互：**端口调用**、**Smithy/HTTP 契约**、**`EventBusPort` 事件**；禁止 import 另一个上下文的内部模块。
2. 13 个端口与 10 个复用接口都是**基础设施端口（出站）**，不是领域仓储；**provider 薄壳就是 ACL 的落点**，只做签名/形状/错误码转换，不含业务规则。
3. 领域对象不得进入端口签名；端口 DTO 只用统一语言里的值对象与标量。`platform_core` 的 `Manifest`、ORM 行、boto3 响应只允许出现在薄壳内部。
4. 错误语义：端口抛 `coa_ports.errors.PortError`（`code` / `message` / `provider` / `provider_code` / `details`）；调用方必须翻译成本上下文的错误，禁止把 `provider_code` 透给客户；对外契约沿用 COA 的 `ValidationError` / `NotFoundError` / `TimeoutError` / `Unavailable`。
5. 反向依赖禁止：领域包不得 import `platform_core`、`coa_local_providers`、`boto3`、`coa_gateway`；实现只由组合根注入。
6. 组合根 `coa-runtime` 按上下文装配：每个上下文一个装配函数，构造参数只接收端口类型。

### 11.4 明确不长的地方（扬长避短）

写死，防止有人拿 DDD 当理由返工：

- **基础设施适配层**（provider、薄壳、SDK 封装）：不做聚合、不建领域事件、不做仓储抽象。
- **纯 CRUD**（namespace / role / grant 的 handler、metric create/list）：只做输入校验 + 存储调用；领域模型只在需要不变量时出现。
- **只做转发的网关**（`data-layer`、`mcp-server`、`coa-gateway`）：不做领域对象，不做业务编排。
- **一次性脚本**（`scripts/prove_*`、快照导出、数据生成）：不进模型。
- **不引入 Event Sourcing / CQRS**；指标观测、健康看板用普通查询与视图，不建读写分离，除非出现明确需求并写进 §10。
- **不为模型漂亮推倒能跑实现**；只在新代码与必须改的跨上下文边界处执行本节，存量实现按 §5 阶段逐步收口。
- **`platform_core` 保持实现库**，不给它补领域层。

### 11.5 对阶段 1 的具体影响

1. **顺序**：§11.2 术语表 → 端口签名/DTO → 薄壳。端口名或 DTO 名与术语表不一致，视为未完成。
2. **命名**：11 个跨服务端口进 `coa-ports`；`ControlPlaneStore` 落 `control-plane`；`OcrPort` 落 `context-manager`。`ContextManagerPort` 是到问答上下文的传输端口（基础设施命名），其 DTO 必须用 `NamespaceId` / `Principal` / `QueryRun` 语义，不得裸传业务对象。
3. **DTO**：统一用 `NamespaceId`、`Iri`、`GraphUri`、`ChunkId`、`MetricName`、`DataSourceId` 等显式别名；禁止用 `dict[str, Any]` 作为跨上下文端口的入参/出参（纯传输信封除外，且键名固定、必须文档化）。
4. **错误**：端口错误统一 `PortError`，`code` 只取统一语言里的 `not_found` / `unavailable` / `timeout` / `invalid_argument` / `conflict` / `unsupported` / `internal`；`provider_code` 只用于日志与诊断。
5. **薄壳单测**：与 §5 阶段 1 判据合并为同一条「薄壳有单测覆盖真实调用」，不设两套判据；测试必须打本地 PG / Oxigraph / TEI，不允许只测 mock。
6. **收尾证据**：阶段 1 交付时给出「跨上下文 DTO 无同名不同义」清单、端口签名与 §11.2 的逐条对照、组合根按上下文装配的入口清单。

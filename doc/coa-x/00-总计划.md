## 1. 定位（校准后）

一句话：**coa-x 是在 COA 代码库内部做二次开发，让 COA 自己在本机跑起来。**

三条边界，写死，后续不再讨论：

1. **宿主是 COA 本身。** 运行时承载体是 `packages/data-layer`、`metric-service`、`context-manager`、`ontology-engine`、`vkg`、`mcp-server`、`control-plane`、`sources`。不是 `packages/platform-core`，也不是 `packages/coa-gateway`。
2. **替换点在 COA 自己的代码里。** AWS 构造点改成「先有接口、再由配置注入」，实现放在 provider 包里被 COA 引用。不新起一套并列系统，不把 COA 挂到 platform 网关后面跑。
3. **`platform_core` 是实现库，不是宿主。** 它的适配器（图、向量、Embedding、LLM、SQL、对象存储、会话、记忆）以库形态进入 COA 的端口实现；它多出来的特性做迁入，不重造。

`coa-gateway` 的定位：P1–M2 的验证跑道（harness），不是交付物。阶段 2 起对外的是 COA 服务本身，网关退为可选。

## 2. 终态与完成定义

终态三句话：

1. 本机一条命令起 COA，不依赖任何 AWS 账号或外网。
2. 功能不低于现有 platform（指标、本体、术语、问答、溯源、画布、健康看板等）。
3. 每个接口一个配置键，可在 **AWS 原生 / 本地 / 第三方** 之间逐接口混搭（例如 graph 用 AWS、llm 用本地），切换不改调用代码。只承诺配置矩阵里标「已验证」的组合。

### 完成定义（DoD，全部可观测；缺一不算完成）

| # | 判据 | 怎么验 |

## 3. 五条原则

1. **接口先行**：每个替换点先有接口（方法签名、输入输出、错误语义），再谈实现。
2. **只依赖接口**：业务代码禁止 import 具体实现；实现类只出现在组合根与 provider 包。
3. **组合根注入**：构造与装配集中在一处，按配置键选实现；业务类构造参数只接收接口实例。
4. **只换插头**：允许改 COA 上游代码，但只做「写死改可注入」，不重写业务逻辑；能复用 `platform_core` 已有实现的不重造。
5. **功能优先、单机优先、易用优先**：先让功能在本机真跑起来，再谈等价性与性能；不为「像 AWS」牺牲可运行性。

缺配置必须明确报错，禁止静默 fallback 到任何实现。

### 为什么重排（避免前面白干）

原计划把「`platform_core` 迁入」放在阶段 6，结果是阶段 2–5 先写一份本地实现，阶段 6 再换成 `platform_core` 另一份，等于同一能力做两遍。修订后：

- **阶段 1 就把 `platform_core` 已有适配器登记为端口实现**，阶段 2–5 只消费端口，不再自写第二份。
- 原阶段 6 拆成两块：已实现能力的「登记与去重」并入阶段 1；尚未实现的新特性放进阶段 5/6。
- `coa-gateway` 不再作为阶段 6 的宿主；阶段 2 起由 COA 服务自身对外。

### 各阶段工作项

**阶段 1 · 端口层与组合根**（本轮开工）

- 新建 `packages/coa-ports`：13 个端口的 Protocol + DTO + 错误类型，纯 typing，零第三方依赖。跨服务端口集中放这里，避免各包互相 import。
- 例外两个端口落消费方包：`ControlPlaneStore` 留 `control-plane`（阶段 7 才实现，先定义后落位）；`OcrPort` 留 `context-manager`（只有文档摄入用）。
- 新建 `packages/coa-runtime`：组合根 + 配置解析。理由：组合根不属于任何业务服务；放 `libs/common` 会让公共库反向依赖所有实现包，破坏依赖方向。
- 10 个复用接口只做归属确认，不重造。
- 把 `platform_core` 已有适配器登记进组合根：`local` 实现首版直接引用它们。
- 11 类违规逐条改注入，每条记文件、行号、改前/改后写法。
- 只写接口与装配，不启动服务。

**阶段 2 · `data-layer`**：前置 `smithy-generated`（codegen 或手写最小替代模块并标注「替代物，非上游生成」）；替换它仅有的 3 个 AWS 点（AgentCore Runtime ARN、AgentCore HTTP、`DescribeSchema` 的 Lambda）；本机起服务，逐条调 5 个契约操作。

**阶段 3 · `metric-service` + `context-manager`**：指标仓库/执行器/目录三处换 PG + 本地目录；`validator` 保持唯一校验入口；`context-manager` 加 Neptune 免签开关，DynamoDB 会话存储换 SQLite/PG。

**阶段 4 · 检索与本体**：`ontology-engine` 的 `dynamo_store` 换 PG，接口不动；`vkg` 接 Postgres；`mcp-server` 的 `use_fuseki` 接上或删除，S3 换本地件。

**阶段 5 · 特性第一批**：指标观测、健康看板、值级溯源。每项写清落哪个包、依赖哪些端口、怎么验。

**阶段 6 · 特性第二批**：A-Box 断言账本、画布、影响分析、合成数据、迁移 bundle。

**阶段 7 · 硬骨头 + 回归**：`control-plane` 做 DynamoDB 语义适配层（分页游标、条件写、乐观锁逐条对齐）；`sources` 用「目录快照 + 本地 SQL/Trino」降级并列能力缺失清单；全量回归 + 配置矩阵 + 一条命令起栈。

## 6. AWS → 本地映射

替换点细化到文件/行号见 doc/_design/86 §4–§5，本表只给包级落点。

| AWS 组件 | COA 内替换点（包） | 本地实现 | 等价程度 |
|---|---|---|---|
| Neptune | `context-manager`、`ontology-engine`、`vkg` | Oxigraph / Fuseki（SPARQL 1.1） | **等价**（查询能力）；不保证 Neptune 专有语义 |
| AOSS / OpenSearch | 检索类包（`context-manager`、`vkg`、`mcp-server`） | 本地 OpenSearch（k-NN 索引与查询）/ pgvector（降级） | **形状等价**（k-NN 有，SigV4、托管扩缩容无）；pgvector 为降级 |
| Bedrock（LLM） | `context-manager` 等调用 LLM 的包 | llama.cpp + 小模型 | **链路等价，能力不对等**（0.5B 仅证链路） |
| Bedrock（Embedding） | 同上 | TEI + `BAAI/bge-m3`（1024 维）/ 外部 HTTP | **等价**（OpenAI 兼容形状）；第三方端点未验 |
| DynamoDB | `control-plane`、`context-manager`、`ontology-engine` | dynamodb-local（API 形状）/ SQLite·PG（降级） | **API 形状等价、语义子集**；分页/条件写/乐观锁需逐条对齐 |
| S3 | `mcp-server`、`data-layer`、`context-manager` | MinIO（S3 API）/ 本地 fs | **等价**（基础对象语义）；fs 无预签名 |
| Athena | `sources`、`metric-service` | 本地 Trino（Presto 协议，提交—轮询—取结果）/ PG 执行器 | **部分等价**；无 Glue 联邦、方言与配额差异 |
| Glue / DataZone | `sources` | 目录快照 | **降级**（仅元数据，无血缘与治理） |
| AgentCore Runtime | `data-layer`、`context-manager` | 本地 HTTP 服务 | **等价物，非 AWS 行为** |
| SQS | 编排类包 | SQLite 队列 | **等价物，非 AWS 行为** |
| StepFunctions | 编排类包 | 本地状态机 | **等价物，非 AWS 行为** |
| EventBridge | 编排类包 | 进程内事件总线 | **等价物，非 AWS 行为** |
| ECS / Cloud Map | 部署层 | docker compose + DNS 别名 | **等价物，非 AWS 行为** |

口径：「等价」= 同协议同语义，调用代码不改；「部分等价/降级」= 协议或能力缺项，必须写进能力缺失清单；「等价物，非 AWS 行为」= 只保证接口可用，不与 AWS 行为做等价性对比。

# 22 - 性能基线（只读路由 / 真实数据量放大）

> 实测日期：2026-11-10。独立栈，未触碰共享端口。只发只读请求（GET + 只读 `POST /sparql`），未调用任何写路由，未改业务代码。

## 结论

以现有防护水平，这套只读面在 **3,624 quad 时全部可用；到 5 万 quad 时无 `kind` 搜索按设计被 422 拒绝、三条图遍历路由已到 5–8 秒；到 10 万 quad 时 `/graph/canvas`、`/graph/path`、`/graph/search?kind=` 全部撞上 28 秒后端超时返回 504**。也就是说，**"所有只读路由都能用"的实际拐点在 3.6k～5 万 quad 之间，5 万是当前上限，10 万起只剩非图遍历路由可用**。

三条硬结论：

1. `/graph/canvas`、`/graph/path`、`/graph/search?kind=` **没有数据量防护**，10 万 quad 起稳定 504；5 万时分别是 5.4s / 5.7s / 8.2s（p95）。
2. `/graph/search` 不带 `kind` **有防护**：50,000-quad 预算，50k 数据即 422（实测 50,900 被拒，预算按 namespace 全图计，包含 900 条指标图）；该路由不会挂，但也不可用。
3. `POST /sparql` 的 10 秒超时只切断 API 响应，**不停止 Oxigraph**：超时后服务端仍在跑，实测约 1,100% CPU / 4.3 GB 内存持续占用，直到重启容器；这是比 504 本身更危险的点。

合成数据规则（每个类 4 条）：`a owl:Class`、`rdfs:label "Perf Class N"@en`、`rdfs:comment`、`rdfs:subClassOf` 指向下一个类。全部写入同一个 namespace 命名图，路径查询的起止点仍用本体里真实存在的 `InvestmentObjective → Classification`。指标固定 100 条，不随 quad 放大，用于区分"图变大"与"指标条数变多"。

字典路由的数据量在 PG 独立放大（`serve_local.platform.dictionary_column`，单一 source）：0 / 10,000 / 50,000 / 200,000 列，单独一张表。

## 口径

- 串行执行，无并发；每路由先 1 次预热（超时探针除外），随后取 N 次：base 6、50k 5、100k 6、500k 5、字典 8。
- p50 / p95 为线性插值；max 为样本最大值。
- 超时探针每个数据档**只打 1 次**：因为服务端不取消，重复打会把 Oxigraph 压死，无法继续测后续路由。每次探针后重启自有 Oxigraph 清场。
- 28 秒 504 来自 `api_proxy_handler._BACKEND_TIMEOUT_SECONDS = 28`，不是客户端超时。
- `returned_rows` 取最后一次成功响应的条数；504 的响应体不含数据。

### 放大后新挂掉的路由

- **10 万 quad 新增**：`GET /graph/canvas`、`GET /graph/path`、`GET /graph/search?kind=class`。三者都返回 504 `The ontology service did not respond in time. Retry the request.`。
- **50 万 quad**：上述三条从"混合 200/504"变成"全部 504"；`/graph/search` 无 kind 仍稳定 422（耗时从 0.41s 涨到 2.49s）；`/sparql` 超时从 10.2s 涨到 14.6s。
- **没有新增挂掉的非图路由**：`statements`、`entities`、`metrics`、`dictionaries`、`answer/quality`、`system-health` 在 50 万 quad 下仍全部 200。

## 未解释现象（如实记录）

1. 100k 时 `canvas` 的 status 集合是 `[200, 504]`，p50 已经 28.0s；200 的那次 `nodes+edges` 记为 0。没有单独复现"200 但空画布"的原因，可能是后端在 28s 边界上返回了不完整结果，也可能是采样时机问题。
2. 500k 的 SPARQL 超时样本是 14.59s，而 base/50k/100k 是 10.2–10.6s。多出来的约 4s 没有定位；当时同实例已有图遍历超时留下的负载。
3. `metrics` 在 50k 档出现一个 448ms 的冷样本，p50 只有 73.9ms；没有重复出现，按冷启动/缓存未命中记录，未深挖。
4. 搜索预算报的是 namespace 全图 50,900 而不是本体图 50,000：900 条指标图也被计入。这是实测数字，不是估算。

## 复现

```powershell
# 1. 起独立栈（PG 6144 / Oxigraph 8088 / engine 8812 / ctx 8898 / bridge 8899）
powershell -ExecutionPolicy Bypass -File .\doc\coa-x\tools\perf-baseline-stack.ps1 -Start

# 2. 灌基础本体（3,624 quad，156 类）
powershell -ExecutionPolicy Bypass -File .\doc\coa-x\tools\perf-baseline-stack.ps1 -Seed

# 3. 指标图（100 条）与基础基线
python .\doc\coa-x\tools\perf_baseline.py load --target 3624 --seed-metrics 100
python .\doc\coa-x\tools\perf_baseline.py measure --label base --quads 3624 --iterations 6 --out base.json

# 4. 放大到目标 quad 数（先重启自有 Oxigraph 清掉上一次超时探针的残留查询）
#    注意：50k 档的无 kind 搜索实测 422；再往上走必须先把图重置回 base
docker restart perf-baseline-oxigraph
python .\doc\coa-x\tools\perf_baseline.py load --target 50000
python .\doc\coa-x\tools\perf_baseline.py measure --label 50k --quads 50000 --iterations 5 --out 50k.json

docker restart perf-baseline-oxigraph
python .\doc\coa-x\tools\perf_baseline.py load --target 100000
python .\doc\coa-x\tools\perf_baseline.py measure --label 100k --quads 100000 --iterations 6 --out 100k.json

# 500k 需要先从 base 重新灌（load 只追加，不重置）
powershell -ExecutionPolicy Bypass -File .\doc\coa-x\tools\perf-baseline-stack.ps1 -Seed
docker restart perf-baseline-oxigraph
python .\doc\coa-x\tools\perf_baseline.py load --target 500000
python .\doc\coa-x\tools\perf_baseline.py measure --label 500k --quads 500000 --iterations 5 --out 500k.json

# 5. 字典单独加压
python .\doc\coa-x\tools\perf_baseline.py seed-dict --rows 50000
python .\doc\coa-x\tools\perf_baseline.py measure --label dict-50k --quads 3624 --iterations 8 --only dictionaries --out dict-50k.json

# 6. 收尾
powershell -ExecutionPolicy Bypass -File .\doc\coa-x\tools\perf-baseline-stack.ps1 -Stop
```

脚本说明：

- `perf-baseline-stack.ps1`：只管理本次专用容器（`perf-baseline-pg` / `perf-baseline-oxigraph`）和 8812/8898/8899 三个自有进程；`-Stop` 只杀命令行匹配本仓库脚本的进程，端口被其他进程占用时跳过。
- `perf_baseline.py`：`load` 用于把 namespace 图精确灌到目标 quad 数；`measure` 只发 GET 和只读 `POST /sparql`；`seed-dict` 只写本地 `serve_local` 测试库。

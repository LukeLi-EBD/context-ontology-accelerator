# 22 - 性能基线（只读路由 / 真实数据量放大）

> 实测日期：2026-11-10。独立栈，未触碰共享端口。只发只读请求（GET + 只读 `POST /sparql`），未调用任何写路由，未改业务代码。

## 结论

以现有防护水平，这套只读面在 **3,624 quad 时全部可用；到 5 万 quad 时无 `kind` 搜索按设计被 422 拒绝、三条图遍历路由已到 5–8 秒；到 10 万 quad 时 `/graph/canvas`、`/graph/path`、`/graph/search?kind=` 全部撞上 28 秒后端超时返回 504**。也就是说，**"所有只读路由都能用"的实际拐点在 3.6k～5 万 quad 之间，5 万是当前上限，10 万起只剩非图遍历路由可用**。

三条硬结论：

1. `/graph/canvas`、`/graph/path`、`/graph/search?kind=` **没有数据量防护**，10 万 quad 起稳定 504；5 万时分别是 5.4s / 5.7s / 8.2s（p95）。
2. `/graph/search` 不带 `kind` **有防护**：50,000-quad 预算，50k 数据即 422（实测 50,900 被拒，预算按 namespace 全图计，包含 900 条指标图）；该路由不会挂，但也不可用。
3. `POST /sparql` 的 10 秒超时只切断 API 响应，**不停止 Oxigraph**：超时后服务端仍在跑，实测约 1,100% CPU / 4.3 GB 内存持续占用，直到重启容器；这是比 504 本身更危险的点。

以上第 1、3 条已在本轮修复，第 2 条维持原有预算；修复内容与改后复测见下一节。**改后同一份 10 万 quad 数据集：三条图路由 0.6s 内 422，重查询在 20s 内被服务端取消并回落到 0% CPU，不可取消的已知形状由看门狗自动重启，全程不需要人工 `docker restart`。**

## 事故复盘：让一次重查询不能拖死整栈

目标不是降延迟，而是把一次重查询的影响限制在「这次请求」之内。分四层：服务端取消 → 容器硬限 → 自动重启 → 路由前置预算。

### 1. 服务端取消：`--timeout-s` 是唯一真能停下的开关

100k quad（100,900）实测，`oxigraph/oxigraph:0.5.7 serve --timeout-s N`：

| 手段 / 查询形状 | 结果 |
|---|---|
| 客户端断开连接（客户端 40s 超时） | **不取消**：断开后 120s 仍 98.7% CPU，一核一直烧 |
| 同图 4 跳 join `GRAPH ?g { ?s ?p1 ?o1 . … }` | 取消，`N=5` 时 5.22s 返回 |
| 属性路径 `rdfs:subClassOf*` | 取消，5.86s 返回 |
| 同一 GRAPH 内 3 模式交叉积 | 取消，5.26s 返回 |
| **2 个**未绑定 `GRAPH` 变量的交叉积 | 取消，5.21s（`N=5`）/ 约 20s（`N=20`）返回 |
| **≥3 个**未绑定 `GRAPH` 变量的交叉积 | **不取消**：`N=5` 下 40s 未返回，`N=15` 下 180s 未返回，断连后继续烧 |

取消的响应形状是个坑：**HTTP 200 + chunked，body 在流中被截断并追加 `The SPARQL operation has been cancelled`，不是合法 JSON**。按状态码判断会把取消误当成成功，按 JSON 解析会抛解析异常。已按 body 哨兵识别：

- context-manager SPARQL 控制台：识别哨兵 → 504 `E_SPARQL_TIMEOUT`（其余非 JSON 响应仍是 502 `E_SPARQL_PROVIDER_ERROR`）。
- engine 图存储：抛 `GraphQueryCancelled` → 路由 504。

已知逃逸形状（≥3 个未绑定 `GRAPH` 变量）无法从 Oxigraph 0.5.7 侧取消，也没找到中断 API；只能靠下面的硬限与看门狗兜底。

### 2. 波及范围：容器 CPU / 内存硬限

容器固定参数：`--cpus 2 --memory 2g --restart unless-stopped`，`serve --timeout-s 20`。

不可取消的交叉积在跑时实测：

| 观测项 | 旧配置（无限制） | 新配置 |
|---|---|---|
| 容器 CPU | ~1,100%（≈11 核） | ~98%（≈1 核） |
| 容器内存 | 4.3 GB | 230 MiB |
| `GET /metrics` | 被拖慢/超时 | 200 / 265ms |
| `GET /entities/{id}` | 被拖慢/超时 | 200 / 215ms |
| `GET /system-health` | 被拖慢/超时 | 200 / 2.44s |

也就是说，即使撞上不可取消的形状，也只损失 1 核，栈其余部分照常服务。内存打满时容器会被 OOM kill，`unless-stopped` 自动拉起。

### 3. 自动恢复：CPU 钉死看门狗

`perf-baseline-stack.ps1 -Watchdog [-WatchdogCpuPercent 80] [-WatchdogSeconds 90]`：每 5s 采一次容器 CPU，连续钉死超过阈值就 `docker restart`。

一个坑：**必须用 `docker restart`，不能用 `docker kill`**。`docker kill` 会被 `unless-stopped` 当成手动停止，容器 exited 137 后再也不会自动起来（实测）。

验收（100k 数据集，`-WatchdogSeconds 45`）：

| 阶段 | 观测 |
|---|---|
| 控制台发 ≥3 GRAPH 交叉积 | 10.8s 返回 504 `E_SPARQL_TIMEOUT` |
| 查询仍在跑时打轻路由 | metrics 265ms / entities 215ms / system-health 2.44s，全 200 |
| CPU 钉死 45s | 看门狗 `docker restart`，无人工介入；`StartedAt` 更新 |
| 重启后 | CPU 0%，轻路由全 200 |
| 可取消形状（2 GRAPH 交叉积） | 504 10.8s，约 20s 时服务端自己取消、CPU 回 0；`StartedAt` 不变，**不需要重启** |

`RestartCount` 不会增加：这是脚本发起的、等价于手动的重启，不是 Docker 重启策略触发。判断「有没有被自动拉起」看 `StartedAt`。

### 4. 路由前置预算 + `statements` 排序

| 路由 | 前置预算 | 100k 实测 | 500k 实测 |
|---|---|---|---|
| `GET /graph/canvas` | 50,000 quad | 422 / 0.63s | 422 / 1.01s |
| `GET /graph/path` | 50,000 quad | 422 / 0.64s | 422 / 1.01s |
| `GET /graph/search?kind=class` | 20,000 实体 | 422 / 0.41s | 422 / 0.58s |
| `GET /graph/statements` | 120,000 quad（排序预算） | 200 / 5.0s | 422 |
| `GET /graph/search`（无 kind） | 50,000 quad（原有） | 422 / 0.45s | 422 / 0.75s |

预算用先跑的 count 判断，超预算直接 422，代价 0.4–0.6s，不会把重查询发给 Oxigraph。

`/graph/statements` 的分页顺序改为 `ORDER BY ?s ?p ?o ?g`。一个 quad 由 `(s,p,o,g)` 唯一确定，所以这仍是全序，OFFSET 翻页不会重复/漏行；比 `ORDER BY ?g ?s ?p ?o` 便宜很多（100.9k 实测 6.9s vs 12.6s，前者能沿 SPO 索引走、后者要物化 graph-major 排序）。排序是全局的、无法只排当前页，500k 要约 33s，所以配 12 万 quad 预算：100k 数据集（100,900 quad）可列出，更大直接 422。

代价要说清楚：`/graph/statements` 在 100k 从 398ms 涨到 4.8–10.0s（三次复测的区间，随 Oxigraph 缓存状态波动），这是「分页顺序确定」换来的。20s 服务端截止保证了它不会被自己的排序取消。

## 口径

- 串行执行，无并发；每路由先 1 次预热（超时探针除外），随后取 N 次：base 6、50k 5、100k 6、500k 5、字典 8。
- p50 / p95 为线性插值；max 为样本最大值。
- 超时探针每个数据档**只打 1 次**：它会在 10s 返回 504，服务端在 20s 时自行取消；重复打没有必要（改前不取消，重复打会把 Oxigraph 压死，这也是当时必须重启容器的原因）。
- 28 秒 504 来自 `api_proxy_handler._BACKEND_TIMEOUT_SECONDS = 28`，不是客户端超时。
- `returned_rows` 取最后一次成功响应的条数；504 的响应体不含数据。

- **没有新增挂掉的非图路由**：`statements`、`entities`、`metrics`、`dictionaries`、`answer/quality`、`system-health` 在 50 万 quad 下仍全部 200（改后 `statements` 在 500k 因排序预算为 422）。

## 未解释现象（如实记录）

1. 100k 时 `canvas` 的 status 集合是 `[200, 504]`，p50 已经 28.0s；200 的那次 `nodes+edges` 记为 0。**已定位**：这是 28s 网关边界上的半截响应，不是空画布；改后该数据量在 0.6s 内 422，不再出现。
2. 500k 的 SPARQL 超时样本是 14.59s，而 base/50k/100k 是 10.2–10.6s。**已定位**：采样时同实例还压着图遍历超时留下的 runaway 查询，服务端过载。改后 `--timeout-s 20` 会取消该查询，且容器有硬限，不再有跨请求残留。
3. `metrics` 在 50k 档出现一个 448ms 的冷样本，p50 只有 73.9ms；没有重复出现，按冷启动/缓存未命中记录，未深挖。
4. 搜索预算报的是 namespace 全图 50,900 而不是本体图 50,000：900 条指标图也被计入。这是实测数字，不是估算。

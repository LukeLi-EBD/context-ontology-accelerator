## 1. 目标与边界

### 1.1 coa-x 是什么

- 在 COA 现有代码上二开，不新起并列系统。
- 把依赖 AWS 的组件换成本地实现：Oxigraph/Fuseki、pgvector、PostgreSQL、BGE-M3、本地 OpenAI 兼容 LLM。
- 整合 platform-core 已有能力，用端口 + 组合根收口，而不是在各服务里散落 `if provider == ...`。
- coa-gateway 只作载体/实验台，不是交付物；网关不聚合、不持有领域状态。

### 1.2 明确不做什么

| 不做 | 原因 |
|---|---|
| 不重写 COA 业务逻辑 | 只换依赖实现，保留既有行为 |
| 不重造 platform-core 已有组件 | 能复用就复用，端口只做薄壳 |
| 不做生产切换、IaC、多租户鉴权 | 本阶段是本机可运行，不是上线 |
| 不承诺未验证组合 | 没真跑过的 provider 不写成「可用」 |
| 不在网关里做聚合/编排 | 避免长出新单体 |
| 不做性能优化 | 当前只记录延迟，不调参 |

### 3.2 四种显式拒绝

| 错误码 | 触发条件 | 行为 |
|---|---|---|
| `config_missing` | 配置键缺失或为空 | 启动即抛，不选默认 provider |
| `provider_unknown` | 值不在该接口的 provider 列表 | 启动即抛，列出 allowed |
| `provider_not_available` | provider 合法但 `implemented=False` | 启动即抛，不偷换实现 |
| `provider_mismatch` | 构造出的对象不满足接口 | 启动即抛，防止薄壳挂错 |

另有 `interface_unknown`、`resolution_failed` 两个容器级错误。`resolve()` 无默认 provider、无 fallback 链；唯一例外见阻塞项 B2。

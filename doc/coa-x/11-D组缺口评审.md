# D 组缺口评审：指标三字段来源 / SPARQL·Links·Paths

日期：2026-11-10。范围：F48–F50 动手前的字段来源结论；SPARQL / Links / Paths 三页签的评审提纲。**本文不含实现**，契约未改。

## 1. `domain` / `evidenceBasis` / `publishable` 从哪来

### 现状（按代码与本地实测）

- COA 契约里 `MetricDefinition` 没有这三个字段；`ListMetrics` 目前只接受 `dataSourceId` / `sourceTable` 两个筛选入参。
- COA 指标服务的存储是导入后落到指标图的 OSI 模型；OSI 的 COA 扩展只承载 `data_source_id`、`source_table`、`unit`、`return_type`、`time_dimension`、`ontology_concepts`、`defined_by`、`effective_from`、`label`（`packages/metric-service/src/coa_metrics/osi_parser.py` 499–509），没有领域 / 依据 / 可发布。
- 这三个字段在**旧平台侧是存在的**：`packages/platform-core/src/platform_core/metrics.py` 读取的元数据列就是 `metric_id, name_zh, domain, evidence_basis, publishable, ...`。也就是说，**值在旧平台元数据里，坑在 COA 指标服务没有承载**。

### 三个候选

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）随 bundle 走** | OSI `custom_extensions` 增三个 key → 导入解析、指标图落库、导出对称 → 契约加字段 → 筛选用精确匹配；旧值按 `metricId` 一次性回填（名字只用于回填前校验唯一性，不做匹配键） | 改指标导入/导出 + 契约 + UI，一处迁移脚本 | 回填只跑一次，之后新导入的指标必须自带这三个 key，否则为 unknown |
| B 运行期读旧表 | `ListMetrics` 时 join 旧平台元数据表 | 前端和契约改动最小 | 服务耦合旧库；旧表退役即断；本地/新命名空间导入的指标没有值 |
| C 新建关系存储 | 为三个字段单开一张表/一次迁移 | 多一套存储与同步 | 只为 3 列建表，收益最低 |

推荐 **A**：这三个是业务元数据，跟着指标定义一起走语义才对；B 只能当过渡，C 不建议。

### 硬约束（写死，实现时不得放宽）

1. **只按 `metricId` 回填，不按指标名。** 指标名不是稳定主键，重命名就错配。回填脚本以 COA 侧稳定标识（`metricId`）为唯一匹配键；名字只用于回填前校验唯一性。旧表内重名（`name_zh` 出现多次）直接报错并列出冲突行，**不做模糊匹配、不做「取第一条」、不做跳过**。
2. **缺值一律记 `unknown`，不许默认 `false`、`true` 或空串。** 三个字段各三档：`true` / `false` / `unknown`。`publishable` 尤其危险——默认 `false` 等于把老指标全标成不可发布，默认 `true` 更糟。存储上 `unknown` 用可空值（PG `NULL`）表达，不占用布尔两态；界面上 `unknown` 必须与 `false` 可区分（例如 `unknown` 显示「未知」，`false` 显示「否」），筛选器提供三态而不是两态。
3. **明确这是 COA 私有扩展。** 三个 key 放在 OSI `custom_extensions` 下是 COA 自己的约定，不是 OSI 标准字段；OSI 未来标准化后要按标准字段迁移，迁移前代码与文档都要标注「COA 私有扩展」，不得当成标准能力对外承诺。

### A 的落地顺序（动手前先做第 0 步）

0. **先摸底**：把旧平台 `metric_definition` 里本命名空间指标的 `domain` / `evidence_basis` / `publishable` 取值分布 dump 出来。如果空值率极高，就只做字段搬运、不建筛选 UI——**字段来源没定就改契约，等于把一个洞挖成三个**。
1. OSI 扩展：解析、校验（类型/枚举不合法只让该指标失败，不拖垮整批）、导出对称。
2. 指标图：三个值随指标落库，`GetMetric` 返回；缺值就是 `unknown`，不写默认值。
3. 契约：`MetricDefinition` 加三字段（`publishable` 用可空布尔，`NULL` = unknown）；`ListMetrics` 加三个精确匹配入参（domain 的多值用重复参数，不发明通配语法）。
4. UI：`/metrics` 加 Domain / Evidence basis / Publishable 三个筛选与列；`unknown` 显示「未知」、`false` 显示「否」、`true` 显示「是」，三者不得合并。
5. 验收：三个筛选各命中一次、非命中返回空、`unknown` 筛选能单独命中、URL 可回放（刷新后筛选仍在）。

#### 追查：`85 = 85 = 85` 是不是巧合（2026-11-10，只读）

三个 85 分别指：`fsldm-metrics.ttl` 的 SKOS 概念 85、旧表 `platform.metric_definition` 85 行、以及（不成立的那一个）「命中 COA 指标图」。逐条查完如下。

**Q1 `metric_id` ↔ `skos:notation`：一一对上，85/85。**

| 数据面 | 行/条 | 说明 |
|---|---:|---|
| 旧平台 `agent-platform-postgres` `platform.metric_definition` | 85 | `count(*) = count(distinct metric_id)`，无重名 |
| 本地 `serve_local` 同名表 | 86 | 旧平台 85 + `synthetic_agreement_exposure` 1 条本地测试行（仓库无出处，旧平台没有） |
| `fsldm-metrics.ttl` `skos:notation` | 85 | 85 个不同值 |
| 交集 | **85** | 差集：仅 PG 有 = `synthetic_agreement_exposure`；仅 SKOS 有 = 空 |

即：除那条本地测试行外，**85 行与 85 个 notation 完全一一对应，`notation` 就是 `metric_id`**。

**Q2 谁生成谁：方向是 PG → SKOS，不是 SKOS → PG。**

`doc/_fsldm/build_metrics_skos.py` 就是生成器，文件头第一行写明「Build doc/_fsldm/fsldm-metrics.ttl from platform.metric_definition」：

- 读源：`docker exec agent-platform-postgres psql -d platform`，`SELECT metric_id, name_zh, display_name, definition, variant_of, domain FROM platform.metric_definition ORDER BY metric_id`。
- 写出口径：一行为一个 `skos:Concept`，`skos:notation = metric_id`，`prefLabel@zh = name_zh`，`definition = definition 首句`，有 `variant_of` 的加 `skos:broader` + `metric:variant true`。
- 反向路径不存在：仓库里没有「SKOS → `metric_definition`」的导入器；PG 那 85 行来自迁移 `V18`（手写 79 条）+ 后续迁移补的 6 个变体。

所以 `85 = 85` **不是巧合，是构造同一**：SKOS 分册是 PG 注册表的投影，不是第二份独立数据。这也解释了为什么补导 metrics 分册不会改变任何以 PG 为准的结论——它本来就是 PG 的另一种投影形态。

**Q3 于是 `0/1` 的性质变了：不是「数据缺」，是「口径没物化」。**

- 旧表不缺数据：85 行，三列 `NOT NULL`，空值率 0。
- 缺的是**物化**：这 85 条口径在 COA 指标图（`urn:coa:vocab#GovernedMetrics`）里一条都没有。图里只有 2 条，一条真实 `loan_account_count`（不在旧表），一条本地合成 `synthetic_agreement_exposure`。
- 所以覆盖率应按两个方向记：`COA 指标 ← 旧表口径` = **0/1**；`旧表口径 → COA 指标实体` = **0/85**。后一个才是 F48–F50 的缺口主体。（以上是追查当时的读数；物化后的数字见下节「物化已执行」。）

换句话说 fail-closed 只对受限策略成立；对 owner/maintainer 是**静默放行**，这才是最危险的一档。

- 403 的响应体由网关生成，不是业务路由的错误结构（`ConflictError` / `NotFoundError` 都不会返回）。
  具体 body 属网关默认行为，本机无部署，按未验证记。

提案验证（同一脚本，把 action 换成上表建议值，命名空间 `ACTIVE`）：

| op | action | ALLOW | DENY |
| --- | --- | --- | --- |
| `UploadDocument` | `manageSource` | admin / owner / maintainer / steward | viewer / analyst / 无角色 |
| `ListDocuments` | `viewNamespace` | 除无角色外全部 | 无角色 |
| `ListDocumentChunks` | `searchDocuments` | 除无角色外全部 | 无角色 |
| `ListFactCandidates` | `viewNamespace` | 除无角色外全部 | 无角色 |
| `ApproveFactCandidate` | `manageOntology` | admin / owner / maintainer / steward | viewer / analyst / 无角色 |
| `RejectFactCandidate` | `manageOntology` | 同上 | 同上 |
| `GetEntityEmbeddings` | `searchDocuments` | 除无角色外全部 | 无角色 |

archived 守卫：`manageSource` / `manageOntology` 在 `namespaceStatus=ARCHIVED` 下对 data-steward 均 DENY（实跑），
与现有写路由一致；三条读路由不受影响。

落地前结论：8 条路由的真实形态是「owner/maintainer 全量可用、steward/analyst 全拒」——既不是「全拒」，
也不是「按角色该有的样子」。映射落地后变成 steward 可写、analyst 可读，读写 action 不重叠。

#### fail-open 修复与防回归测试（2026-11-10 已落地）

三件事都按「先红后绿」做完。

1. **`denyAll` 改真短路拒绝**。`handler()` 在 `if roles_table:` 分支内、创建 `roles_dao` 之前判断
   `cedar_action == _UNMAPPED_ACTION`，命中即 `logger.warning("Unmapped route denied")` +
   `emit_authorization_deny(reason="deny_all_unmapped_route")` + 直接返回 Deny 策略，**不进 `evaluate()`**
   （`handler.py:885-905`）。两个位置约束是有意的：
   - 放在 `if roles_table:` 内而不是函数开头：下面的 `else` 是显式 dev-mode 逃生口
     （`ALLOW_WITHOUT_ROLES=true`，此时 Cedar 根本不跑），短路放在分支外会连它一起挡掉；
   - 只认哨兵值，不按「action 名不在 schema 里」判断——那会把将来新增的合法 action 静默拒掉。

2. **owner/maintainer 的全 action permit 是「有意」，不是历史遗留；策略不改**。
   `namespace_owner.cedar:1-3` 注释原文即「full access within their namespace ... Grants all actions
   (manage, delete, grant, etc.)」，`namespace_maintainer.cedar:1` 写「full access within their namespace
   (same as owner)」，两者同为无约束 `permit(principal, action, resource)`。让 owner/maintainer 拥有全部
   action 是有意的授权模型；fail-open 的成因不是「策略写宽了」，而是「未映射路由借一个未声明的 action
   去问宽策略」。所以修在映射层短路，而不是把 owner 策略改成 action 白名单——后者会让 owner 在每次新增
   action 时静默失效，等于把 fail-open 换成 fail-silent（`_MUTATING_ACTIONS` 里的 archived 守卫另算，它只
   收紧 ARCHIVED 下的写）。

3. **防回归测试先红后绿**。`TestUnmappedRouteFailsClosed`（`test_authorizer_handler.py:991-1052`）走真实
   Cedar 评估（`_FakeRolesDao` + `_resolve_roles` 返回 namespace-owner），参数化两条**真正未映射**的路由：

   | 阶段 | 命令 | 结果 |
   | --- | --- | --- |
   | 红（有测试、无短路） | `pytest ... -k TestUnmappedRouteFailsClosed` | `2 failed, 170 deselected`；原始断言 `AssertionError: assert 'Allow' == 'Deny'`，日志行 `effect=Allow ... namespace-owner` |
   | 绿（加短路后） | 同上 | 2 passed |
   | 绿（整个文件） | `pytest tests/unit/test_authorizer_handler.py` | `181 passed in 0.78s`（随后补了 `ALLOW_WITHOUT_ROLES` 惰性用例，见下节；该用例加入前是 180 passed） |
   | 绿（control-plane 单测全量） | `pytest tests/unit`（PYTHONPATH 含 `smithy-generated/control-plane-python-server`） | `875 passed in 6.36s` |

   参数化第二条是 `POST /namespaces/{namespaceId}/documents/{documentId}/restore`，不是
   `POST /namespaces/{namespaceId}/documents`——后者已按映射表变成 `manageSource`，不再是「未映射」；
   拿它当反例会把修复本身测成失败（第一版就是这么翻红的）。

   原始日志：`%TEMP%\pytest-red.log`、`%TEMP%\pytest-green2.log`、`%TEMP%\pytest-cp-all.log`。

结论：未映射路由现在与角色无关地判 Deny——短路在角色解析之后、Cedar 评估之前，判定不读角色，
platform-admin 也不会被放行；`denyAll` 从「靠策略语义碰运气」变成「不进引擎的硬拒绝」。

#### 第二个 fail-open 入口：`ALLOW_WITHOUT_ROLES`（2026-11-10 取证）

**结论：生产环境误开它不会绕过短路，但那不是因为有 prod 守卫，而是因为它是「两把钥匙」。**

- `handler.py:885-935`：`if roles_table:` 走 Cedar（短路也在这条分支内），`else` 才看

## 2. SPARQL / Links / Paths（单列评审，先不实现）

三个页签在契约里都没有对应 op：裸 SPARQL 无 `RunSparql`，Links 无 `FindLinks`，Paths 无 `FindGraphPath`。**评审通过前保持未落位**，不随只读浏览悄悄上线。

### 必答项

- **超时**：服务端 10 秒硬上限 + 客户端可 abort；结果行上限 5000，截断必须显式标记（不能悄悄只返回前 N 行）。
- **图范围**：只允许本命名空间的命名图；禁止 `FROM` / `FROM NAMED`、`SERVICE`、`LOAD`；默认图不参与，避免跨命名空间串读。
- **注入边界**：语句类型白名单 `SELECT` / `ASK`，拒绝多语句；只读端点（只读副本或只读 Oxigraph 视图）；拒绝 `CONSTRUCT` / `DESCRIBE` / `UPDATE` / `INSERT` / `DELETE` / `CLEAR` / `DROP`。
- **规模**：Links 深度 ≤3；Paths 只用最短路径且限制节点数；两者都要显式「无结果」空态，不返回空数组装成功。
- **配额**：每命名空间每分钟查询数上限，超限 429 并给可读原因。
- **审计**：记录查询文本哈希、耗时、行数、是否截断；不记录结果内容。

### 结论

三个 op 要一起评审、一起上，避免只放一半（例如只做 Links 不做 Paths）。评审通过前不动契约、不加页签。

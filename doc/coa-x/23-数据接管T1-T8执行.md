## 2. T1–T8 可执行动作与判定标准

### T1 文档总量一致

- **执行**：
  1. 老栈 `GET /documents?limit=100&offset=N` 累加 `items`，直到取完；同时读响应 `total`。
  2. 新栈先 `GET /namespaces` 取全部命名空间，再对每个 `GET /namespaces/{ns}/documents?maxResults=100&nextToken=` 累加；`nextToken` 原样回传。
- **期望**：老 = 3,066；新 `ListDocuments` 分页累加 = 3,066。
- **判定**：`老累计 == 新累计 == 3066` 才通过。任一端不等于 3066，或两端不等，记「对不上（差 N）」。
- **备注**：老栈 `total` 字段只作交叉核对，判据按「分页累加」执行。

### T2 切片一致

- **执行**：T1 取到的文档 ID 全集做对称差；逐文档 chunk 数取存储层 `platform.document_chunk GROUP BY document_id`（老库 `5432/platform`、新库 `5944/serve_local`），并对两端 `GET /documents/{id}/chunks` / `GET /namespaces/{ns}/documents/{id}/chunks` 抽查交叉验证。
- **期望**：文档 ID 集合相同；3,066 个文档的 chunk 数逐条相等；缺失/多余 = 0。
- **判定**：`缺失文档 + 多余文档 = 0` 且 `chunk 数不等的文档 = 0`。任一非 0 即不通过。
- **备注**：全量比对，不抽样；差异按文档 ID 列前 20 条 + 总数。老栈 documentId = 文件内容 SHA-256（T3 抽样 3/3 验证），新栈 documentId = UUID；ID 体系本身不同须同时登记。

### T3 文档字节一致

- **执行**：
  1. 以固定种子 `20261110` 对老栈文档 ID 按 `sha256(seed+id)` 升序抽样 50 个（可复跑、可复现）。
  2. 老栈 `GET /documents/{id}/source` 取原始字节，算 SHA-256。
  3. 新栈尝试 `GET /namespaces/{ns}/documents/{id}/source` 与 `GET /documents/{id}/source`，记录路由是否存在。
- **期望**：50/50 两端 SHA-256 相等（契约侧）；旧侧 50/50 存储字节哈希与 `documentId` 相等。
- **判定**：`不等条数 = 0` 通过；缺失（404/空）也计为不等，并单列「新栈无该文档」。
- **备注**：原始判据写的是 `DownloadDocument`，新契约暂无该 op。**契约缺口已登记为补 op 线的第 33 个 op（D-T3-3，本轮不改 `.smithy`）**；本轮 T3 按拍板口径改走存储层字节校验，不再挂「永久阻塞」。契约缺口与数据缺口分开记账，互不折算。

### T4 实例断言一致

- **执行**：两端执行同一组只读 SPARQL：
  - 总量：`SELECT (COUNT(*) AS ?c) WHERE { GRAPH ?g { ?s ?p ?o } }`
  - 分图：`SELECT ?g (COUNT(*) AS ?c) WHERE { GRAPH ?g { ?s ?p ?o } } GROUP BY ?g ORDER BY ?g`
  - 老栈走 `GET /browse/sparql?query=`；新栈走 `7878/query`，并用 `8699/browse/sparql` 交叉验证。
- **期望**：命名图集合相同；每个命名图 statement 数相等；总量相等。
- **判定**：`图集合差异 = 0` 且 `每图计数差异 = 0`。分图口径同时输出：
  - 全命名图（含 `urn:platform:inferred:*` 推理图）
  - 仅 `urn:platform:graph:tbox:*` 的 TBox 子集
  任一显著差异都记缺陷；若仅推理图差异，按「口径待拍板」单列，不折算为通过。
- **执行分两步（拍板口径）**：
  - **T4a（本轮）等价作用域比**：老栈 1,935 张图按图角色/本体 id 聚合，只取与「被测命名空间同域」的子集，与 `demo-ns` 对齐后比。**可比性前提先写在 §8.1，再给数**，不许反向挑一组能对上的图。
  - **T4b（登记，本轮不做）全量比对**：需等「一条命令起栈」落地后使用专用图实例，禁止在共享 `7878` 上灌 385k 全量。
- **备注**：原判据写「6 万级总量」，老栈实测全图 **384,854**（含 1,905 个历史 TBox 版本图与推理图），不是 6 万级；量级本身先对偏，按实际计数比对。

### T5 版本一致

- **执行**：
  1. 老栈 `GET /ontology/versions`（默认 `includeDeprecated=false`）取已发布版本集合：`count`、每个版本的 `id` + `contentHash`。
  2. 新栈同路径取同结构。
- **期望**：已发布版本条数相等（老栈实测 `count = 610`）；同一 `id` 的 `contentHash` 相等。
- **判定**：`条数相等` 且 `contentHash 不同/缺失的版本 = 0`。
- **备注**：原判据的「已发布版本 610」按**条数 610** 解释（实测 `/ontology/versions` 返回 `count=610`、`total=1908`，610 不是单个版本 ID）；按整组集合比对，比只比一条更严。

### T6 黄金查询一致

- **执行**：跑第 4 节冻结的 20 条（10 指标 / 5 SPARQL / 5 问答），两端各取响应，按第 3 节规范化后算 SHA-256，逐条比对。
- **期望**：20/20 两端 SHA-256 相等。
- **判定**：`不等条数 = 0` 通过；任一端 4xx/5xx 计「不可比」，不得记为通过。问答条目若因新栈未接 LLM 而 5xx，单列「能力缺失」并计入不通过。
- **备注**：原始判据未定义「规范化」，本文冻结规则见 §3.4。

### T7 溯源一致

- **执行**：
  1. 老栈 `GET /facts` 取 fact 全集；若为空（当前实测 `count=0`），改从 `platform.prov_event` 取 `activity_id` 全集作为 decision/activity 抽样池。
  2. 固定种子 `20261110` 抽 20 个 `activity_id`；两端 `GET /prov/activities/{id}` 取链条。
  3. 对比：链条可解析性、活动条数、`actor` / `actor_kind` 端点归属。
- **期望**：20/20 可解析；活动数相同；端点归属相同。
- **判定**：`不可解析条数 = 0` 且 `活动数不同 = 0` 且 `归属不同 = 0`。
- **备注**：老库 `platform.fact_assertion` 实测 0 行，`/facts` 返回 `count=0`；「fact 链」无样本，按 decision/activity 链执行，并把「fact 链缺失」单列为数据缺口。

### T8 指标行 100% 有命名空间归属

- **执行**：
  1. 读老表 85 行 `metric_id` / `definition` / `unit` / `domain`。
  2. 由本线产出映射表（拍板口径：不依赖外部）：按 `definition` 规范化全等匹配，其次相似度 ≥ 0.90；0.70–0.89 记「需产品判定」；< 0.70 记「无归属」，**不硬凑目标**。表落 `doc/coa-x/23-附录-旧指标命名空间映射表.md`。
  3. ① 未命中 = 映射表里判「无归属/需产品判定」的行数；② 悬空 = 目标 namespace 不存在或目标指标在新栈查不到；③ 固定抽样 20 条映射调 `GET /namespaces/{ns}/metrics/{name}`。
- **期望**：① 未命中 = 0；② 悬空 = 0；③ 不可读 = 0。
- **判定**：三项任一非 0 即不通过。三项全 0 才判「对上」。
- **备注**：`17` §4.1 的硬前置已由本线自产满足；映射表推导规则与逐条结论见附录。

## 3. 口径落地（已拍板）

1. **「随机」= 固定种子可复现**：种子 `20261110`，对候选 ID 排序后按 `sha256(seed + id)` 升序取样。避免每轮抽样不同导致结论不可复核。
2. **T4 双步**：T4a 本轮只做「等价作用域比」（可比性前提先写、后给数）；T4b 全量比对等专用图实例，本轮不做、只登记。推理图差异单列，不偷偷折算。
3. **T5 的 610**：按已发布版本**条数**理解，不是版本 ID；比整组 `contentHash` 集合。
4. **T6 规范化**：对每端响应做 `json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",",":"))`；剔除易变字段 `requestId`、`latencyMs`、`elapsedMs`、`createdAt`、`updatedAt`，其余保留。问答只保留稳定字段（`answerable`、排序后的 `citations` 的 `documentId`/`chunkId`、`metricIds`），**不哈希自然语言 answer**（LLM 输出非确定，哈希必然不等；原判据未覆盖这一点）。
   - **指标 label 口径（拍板）**：`label` 剥离展示后缀（`〔行业〕` / `〔推测〕`）后相等即算「同一指标」，因为同一性由 `definition/unit/domain` 决定（实测 10/10 相等）。**语义投影那一栏仍按原样保留 4/10，不改数**；差异逐条列在 §7.1.1，不悄悄消掉。
5. **T7 的 fact/decision**：fact 链无样本时用 `prov_event` 的 activity 链，不把「fact 为空」当成通过。
6. **T8 的映射表**：由本线自产（definition 语义匹配 + 逐条结论），不再等外部；匹配不上明确标「无归属」。
7. **T3 取证层**：契约侧补 `DownloadDocument`（登记为第 33 个 op），本轮用存储层字节算 SHA-256；缺 op 不再判「永久阻塞」。

### 11.1 修法

### 11.3 闸门位置与错误码口径（补记）

**位置**：`dispatch()` 内，`_match()` 返回模板之后、`KERNEL` 分支与 `_load_handler()` 之前（`coa_api_local.py` 行 1938–1955）。即：路由匹配 → **本闸门** → handler 执行。

**在鉴权之前还是之后**：

- **本地桥（8699）**：鉴权这一步根本不存在。AWS 上的 API Gateway Lambda authorizer（`packages/control-plane/src/coa_control_plane/authorization/handler.py`）在本地被绕过，桥直接往 `requestContext.authorizer` 注入 `platform-admin`。所以本地没有「未认证」状态，任何请求都是管理员；非法 namespaceId 一律先得到 400，不会出现 401。实测：不带 `Authorization` 头调 `GET /namespaces/{UUID}/metrics` 仍 200。
- **AWS 部署**：网关 authorizer 先于集成执行，本闸门在 Lambda 内，因此顺序是 **401（身份）先于 400（参数）**。这是正确的优先级——未认证请求不应先被告知「参数格式错了」。本地无法验证该顺序，只能按代码位置说明。

**错误码改名**：`INVALID_NAMESPACE_ID` → **`E_NAMESPACE_ID_INVALID`**（HTTP 400）。`error` 字段保持扁平字符串形态，与错误码线「`error` 是 `E_` 前缀码」的规则一致；`message` 保留人读描述。实测三条代表性路由（metrics / documents / sparql-POST）均返回 `{"error":"E_NAMESPACE_ID_INVALID",...}` + 400。

> 说明：桥内本地基建端点（`/local/seed-catalog`、`/_local/objects/*`）仍是旧式字符串码（如 `namespaceId is required`），它们不在 Smithy 契约内，本轮未改，留给错误码线一并收口。

**合并时必查：两个闸门的顺序**

鉴权线已把鉴权改成默认 `enforce`（尚未合并，本分支看不到）。合入后 `dispatch()` 内会有两个闸门：**鉴权闸门**与**本 UUID 闸门**。顺序要求固定为 **先鉴权（401）、后 UUID（400）**。若 UUID 校验跑在鉴权之前，一个未认证请求传错 namespaceId 会拿到 400，把「认证问题」伪装成「参数问题」，客户端会去修参数而不是重新登录。

- [ ] 合并时确认 `dispatch()` 中鉴权闸门在 UUID 闸门之前（实测：未认证 + 错 namespaceId 必须 401，而不是 400）。

## 12. D-T8-4 分页缺陷（单独立项）

## 13. D-T8-4 两处修复：`/answer/quality` 与 `/facts`

### 13.1 原来的 `limit=10` 到底限住了什么

`limit` **不只是分页参数，它是评估范围**：实现是 `golden[:limit]`，`summary.cases` / `passRate` / `citationCoverageRate` 全部以截取后的 `cases` 为分母。也就是说，`limit` 小一点，质量分就只在子集上算。

**现在（黄金集 10 条）有没有算错**：没有。黄金集恰好 10 条，默认 10、上限 10，每次跑都是全量 10/10，历史结论的分母就是全体。

**但这不是设计安全，是数字巧合**：上限 10 与条数 10 重叠。一旦黄金集加第 11 条，默认值和硬上限都会只跑前 10 条，`passRate` 变成 10 条子集的结果；虽然 `goldenSet.count=11`、`evaluated=10` 已经存在响应里，但没有 `truncated` 标志，看板上只盯 `passRate` 的人不会注意到分母变了。

**历史数据影响范围（已实测）**：`platform.answer_quality_run` 在**老栈 5432 和新栈 5944 都是 0 行**（`SELECT count(*), min(evaluated), max(evaluated)` 均为 `0 | NULL | NULL`）。所以「已经有历史质量分是拿子集算的」在本环境**不成立，没有需要重算或下架的历史结论**。

机制上的问题仍然存在：历史行只存 `golden_set='r02-golden-10'` 字符串，不存 `totalCount`。只要有环境跑过（`evaluated` 最多只可能是 10），黄金集扩容后就无法用 SQL 区分某次 run 是全量还是子集。从本次起 `detail` JSON 额外写入 `evaluatedCount` / `totalCount` / `truncated` / `goldenSet`；扩容后新旧 run 的 `passRate` 不可直接比，必须先对齐分母。

### 13.2 `/answer/quality` 修法

- `limit` 默认 **200**、上限 **200**（原默认 10、上限 10）。
- 响应新增（顶层）：`evaluatedCount`（本次实际评估条数）、`totalCount`（本次可评估的黄金集条数）、`truncated`（`evaluatedCount < totalCount`）；`goldenSet` 内新增 `available`，保留原有 `count` / `evaluated`，便于旧调用方继续读。
- 落库 `platform.answer_quality_run.detail` 同步写入这四个字段。
- 未改 `.smithy`：该路由是 kernel 路由，不在 COA 契约模型内。

### 13.3 `/facts` 修法：选 `totalCount` + `truncated`，不选 `nextToken`

理由：

1. `FactLedger.list()` 已有一套过滤 SQL（state/subject/predicate/sourceDocumentId），`COUNT(*)` 复用同一 `WHERE`，总数与页内结果不会漂移；游标方案要自己维护 offset 编码与排序稳定性。
2. facts 是有限审核面（`maxLimit=500`），调用方的真实需求是「还有没有」，不是无限翻页。
3. 改动面最小，且 `count` 语义保持「当页条数」不变，不破坏既有调用方。

返回变为：`{state, items, count, totalCount, truncated, conflicts}`。`truncated = totalCount > 本页 SQL 行数`。

**已知边界**：`conflict=true` 是在分页之后做的二次过滤，`truncated` 只表示「SQL 过滤后还有更多行」，不表示「还有更多冲突组」；要看冲突组用 `/facts/conflicts`（该接口本来就返回全量分组）。

### 13.4 实测

| 调用 | 结果 |
| --- | --- |
| `GET …/facts?limit=1`（库内 2 条） | `count=1`、`totalCount=2`、`truncated=true` |
| `GET …/facts?limit=100` | `count=2`、`totalCount=2`、`truncated=false` |
| `GET /answer/quality`（黄金集 10 条） | `evaluatedCount=10`、`totalCount=10`、`truncated=false` |
| 临时把黄金集扩到 15 条后 `GET /answer/quality` | `evaluatedCount=15`、`totalCount=15`、`truncated=false`（不再被 10 卡住） |

## 14. D-T5-3 排查：为什么同一栈里「版本 15 / 提案 15」与「提案 0」同时成立

> 触发：B0 重生成时看到 `/ontology/versions` 显示「版本 (15) / 提案 (15)」，而 `platform.ontology_proposal` 0 行、`/ontology/proposals/?namespace=<ns>` 返回空。
> 本轮**只读排查**：不改代码、不写库；所有 SQL 均为 `SELECT`，所有 HTTP 均为 `GET`。

### 14.1 四问结论（速览）

| # | 问题 | 结论 |
| --- | --- | --- |
| ① | 两个接口各自读哪个库 | `/ontology/versions` 与 legacy `/ontology/proposals` 是 **kernel** 路由（`platform_core/api.py:3031`、`:3086`），都走 `runtime.ontology` → `list_versions` / `list_proposals`（`adapters/ontology_pg.py:4304`、`:2830`），SQL 写死 `FROM platform.ontology_version` / `FROM platform.ontology_proposal`，**库由 `PLATFORM__DATABASE__URL` 决定**；M3 栈该值是 **`serve_local`**。COA 契约 `/ontology/proposals/?namespace=` 是 **ontology-engine** 路由（`coa_ontology/proposals.py:1028` → `:1070`），读 `dynamo_store.list_proposals_newest_page`（`dynamo_store.py:1450`）→ **DynamoDB 单表**（`DYNAMODB_TABLE=coa-local-ontologies`），**仓内没有任何 PG 提案读实现**。B0 查的 `platform.ontology_proposal` 是**第三个位置**（`COA_METADATA_PG_DSN` 指向的 `platform` 库） |
| ② | 为什么会分叉 | **不是单纯「数据没迁」，是代码路径 + DSN 双分叉**，再叠加第三个库。同一栈内三套存储指针：kernel 用 `PLATFORM__DATABASE__URL`（serve_local）、COA 元数据用 `COA_METADATA_PG_DSN`（platform）、engine 提案用 Dynamo。同一个「提案」概念有两条 handler、三个存储；「数据没迁」只是其中一条（platform 库）的后果，另两条分别是「读错存储」和「夹具冒充业务数据」 |
| ③ | 按契约和数据接管，哪个才算对 | **契约形态**：namespace 作用域 + `maxResults`/`nextToken` 的 `ListProposals`（engine `proposals.py:1028`）是目标；kernel 的单租户 `/ontology/versions` 是兼容层，不是目标。**但当前实现侧还没有「对的存储」**：engine 只实现了 Dynamo，PG 侧没有提案读路径；kernel 的 PG 表又没有 namespace/ontology 归属列。所以今天不存在「哪一边已经对了」，只有「目标形态已定、存储与归属未定」。T5 判据只判已发布版本 contentHash + 发布历史条数、**不含提案**，故 D-T5-3 是 **T5 的执行前提缺口**，不是判据本身；也**不是 T4b**（T4b 是图语句全量比对） |
| ④ | 要改哪边 | 三边都要改，但都不在本轮：**数据侧**迁老栈 1,908 版本 + 1,313 提案（不是搬 15 条夹具），并给出 namespace/ontology 归属映射；**实现侧**二选一并写死——engine 补 PG 提案实现，或明确 Dynamo 为唯一事实源并把它纳入本地可起栈与迁移清单；**起栈侧**禁止 kernel 与 COA 指向两个库而文档不说，或直接收敛为一库。详见 §14.4 |

### 14.3 分叉链条：15、0、空 是三个独立缺口

1. **15 条不是业务数据**：`serve_local` 的 15 个版本与 15 条提案是 2026-11-09 chain smoke 夹具，`version_id` 一一对应，状态含 superseded/draft/approved/published/proposed 的混合，`ont-7c6971e77b7d` 一个版本占 6 条提案。
2. **`platform.ontology_proposal` 0 行不是「没有提案」，是「没迁」**：老栈同表 1,313 行；新 `platform` 库版本表同样是 0，说明整块本体历史都没进 `platform`。
3. **engine 返回空不是「没有提案」，是「读的不是 PG」**：`proposals.py` 只调 Dynamo；就算 PG 里有 1,313 条，这条路由也永远看不到。M3 栈没有配 Dynamo endpoint（`printenv` 无 `AWS_ENDPOINT`/`DYNAMODB_ENDPOINT`），表名 `coa-local-ontologies`，因此「本地空表」既可能是真空表，也可能是环境未接；两种情况下它都不等于 `platform` 库。

三者不能互相折算：修好任何一个，另外两个仍然让结论为假。

### 14.4 数据接管的正确设计与改动边界

1. **迁的是老栈 1,313 条提案，不是 15 条夹具**。版本 1,908（其中已发布 610，T5 的判据对象）与提案 1,313 必须同批迁移：`ontology_proposal.version_id` 对 `ontology_version` 有外键，先版本后提案，且 `version_id` 与 `content_hash` 必须原样保留，否则 T5 直接失效。
2. **归属列是硬缺口**：实测老栈 `platform.ontology_version` 与 `platform.ontology_proposal` **都没有** `namespace` / `ontology_id` 列（提案只有 `version_id` 外键）；新栈 `serve_local` 的同名表**也没有** `ontology_id` 列。也就是说，今天无论迁到哪个库，都不能从现有列推出「这条提案属于哪个命名空间/本体」。归属必须由迁移映射表显式给出——这与 D-T1-2（文档 ID 体系不兼容）是同一类前置：接管前先定映射规则。这也是 D-T5-2「版本接口不按 ontologyId 隔离」的根因：桥把 `ontologyId` 丢掉后转全局路由（`coa_api_local.py:1169-1170`），PG 侧也确实没有可过滤的列。
3. **实现侧二选一，不能继续三套并存**：
   - A. **PG 为唯一事实源**：给 engine 补 PG 提案存储实现（`ListProposals` 的 PG 版），Dynamo 仅作历史兼容；
   - B. **Dynamo 为唯一事实源**：把 Dynamo 纳入本地可起栈（本地 endpoint + 建表 + 种子），并把提案列入数据接管清单；PG 侧提案表只保留 kernel 兼容读。
   今天的状态是「A 没做、B 也没做」，所以两边都读不到对方的写。
4. **起栈侧写清 surface→库**：`PLATFORM__DATABASE__URL=serve_local` 与 `COA_METADATA_PG_DSN=platform` 同时存在，是本次「同栈不同库」的直接来源；起栈文档必须逐 surface 标注库名，或收敛为一库。
5. **T5 判据不动，但缺口要写死**：T5 原文只判「已发布 610 的 contentHash + 发布历史条数」，提案不在内。建议后续在 T5 增一条「提案条数与老栈 1,313 对账」，或显式写 `proposals: out of scope`；本轮按「T5 执行前提缺口」登记，不改判据、不折算 T5 结论。

# 17 M3a 出口盘点（M3b 待本地化合并清单）

> 日期：2026-11-10
> 范围：只读核对 `00-总计划.md`、`07-研发台账.md`、`09-platform整合评估.md`、`12-剩余51条批量排期.md` 及本轮实测证据；不改功能代码、不建 PR。
> 本文回答两件事：① 两张 M3b 待本地化表合并后到底有多少项、多少人日，M3a 出口闸门是否触发 M3b 拆分；② 143 条功能点在 P4 合入后应记成多少。

## 0. 结论摘要

### 0.1 M3a 整体：**不能出**

M3a 的定义是「143 功能点全落位 + `platform-core` 目录删除 + C1–C9 全绿」（`11-复盘与规划.md` 决策 2）。本轮只读核对结果：

| M3a 条件 | 当前状态 | 是否满足 |
|---|---|---|
| 143 功能点全落位 | 主线账面 `135 已落 / 3 部分 / 5 未落`（P4 后半 / P5 / P7 / P9 合并后实测；原 `117 / 3 / 23`，P4 合入时按本文口径曾记为 `117 / 12 / 14`） | **否** |
| `platform-core` 目录删除 | `Test-Path packages/platform-core` = `True`，目录下 29 个条目 | **否** |
| C1–C9 全绿 | 本轮未逐条复核；在 143 与目录删除两项已不满足的情况下，不构成 M3a 可出的理由 | **未验证** |

**M3a 今天不能出。** 卡点不是 M3b 盘点超阈值：未落已从 14 条（严格口径 23 条）降到 **5 条**，但剩下的是 F72–F74（缺 `RunSparql`）与 F17/F18（P8 未开），`platform-core` 目录还在、C1–C9 未复核。条数减少不改变出口结论。M3b 盘点只是 M3a 出口前的必做项，不是唯一项。

### 0.2 M3b 盘点闸门：按正式两表口径**通过**，不触发拆分

`00-总计划.md` §5.2 的硬约束是：以 `07-研发台账.md` §4.7 的「AWS 依赖未本地化」+「产品有、本地未接的能力」两张表合并计数，超过 **10 项或 20 人日（先到为准）** 就拆 M3b-1 / M3b-2。

按这个正式口径合并去重后：

- **项数 4 项**（其中「推理引擎」已由 P3 收口，剩余接口占位 0.5–1 人日）；
- **人日 6.5–11 人日**（估算，依据见 §2）；
- 4 < 10，6.5–11 < 20 → **不触发 M3b-1 / M3b-2 拆分**。

### 0.3 但这个口径不完整：全量 M3b 实际超过阈值

`§4.7` 两张表只覆盖了 M2 实测中已经暴露出来的缺口，并不等于 M3b 全部。`07-研发台账.md` §7「未解决阻塞项」里的 **B1、B8、B9、B10、B15** 都直接挡 8080 退役或数据接管，且不在两张表内。把这几项纳入后：

- 项数至少 **10 项**；
- 人日至少 **30 人日以上**（包级粗估，不是可承诺的精确值）；
- **超过 10 项 / 20 人日，必须拆 M3b-1 / M3b-2**。

因此本文给两套数：**正式两表口径 = 4 项 / 6.5–11 人日**；**全量口径 = ≥10 项 / >30 人日**。M3a 出口文档应同时登记这两套数，不能只拿前者证明「M3b 很小」。

### 0.4 143 重核：P4 只算「后端半边」，新计数 `117 / 12 / 14`

- 用户给的旧计数 `112 / 3 / 28` 是 P10/P11 并行线自己的基数（106 + 6），不是主线终态；主线合并后是 `117 / 3 / 23`，差额 5 条正是主线 P3 的 C 组 +5。
- P4 合并的是**字典/术语存储**，不是 F58–F66 的完整功能链：契约里没有 `ListTerms` / `ListDictionaries` / `GetDictionary` / `RefreshDictionaries` / `GetDictionaryView` / `GetDictionaryCommentCoverage` 六个 op，`web-app` 里没有术语/字典页面或 hook，两张字典表当前都是 0 行。
- 按台账口径，P4 只能把 F58–F66 记成**部分落位（后端半边）**，不能记已落。新计数：**117 已落 / 12 部分 / 14 未落**（=143）。
- 若按用户旧基数对齐，则为 **112 / 12 / 19**（=143）。
- 不采用 `126 / 3 / 14`：那是把 P4 当全链落地，和契约、页面、数据三项证据都不符。
- **2026-11-10 更新**：P4 后半（`51e3a3a7` / `7c4edebe`）、P5（`0a388cf6`）、P7（`a7be6714`）、P9 相继合入主线后，6 个字典/术语 op、2 个指标卡 op、`CheckAnswerable` 与两处页面均已实测，计数改为 **135 / 3 / 5**（18 条转已落：F58–F66 9、F54–F57 4、F76/F79 2、F113/F115/F117 3）。上文的 `117 / 12 / 14` 只对 P4 首次合并（仅存储）有效，不再作为当前口径。

### 3.2 M3a 出口结论

- **M3b 盘点闸门：通过。** 两表合并 4 项 / 6.5–11 人日，未到 10 项或 20 人日；按 `00-总计划.md` §5.2 不需要拆 M3b-1 / M3b-2。

**全量口径合计（B1、B8、B9、B10、B15 + 正式两表 4 项 + 旧指标映射前置 1 项）：至少 10 项，包级粗估 30 人日以上。** 这已经超过 10 项 / 20 人日阈值。

### 3.4 为什么两表会少算

- M2 的验收范围是「已通路由 + 已暴露缺口」，不是「所有 AWS 站点」。B1 里的 control-plane 77 处、sources 140 处属于阶段 3/4/7 的搬迁量，M2 没跑到，所以没进 §4.7。
- `platform-core` 目录删除的判据是 `grep -rn "platform_core"` = 0，而 B1/B8 的包仍在请求期引用 AWS；只清 §4.7 两项，`platform-core` 仍然删不掉。
- 因此，**正式两表口径只能证明「M2 暴露的缺口不大」，不能证明「M3b 总量不大」。**

### 3.5 M3b-1 / M3b-2 拆分建议（按全量口径，推荐直接采用）

虽然正式两表口径不触发拆分，但全量口径已超阈值，建议在 M3a 出口文档里直接预置拆分，避免 M3b 开工时再吵一次口径。

|---|---|---|---|

## 4. 挡的是哪个 M3b 目标（T1–T8 映射）

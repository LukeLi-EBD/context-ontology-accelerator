## 0. 目标、范围与优先级约束

### 0.1 复述目标

把 COA 从「平台 API 的另一个前端」变成唯一入口：单一契约入口、数据接管（T1–T8 对上）、本地一条命令可复现、143 条功能点逐条有运行证据。

### 0.2 本轮新增的最高优先级约束（硬约束，不倒挂）

**P0 功能闭环 → P1 后台自动解析与批量导入 → P2 性能（只做基线、明显阻塞项、低成本） → P3 鉴权（只做最小预留、方案占位、风险登记）。**

落地为四条执行规则：

| 规则 | 含义 | 违反示例（本轮禁止） |
|---|---|---|
| R1 顺序不倒挂 | 批次、资源分配、验收顺序都按 P0→P1→P2→P3 | 先做 14 天双跑再修页面空白 |
| R2 每个任务答得出「服务哪个 P」 | C 表每个任务的「目标」列以「服务 Px：」开头 | 「顺手重构」「统一风格」这类无 P 归属的任务 |
| R3 P2/P3 不得挤占 P0/P1 | P2/P3 只允许在 P0/P1 资源空闲时填充，且不得推迟 P0/P1 出口 | 为做性能基线推迟提案页修复 |
| R4 例外必须升级并说明 | 涉及可用性事故、敏感数据、外网上线门禁的，即使原属 P2/P3 也要升级为阻塞项 | 把「一次慢查询打挂全栈」记成性能优化排到 P2 |

### 0.5 四条定级裁定（本轮最需要拍板的部分）

#### 裁定 1：交付质量（主线没收到收益、没 tag）→ **P0**

- **判定**：落 P0，作为 P0 的前置，不是 P0 之外的「管理事项」。
- **理由（三条，都可验）**：
  1. P0 的定义是「可演示、可验收」。验收必须回答「演示的是哪个版本」；`d840e2b5` 无 tag、主线未收到合并，这个问题现在答不出来。**没有可解析的基线 = 无法验收**。
  2. 生成物停在 152 op，模型 154 op。历史事故已证明后果：生成客户端缺 command 时页面直接起不来（`Unsupported export 'RunSparqlCommand'`，07 号 §1.4）。F72–F74 三条正是 RunSparql 页面 —— **生成物不追平，P0 的三个页面客观上无法验收**。
  3. 它不产生新功能，但它是 P0 其余 13 个任务的共同前置；放在 P0 之外会导致「P0 完成」这个结论在评审时无法成立。
- **反方意见与驳回**：「合并是流程工作，不算功能」——驳回。判据不是工作性质，而是**是否阻塞 P0 出口**；它阻塞，所以是 P0。
- **边界**：只做「合并 + 定版 + tag + 台账再基线」，不做分支历史整理、不做 commit 规整（那是无 P 归属的伪任务）。

#### 裁定 2：性能（Oxigraph 超时不终止）→ **升级为 P0 阻塞缺陷**，但只做最小集

- **判定**：`10s 超时只返回 504、不终止查询`、`canvas`/`path`/`带 kind 搜索`无防护 → **P0**。其余性能工作（基线测量、排序索引、压测、调优）→ **P2**。
- **依据（为什么不是 P2）**：
  1. 后果不是「慢」，是「不可用」：实测 1100% CPU / 4.3GB，进程不回收，**必须重启容器才能恢复**（登记：23 号与 13 号评审）。
  2. 它直接击穿 P0 的「可演示」：演示中任意一次慢查询会让后续所有页面超时，演示不可恢复。P0 判据里「页面能打开」在这种状态下不成立。
  3. 它挡住 P1 的「可重复运行」：导入与对账脚本都会打图查询，一次打挂就让整批导入中断且不可续跑。
  4. 符合 R4：可用性事故不因归类为「性能」而降级。
- **切分线（关键，避免借升级之名做重度性能专项）**：

| 归 P0（阻塞） | 归 P2（可延后） |
|---|---|
| 查询可取消 + 服务端终止（P0-12） | 延迟基线测量与报表（P2-01） |
| 全局并发上限 + 行数/超时上限 + 504/413（P0-13） | `/graph/statements` 稳定排序与索引优化（P2-02） |
| `canvas`/`path`/`kind` 三路由同等级防护（P0-13） | 5 万 quad 上限提升、批量写入吞吐、缓存（不做） |
| 事故后可恢复性验证（10 次慢查询后无需重启） | 全链路压测、容量规划（不做） |

- **验收口径**：连续 10 次慢查询后 CPU < 50%、RSS < 2GB、**无需重启**，且三路由超限返回 504/413。做不到这条就不算 P0 出口。

#### 裁定 3：鉴权 → **既有资产不计工作量；新增只做最小预留；敏感数据/外网项升级为上线阻塞**

- **既有事实（不计入 P3 工作量，也不当成本轮成果）**：已合入的 37 条生产鉴权映射与闸门顺序（无 token → 401、非法 UUID → 400、有 token 合法 → 200、有 token 非法 → 403）属于已发生的工作。本轮**不重复实现、不重新设计**，只在 G.3 记为「既有资产 + 待复验」。
- **新增鉴权工作只允许三类**：新 op 的鉴权占位（P3-01）、未映射路由默认短路 Deny 的核查（P3-02）、风险登记册与上线门禁清单（P3-03，含 P3-04 只读取证）。
- **例外升级（不因叫 P3 就压着）**：凡涉及敏感数据、外网暴露、上线门禁的，在 G.3 单独登记并标注「阻塞上线」；其中「跨命名空间越权」与「未映射路由默认放行」两条，若 A-06 失效则**同步升级为 P0 阻塞**。
- **一个反向调整**：合并后的鉴权冒烟 4 用例（P0-14）定 **P0**。理由：它不是新增鉴权能力，而是 P0 演示的回归前置 —— 闸门顺序一旦回归，所有页面 401/403，P0 直接不可演示。把「验证既有闸门」误判为 P3 会得出「鉴权阻塞 P0 却排在最后」的荒谬结论。

#### 裁定 4：数据线拆开定级

| 事项 | 定级 | 理由 |
|---|---|---|
| 提案页最小读路径（存储不可用返回 200 `{"proposals":[]}`、页面空白） | **P0-10** | 页面可见缺陷：用户看到的是「没有提案」而不是「后端坏了」。P0 判据是「功能闭环、可演示」，一个必然空白的页签不算闭环；且它是 P1 导入的读侧对账前提（不修就无法判断迁移后是 0 条还是读不到） |
| 1,908 版本 / 1,313 提案 / 10,134 事件迁移 | **P1**（拆为 P1-04 管线、P1-05 演练、P1-06 三表、P1-09 现网） | 归 P1 的「批量导入」口径：要求可重复运行、失败可恢复、有日志、有结果校验。它不阻塞 P0 演示（演示用克隆数据即可），但阻塞 8080 退役 |
| 现网执行 V50/V51 | **P1 尾**，不是 P2 | 它属于「批量导入」而不是「性能」；但必须排在 P0 出口之后，且以克隆演练（P1-05/06）为前置 |

> 一句话：**页面读不出来 = P0；数据搬不过去 = P1；搬得慢 = P2；谁能搬 = P3。**

### A.2 根因（区分直接原因与根因）

**直接原因**

1. 并行线以「分支绿」为完成标准，没有「主线可复现」这一出口定义。
2. 生成物被当构建副产物而非版本资产；B0 在已合并分支上留 29 个未提交文件，契约真相放在一个人的工作区里。
3. 数据迁移排在功能之后且未先冻结源端，测量基线一直在动。
4. 契约只做静态校验（shape/挂载），没有「模型 op = 生成命令 = 桥路由 = 页面调用」的运行时一致性门禁。
5. 台账诚实但手工，两套计数口径（135/3/5 与 117/12/14）长期并存。

**根因**

| 维度 | 根因 | 证据 |
|---|---|---|
| 技术 | 桥作为第二 API 面长期存在，读写路径不对称 | 45 条功能点无契约；5 孤儿 op 四视角四答案 |
| 架构 | 三处存储分叉未收敛，读写各指不同库 | kernel 读 `serve_local`、元数据读 `platform`、提案读 Dynamo |
| 质量 | 没有「可复现」的机器判据，只有「已落位」的人工记账 | 07 §4.8 自认可复现 0 条；测试 83/82 |

### D.2 串行判定的四项举证

> 六条串行链，每条四项齐全：冲突证据 / 为什么无法隔离 / 最小串行集与耗时 / 并行替代方案。

**S1：P0-01 → P0-02 → P0-03（合并与定版，P0）**

- 冲突证据：P0-02 改 `platform_core/api.py`，而 P0-01 刚把 integ 的 `api.py` 合入；P0-03 输出整棵 `smithy-generated/**`；P0-06 的采纳提交也可能改同一个 `coa_api_local.py`。
- 为什么无法隔离：生成物是全局单树，所有前端与服务共用；合并是分支图上的单点，不存在「两个主线」；桥注册表是单文件。
- 最小串行集与耗时：P0-01（1.0）+ P0-02（0.5）+ P0-03（1.0）= **2.5 人日**；P0-06 采纳提交另排队 0.5 人日。
- 并行替代方案：P0-04/P0-05/P0-06-triage 在 P0-03 期间并行；但生成、合并、桥注册三者不可并行。

**S2：P0-12 → P0-13 → P0-11（查询安全与分页，P0）**

- 冲突证据：三者都改 `packages/ontology-engine/src/coa_ontology/catalog/routers/graph.py`；P0-11 还改 `stores/neptune_db_graph.py` 的 `list_statements`。p15 已同时改过这组文件，属同热点。
- 为什么无法隔离：超时取消、路由上限、分页排序作用于同一条查询执行链；拆文件也会在 router 注册表汇合。
- 最小串行集与耗时：P0-12（2.0）+ P0-13（1.5）+ P0-11（1.5）= **5.0 人日**。
- 并行替代方案：P0-12 可单独先发；P0-13/P0-11 若要并行，需先把 `graph.py` 拆成 `guards.py` 与 `pagination.py`（额外 0.5 人日且引入注册表冲突），**不划算，故不采用**。

**S3：P1-03 → P1-10 → P1-11（冻结、双跑、停用，P1）**

- 冲突证据：三者都作用于同一 Docker 宿主、同一组 8080 端口与卷；P1-10 的双跑对比依赖 P1-03 的冻结生效。
- 为什么无法隔离：只有一套 8080，没有第二套可并行操作；回滚必须保持单一时间线。
- 最小串行集与耗时：P1-03（1.0）+ P1-10（1.0）+ P1-11（0.5）= **2.5 人日**，另加 14 天日历门槛（非人日）。
- 并行替代方案：只读预检（端口/卷/容器状态）可并行；P2-04 停 8082 可与 P1-03 同日但需排队（同宿主）。

**S4：P0-10 → P1-04 → P1-05 → P1-06 → P1-07 → P1-09（存储与批量导入，P0→P1）**

- 冲突证据：P0-10 与 P1-04 都改提案 reader；P1-04/05/06/07 与 P1-09 共用 V50/V51 迁移号、同一批表、同一份 1,908/1,313/10,134 数据；V51 的触发器依赖 V50 的列；P1-07 的校验对象就是 P1-06 的产物。

- 并行替代方案：克隆实例上的演练（P1-04~06）与 P0 页面线完全并行（资源互斥：克隆库 vs web-app），实际并行窗口成立；只有 P1-09 必须串在演练之后，且必须先备份。

**S5：前端注册（P0-07 / P0-08 / P0-09 的 `App.tsx` 与 i18n）**

- 冲突证据：三条线都要在 `App.tsx` 注册路由、在 i18n index 加 key。
- 为什么无法隔离：注册表是单文件；页面组件本身可隔离。
- 最小串行集与耗时：每批注册 **0.5 人日**（不是整条任务串行）。
- 并行替代方案：页面文件独立开发；注册由一个前端 owner 在批次末一次性做；i18n 用独立 namespace 减少冲突。

**S6：契约挂载（P1-08 / P2-06 的 `use` + `operations`）**

- 冲突证据：每个新 op 都要在 `control-plane.smithy` 的 `use` 与 `operations` 列表各加一行；桥侧还要在 `coa_api_local.py` 路由表加一条。
- 为什么无法隔离：两个注册表都是单文件/单列表，Git 无法按语义合并。
- 最小串行集与耗时：每批一次挂载 + 一次桥注册，合计 **0.5 人日**。
- 并行替代方案：op 定义写独立 `.smithy` 文件，多线并行开发；批次末由契约 owner 一次性挂载、桥 owner 一次性加路由并跑 `validate`。即「代码并行、挂载串行」的最小集。

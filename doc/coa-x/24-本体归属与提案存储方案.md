## 0. 结论摘要

| 项 | 结论 |
| --- | --- |
| 目标库 | **定 `platform`（2026-11-10 拍板）**。前提核查已做：`serve_local` **没有**任何契约要读的独占表；`platform` 是严格超集（71 vs 74 张表，多出 `coa_local_items` / `coa_local_projects` / `coa_ontology_embeddings`；交集 71 张表列定义零漂移）。故这是「选库」不是「并库」，方案无需重写。DSN 切换顺序见 §5.1 |

| 实现侧 | **推荐 A：PG 为提案唯一事实源**（engine 的 `ListProposals`/`GetProposal` 读写 `platform.ontology_proposal`）。判据不是改动量，而是：只有 A 能同时满足「namespace 作用域成立」「分页是稳定 keyset」「提案与版本同库同事务」「本地可复现可对账」四条；B（Dynamo 唯一源）在分页上只是名义成立（现实现全表扫描后切片），且与版本分居两库，T5 仍不可核 |
| 废弃标记 | Dynamo 提案路径降级为「仅 AWS 部署」并在本地栈默认关闭；启动时未显式选择存储则 **fail closed**（`E_ONTOLOGY_STORE_UNCONFIGURED`），读不到数据必须是 503，不能是 `200 {"proposals":[]}`。**上游 AWS 实现不在移除范围**（拍板） |

| T7/PROV | **并行，不是本线前置**。本线的链式证据走 `/ontology/verify`（桥已映射，见 `coa_api_local.py:1286-1287`）；T7 缺的是 fact/decision 的 PROV 读路由，属另一条契约缺口 |
| 两个待修缺陷 | `install_ontology_jobs()` 无调用点、读不到数据返回 `200` 空列表——**只登记，待生成物定版、集成分支稳定后再改**（§5.4） |

- `ontology_id` 则**可以**由 `graph_iri` 推导：后缀 `ont-xxxxxxxxxxxx` 就是血缘根（回滚版本指向同一根），1,908/1,908 命中，无例外。

### 1.4 目标库核查：`serve_local` 没有独占表（2026-11-10 实测）

拍板前要确认的只有一件事：**是否有契约要读的表只存在于 `serve_local`**。逐库对比 `information_schema`：

| 对比项 | `5444/serve_local` | `5444/platform` | 结论 |
| --- | --- | --- | --- |
| 表数量 | 71 | **74** | `platform` 多 3 张 |

### 2.3 回填规则（必须覆盖真实数据）

1. **`ontology_id`（100% 自动）**：`substring(graph_iri from '^urn:platform:graph:tbox:(ont-[0-9a-f]{12})$')`。
   - 覆盖 1,908/1,908；1,645 个去重值；回滚行与父版本同值（实测 0 例外）。
   - 提案表不重复解析 RDF/文件名，直接 `UPDATE … FROM ontology_version`，覆盖 1,313/1,313（FK 保证无孤儿）。
2. **`namespace_id`（不自动）**：按映射文件，键为 `ontology_id`，值为目标 `namespace_id`（UUID v4）。规则匹配顺序固定：
   - 精确 `ontology_id` → 命名空间；
   - `ontology_id` 前缀（如 `ont-7c69*`）→ 命名空间；
   - 未命中 → NULL，不猜、不落到 `demo-ns`、不落到夹具命名空间。
   - 每条命中写 `attribution_source='mapping:<file>#<line>'`；未命中写 `legacy_unmapped`。
3. **提案的 `namespace_id` 不独立回填**：一律取所属版本的 `namespace_id`，避免同一版本下提案与版本分属两个命名空间（V51 触发器兜底）。
4. **事件表不加列**：`ontology_event` 经 `version_id` 关联即可得到 `ontology_id`/`namespace_id`；加列会与版本行产生双写不一致。

### 2.4 无归属旧行怎么处理

采用 V47 已验证过的策略，不发明默认命名空间：

- `namespace_id` 保持 **NULL**，`attribution_source='legacy_unmapped'`；
- 这些行对「命名空间作用域查询」不可见（`WHERE namespace_id = $1` 自然排除），但老的单租户 `/ontology/versions` 仍能读（保持现有功能不破坏）；
- V50 迁移日志输出 `NOTICE 'V50: X of 1908 ontology_version row(s) have no derivable namespace'`，让未归属数量进 log，而不是等人事后发现；
- 后续用映射文件脚本补齐；补齐后再执行 V51 收紧。
- **禁止**把未归属行塞进 `demo-ns` / `ui-smoke-test`：那会让 T5/T8 的「归属完整」变成假绿。

### 2.5 加完之后必须跟着改的查询

只加列不改查询 = 多了两列、串租照旧。清单：

| # | 位置 | 改法 |

## 3. 二、实现侧二选一

### 3.1 判据打分

按用户给的判据（namespace 作用域 + 分页契约同时成立），再叠加数据接管不可回避的三条硬约束：

| 维度 | A：PG 单源（engine 读写 `platform.ontology_proposal`） | B：Dynamo 唯一事实源 |
| --- | --- | --- |
| namespace 作用域 | ✔ 加列 + 复合索引，`WHERE namespace_id=$1` 与授权同源 | ✔ PK 前缀 `{ns}#PROPOSAL#` 天然成立 |
| 分页契约 | ✔ 真 keyset：`(created_at DESC, proposal_id DESC)` + 作用域绑定令牌 | ✘ 名义上有 `nextToken`，实现是「全量拉取后切片」（`dynamo_store.py:1466`）；要成立需重写 Query + SK 排序 |
| 与版本同源 | ✔ 同库同事务，`version_id` FK 保留，发布历史可 join | ✘ 版本在 PG、提案在 Dynamo；「同一发布事件的两半」永远跨存储，T5 仍不可核 |
| 本地可复现 | ✔ PG 已在栈内 | ✘ M3 无 Dynamo endpoint；需引入 DynamoDB Local + 建表 + 种子 |
| 数据迁移 | 1,908 + 1,313 行直接进同构表 | 1,313 行要转成 item JSON，S3/artifact 键需重建 |
| 代码改动 | V50 + 新 adapter（读写 6 条路由）+ 桥透传 | 改 Dynamo 分页实现 + 本地 Dynamo 基建 |
| 对既有功能破坏 | 需保证 kernel 老路由不断（列可空、老查询不加过滤照旧） | 需把版本也搬走，或承认永久双源 |

### 3.2 推荐：A（PG 单源）

**理由（按判据，不按改动量）**：只有 A 让两条契约同时真正成立——namespace 是列与索引的一部分，分页是数据库排序而不是内存切片；且它顺带把「版本/提案/事件」放回一个库，T5 才第一次可核。B 的唯一优势是省掉加列，但它的分页今天并不成立，且会把「版本—提案分居」从缺陷升级为设计，与数据接管目标相反。

**A 的代价，写清楚**：

1. **表要扩语义**：engine 提案比 kernel 列多（`proposal_type`、`source_type`、artifact 键、job 关联、ontology 名称等）。建议新增 `payload jsonb` 承接引擎专有字段，**不逐列爆炸**；kernel 既有 `diff`/`impact` 继续用。
2. **读写路径要重写**：`proposals.py` 的 `list/get/create/update/accept/cancel/reject` 六类调用从 `dynamo_store` 切到新 adapter（`coa_providers` 层，按 `COA_PROVIDER_ONTOLOGY_JOBS` 选择）；校验/推理 **job** 仍在 item store，不迁（job 不是提案）。
3. **artifact 仍不在 PG**：`ontology_turtle`/`r2rml_turtle` 在 S3/fs，列表接口继续剔除（现状已剔除）；PG 只存 `artifact_key`，**不做字节入库**。
4. **键集分页要自己实现**：`nextToken` 需带 `(created_at, proposal_id)` + 作用域签名；这是新代码，不能沿用 `decode_next_token` 之外的黑盒。
5. **不改 `.smithy`**：`ListProposals` 的输入输出已存在，A 是实现补齐，不是契约变更。
6. **双写窗口**：切换期若同时写 PG 与 Dynamo，必须只允许一个读源（PG），否则又制造第四种真相；建议不双写，直接以「停写—迁移—切换」维护窗口完成。

### 3.3 选定后哪边废弃、怎么标记

| --- | --- | --- |

### 4.3 contentHash 怎么核

- **不重算**。`content_hash` 是历史事实，重算会把「迁移」变成「重新发布」；T5 比的是与老栈相同。
- 逐行：`SELECT version_id, content_hash FROM … ORDER BY version_id` 两端各导出，`diff` 必须 0 行（610 已发布 + 其余 1,298 条也一并核，成本相同）。
- 整表：对有序清单取 `sha256`，两端 must equal；同时核 `triple_count` 与 `graph_iri`（只核 hash 会漏掉图指向错误）。
- 图侧不复核字节：`graph_iri` 指向的 Oxigraph 图是否已灌入属 T4 范围，不在本线；本线只保证「指针与图 URI 不漂移」。

### 4.4 T5 判据怎么改才算通过

原判据（记为 **T5-0**，不改写）：「已发布 610 在 `GetOntologyVersion` 的 `contentHash` 与 8080 相同；发布历史条数一致」。

迁移后 T5 按以下四项**同时**通过才判通过：

| # | 判据 | 机械检查 | 通过线 |
| --- | --- | --- | --- |
| T5-a | 版本一致（原判据） | 610 已发布版 `contentHash` 逐条相等；整表 1,908 条 hash 清单差分 | 差异 0 |
| T5-b | 发布历史一致（原判据落地化） | 提案 1,313 与 ontology_event 10,134 的条数、按 `version_id` 分布、按 action 分布两端相等 | 差异 0 |
| T5-c | 归属完整 | `ontology_version`/`ontology_proposal` 的 `ontology_id` 空 0；`namespace_id` 空的数量**单独上报**；契约 `ListProposals?namespace=X` 条数 = `SELECT count(*) WHERE namespace_id=X` | `ontology_id` 空 0、契约条数差 0；`namespace_id` 未归属不得记为通过 |
| T5-d | 分页契约 | `maxResults=100` 翻页累加 = 总数 1,313（按命名空间分别累加）；跨命名空间 `nextToken` 复用返回 400 | 差异 0、越权 0 |

> 原「发布历史条数」过去没有定义载体。本方案把它定义为 **proposal 行 + ontology_event 行** 双证：只数提案会漏掉 imported/superseded 等事件，只数事件会把同一提案的多次状态变更当成多条发布。
> `namespace_id` 未归属是**已知缺口**，在 T5 报告里单列，不折算成通过，也不折算成失败——它取决于映射文件何时给全。

### 4.5 T7 / PROV 定位

- **并行，不是前置**。本线的链式证据是 ontology_event，验证入口是 `/ontology/verify`（kernel，桥 `coa_api_local.py:1286-1287` 已映射）；不依赖 fact/decision 的 PROV 路由。
- T7 缺的是 `/prov/decisions`、`/prov/activities/{id}` 这类读路由（D-T7-1），属另一条契约缺口；它只影响 T7 的「HTTP 可校验性」，不影响本线迁移能否完成。
- 唯一的交汇点：若验收要求「发布历史必须能通过契约读出来核对」，那么本线在 T5-c/T5-b 的契约侧检查会顺带被 T7 的读路由缺口挡住——届时按「先 DB 后契约」两级证据执行，不把 T7 缺口算成本线失败。

### 4.6 回滚

- V50 只加列/索引 + `ontology_id NOT NULL`：回滚 = `DROP COLUMN`（三列）与索引；`ontology_id` 是纯推导值，无外部写入，可安全重建。
- 数据导入用**独立目标库/影子库**（沿用 5944 克隆模式）先行；校验全绿再切读。若坚持原地导入，必须先建迁移台账表记录本次插入的 id 集合，回滚按台账删除，禁止 `TRUNCATE` 共享库。
- 事件表回滚风险最高：`event_id` 与 `hash` 一旦被新序列覆盖就无法复原，因此第 5 步必须显式写 id、插入后立即 `setval`，并在回滚脚本中先校验 `MAX(event_id)` 未超基线。

1. **选的是存活路径**：lifecycle 路由读的是 kernel 的 `PLATFORM__DATABASE__URL`。切到 `platform` 后，同一段前端代码自动读迁后的数据，不需要重写；映射层也只依赖 kernel 响应形状，而 V50 不改这个形状。
2. **会自然退场的是 fallback 分支**：等 engine 按 §3 接了 PG、扁平路由也能返回真实提案，`getProposal` 不再 404，fallback 不触发。届时删掉一个 `catch` 分支即可，成本可忽略；保留也无害（防御性读）。
3. **绑定条件 A（必须一起改）**：`ontologyId` 现在取常量 `fsldm-local`。D-T5-2 修复后，若桥开始按真实 `ontologyId` 过滤，而 kernel 的 `ontology_id` 是 `ont-xxxxxxxxxxxx`，常量会匹配不到、fallback 失效。**修 D-T5-2 时必须把这里的来源换成「namespace → ontologyId」的真实映射**，否则最小修复会过期。
4. **绑定条件 B（迁移范围要改）**：`serve_local` 已不全是夹具——`ont-53fb5cb43f5b` / `prop-32e6cc1834cd` 是今天新建的真实工作数据，老栈没有。切 `platform` 前若按原计划「夹具不迁、随库退役」，这条提案会消失。迁移清单要加「serve_local 真实行」这一类，不能只迁老栈 1,908 + 1,313。

### 6.7 考虑过但没选的更小路径

| 方案 | 为什么不做 |
| --- | --- |
| 把 kernel 那 15 条提案复制进 Dynamo，扁平路由自然能读 | 用户已明确否掉临时双写；而且复制后两份会继续分叉，下一次状态变更又不一致 |
| 桥把 `/namespaces/{ns}/proposals*` 直接改指 kernel | 响应形状不同（`proposalId`/snake_case、无 turtle），页面会拿到 `undefined` 字段；要可用就得在桥里写一层形状适配，等于把「分叉」藏进桥，且切 platform 后这层适配要删——比前端 fallback 更容易白改 |
| engine 的扁平读路径回落到 HTTP 调 kernel | engine 目前零 PG、零 kernel 耦合；加一条跨服务回落会把「谁是事实源」搅得更乱，且延迟/错误语义都变复杂 |
| 先迁数据再修页面 | 迁移是 1,908 + 1,313 + 10,134 规模，且要先做归属列；为了一条今天就能看的提案排这么长的队不合理 |

## 7. 实施边界（不在本轮范围）

- 不写 V50/V51 文件、不改 `MIGRATIONS` 注册表、不改 `SUPPORTED_SCHEMA_VERSION`。
- 不实现 engine 的 PG adapter、不改桥路由透传、不改 `.smithy`。
- 不迁移任何数据，不建映射表，不写 `platform.*`。
- **不改任何 DSN / env / compose**：`PLATFORM__DATABASE__URL` 仍指 `serve_local`，切换在迁移对账之后（§5.1）。
- **不修 D-T5-4 / D-T5-5**：只登记，等生成物定版、集成分支稳定后再动代码（避免与合并/重生成互踩）。
- 不改 T4/T6/T7 的既有结论；D-T5-3 仍按「T5 执行前提缺口」登记。

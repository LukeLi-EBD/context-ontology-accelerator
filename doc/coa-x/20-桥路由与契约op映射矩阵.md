# 桥路由 ↔ 契约 op 映射矩阵

> 口径：以本地桥 `doc/coa-x/tools/coa_api_local.py` 的 `ROUTES`（138 条，**method-agnostic**）为基准，
> 逐条对 `models/src/main/smithy/` 的 150 个 operation。
> 判据：路径模板归一化（`{x}` → `{}`）+ HTTP 方法 + 主要入参名；方法从节点实现取，不从 `ROUTES` 猜。
> 只读结论，本轮不改任何 `.smithy`。

## 1. 表一：有路由、无 op（真正的契约外缺口）

7 条全部是 `ONTOLOGY` provider，即 8101 本体引擎的入口。契约只覆盖了其中一族的一半，另外两族整族缺席。

| # | 路由 | 方法（引擎实现） | 家族 | 契约现状 | 建议补的 op（待核准，本轮不建） |
|---:|---|---|---|---|---|
| 1 | `/namespaces/{namespaceId}/embeddings` | `POST` 201 | 向量 | 只有 `/embeddings/search`、`/embeddings/by-entity/{entityUri}` | `CreateEmbedding` |
| 2 | `/namespaces/{namespaceId}/embeddings/batch` | `POST` 201 | 向量 | 同族缺批写入入口 | `BatchCreateEmbeddings` |
| 3 | `/namespaces/{namespaceId}/embeddings/by-ontology/{ontologyId}` | `GET` 200 | 向量 | 同族缺按本体列举 | `ListOntologyEmbeddings` |
| 4 | `/namespaces/{namespaceId}/induce/datasources` | `GET` 200 | 归纳 | 只有 `/induce/datasources/induced`，缺「可归纳数据源」候选读 | `ListInducibleDatasources` |
| 5 | `/namespaces/{namespaceId}/validate` | `POST` 202 | 校验 | 契约的 `RunValidation` 打的是 KERNEL `/graph/validate`，不是这条 | `StartValidation` |
| 6 | `/namespaces/{namespaceId}/validate/jobs` | `GET` 200 | 校验 | 无对应 op | `ListValidationJobs` |
| 7 | `/namespaces/{namespaceId}/validate/jobs/{jobId}` | `GET` 200 | 校验 | 无对应 op | `GetValidationJob` |

依据：

- 引擎路由定义：`packages/ontology-engine/src/coa_ontology/catalog/routers/embeddings.py:55`（`POST /`）、`:73`（`POST /batch`）、`:136`（`GET /by-ontology/{id}`）；`validation/routers/validate.py:173`（`POST /` 202）、`:198`（`GET /jobs/{jobId}`）、`:230`（`GET /jobs`）。
- 桥的 8101 转发映射逐条存在：`packages/ontology-engine/src/coa_ontology/api_proxy_handler.py:78`（induce/datasources）、`:133-140`（embeddings 三条 + validate 三条）。
- 契约同族已有 op 的落点：`embeddings.smithy`（`SearchEmbeddings`、`GetEntityEmbeddings`）、`ontology-induction.smithy`（`StartInduction`、`ListInducedDatasources`）、`ontology-graph.smithy`（`RunValidation`）。

**结论**：表一是下一轮要补的全部。前 4 条是「同族漏入口」，补起来风险低；第 5–7 条要先回答一个产品问题——引擎的 namespace 校验 job 与内核的 `RunValidation` 是不是同一件事，若是，应当收敛成一条（见 §3）。

## 3. 表三：两边都有但对不上

### 3.1 路径参数名

131 条重合路径逐条比对，**0 条不一致**（`{namespaceId}`、`{sourceId}`、`{tableId}`、`{columnName}`、`{versionId}`、`{proposalId}` 等全部同名）。

### 3.2 同功能、不同路径

| 功能 | 契约 | 桥/实现 | 差异 | 需要谁定 |
|---|---|---|---|---|
| 命名空间 SHACL 校验 | `RunValidation` `POST /namespaces/{id}/graph/validate`（KERNEL） | `POST /namespaces/{id}/validate`（8101 引擎，202 job） | 后端不同：内核同步、引擎异步 job；路径也不同 | 产品/架构：收敛成一条还是两条并存 |
| 文档原始内容 | `DownloadDocument` `GET .../content` | 内核 `GET .../source` | 路径尾段不同，且桥无入口 | 契约先行，等 R2 接线时按 `/content` 实现 |
| 事实冲突批量裁决 | `BatchKeepFactConflicts` `POST .../facts/conflicts/batch` | 内核 `api.py:2792,2866` 注释说明该路由是 `ResolveFactConflicts(action:"batch")` 的别名入口 | 一个实现、两个入口 | 保持现状；契约已把两者都建出来，不构成缺口 |

### 3.3 方法与响应形状

- `ROUTES` 本身不带方法，方法只能从节点实现核对。已核的 131 条里没有出现「同路径两个 op 抢同一方法」：12 组多 op 路径（3 组同路径三 op）全部按 `GET/POST/PUT/PATCH/DELETE` 区分。
- 响应形状本轮**未做**逐条实测对比——需要起栈逐条采样才能落实，属下一轮工作，不在这里假装有结论。

## 4. 台账：5 个「登记过」的 op——结论与前提相反

你给的前提是「登记了、没实现、无入口」。实查结果是：**5 个全部有内核实现**，缺的是桥入口和契约名字。

| op | 登记出处 | 契约 | 桥入口 | 内核实现 |
|---|---|---|---|---|
| `ListOntologyTransitions` | `09-platform整合评估.md:120,373,374,477,582,648`；`07-研发台账.md:416` | 无 | 无 | **有**：`platform_core/api.py:4071,4078`、`adapters/ontology_pg.py:2812` |
| `GetOntologyImport` | `09:294,295,483,588,648`；`07:606` | 无 | 无 | **有**：`platform_core/api.py:3509` |
| `PublishOntologyImport` | `09:296,297,484,589,648`；`07:607` | 无 | 无 | **有**：`platform_core/api.py:3521` |
| `PutOntologyShapes` | `09:298,299,485,590,648`；`07:608` | 无 | 无 | **有**：`platform_core/api.py:3556` |
| `GetOntologyShapes` | `09:300,301,310,486,591,648,666`；`07:609` | 无 | 无 | **有**：`platform_core/api.py:3595`（另有 `/validation/shapes`，3676） |

产品侧早已判过：`07-研发台账.md:602-611` 把这批归为「B 类：无落点，转批 C，不写」，理由是 143 个功能点里没有对应界面，`GetOntologyShapes` 只在发布闸门内部用。

所以准确分类是 **「登记过、有实现、无入口、无契约、无产品功能点」**，不是纸面功能。它比纸面功能更危险的地方在这里：

- 盘点看内核，会认为已经交付；
- 盘点看桥，会认为根本没有；
- 盘点看契约，什么都看不到；
- 盘点看 143 功能点，明确写了不交付。

四个视角四个答案。建议维持「不建 op」的决议，但把这一条写进契约的 out-of-scope 说明（或本文档），否则下一轮还会被当成缺口重新盘一次。

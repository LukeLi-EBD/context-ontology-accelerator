## 0. 目标理解、范围与关键假设

### 0.1 复述：这个项目到底在做什么

把 COA 从「平台 API 的另一个前端」变成「唯一的平台入口」：

1. **单一入口**：对外只有 COA 的 Smithy 契约与 web-app，8080/8082 最终无监听（C1–C9）。
2. **契约先行**：页面上的每个动作都必须有 operation 背书，路由由契约生成，不手写影子接口。
3. **数据接管**：8080 的文档、切片、图、本体版本/提案/事件、指标、PROV 全部迁入 COA，T1–T8 逐条对上后才能退役。
4. **本地可复现**：一条命令起全栈，任何人能在本地复现同一套数据与页面。
5. **功能对等**：143 条原子功能点逐条有落点、有证据，不以「分支绿」代替「主线可复现」。

### 0.2 范围

- 包括：契约/生成物、桥与路由、control-plane、ontology-engine、platform-core 数据层、web-app、数据接管、8080/8082 退役、测试与门禁、并行治理。
- 不包括：AWS 生产部署细节、新功能产品设计、性能调优（项目已明确结束）、趋势图类新增。

## A. 复盘

### A.1 复盘摘要（10 条）

1. **集成质量已达标，交付质量没有**：`d840e2b5` 四道门全过，但主线零收益、无 tag、生成物落后 2 个 op。现在能证明的是「分支可构建」，不是「产品可交付」。
2. **集成并不完整，且不是文档问题**：除 9 笔计划合并外，还有 5 条带 unique 提交的代码分支未合（`git cherry` 判定）。其中 `feat/p10-p11` 的「上传文档镜像到 KBSearch 读取的库」关系文档可用性，可能影响 T1/T2 的复跑解释；`feat/canvas-full` 的查询形状防护可能包含 SPARQL 防护的现成经验。
3. **契约第一次真正闭环，但闭环的是结构不是产品**：154 op 全挂载、0 DANGER；143 条功能点仍是 135/3/5，其中 45 条靠契约外本地桥。台账在 B0 前时点自认「按审计口径可复现 0 条」。契约是背书，不是运行证据。
4. **数据接管只有 1/8**：T1 文档 3066 vs 9、T2 切片 15218 vs 60、T3 原文 0/50、T4a 本体 ID 交集 0、T5 版本 ID 交集 0、T6 SPARQL/问答不可比、T7 三条 PROV 路由全 404；只有 T8 指标 85/85 对上。8080 仍是唯一完整实例。
5. **8080 还在被并行线写入，分叉每天变大**：T1–T8 实跑期间 `prov_event` 从 609 涨到 615，图量十分钟涨 42。只读冻结现在是「设计在 m3 分支、代码未合、未上线」，每拖一天，T1–T7 的复跑基线都要重采。
6. **存储分叉有明确解，但没有执行**：目标库 `platform` 已拍板（74 表 vs `serve_local` 71 表，交集 71 表零列漂移），V50/V51 方案已出，1,908 版本 / 1,313 提案 / 10,134 事件一条未迁。问题不是选型，是执行未开始。
7. **存在确定的生产可用性事故**：SPARQL 10 秒超时只返回 504、不终止 Oxigraph，实测 1100% CPU / 4.3GB，需重启容器；`canvas`、`path`、带 `kind` 的搜索无同等防护；5 万 quad 是当前上限。这是 P0，不是性能调优。
8. **鉴权从「全裸」到「有闸门」，但只在本地成立**：138 条桥路由原本身份/命名空间校验全无；生产映射覆盖 90 条，48 条本地独有在云上会 `denyAll`，本地仅进程内补。合并后必须重验 4 个顺序用例，不能把「本地能过」当「线上安全」。
9. **质量防线是名义上的**：测试 83 vs 82 差 1 条未命名；38 个 unit 文件只有 1 个进 Nx 图；契约 DANGER 清零靠人工清单而不是持续门禁；分页「读第一页当全量」已被证实是一类缺陷（D-T8-4，7 条列表路由），不是一次误判。
10. **并行治理已经失控**：实际 45 个 worktree（29 已合、16 活跃），比用户口径的 13 条多出 3 条文档线、5 个 detached 审计目录、5 条旧代码线。并行收益已被协调成本吃掉，下一阶段活跃线必须压到 ≤8 条。

### A.3 根因分析

**直接原因**

1. 并行线以「分支绿」为完成标准，没有「主线可复现」这一出口定义。
2. 生成物被当作构建副产物，而不是需要定版的版本资产；B0 在已合并分支上留了 29 个未提交文件，等于把契约真相放在一个人的工作区里。
3. 数据迁移排在功能之后，且没有先冻结源端；测量基线一直在动。
4. 契约只做静态校验（shape/挂载），没有「模型 op = 生成命令 = 桥路由 = 页面调用」的运行时一致性门禁。
5. 台账诚实但手工，数字靠人抄；两套计数口径（135/3/5 与 117/12/14）长期并存。

**根因（按维度）**

| 维度 | 根因 | 证据 |
|---|---|---|
| 技术 | 桥作为第二 API 面长期存在，写路径与读路径不对称 | 45 条功能点无契约；5 个孤儿 op 四视角四答案 |
| 架构 | 三处存储分叉未收敛，读写各指向不同库 | kernel 读 `serve_local`、元数据读 `platform`、提案读 Dynamo |
| 质量 | 没有「可复现」的机器判据，只有「已落位」的人工记账 | 07 §4.8 自认 0 条可复现；测试 83/82 |
| 流程 | 批次没有出口门禁，合并与定版分离 | 9 笔合完但无 tag、生成物落后 |
| 协作 | 45 个 worktree、无 owner 清单、无归档规则 | 16 条活跃，5 条 unique 未合 |
| 资源 | 单 Oxigraph、共享 5444/7878、单人掌握契约 | T4b 无法在共享实例执行；B0 单点 |

### A.4 架构复盘

**模块边界**

- `control-plane` 持有契约与控制面，`platform_db` 放在 control-plane 下（schema 跟域走）是对的；`platform-core` 退化为薄转发层，R1/R2 的方向正确。
- 但 `platform-core` 仍保留 135 个端点、74 张表、`/system-health`，COA 并没有真正「内化平台」，只是「前面加了一层桥」。这是当前最大的架构债。
- `ontology-engine` 同时承担图查询、本体目录、提案/版本、质量运行，边界过宽；PROV 读路由缺失说明「写进去的链」没有对应的「读出来」出口。

**接口契约**

- 三套 service（ControlPlane / DataLayer / Ontology）对外统一 base URL，方向正确；`verifyOperationsMounted` 把「定义了没挂」变成机器错误，是本轮最有价值的机制。
- 契约的缺口不在 shape，而在「四个视角」：模型、生成客户端、桥路由、产品功能点各有一套账。5 个孤儿 op 是典型：内核有实现、桥没入口、契约没定义、产品没功能点，四个视角四个答案。
- 7 条「有路由无 op」全部落在 ontology-engine，说明 engine 的本地入口先于契约长出来，属于契约倒挂。

**数据流**

`web-app → 8099 桥 → control-plane 8101 / engine → PG(platform|serve_local) + Oxigraph + Dynamo(proposal)`。

- 三处存储分叉：版本/元数据在 `platform`，图在 Oxigraph，提案在 Dynamo；目标库 `platform` 是严格超集，方案成立。
- 读写不对称：写走 PG，读有的走 `serve_local`，提案读走 Dynamo；同一功能点的读写在两个库，事务边界不成立。
- 列表路由「第一页当全量」是一类缺陷：`/metrics` 默认 50 条有 `nextToken`，`/facts`、`/answer/quality` 则是静默截断。前端页签少显示、对账少算数量，都会被误判成数据缺失。

**耦合与单点**

- 共享 5444 PG、共享 7878 Oxigraph 被多条并行线同时写，导致 T4b 无法得到「新栈应有量」。
- `smithy-generated/**` 是全局单写树；`control-plane.smithy` 的 `use`/`operations` 列表是全局单写点；`App.tsx`、i18n index、`coa_api_local.py` 是前端/桥的单写热点。
- 单 Oxigraph 实例 + 无查询取消 = 单点故障；8080 是唯一完整数据实例 = 数据单点；B0 工作区 = 契约单点。

**扩展性/可维护性**

- 5 万 quad 上限、同步 SPARQL、无并发闸门，决定了当前只能算「本地演示规模」，不能算「可接管生产」。
- 33 篇文档、两套计数口径、24/26 不在集成分支，维护性已经被文档本身拖累。

### A.6 结论与决策

**保留**

- 契约先行 + `verifyOperationsMounted` 机器门禁。
- 目标库 `platform`（严格超集、零列漂移）。
- 一条命令起栈、独立端口段、克隆库演练。
- 台账「不造数、对不上就写对不上」的诚实口径。
- 集成分支「先合后验、四道门禁」的流程。

**调整**

- 并行活跃线 16 → ≤8；新增 worktree 必须登记 owner 与合并点。
- B0 从「某人的工作区」改为「干净目录 + 单一 owner + tag」。
- 8080 只读冻结从「后续步骤」提前到 P1 首日。
- T7/PROV 从「结构性缺陷」提升为 P1 任务，不再等数据线。
- 台账改为脚本生成核心数字，人工只写判断。

**重构**

- 桥从「第二 API 面」收缩为「契约的瘦适配/纯转发」；45 条契约外路由分 A/B/C 三档处理。
- 提案唯一事实源迁到 PG `platform`，Dynamo 降级为 AWS-only。
- 数据访问统一到 `platform`，`serve_local` 只保留本地夹具用途。

**停止**

- 修 8082 宿主转发（该组件要退役，修它是负收益）。
- 8080 新功能开发（只允许只读与冻结）。
- F86 趋势图（产品已拍板不做，记「产品决策关闭」而不是「未落」）。
- 无产品功能点的孤儿 op 新增；先裁决，再决定保留或删除。
- 用「只编译」「只合分支」「按钮在」记账。

**决策、理由、优先级与验收**

| 决策 | 对象 | 理由 | 优先级 | 验收标准 |
|---|---|---|---|---|
| 保留 | 契约先行 + 挂载门禁 | 唯一能防「定义了没挂」的机器机制 | P0 | 模型 op = 挂载 op = 生成命令 |
| 保留 | `platform` 为目标库 | 74 表严格超集、交集零漂移 | P0 | T5 四项 0 差异 |
| 调整 | 并行活跃线 ≤8 | 45 worktree 已产生协调成本与隐性漏合 | P0 | 活跃清单 ≤8；无未登记 worktree |

### D.2 串行判定的四项举证

**S1：X01 → X02 → X03（合并与定版）**

- 冲突证据：X02 改 `platform_core/api.py`，X01 刚把 integ 的 `api.py` 合入；X03 输出整棵 `smithy-generated/**`；X06 的采纳提交也可能改同一个 `coa_api_local.py`。
- 为什么无法隔离：生成物是全局单树，所有前端/服务共用；合并是分支图上的单点，没有「两个主线」；桥注册表是单文件。
- 最小串行集与耗时：X01（1.0）+ X02（0.5）+ X03（1.0）= 2.5 人日；X06 采纳提交另排队 0.5 人日。
- 并行替代方案：X04/X05/X06-triage 可在 X03 期间并行；但生成、合并、桥注册不能。

**S2：P1-01 → P1-02 → P1-03（图查询安全）**

- 冲突证据：三者都改 `packages/ontology-engine/src/coa_ontology/catalog/routers/graph.py`；P1-03 还改 `stores/neptune_db_graph.py` 的 `list_statements`。p15 已同时改过这组文件，属于同热点。
- 为什么无法隔离：超时取消、路由上限、分页排序作用于同一条查询执行链；拆文件也会在注册表汇合。
- 最小串行集与耗时：P1-01（2.0）+ P1-02（1.5）+ P1-03（1.5）= 5.0 人日。
- 并行替代方案：P1-01 可单独先发；P1-02/P1-03 若要并行，需先把 `graph.py` 拆成 `guards.py` 与 `pagination.py`（额外 0.5 人日，且引入注册表冲突），不划算。

**S3：P1-04 → P1-05（8080/8082 操作）**

- 冲突证据：两者在同一 Docker 宿主、同一组端口与卷；P1-05 停 8082 后若 8080 冻结失败，无法判断是哪个动作导致。
- 为什么无法隔离：只有一个宿主，没有第二套 8080/8082；回滚必须保持单一时间线。
- 最小串行集与耗时：P1-04（1.0）+ P1-05（0.5）= 1.5 人日，同日完成。
- 并行替代方案：可先做只读预检（端口、卷、容器状态）并行，但变更动作不可并行。

**S4：P1-06 → P1-07 → P1-08 → P3-01 → P3-03（存储与数据迁移）**

- 冲突证据：P1-06 与 P1-07 都改提案 reader 与 `ontology_proposal` 表；P1-07/08 与 P3-03 共用 V50/V51 迁移号、同一批表、同一份 1,908/1,313/10,134 数据；V51 的触发器依赖 V50 的列。
- 为什么无法隔离：schema 版本是单值，迁移注册表是单列表；回填与收紧必须按序；fail-closed 必须先于迁移，否则迁移期间读空会被误判成 0 条。
- 最小串行集与耗时：P1-06（1.0）+ P1-07（2.0）+ P1-08（2.0）+ P3-01（1.5）+ P3-03（1.0）= 7.5 人日（P3-02 可并行）。
- 并行替代方案：克隆实例上演练可与代码线并行；现网应用只能串行，且必须先备份。

**S5：契约挂载（P1-09 / P1-10 / P2-06 的 `use`+`operations`）**

- 冲突证据：每个新 op 都要在 `control-plane.smithy` 的 `use` 与 `operations` 列表各加一行；桥侧还要在 `coa_api_local.py` 的路由注册表加一条。三条线同时改必冲突。
- 为什么无法隔离：两个注册表都是单文件/单列表，Git 无法按语义合并。
- 最小串行集与耗时：每批一次挂载 + 一次桥注册，合计 0.5 人日；不是整条任务串行。
- 并行替代方案：op 定义写独立 `.smithy` 文件，三线并行开发；批次末由契约 owner 一次性挂载、由桥 owner 一次性加路由并跑 `validate`。这是「代码并行、挂载串行」的最小集。

**S6：前端注册（P2-01 / P2-02 / P2-03）**

- 冲突证据：三条线都要在 `App.tsx` 注册路由、在 i18n index 加 key。
- 为什么无法隔离：注册表是单文件；页面组件本身可隔离。
- 最小串行集与耗时：每批注册 0.5 人日。
- 并行替代方案：页面文件独立开发，注册由一个前端 owner 在批次末统一做；i18n 用独立 namespace 文件减少冲突。

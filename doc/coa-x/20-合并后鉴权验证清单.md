# 20 合并后鉴权验证清单

> 适用：`feat/authz-close` 合并进主线之后。
> 目的：`dispatch()` 在合并时会被同时改到鉴权闸门（401）与 namespaceId UUID 闸门（400），
> 这里把「合并后的正确顺序」和「必须重跑的验证」固定下来，避免合并当天靠记忆。
> 前置：Docker、`.venv-coa-local`；默认端口 8599（桥）/ 5844（PG），不与共享 8099/5173 冲突。

## 一、合并后的目标顺序

已知冲突块：`coa_api_local.py` 的 2462–2486 与 2490–2494 两段。合并后的 `dispatch()`
必须是：

```python
matched = _match(path)
template, path_params, module = matched
decoded_params = {k: unquote(v) for k, v in path_params.items()}

auth_context, auth_error = _safe_authorize(          # ① 401，产出 actor
    request.method, template, decoded_params, request_headers
)
if auth_error is not None:
    return _cors(auth_error, origin)
actor = auth_context["email"]

bad_namespace_id = _invalid_namespace_id(decoded_params)   # ② 400
if bad_namespace_id is not None:
    return _cors(JSONResponse(..., status_code=400), origin)

if module == KERNEL:                                  # ③ 正常链路
    return _cors(await _kernel_proxy(request, template, decoded_params, actor), origin)
handler = _load_handler(module)
```

冲突解决时守住四条：

1. `_safe_authorize` 必须在 `_invalid_namespace_id` **之前**。顺序反了，
   未认证请求会先拿到 400，等于把 id 合法性变成无需认证的探测面。
2. `actor` 必须来自 `auth_context["email"]`，不能沿用任何 `LOCAL_USER` 常量或 body 字段。
3. `_kernel_proxy` 必须保留 `actor` 参数（4 参版本）；数据接管线的版本没有它，
   合并时以鉴权线为准，否则 KERNEL 写操作会退回默认 operator。
4. `requestContext.authorizer` 必须是真实鉴权 context，不能恢复固定
   `platform-admin` 的注入。

## 二、门禁顺序验证（一条命令）

```powershell
powershell -ExecutionPolicy Bypass -File doc\coa-x\tools\verify-authz-gate-order.ps1
```

脚本自起隔离桥与隔离 PG，铸真实 dev token，跑六个用例（4 个闸门顺序 + 2 个跨命名空间），
结束时停进程与容器。加 `-KeepRunning` 可保留容器排查。

跨命名空间两个用例需要第二个 dev 用户只有 NS_A 的 `namespace-owner`：脚本调用
`seed_namespace_grant.py` 写一条 `ResourceRoleMappings` 行（字段形状与
`POST /namespaces/{namespaceId}/grants` 完全一致），不建命名空间、不建角色行。

| # | 用例 | 期望 | 作用 |
|---|---|---|---|
| 1 | 无 token + 合法 UUID | `401 E_UNAUTHENTICATED` | 防鉴权被绕过 |
| 2 | 无 token + 非法 UUID | `401`，**不是 400** | **判据**：顺序正确性 |
| 3 | 有 token + 非法 UUID | `400 E_NAMESPACE_ID_INVALID` | UUID 闸门仍生效 |
| 4 | 有 token + 合法 UUID | 进入正常链路（非 401/400/503） | 防改坏正常请求 |
| 5 | NS_A owner + NS_A（POST） | 授权放行，进入 handler（非 401/403/503） | 跨命名空间用例的正向对照 |
| 6 | NS_A owner + NS_B（POST） | `403 E_FORBIDDEN`，`action=manageSource` | **判据**：两个都是合法 UUID，拒绝只能来自授权而不是格式校验 |

2026-11-11 在 `integ/merge-20261110`（HEAD `a7f0eec4`）实测 **6/6 PASS**：

| # | 状态 | body（截断） |
|---|---|---|
| 1 | 401 | `{"error":"E_UNAUTHENTICATED","message":"Missing or invalid bearer token",...}` |
| 2 | 401 | 同上（不是 400，顺序正确） |
| 3 | 400 | `{"error":"E_NAMESPACE_ID_INVALID","message":"namespaceId must be a UUID v4; got 'not-a-uuid' ...` |
| 4 | 200 | `{"items": []}` |
| 5 | 400 | `{"error": "Invalid sourceType: Field required"}`（授权已过，业务校验拒绝） |
| 6 | 403 | `{"error":"E_FORBIDDEN","message":"Permission denied for action 'manageSource'.","action":"manageSource"}` |

合并冲突解决后必须原样再跑一次，退出码 0 才算过。

## 三、合并后必须重跑的验证

按顺序勾。命令默认桥 `8599`、PG 容器 `coa-authz-pg`、DSN
`postgresql://platform:platform_dev@127.0.0.1:5844/...`。

### 3.1 身份与状态码

- [ ] **无 token → 401**：`curl -i http://127.0.0.1:8599/namespaces`
      断言 `401`、`error=E_UNAUTHENTICATED`、带 `WWW-Authenticate: Bearer`。
- [ ] **有 token → 200**：用 dev issuer 铸 token 后 `GET /namespaces`，断言 `200`。
- [ ] **权限不足 → 403**：alice（`platform-viewer`）向非自有命名空间
      `POST /namespaces/<id>/sources`，断言 `403`、`error=E_FORBIDDEN`、`action=manageSource`。
- [ ] **未映射路由 → 403 `E_UNMAPPED_ROUTE`**：仅当仍有本地独有路由未进生产映射时出现。
      合并后本地补只剩 **5 条**，启动日志应打印 `+5 local-only routes`（原 48 条中 43 条
      已进生产 `_PATH_MAPPING`）。若仍打印 48/37，说明桥加载的是旧的 control-plane 包。

      `+5` 的来源可追：生产 `_PATH_MAPPING` 现 139 条，桥的
      `_LOCAL_AUTHZ_EXTENSIONS` 48 条，两者取差集即下表 5 条（逐条核对过）：

      | # | 路由 | 方法 → action | 上云后 |
      |---|---|---|---|
      | 1 | `/namespaces/{ns}/embeddings` | POST `manageSource` | `denyAll` |
      | 2 | `/namespaces/{ns}/embeddings/batch` | POST `manageSource` | `denyAll` |
      | 3 | `/namespaces/{ns}/embeddings/by-ontology/{ontologyId}` | GET `searchDocuments` | `denyAll` |
      | 4 | `/namespaces/{ns}/induce/datasources` | GET `viewNamespace` | `denyAll` |
      | 5 | `/namespaces/{ns}/validate/jobs` | GET/POST `viewNamespace` | `denyAll` |

      这 5 条对应 G.3 的 AR-04（功能上线门禁，非安全）：上云前必须补齐契约与
      `_PATH_MAPPING`，否则演示过的功能在线上固定 403。本地栈内它们由
      `_apply_local_authz_extensions` 在进程内补映射，不修改生产代码与契约。

### 3.2 操作人归属（不能是 platform-admin）

- [ ] alice 创建命名空间，查库确认 owner/createdBy 是 `alice@example.invalid`：

      docker exec coa-authz-pg psql -U platform -d platform -tAc \
        "SELECT item->>'namespaceId', item->>'ownerId', item->>'createdBy'
           FROM coa_local_items WHERE item->>'namespaceId'='<namespace-id>'"

- [ ] alice 给 bob 授角色，确认 `grantedBy` 是 alice：

      docker exec coa-authz-pg psql -U platform -d platform -tAc \
        "SELECT item->>'principalId', item->>'role', item->>'grantedBy'
           FROM coa_local_items WHERE item->>'grantedBy' IS NOT NULL
           ORDER BY item->>'grantedAt' DESC LIMIT 5"

  断言结果里不出现 `platform-admin` / `local-user` 作为操作人。

### 3.3 fail-closed

- [ ] 先铸到有效 token，再 `docker stop coa-authz-pg`，请求一个受保护路由：
      `GET /namespaces` 必须是 `503 E_AUTHZ_UNAVAILABLE`，不能 200、不能降级成只读或 admin。
      （若连接超时，也算未放行，但要记录实际表现；恢复后 `docker start coa-authz-pg`。）
- [ ] 授权组件恢复后，同一请求重新 200，确认不是永久熔断。

### 3.4 启动日志与配置

- [ ] `COA_LOCAL_DEV_AUTH=on` 时打印 dev issuer 警告；`off` 且无 `JWKS_ISSUER` 时启动失败（不静默降级）。
- [ ] `COA_LOCAL_AUTH_MODE` 不设置 = `enforce`：无 token 必 401。
- [ ] 显式 `COA_LOCAL_AUTH_MODE=disabled`：启动打印警告，无 token 可访问。
      这是唯一免鉴权口子，只在本机做负向确认，确认后立即恢复 `enforce`。
- [ ] `dev role bootstrap: [('local-dev@example.invalid', 'platform-admin')]` 只写正常
      `ResourceRoleMappings` 行，可通过 API 撤销。
- [ ] `OPTIONS *`、`GET /health`、`/_local/objects/*` 仍开放；`/local/auth/*` 仅在 dev auth 开启时存在。

## 四、`-m unit` 能不能跑到守卫测试

结论：**能跑到，且 CI 不会过滤掉。**

证据：

- 模块级标记在 `packages/control-plane/tests/unit/test_authorizer_handler.py` 顶部：
  `pytestmark = pytest.mark.unit`。
- Nx 的 `control-plane:test` 命令显式带 `-m unit`：
  `uv run pytest packages/control-plane -m unit -v ...`。
- 本地实跑：

      uv run pytest packages/control-plane -m unit -q
      # 887 passed, 12 deselected

       uv run pytest packages/control-plane -m unit -k "no_secured_smithy_operation_is_left_unmapped" -v
      # 2 passed（ControlPlaneService / DataLayerService 各一条参数化）
      # 另有 test_no_mapped_action_is_outside_cedar_schema 1 passed

- `pr.yml` 的 package 测试走 `pnpm nx affected -t test`（即上面的 `-m unit` 命令），
  repo-level `uv run pytest tests/unit -q` 不带 marker 过滤。

合并后自查一次：

```powershell
uv run pytest packages/control-plane -m unit -k "no_secured_smithy_operation_is_left_unmapped" --collect-only -q
```

必须列出 2 个用例。若为 0，说明模块被改了 marker 或被新配置排除，守卫等于白写。

## 五、边界

- 本清单只针对本地桥与鉴权；不动契约、生成产物、`web-app`。
- 不合并、不推、不建 PR 由本线执行；合并动作与最终冲突解决由整合线完成。
- 验证产生的容器与进程在脚本结束时自动停止；共享 8099/5173 不受影响。

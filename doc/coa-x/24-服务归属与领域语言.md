## 0. 结论摘要

1. **数字口径先对齐**：任务描述里的 `144 + 8 = 152` 在当前主线 HEAD 上不成立。主线 `9b1e793c` 是 `110 + 7 = 117`；`144 + 8 = 152` 对应集成预演分支 `integ/merge-20261110`（`e39a92ae`），比主线多 35 个 op。本文第 1–4 部分的完整盘点按 **152** 口径做，并在 §1.1 单列这 35 个尚未进主线的 op，避免把“预演态”当成“已上线态”。
2. **绑定关系本身是干净的**：152 个 op 定义，152 个都唯一挂在某个 service 的 `operations` 列表里；0 个孤儿、0 个重复挂载；两个 service 的 `use` 导入与 `operations` 列表双核对无缺项。**问题不在“绑错了”，而在“从来没有规则”。**
3. **两个 service 不是限界上下文**：`ControlPlaneService` / `DataLayerService` 是**部署平面**（控制面 / 数据面），不是领域。ControlPlane 承载了本文划分的 11 个上下文中的 10 个。把 144 个 op 塞进一个 service，是历史堆积，不是领域设计。
4. **真正的归属冲突不是 `FindLinks` 一条**：`FindLinks` 只是症状。根因是**图读取家族被劈成两半**——`GraphTraverse` 在 DataLayer，而 `FindLinks` / `FindGraphPath` / `GetCanvasSubgraph` / `GraphSearch` / `GetGraphClass` 等在 ControlPlane；同一个读取语义，两个平面都能找到先例，所以每加一个新 op 都要重新猜一次。
5. **建议改归属的只有 4 个 op（`GetEntity`、`GetEntityProvenance`、`GetEntityEmbeddings`、`SearchEmbeddings`）**，其余 148 个保持现状；另有 10 个只读语义的 `POST` op 建议补 `@readonly`，4 个查询 op 待确认是否持久化 run 记录后再定。本轮不建议新建 service。
6. **语言问题共 12 类**，最贵的是：`proposal` 一词两义、`source` / `datasource` / `dataSourceId` 三套叫法、`entityId` / `entityUri` / `uri` / `iri` 四套叫法、指标同时存在 `name` 与 `metricId` 两个主键。
7. **优先级**：P0 只做“文档裁决 + 加 `@readonly`”（零 wire 破坏）；P1 做实体读取的平面归属；P2 才考虑重命名与统一主键（wire 破坏，必须与前端同批改）。
8. **追加裁决**：`/validate`（本体级异步校验）与 `RunValidation`（图质量快照）**不是同一件事**；契约线补 **2 个 op**（不是 3 个），归 C6 / `ControlPlaneService`，保留异步，列表 op 暂不补。见 §3.12。

### 1.5 从盘点得到的四个事实

1. **文件粒度与领域粒度不一致**：`ontology-graph.smithy` 一个文件 23 个 op，横跨本体资产 CRUD、图查询、画布、推理、验证；`control-plane.smithy` 既放 service 定义又放 2 个健康检查 op。
2. **namespace 比 service 更接近领域**，但也不是领域：`facts` 11 个 op 同时含事实账本与冲突裁决；`ontologygraph` 24 个 op 同时含本体资产、图查询、推理。
3. **平面切分只在一处真正发生**：`documents` 的 7 个 op 被拆成 CP 6 + DL 1；其余 namespace 都整块落在某一个 service。也就是说，“按读写分平面”的规则只被执行了一次，没有形成制度。
4. **`FindLinks` 的冲突是文档冲突，不是绑定冲突**：集成预演分支里它已正确绑定到 `ControlPlaneService`；冲突来自 `doc/coa-x/09-platform整合评估.md:474` 的旧记录写的是 `DataLayerService`。

### 1.6 范围外但顺带确认的事实

- `data-layer.smithy` 里 `RateLimitExceededError` 没有 `use` 导入，但该 shape 定义在同 namespace 的 `serve.smithy:72`，**不是缺陷**。

- 主线与集成预演没有“反向删除”，不存在改名后旧 op 残留。

## 2. 领域划分建议

### 2.0 三条原则

1. **限界上下文按业务能力切，不按 namespace、不按 service 切。** namespace 是代码模块的历史结果，service 是运行时平面；两者都不能直接当上下文。
2. **一个 op 只属于一个上下文；一个上下文可以跨两个平面。** 例如“文档”上下文同时有控制面写入与数据面下载，这不矛盾。
3. **边界用两个问题检验**：这个上下文**拥有哪份状态**？它**能对什么说“不”**？答不出来的，就不是独立上下文。

### 2.1 十一个上下文

#### C1 命名空间与访问治理（16 op）

- **负责**：namespace 生命周期与状态；平台/命名空间角色的只读目录；namespace grant 与 platform grant 的创建、查询、删除。
- **不负责**：身份认证与 principal 目录（外部 IdP）；策略求值引擎（Cedar）；资源级权限判断。
- **边界**：grant 只是 `(principal, role, scope)` 绑定，它不创建角色、不创建 principal。角色定义在平台配置里，这里只读。
- **op**：`CreateNamespace`、`GetNamespace`、`ListNamespaces`、`UpdateNamespace`、`DeleteNamespace`、`UpdateNamespaceStatus`、`ListPlatformRoles`、`ListNamespaceRoles`、`GetNamespaceRole`、`CreateGrant`、`ListNamespaceGrants`、`DeleteGrant`、`ListPrincipalGrants`、`CreatePlatformGrant`、`ListPlatformGrants`、`DeletePlatformGrant`

#### C2 数据源接入与扫描（21 op）

- **负责**：结构化数据源的注册、审批、表/列元数据、重扫计划、扫描作业、源文件上传地址。
- **不负责**：文档上传与分块（C9）；本体归纳（C5）；指标定义（C4）；抽取事实的审批（C9）。
- **边界**：源审批决定“这份元数据能否被下游使用”，但不生产本体；扫描只产出元数据，不改图。
- **op**：`ListSources`、`CreateSource`、`GetSource`、`DeleteSource`、`RescanSource`、`UpdateSourceMetadata`、`GetSourceUploadUrls`、`ListSourceTables`、`GetSourceTable`、`ApproveSource`、`RejectSource`、`ReviewSourceTable`、`UpdateSourceTableMetadata`、`ReviewSourceColumn`、`KeepRescanRemoval`、`UpdateSourceColumnMetadata`、`UpdateSourceTableKeys`、`GetSourceScanJob`、`ListSourceScanJobs`、`PutSourceRescanSchedule`、`PutSourceEventRescan`

- **不负责**：本体类/属性定义（C7）；指标别名（C4）；文档分块（C9）。
- **边界**：术语是给检索与问答用的业务词表，**不是**形式化的 OWL 类。术语可以映射到类，但两者不能互相替代。
- **op**：`ListTerms`、`ListDictionaries`、`GetDictionary`、`GetDictionaryView`、`GetDictionaryCommentCoverage`、`RefreshDictionaries`

#### C4 指标口径（14 op）

- **负责**：命名空间级指标注册表的增删改查、校验、批量删除、OSI 导入导出；指标目录（族/报表清单）；平台指标卡（Postgres 读模型）。
- **不负责**：指标计算与结果（C10）；指标与问题之间的答案生成（C10）。
- **边界**：本上下文定义“算什么”，不回答“值是多少”。**注意当前有两个存储**：命名空间指标注册表与 `platformmetric` 指标卡不是同一张表，但属于同一个上下文下的两个子域，不应因此拆 service。
- **op**：`CreateMetric`、`GetMetric`、`ListMetrics`、`UpdateMetric`、`DeleteMetric`、`ValidateMetric`、`BulkDeleteMetrics`、`ImportOsi`、`GetImportJob`、`GetOsiUploadUrl`、`ExportOsi`、`GetMetricFamily`、`GetMetricReportManifest`、`GetMetricCard`

### 3.2 `FindLinks`：冲突在文档，不在契约

- **现在**：`ControlPlaneService`，namespace `ontologygraph`，`GET /namespaces/{namespaceId}/graph/links`。
- **旧记录**：`doc/coa-x/09-platform整合评估.md:474` 写的是 `DataLayerService`，理由是“邻接查询属图遍历”。
- **契约内裁决**：`ontology-graph-links.smithy:27-31` 已明确写“Service: ControlPlaneService, NOT DataLayerService”，并声明 `09` 的旧记录被取代。
- **建议**：**保持 CP**，把 `09` 的旧记录改成“已被 24 号文档取代”。理由不是“CP 更好”，而是它必须和 `FindGraphPath`（`GetCanvasSubgraph`、`GetCanvasManifest`）待在同一个客户端里；如果只把 `FindLinks` 搬到 DL，前端画布的 Links 页签与 Paths 页签会落在两个 client 上。
- **代价**：A（改文档）。如果最终选择“图读取全部进 DL”，代价升到 C，且要一次搬 13 个 op，不建议单搬 `FindLinks`。

### 3.3 `RunSparql`：归属正确，但需要把“为什么”写下来

- **现在**：`DataLayerService`，`POST /namespaces/{namespaceId}/sparql`，已带 `@readonly`。
- **建议**：保持 DL。
- **理由**：它执行只读查询、不改变控制面状态；`POST` 只是为了承载长查询体，不是写语义。它与 `Query`/`TranslateSPARQL` 同属 C10 的运行时查询面。
- **代价**：A。无需改动。

### 3.4 `CheckAnswerable`：归属正确，但缺 `@readonly`，且与“质量”不是一回事

- **现在**：`DataLayerService`，`POST /namespaces/{namespaceId}/answerable`，未标 `@readonly`。
- **建议**：保持 DL，补 `@readonly`。
- **理由**：它是在线预检——回答“这个问题在当前本体/术语/指标/事实覆盖下能不能答”，不写任何状态。它和 `GetAnswerQuality`（离线质量评估）是两个生命周期，不能因为名字里都有 “answer” 就合并。
- **代价**：B。

### 3.5 `DownloadDocument`：保持 DL，但要和 `DownloadOntology` 划清

- **现在**：`DataLayerService`，`GET /namespaces/{namespaceId}/documents/{documentId}/content`。
- **建议**：保持 DL。
- **理由**：返回的是文档字节流，属于运行时读取；上传在 CP 是因为它创建登记行并触发抽取。
- **真正的不一致**：`DownloadOntology`（`GET /namespaces/{namespaceId}/ontologies/{ontologyId}/download`）在 CP，也是“下载字节”。两者不是同一概念：一个是**源文档内容**，一个是**治理产物导出**。建议在术语表里明确：`Download` 只用于“取原始/已存字节”，`Export` 用于“转换后产物”。按这条规则，`DownloadOntology` 保留 CP 是合理的，但 `ExportOntologyVersion` / `ExportOntologyBundle` / `ExportOsi` 应与它区分。
- **代价**：A（写规则）。若要强行统一，C。

### 3.6 `GetEntity` / `GetEntityProvenance`：建议移到 DataLayer

- **现在**：`ControlPlaneService`，`GET /entities/{entityId}`、`GET /entities/{entityId}/provenance`；路径**不带 `namespaceId`**，注释说明实体 IRI 自带身份。
- **建议**：移到 `DataLayerService`，与 `GraphTraverse`、`KBSearch`、`Query` 同平面。
- **理由**：这是 A-Box 实体投影与来源读取，纯读、无控制面状态；放在 CP 的唯一历史原因是它自成一个 `entity` namespace。控制面应该拥有“治理动作”，不应该拥有“实体查询”。
- **代价**：C。生成客户端从 CP client 移到 DL client；前端实体详情页的 service 引用要改。
- **附带风险（不算归属）**：路径不带 `namespaceId`，与全仓其余路由的命名空间隔离方式不同。若实体 IRI 可跨命名空间，需确认鉴权层能按 IRI 反查所属 namespace；否则这是一个跨租户读取口子。这个问题应在鉴权线单独处理，本文只登记。

### 3.7 `GetEntityEmbeddings` / `SearchEmbeddings`：建议随实体读取一起移到 DataLayer

- **现在**：`ControlPlaneService`，`GET /namespaces/{namespaceId}/embeddings/by-entity/{entityUri}`、`POST /namespaces/{namespaceId}/embeddings/search`。
- **建议**：移到 `DataLayerService`。
- **理由**：嵌入检索是运行时检索原语，和 `KBSearch` 同类；它不改变治理状态。如果只搬实体读取而留下嵌入，C8 仍然跨两个平面，问题没解决。
- **代价**：C。与 F-03 同批做，避免两次改客户端。

### 3.8 图读取家族：这是 `FindLinks` 冲突的根因

| op | 现在 | 语义 |
|---|---|---|
| `GraphTraverse` | **DL** | 从起点按谓词/深度遍历 |
| `FindLinks` | CP | 有界邻接 |
| `FindGraphPath` | CP | 两点间路径 |
| `GetCanvasSubgraph` | CP | 画布子图 |
| `GetCanvasManifest` | CP | 画布清单 |
| `GraphSearch` | CP | 图检索 |
| `ListStatements` | CP | 三元组列表 |

- **判断**：这 13 个 op 都是只读图查询。按“控制面=治理动作、数据面=运行时读取”的规则，它们**应该全在 DL**；按“已经能跑、别动”的现状，其中 12 个在 CP、1 个在 DL。两种都能自洽，但不能一半一半。

### 3.9 `ImportBundle` 与 `ImportOntology`：两个入口，边界未定义

- **现在**：`ImportBundle`（`ontologybundle`，CP）与 `ImportOntology`（`ontologylifecycle`，CP）都能“导入本体”。
- **建议**：定义分工并写进术语表：
  - `ImportBundle` = 导入**多件套可移植包**（本体 + 版本元数据 + 可选字典/指标），面向迁移；
  - `ImportOntology` = 导入**单份本体文件**（Turtle/RDF-XML/JSON-LD），面向日常更新。
- **如果实现上是同一条路径**：保留一个，另一个标 deprecated；不要留两个语义相同、行为不同的入口。
- **代价**：A（先写规则）；若合并 op，D。

### 3.12 裁决：`/validate`（本体异步校验）与 `RunValidation`（图质量快照）不是同一件事

**结论（可直接执行）**：

1. **不是同一件事。** `/validate` 是**本体级、异步、多 tier 的校验作业**；`RunValidation` 是**图级、同步、计数型健康快照**。
2. `/validate` 归 **C6 本体版本与发布**，挂 **`ControlPlaneService`**，保留**异步 job** 语义。
3. 契约线**补 2 个 op，不补 3 个**：
   - `StartOntologyValidation`：`POST /namespaces/{namespaceId}/validate`，202；
   - `GetOntologyValidationJob`：`GET /namespaces/{namespaceId}/validate/jobs/{jobId}`；
   - `ListOntologyValidationJobs` **暂不补**：web-app 没有任何调用点，且引擎实现是进程内内存列表（`validate.py:230`），进程重启即丢；契约化会制造“可列历史”的假能力。等有消费方并落 Dynamo 后再补。
4. `RunValidation` 保持现有 op、路径、同步语义；不改名（改名会动前端 System Health 页），但在 op 描述里明确它是 “graph quality snapshot”，**不是**本体校验。

**裁决依据（三方对比）**：

| 维度 | `ValidateProposal`（已有） | `/validate`（待补） | `RunValidation`（已有） |
|---|---|---|---|
| 对象 | 归纳提案的 Turtle | 整份本体（`ontology_id` 或内联 Turtle） | 当前命名空间图 |
| 触发点 | 接受提案前 | 本体入库后 / 发布前质量门 | 系统健康页即时查询 |
| 同步性 | 异步 job | 异步 job（202） | 同步 |
| 请求体 | `ValidateProposalRequest` | `ValidationRequest`：`ontology_id`、`tiers`、`shacl_shapes_turtle`、`competency_questions` | 无 |
| 输出 | 多 tier findings + 报告 | `ValidationReport`：findings、`StructuralMetrics`、`passed`、`tiers_run` | 计数：orphan / unlabeled / shacl / inference |
| 持久化 | `VALIDATE` job | `ONTVALIDATE` job（Dynamo） | 无 |
| 现有消费方 | 提案页 | web-app 有 service 函数，暂无页面调用 | System Health 页 |
| 归属 | C5 / CP | **C6 / CP（新增）** | C7 / CP |

**证据位置**：

- 引擎异步校验：`packages/ontology-engine/src/coa_ontology/validation/routers/validate.py:173`（POST `/`，202）、`:198`（GET job）、`:230`（GET list）；job 写入 `ONTVALIDATE`，见 `:49-63`。
- 请求/响应 shape：`packages/ontology-engine/src/coa_ontology/validation/schemas.py:40`（`ValidationRequest`）、`:72`（`ValidationReport`）、`:93`（`JobResponse`）。
- 引擎同步图校验：`packages/ontology-engine/src/coa_ontology/catalog/routers/graph.py:403`，返回 `QualityValidation` 计数。
- 路由映射：`packages/ontology-engine/src/coa_ontology/api_proxy_handler.py:138-140`（`/validate`、`/validate/jobs`、`/validate/jobs/{jobId}`）、`:109`（`/graph/validate`）、`:69`（提案校验）。
- 契约现状：`models/src/main/smithy/ontology-graph.smithy` 的 `RunValidation` 打 `/graph/validate`；`ontology-induction.smithy` 已有 `ValidateProposal` + `GetProposalValidationJob`。
- 消费方：`packages/web-app/src/services/ontology-engine.ts:1001`（trigger）、`:1012`（get job）；全仓无 list 调用点，也无页面消费。

**为什么必须保留异步**：

- 校验要跑 tier1/2/3，可带自定义 SHACL 与能力问题，输入可达整份本体；同步会撞 API Gateway / Lambda 超时。
- 现有实现已经是 202 + 后台线程 + Dynamo job；契约改成同步等于让客户端等一个可能超过 29 秒的请求，是行为回退。

**为什么不是 3 个 op**：

- `ListOntologyValidationJobs` 只有引擎内存实现，且没有消费方。按项目既有口径“无界面落点的 op 不凑数”，不补。
- 若契约线目标是“引擎路由 1:1”，也要先把列表落 Dynamo 并明确保留期，再补；否则补出来的是一个重启即空的接口。

**命名边界（同时写进 §4.1 术语表）**：

- `ValidateProposal`：只用于**提案**（C5，接受前）。
- `StartOntologyValidation` / `GetOntologyValidationJob`：只用于**整份本体**（C6，入库后 / 发布前）。
- `RunValidation`：只用于**图质量快照**（C7，同步）；建议在 op 描述首行写 “Graph quality snapshot (not ontology validation)”。
- 禁止再新增裸 `Validate*` / `*ValidationJob` 名字；必须带对象前缀（Proposal / Ontology / Graph）。

**代价**：

- 新增 2 个 op + 一组 shape（`ValidationTier`、`ValidationFinding`、`StructuralMetrics`、`ValidationReport`、`ValidationJob`）；不改任何现有 op 的 wire。
- 引擎与网关**零改动**：三条路由已存在且已代理。
- 需要重跑生成、补 `@examples`、补契约测试；前端暂不接页面，不产生 UI 改动。
- 若坚持补第 3 个列表 op，额外成本低但会引入非持久语义；不建议。

**代价档位**：N（新增契约面，不改现有 wire）。已记入 §3.1 的 F-13。

### 4.2 冲突清单

#### L-01 `proposal` 一词两义（最贵）

- **位置**：
  - C5 归纳：`ListProposals`、`GetProposal`、`AcceptProposal`、`RejectProposals`、`CancelProposal`、`UpdateProposal`、`GetProposalUploadUrls`；`proposalId: Uuid`；`ProposalStatus`（`ontology-induction.smithy:187`）。
  - C6 版本：`ProposeOntologyVersion`、`ListOntologyProposals`、`GetOntologyVersionProposal`、`ReviewOntologyProposal`；`proposalId: OntologyProposalId`（`ontology-lifecycle.smithy:402`）；`OntologyProposalStatus` / `OntologyProposalDecision`。
- **问题**：同一个 `proposalId`，一个是 `Uuid`，一个是 `OntologyProposalId`（字符串）；同一套动作 `accept` / `review` 作用在两个完全不同的对象上。
- **建议**：C5 统一为 `InductionProposal`（`inductionProposalId`）；C6 统一为 `OntologyProposal`（`ontologyProposalId`）。至少先把 **shape 名**改掉，op 名可以后置。
- **代价**：D（字段/类型改名破坏 wire）；只改 shape 名与文档为 B。

#### L-02 `ontology` 与 `graph` 混用

- **位置**：namespace `ontologygraph`；op `GetOntology*` 与 `GraphSearch` / `FindGraphPath` / `GetGraphClass` 混排；URI 同时有 `/ontologies/...` 与 `/graph/...`；字段 `ontologyGraph`（`CheckAnswerable`）、`graph`（实体边/指针）。
- **问题**：`ontology` 是受治理资产，`graph` 是运行时视图；现在两者都能指“图”，新人无法从名字判断该用哪个。
- **建议**：保留两个词，但严格分工——`ontologyId` 只指资产；`graph` 只指命名图 URI（如 `urn:platform:graph:tbox:*`）。`GetOntologyDiff` 这种读图差异的 op 可以保留名字，但文档必须写“读的是该本体的发布图”。
- **代价**：A（写规则）；若改 op 名，D。

#### L-03 `source` / `datasource` / `dataSourceId`

- **位置**：`unifiedsources` 用 `sourceId` / `SourceId` / `sourceTable`；`metric` 用 `dataSourceId`（`DataSourceId`）；`ontologyinduction` 用 `ListInducedDatasources`、`datasourceIds`、`InductionSourceType`；`documents` 的 `SourceType` 又有 `DOCUMENTS`。
- **问题**：同一个“数据源”概念有三套拼写；`dataSourceId` 与 `sourceId` 是否是同一个 ID，契约没有说。
- **建议**：统一为 `source` / `sourceId`；`dataSourceId` 若确实是另一个实体，必须在文档里定义为“指标绑定视角的源”，否则改名为 `sourceId`。
- **代价**：D（字段改名）。

#### L-04 `entityId` / `entityUri` / `uri` / `iri` 四套叫法

- **位置**：
  - `GetEntity` / `GetEntityProvenance`：`entityId: EntityRef`，路径 `/entities/{entityId}`，实际值是 IRI（示例 `urn:coa:entity:...`）。
  - `GetEntityEmbeddings`：`entityUri`（`embeddings.smithy:154`）。
  - `FindLinks`：入参叫 `uri`（文件头明确“不是 entityUri”）。
  - 响应与图模型：`iri`（`OntologyClassRef`、`OntologyTreeNode`）、`uri`（`GraphLinkNode`）。
- **问题**：同一个 RDF 资源，四个字段名；`entityId` 听起来像代理键，实际是 IRI。
- **建议**：**IRI 一律叫 `iri`**；如果路径参数必须叫 `entityId`，在文档里写死“它的值就是 IRI”，并禁止再新增 `entityUri` / `uri` 同义字段。
- **代价**：D（路径/字段改名）；只改文档为 A。

#### L-05 指标同时有 `name` 和 `metricId` 两个主键

- **位置**：`MetricDefinition.metricId`（`metric-service.smithy:197`）；`GetMetric` / `UpdateMetric` / `DeleteMetric` 用 `/metrics/{name}`（`:338`、`:414`、`:484`）；`GetMetricCard` 用 `metricId`（`metric-card.smithy:204`）。
- **问题**：注册表资源有 `metricId`，但所有按 ID 的操作实际按 `name`；平台指标卡又按 `metricId`。调用方无法判断哪个是权威标识，跨存储 join 只能靠名字。
- **建议**：定一个权威键。推荐 **`metricId` 为权威键，`name` 只做展示与兼容查询**；短期至少在 `MetricDefinition` 文档里写“name 是唯一键，metricId 是平台侧 ID”，避免两边都叫 ID。
- **代价**：D（路径参数从 `name` 改 `metricId`，破坏前端与脚本）。

#### L-06 `job` 与 `run` 混用

- **位置**：`ListIngestionRuns`（`IngestionRun` / `runId`）、`GetSourceScanJob`、`ListSourceScanJobs`、`GetInductionJob`、`GetInferConstraintsJob`、`GetProposalValidationJob`、`GetImportJob`、`GetIngestStatus`（返回 jobId）、`GetReasoningStatus`（jobId）。
- **问题**：同一类“异步执行记录”，一半叫 job，一半叫 run；状态枚举也各叫各的（`IngestionRunStatus`、`InductionJobStatus`、`ProposalValidationJobStatus`、`SourceScanJobStatus`）。
- **建议**：定规则——**离线批处理叫 `job`，长时数据导入叫 `run`**；或全部收敛到 `job`。至少新增 op 不得再造第三种叫法。
- **代价**：A（写规则）；重命名为 D。

#### L-07 审批动作有三套词：approve / accept / review

- **位置**：`ApproveSource` / `RejectSource`；`ApproveFactCandidate` / `RejectFactCandidate`；`AcceptProposal` / `RejectProposals`；`ReviewOntologyProposal`（decision `APPROVE`/`REJECT`）；`ReviewSourceTable` / `ReviewSourceColumn`（`ReviewDecision`）。
- **问题**：同一个“人做通过/拒绝”的动作，四个动词；其中 `Accept` 还可能表示“机器接受候选”，与人工审批混淆。
- **建议**：**人工审批统一用 `Review` + `ReviewDecision`**；`Accept` 只保留给“把候选提案转为正式对象”的机器动作（如果确实是机器动作）。若全是人工，则统一为 `Approve` / `Reject`，删掉 `Accept`。
- **代价**：D（op 名与枚举值）。

#### L-08 validate / verify / check / run / start 五个动词

- **位置**：`RunValidation`（图质量）、`ValidateMetric`（指标定义）、`ValidateProposal`（提案）、`StartOntologyValidation` / `GetOntologyValidationJob`（整份本体，待补）、`VerifyOntology`（审计链）、`CheckAnswerable`（可答性）。
- **问题**：都表示“检查”，但检查对象、是否写状态、返回什么，全不一样。
- **建议**：固定语义矩阵：
  - `Validate` = 对输入做规则校验，返回错误列表；
  - `Verify` = 对已存数据做完整性/审计校验；
  - `Check` = 预检“能不能做”，返回布尔/原因；
  - `Run` = 执行一个会产生结果的作业。
- **三类校验的对象边界（裁决见 §3.12）**：`ValidateProposal` = 提案（C5，异步）；`StartOntologyValidation` = 整份本体（C6，异步）；`RunValidation` = 图质量快照（C7，同步）。`RunValidation` 现有版本**不改名**，只在描述里补“graph quality snapshot”；若进入破坏窗口，建议改名 `GetGraphQuality`，不要叫 `ValidateGraph`，避免与本体校验混淆。
- **代价**：A（文档）；改名 D。

#### L-09 import / ingest / upload / load / fetch / download / export 七个动词

- **位置**：`ImportOsi`、`ImportBundle`、`ImportOntology`；`IngestOntologyFromS3`；`UploadOntology` + `GetOntologyUploadUrl`；`LoadFoundationalOntology`；`FetchOntology`；`DownloadOntology` / `DownloadDocument`；`ExportOsi` / `ExportOntologyBundle` / `ExportOntologyVersion`。
- **问题**：同样是“把本体弄进来/弄出去”，七个动词，边界没有定义。
- **建议**：
  - `Upload` = 客户端把字节交给我们（两段式：先要 URL，再上传）；
  - `Import` = 服务端接收一个**包/文件**并登记；
  - `Ingest` = 把已登记的内容解析进图存储（异步）；
  - `Fetch` = 从远端 URL 拉取；
  - `Load` = 把基础本体装进命名空间；
  - `Download` = 取原始/已存字节；
  - `Export` = 生成转换后的产物。
- **代价**：A（写规则）；改名 D。

#### L-10 `Get*UploadUrl` 单复数不一致

- **位置**：`GetOsiUploadUrl`（单）、`GetOntologyUploadUrl`（单）、`GetProposalUploadUrls`（复）、`GetSourceUploadUrls`（复）。
- **问题**：单复数不表达实际返回一个还是多个 URL；调用方无法从名字判断。
- **建议**：只有确实返回多个 URL 时才用复数；否则统一单数。若两者都可能，改成 `Create*UploadUrls` 并在 output 里返回列表。
- **代价**：B/D（改名破坏客户端）。

#### L-11 枚举值大小写与风格不一致

- **位置**：`FactState` 用 `active`/`retracted`（小写 wire）；`ProposalStatus` 用 `inducing`/`pending`（小写）；`FactCandidateStatus` 用 `PENDING`（大写）；`ReviewStatus` 用 `PENDING_REVIEW`；`DocumentStatus` 用 `UPLOADED`；`OntologyProposalDecision` 用 `APPROVE`；`GroundingMode` 用 `NONE`/`STANDARD`/`ENHANCED`。
- **问题**：wire 值一半小写、一半大写下划线；同一个“待处理”在不同枚举里是 `pending` / `PENDING` / `PENDING_REVIEW`。
- **建议**：统一为大写下划线（与多数枚举一致），并在术语表里定义通用状态词：`PENDING` / `APPROVED` / `REJECTED` / `RUNNING` / `COMPLETED` / `FAILED` / `CANCELLED`。
- **代价**：D（wire 值变更，必须与前端同批）。

#### L-12 路径参数命名与蛇形/驼峰混用

- **位置**：`DeleteOntology` 用 query `ontology_id`（`ontology-graph.smithy:259-269`），其余全仓用 camelCase（`namespaceId`、`metricId`、`proposalId`）。
- **问题**：唯一一个 snake_case 的 wire 参数，客户端生成后会与其它参数风格不一致。
- **建议**：改为 `ontologyId`；如果担心破坏已有调用，先在新版加 `ontologyId` 并保留 `ontology_id` 一个版本，再删旧参数。
- **代价**：D（参数改名）；兼容期方案为 C。

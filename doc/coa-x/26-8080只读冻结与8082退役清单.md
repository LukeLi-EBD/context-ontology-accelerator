## 0. 一页结论

1. **冻结拦在哪：进程内 ASGI 中间件，`platform_core/api.py` 的 `create_app`（1759）。**
   不选桥（桥不转发 8080，拦不到），不选 compose/网络层（只做全通/全断，没有方法级粒度）。
2. **判定「写」用「方法默认拒绝 + 读型 POST 白名单」，不在运行时写死 148 条路径。**
   148 个操作里 50 个非 GET（POST 44 / PUT 3 / DELETE 3）；逐条分类为
   **W 35（改状态）/ W2 2（只追加记录）/ A 1（只写导出物）/ R 5（纯读）/ X 7（设计上本就拒绝）**。
   运行时只嵌 **7 条放行正则 + 5 条只读正则 + 1 条 OPTIONS 放行**。
3. **被拦返回 409**，体沿用 `PortError` 形状：`{"error":{"code":"Conflict","providerCode":"E_PLATFORM_READ_ONLY",...}}`，
   每拦一次写一行 JSONL 审计到 `/data/audit/readonly-YYYYMMDD.jsonl`（宿主 `D:\agentABC\data\audit\`）。
4. **一键恢复写不重启**：哨兵文件 `D:\agentABC\data\READONLY` 存在即冻结，删除即恢复（1s 缓存）。
   安装冻结机制本身需要**一次**重建 + 重启 `agent-platform-api`（约 1 分钟窗口），之后开关零重启。
5. **8082 退役 = `docker stop` 五个容器，不动卷、不动网络、不删镜像。**
   前置 4 项检查（锁、验收日志、连接、容器内 exec），回滚用 `docker start` 五连，
   batch 收尾按「端口 0 监听 + 容器全 exited + 两个卷仍在」判。
6. **冻结只封 HTTP 入口**：`docker compose exec ... platform` 的 CLI 写入、容器内后台任务、
   直连 PG/Oxigraph 都不在中间件视野内。影子双跑期间必须同时约束这三条（§1.7）。

## 1. 8080 只读冻结机制设计

### 1.1 三个候选拦截位，为什么选内核入口

| 位置 | 能拦到什么 | 拦不到什么 | 结论 |
|---|---|---|---|
| **P1 内核入口**：`create_app` 加 ASGI 中间件（`api.py:1759`，CORS 之后 `1774`） | 所有到达 8080 的 HTTP 请求，含宿主 curl、容器间调用、旧 UI、web-app 代理 | CLI（`platform ...` 子命令）、后台任务、直连 DB/图库 | **采用** |
| P2 桥：`doc/coa-x/tools/coa_api_local.py`（8799） | 只有经过桥的 COA 契约流量 | **8080 完全不经过桥**（桥只在本文件 `511` 引用了一份 8080 配置文件路径，不做转发） | 无效，排除 |
| P3 compose / 网络层：改端口映射、断网、iptables、限流 | 全通/全断；连接级 | 方法级判定（Docker 无按 HTTP 方法过滤能力）；断网会同时杀掉只读流量 | 只能当「硬停」手段，不能当只读冻结 |

P1 还有一个决定性优势：**指向 8080 的客户端一个都不用改**。8080 仍是 8080，只是写请求被就地拒绝。

### 1.2 三个方案对比

| # | 方案 | 改动面 | 粒度 | 开关成本 | 绕过面 | 代价 | 风险 |
|---|---|---|---|---|---|---|---|
| **A** | **进程内 ASGI 中间件（推荐）** | 1 个新文件 + `api.py` 1 处注册 + 1 个 GET 状态端点 + compose 2 个环境变量 | 方法 + 路径正则 | 哨兵文件，**1s 生效、零重启** | CLI / 后台任务 / 直连库 | 新代码约 90 行；安装需**一次**重建+重启（≈1 min） | 低：在 handler 之前短路，不改任何业务路径 |
| B | 宿主反向代理（nginx/Caddy）挡在 8080 前 | 新容器 + 端口重排（8080→18080）+ 代理配置 | 方法 + 前缀 | 改配置 + reload | 容器间直连（`agent-platform-api:8080`）、`docker exec` | 0.5–1 人日 | 高：要挪原容器端口，`/ws` 升级、`Origin: null` 的 file:// CORS、healthcheck 全要重测 |
| C | 只读凭证 + 网络隔离（PG 只读角色、图库断网） | 建角色、换连接串、改网络 | 库级，不可按接口 | 换 env + 重启 | 全断或全不断 | 0.5 人日 | 高：读也要连库；Oxigraph 无鉴权；会把「读」一起弄坏 |

**选 A。** 理由排序：粒度（唯一能做方法级）＞ 对现有客户端零影响 ＞ 可即时开关 ＞ 改动面最小。
B 的代价主要不在写配置，而在**挪 8080 端口**——那会让 `web/app.js:7`、`browse.js:8`、
`vite.config.ts:23-27` 的 `/ws` 代理、compose healthcheck（`docker-compose.yml:229-236`）
一次性全部失配，等于在冻结之外又叠一次迁移风险。

C 不作为主方案，但建议作为**纵深防御的第二道**（见 §1.6 第 5 条，可选、本轮不做）。

### 1.3 「写」的判定：148 / 50 的事实与逐条分类

### 1.4 被拦时的状态码、响应体与审计

状态码：**409 Conflict**（沿用 `_HTTP_STATUS["Conflict"]=409`，`api.py:99-105`）。
不用 403（那是权限语义，会与 `PermissionDenied` 混淆），不用 503（会被当成服务不可用，
触发上层重试与告警风暴）。

响应体（与 `PortError` handler 同形状，`api.py:1775-1787`）：

```json
{
  "error": {
    "code": "Conflict",
    "provider": "platform",
    "providerCode": "E_PLATFORM_READ_ONLY",
    "message": "platform is in read-only freeze; writes are disabled until the freeze is lifted",
    "retryable": true,
    "details": {
      "method": "POST",
      "path": "/facts",
      "mode": "read_only",
      "auditId": "0f3c9a1e8b7d4c2a",
      "since": "2026-11-10T09:12:33+08:00"
    }
  }
}
```

响应头：`X-Platform-Mode: read-only`、`X-Audit-Id: <auditId>`。**不加** `Retry-After`——
冻结是人手动解除的，给秒数只会诱导客户端盲目重试。

审计：每请求一行 JSONL，追加写，路径 `/data/audit/readonly-YYYYMMDD.jsonl`
（容器 `/data` → 宿主 `D:\agentABC\data`，见 `docker-compose.yml:227-228`）。

| 字段 | 含义 |
|---|---|
| `ts` / `since` | 请求时刻 / 本次冻结生效时刻 |
| `auditId` | 16 位 hex，同时回给客户端，便于对账 |
| `event` | `blocked` / `allow_read` / `allow_refused_by_design` |
| `method` / `path` / `query` | 原样（query 截断 2KB） |
| `client` / `userAgent` | `request.client.host`（含端口）/ UA |
| `rule` | `W` / `W2` / `A` / `R` / `X`（命中的分类） |
| `bodyBytes` / `bodySha256` | **只记长度与哈希，不落 body**（可能有敏感内容） |
| `pid` / `version` | 进程号与 `platform_core.__version__`，用于确认是哪一次部署 |

写入方式：`open(path,"a",encoding="utf-8")` + 单行 `json.dumps(ensure_ascii=False)` + `flush()`。
uvicorn 单进程（compose 未设 `--workers`），无并发写竞争；审计写失败**不得**影响 409 返回
（`try/except` 包住，失败只写 stderr 一次，并置 `X-Audit-Failed: 1`）。

### 1.5 一键冻结 / 一键恢复

**唯一开关是哨兵文件**，环境变量只决定「进程启动时的默认值」：

| 动作 | 命令（未来执行时用） | 生效 |
|---|---|---|
| 冻结 | `New-Item -ItemType File D:\agentABC\data\READONLY` | ≤1s（缓存 TTL） |
| 恢复写 | `Remove-Item D:\agentABC\data\READONLY` | ≤1s |
| 看状态 | `.\doc\coa-x\tools\readonly.ps1 status` | — |

中间件每次请求 `os.stat` 哨兵（1s 缓存，避免每请求一次 IO）：

- 文件存在 → 冻结；
- 文件不存在 → 可写；
- `stat` 抛权限错误 → **保持上一次缓存状态**并记 stderr，不翻转（避免权限抖动导致半开半关）；
- 进程启动时文件不存在 → 可写（默认不停机）。

设计上刻意**不做**「无哨兵即冻结」的 fail-closed：若宿主机磁盘/权限异常，会让一个健康栈
突然写不进去，代价大于收益。冻结是运营动作，不是安全边界。

### 1.7 冻结边界（必须和影子双跑一起讲清）

冻结只管 **8080 的 HTTP 入口**。以下四条不在视野内，必须靠流程约束：

1. `docker compose exec platform platform <子命令>`（`smoke-*`、`graph-count`、`bulk-index` 等）——
   直接调内部函数，不过中间件。冻结期间禁止在共享栈上跑任何 `smoke-*` / 验收 / 索引脚本。
2. `scripts/bulk-index.ps1`、`burst.ps1`、`seed.ps1` —— 它们的写走 HTTP 还是 CLI 需逐条确认，
   未确认前一律按「会写」处理（U5）。
3. 容器内后台任务（embedding 队列、索引收尾）—— 冻结前必须先排空：确认没有进行中的
   `documents/*/index` 调用（观察 `docker logs --since 5m agent-platform-api` 无写请求）。
4. 直连 `127.0.0.1:5432` 或图库 —— 本机任何带 psql 的脚本都能绕过。冻结期间共享栈的
   PG 口令不外发，并约定「谁直连谁签收」。

结论：冻结能保证「经 8080 的写为 0」，不能保证「全库零写」。影子双跑的漂移检测必须
**同时**看两侧计数（文档数、断言数、发布版本数），不能只看 8080 的 409 计数。

### 1.8 冻结 / 解冻的操作序列（设计，不执行）

冻结前：

1. 排空：`docker logs --since 10m agent-platform-api | Select-String 'POST|PUT|DELETE'` 无新增。
2. 记基线：文档数、断言数、`tbox/current` 版本、`platform.graph_pointer` 全表快照。
3. `readonly.ps1 on`。
4. 自检三连：`GET /healthz` 200；`GET /readonly` 返回 `read_only`；`POST /facts`（空体）
   必须 409 `E_PLATFORM_READ_ONLY` 且审计文件新增一行。**这一步是冻结是否真的生效的唯一证据。**
5. 把 `since` 与基线一起写进影子双跑的开跑记录。

解冻前：确认影子双跑判据已达标（`09` §8.3 T1–T8），再 `readonly.ps1 off`，
复核 `GET /readonly` 为 `read_write`、同一 `POST /facts` 变为 400/422（不再是 409）。

# 19 本地栈鉴权盘点

> 分支 `feat/authz-close`，基线 `feat/statements-route-authz` @ `9a36752c`。
> 盘点对象：`doc/coa-x/tools/coa_api_local.py` 的 `ROUTES`，共 **138** 条。
> 云端行为以 `coa_control_plane.authorization.handler` 的 `_PATH_MAPPING` 与 Cedar 策略为准；
> 本文只描述本地桥及其与云上的差异。

## 结论

**本地栈此前等于没有权限系统。这是既有事实，不是「待优化」。**

桥在 dispatch 之前无条件把 `requestContext.authorizer` 写成固定平台身份
（`principalId=local-user`、`email=local-dev@example.invalid`、`globalRoles=platform-admin`），
从头到尾没有读过 `Authorization` 头。因此：

- 138 条路由**全部**满足「身份校验 = 无、命名空间权限 = 无」；
- 任何人都能调用所有 op，包括跨命名空间读写；
- 写操作的操作人只有三种来源，没有一种来自真实调用者：

| 来源 | 适用路由 | 具体行为 |
| --- | --- | --- |
| A. 固定平台身份 | 进程内 handler（namespaces / roles / grants / sources / metrics / documents / candidates / graph traverse） | 直接使用桥注入的 `requestContext.authorizer`，落库的是 `local-user` / `local-dev@example.invalid` |
| B. 客户端 body | 进程内 KERNEL（facts / proposals / publish / rollback / import / reasoning 等） | 取 `payload["actor"]`，缺省 `operator`；调用方可以任意伪造 |
| C. 8101 透传 | ontology-engine 代理（induce / proposals / ontologies / embeddings 等） | bridge 原样转发 body，8101 侧没有身份注入面；审计归属取决于 body 或 8101 默认值 |

生产 `_PATH_MAPPING` 覆盖其中 **90** 条；其余 **48 条**是本地独有路由，改造后仅在
本进程内补映射，**在 AWS 上会 `denyAll`**，详见第二节。

## 二、48 条「本地补」路由：云上会 `denyAll`

这 48 条路由存在于本地桥的 `ROUTES`，但**不在**生产 `_PATH_MAPPING`。
云端请求到达 `AuthorizerFn` 时，`_map_request_to_cedar` 只能返回 `denyAll`，
handler 在策略评估前直接 Deny；本地桥把它转成 `403 E_UNMAPPED_ROUTE`。

本地桥只做本进程扩展（`_apply_local_authz_extensions`），启动打印
`[api] authorization map: +48 local-only routes`，**不修改生产代码与契约**。

风险与使用约束：

- 本地能跑不代表云上能跑。这些 op 若要上线，必须先补契约、`_PATH_MAPPING`
  与 Cedar 策略，否则线上固定 403。
- 不要把「48 条本地补」理解成「这些接口已经鉴权完毕、可以直接发布」。
- 新增本地路由时，必须同步补 `_LOCAL_AUTHZ_EXTENSIONS`，否则请求会 fail-closed 到
  `E_UNMAPPED_ROUTE`，而不是静默放行。

## 三、改造后的行为约定

每个请求都复用生产 `coa_control_plane.authorization.handler`：
JWT 验签（RS256 / JWKS / `iss` / `exp`）→ 解析全局与命名空间角色 → Cedar 策略评估
→ 才进入业务 handler。

| 条件 | 状态码 | 错误码 | 附加信息 |
| --- | --- | --- | --- |
| 缺少 `Authorization`、验签失败、过期、issuer 不匹配 | `401` | `E_UNAUTHENTICATED` | `WWW-Authenticate: Bearer`，body 带 `detail` |
| 身份有效，但缺少该 action 的授权 | `403` | `E_FORBIDDEN` | body 带 `action`（如 `manageSource`） |
| 路由不在授权映射里（fail-closed） | `403` | `E_UNMAPPED_ROUTE` | 不应出现在正常契约路由上 |
| 授权组件自身异常（JWKS、策略加载、DAO 等） | `503` | `E_AUTHZ_UNAVAILABLE` | 不降级、不放行 |

约定：

- **任何校验失败都不会降级成 admin**，也没有「失败后按只读放行」的分支。
- 写操作的操作人从 token 身份取：进程内 handler 使用真实 `requestContext.authorizer`；
  KERNEL 调用由桥注入 `actor`（body 中的同名字段会被覆盖），字典刷新额外覆盖
  `requestedBy`；`_kernel_call` 同时设置 `x-actor`。
- 本地 dev issuer（`COA_LOCAL_DEV_AUTH=on`）只替代 IdP：token 仍按生产规则真实验签，
  只是签名密钥在桥进程内存中生成，且提供 `/local/auth/token`、`/local/auth/jwks`、
  `/local/auth/config`。dev 身份不是绕过授权，缺授权记录一样 403。
- 启动时 `COA_LOCAL_DEV_ADMIN_USER`（默认 `local-dev@example.invalid`）写入
  `platform-admin`，其余 `COA_LOCAL_DEV_USERS` 只写 `platform-viewer`。两者都是正常的
  `ResourceRoleMappings` 行，可通过 API 撤销。
- 路由之外仍有四个非鉴权面：`OPTIONS *`（CORS 预检）、`GET /health`、
  `/_local/objects/*`（本地对象存储）、`/local/auth/*`（仅 dev auth 开启时）。
  它们都不承载业务 op。

### `COA_LOCAL_AUTH_MODE`

| 取值 | 行为 |
| --- | --- |
| `enforce`（默认，不设即此值） | 所有请求验签 + 授权；缺 `JWKS_ISSUER` 且未开 dev auth 时启动失败 |
| `disabled` | 跳过全部身份与授权校验，启动打印显著警告 |

`disabled` 是唯一的免鉴权口子，**必须显式设置**才会生效，默认关闭。它的风险：

- 任何人都能调用所有 op，包括删除命名空间、发布本体、改授权；
- 写操作的操作人退回固定本地身份，审计记录不可信；
- 只允许本机临时排障，**禁止在共享实例、演示环境或任何非本机环境使用**。

## 四、已知缺口：没有命名空间段的 6 条路径

以下路径的 contract 形状里没有 `{namespaceId}`，Cedar 拿不到 `resource.id`，
命名空间级角色（`namespace-owner` 等要求 `resource.id == namespaceId`）无法命中。
它们目前只能落**全局读权限**（`platform-viewer` / `platform-admin`）：

| 路径 | 方法 | 当前落点 action | 实际暴露 |
| --- | --- | --- | --- |
| `/entities/{entityId}` | GET | `searchDocuments` | 全局 viewer 可读任意命名空间的实体 |
| `/entities/{entityId}/provenance` | GET | `searchDocuments` | 同上，含来源链 |
| `/metrics/{metricId}` | GET | `readMetric` | 全局 viewer 可读任意命名空间的指标卡 |
| `/browse/ontology/tree` | GET | `viewNamespace` | 全局 viewer 可浏览任意命名空间的本体树 |
| `/browse/ontology/instances` | GET | `viewNamespace` | 同上，含实例 |
| `/answer/quality` | GET | `query` | 全局 viewer 可读任意命名空间的质量结果 |

说明：`POST /namespaces/{namespaceId}/answerable` 路径里有 namespace 段，**不属于**
本缺口；它按命名空间授权，正常收紧。上述 6 条的限制是：全局 viewer 无法被限制在
单个命名空间；只拥有某个命名空间角色的用户反而读不到（因为不是全局角色）。

### 可能的两种解法（本轮不改）

**方案 A：路径补 namespace 段**

- 形态：新增 `/namespaces/{namespaceId}/entities/{entityId}`、
  `/namespaces/{namespaceId}/metrics/{metricId}` 等，或把全局路径标记为 deprecated。
- 收益：`resource.id` 与命名空间对齐，`namespace-owner` / 命名空间级 viewer 能精确生效，
  权限模型与其余路由一致。
- 代价：Smithy 契约、生成客户端、前端调用点、MCP 与文档都要跟着改；旧路径需要兼容期
  （双写或重定向）；涉及 F 编号与契约版本，必须走契约线与生成线，不能只在鉴权线改。

**方案 B：保持全局，明确标注为跨库读**

- 形态：不改路径，为这几类读定义专用的全局 action（如 `readGlobalEntity`、
  `readGlobalMetric`），只授予明确需要跨命名空间读的角色，并在文档与策略里标注
  「跨命名空间读」。
- 收益：不动契约与客户端，改动面最小。
- 代价：授权粒度仍是全局；任何持有该 action 的角色都能读所有命名空间，无法按命名空间
  收敛；需要新增 action 与策略，且必须配文档说明，否则容易被误当成普通读权限。

两条路都需要契约/生成线配合，**本轮只记录选项与代价，不实施**。

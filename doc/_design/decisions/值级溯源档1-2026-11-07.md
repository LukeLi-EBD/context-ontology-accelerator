## 2. 标记还是删除：为什么是「只标记」

1. **先例与规范一致**：`platform.ontology_orphan_mark`（V38）已经把「历史行永不删除、旁路只增标记」定成了本仓的行事方式；`source_ref_registry` 是审计存储，删行等于销毁「这条引用曾经发给过谁」的证据。
2. **删除会把 STALE 变成 NOT_FOUND，语义倒退**：`source_ref.resolve()` 靠「registry 有行、活表查不到」判定 `E_SOURCE_REF_STALE`；删掉 registry 行后同一个 ref 会变成 `E_SOURCE_REF_NOT_FOUND`（"从未存在"），比"发放过但目标没了"更难解释。
3. **回退成本**：标记可单条撤销（`active=true`），删除不可逆。

放弃的方案及理由：

| 方案 | 为什么不用 |
| --- | --- |
| 给 `source_ref_registry` 加 `status` 列 | 需 ALTER 既有表；本轮边界禁止跑迁移，且改既有审计表结构风险高于新建旁路表 |
| 改 `locator` jsonb 塞失效标记 | 会污染审计记录本身，解析器与外部消费者都可能误读 |
| 物理 DELETE 144 行 | 见上 1/2 |

## 4. 断链检测怎么用

```powershell
# 默认查 8080（agent-platform-postgres / platform）
powershell -ExecutionPolicy Bypass -File platform/scripts/source-ref-health.ps1

# 列出全部未标记断链明细
powershell -ExecutionPolicy Bypass -File platform/scripts/source-ref-health.ps1 -Detail

# 指向另一台栈（例：验收栈，只读）
powershell -ExecutionPolicy Bypass -File platform/scripts/source-ref-health.ps1 -Container platform-acceptance-postgres
```

输出字段：`observation_refs_total / live / stale_total / stale_marked / stale_unmarked / freshness_raw / freshness_active / mark_cause[...]`。
退出码：**0 = 无未标记断链**（PASS）、**1 = 存在未标记断链**（FAIL，逐条列出 ref）、**2 = 执行失败**（psql 报错）。

检测口径与 `platform/src/platform_core/source_ref.py` 的解析器逐字段对齐：

- `obs` → `(metric_id, definition_version, entity_key, window_start, window_end)` 精确命中；
- `obs-set` → `asOf` 命中 `as_of`，或 `periodStart/periodEnd` 覆盖 `window_start/window_end`，再叠加可选 `entityKey / institution / fixture`；
- `doc` / `fact` / `computation` 不在此检测范围（`doc` 与 `fact` 是自证活表查询，`computation` 是自指记录）。

**为什么是脚本而不是端点或 pytest**：本轮边界禁止重建镜像与重启容器，新增 FastAPI 路由（T7 的 `/provenance/coverage`）在现网镜像里**不会生效**；pytest 用例走 `metadata.migrate()`，只能看到迁移登记过的对象，而标记表刻意未登记迁移（§5.4）。脚本是唯一「现在就能在 8080 上跑、且结果立刻可信」的形态。

## 7. 残留与已知风险（不隐瞒）

1. **`FIN-INS-017` 仍 0 引用**：定义四元组缺 `denominator_agg`，`/output?compute=true` 拒绝出数（`E_METRIC_EVIDENCE_MISSING`）。这是**定义缺口**，不是调用缺口；doc 75 把 T9 定为「一次 `/output` 调用即解决」的结论在本库不成立。补齐须走口径变更流程。
2. **标记表未登记为迁移**：`platform.source_ref_stale_mark` 是用直接 DDL 建在 8080 的（本轮禁止跑迁移，且 SQL 目录按既有约定只允许存在 V42）。风险：**按迁移重建 8080 时该表会消失，标记随之丢失**。下个迁移窗口应以 **V43** 入库（DDL 见附录 A），在此之前重建栈须重新执行 `mark_stale.sql`。
3. **一条 ref 用了大写 `fixture=True`**：`src://obs-set/FIN-BANK-035@v3.0?fixture=True&…`，与 `_canonical_query` 的 `true/false` 不一致，说明历史上有一处发放路径直接 `str(bool)`。它本身已失效并被标记，本轮**不修**（改需动 ref 规范与代码）。登记为待查项。
4. **`stale_marked` 未进入解析器**：`source_ref.resolve()` 仍会对已标记 ref 返回 `E_SOURCE_REF_STALE`（这是刻意的——标记不改变解析语义，只用于读侧统计与告警）。若要让前端区分「失效且已归档」与「失效未处置」，需读侧接入标记表，属后续档。
5. **新鲜度有两个数字**：raw 61.19% 与 active 100.00%。对外只能报 active 并同时披露 144 条已标记失效，**不得只报 100%**（那等于把分母洗掉）。

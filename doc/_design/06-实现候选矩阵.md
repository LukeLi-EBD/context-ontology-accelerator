## 0. 结论摘要

| # | 结论 | 一句话理由 |
|---|---|---|
| 1 | **主候选 = C（混合容器）：Oxigraph 容器 + `reasoner`（ROBOT/ELK/HermiT）容器 + Python 平台 + PG** | RDF 原生、SPARQL 全量、OWL 可插拔，同时保留单机 compose |
| 2 | **备选 = A（纯 Python 进程内）** | 零容器、最易分发；代价是 OWL DL 依赖 owlready2 拉 JVM（待实测） |
| 3 | **B（JVM 正统 Fuseki）只在“全 JVM 团队”时选** | 生态完整但两套世界（JVM + Python），运维更重 |
| 4 | **D（极简 dev）不是产品形态** | 只用于 demo/测试，无推理无 embedding |
| 5 | **切换成本低**：端口不变，只换 compose profile + 配置 | 这是端口契约设计的目的 |
| 6 | **Neo4j/Neptune 只在明确判据下引入**（§4） | 不是为了“以后可能”，而是有基准与增长曲线 |
| 7 | **LLM 默认外部 OpenAI 兼容 API；本地模型仅 profile** | 默认形态无 GPU/无模型盘（§2.5） |

## 1. 四套候选

### 1.1 A：纯 Python 进程内

```yaml
组件: pyoxigraph（进程内）+ rdflib + pySHACL + morph-kgc
       + owlready2（内嵌 HermiT）+ FastAPI + PostgreSQL + pgvector
容器: platform + postgres（2 个；图在 platform 进程内）
```

| 项 | 说明 |
|---|---|
| 适合谁 | 单人/小团队、要 pip 安装或单文件分发、Python 栈 |
| 优点 | 依赖最少；调试最简单；无跨容器网络 |
| 代价 | 图库与内核同生命周期；**OWL DL 依赖 owlready2 拉起 JVM（稳定性/内存待实测）**；大图进程内存压力大 |
| 结论 | **备选/轻量模式**；DL 需求弱或可接受外部容器时首选 |

### 1.2 B：JVM 正统

```yaml
组件: Apache Jena Fuseki（TDB2）+ Jena reasoner（RDFS/OWL mini）
       + Jena SHACL + HermiT/ELK（Jena 集成）+ Python 应用侧 + pgvector
容器: fuseki + postgres + platform（3 个起）
```

| 项 | 说明 |
|---|---|
| 适合谁 | 团队已有 Java/Jena 经验；需要 Jena 生态（TDB2、Fuseki UI、SHACL） |
| 优点 | SPARQL 1.1 与 GSP 成熟；推理器集成在同一 JVM；单一图栈 |
| 代价 | 两套语言栈（JVM + Python）；Fuseki 配置/调优知识门槛；R2RML 需额外组件 |
| 结论 | **仅在全 JVM 团队时选**；否则不作为主候选 |

### 1.3 C：混合容器（推荐）

```yaml
组件: oxigraph 容器（SPARQL 1.1 HTTP）
       + reasoner 容器（ROBOT / ELK / HermiT / Konclude）
       + platform（Python：rdflib/pySHACL/morph-kgc）
       + postgres（pgvector + FTS）
容器: platform + postgres + oxigraph + reasoner + embedding（lean 3 / learn 5）
```

| 项 | 说明 |
|---|---|
| 适合谁 | 默认目标用户：单机、要 RDF 原生 + 可选 OWL DL、要可视调试 |
| 优点 | 图库可独立重启/备份；推理按 profile 起停；Python 生态做业务 |
| 代价 | 比 A 多一个（或两个）容器；需管理 HTTP 端点与健康检查 |
| 结论 | **主候选** |

### 1.4 D：极简 dev

```yaml
组件: pyoxigraph（内存或文件）+ FastAPI
容器: 1（platform）；无 PG（SQLite 仅测试）/无推理/无 embedding
可选: 本地 BGE 进程（只读调用）
```

| 项 | 说明 |
|---|---|
| 适合谁 | demo、教学、CI、离线单文件试用 |
| 优点 | 一条命令起；零外部依赖；启动秒级 |
| 代价 | 无事务元数据、无推理、无语义检索；**不是生产形态** |
| 结论 | **仅 dev/demo** |

### 2.1 元数据存储候选（结论：不换库）

| 候选 | PG 协议 | 开源/单机 | 内存模型 | 结论 |
|---|---|---|---|---|
| **PostgreSQL 18（默认，≥18.6）** | ✅ | ✅ | page cache + 磁盘 | **保留**；几 GB 元数据场景足够 |
| PG + tmpfs/RAM disk + `unlogged` | ✅ | ✅ | 文件系统在内存 | 仅可重建数据；**权威数据红线禁用** |
| Hologres | ✅ | ❌ 云/商业 | 内存+列存 | 不适合（不能单机自部署） |
| SingleStore | △ MySQL 为主 | ❌ 商业 | 行存内存+列存 | 不适合（非开源/非 PG 原生） |
| CockroachDB / YugabyteDB | ✅ | △ / ✅ | 磁盘优先（LSM） | 不适合（分布式、单机更重） |
| DuckDB | ❌ 服务端 | ✅ | 列存 | 不适合（单写者、分析型） |
| Apache Ignite / Redis | ❌ | ✅ | 纯内存 | 只能做缓存，不能当权威元数据 |

**结论：没有同时满足“PG 协议 + 纯内存 + 成熟开源 + 单机自部署”的产品；不换库，只做参数调优（见 03 §3.7）。**

### 2.2 对象存储候选

| 能力 | `fs`（默认） | `pg`（可选） | `silo`（P1） | `S3`（未来） |
|---|---|---|---|---|
| Range 读 | ✅ | △（仅 LO） | ✅ | ✅ |
| 流式 | ✅ | △（仅 LO） | ✅ | ✅ |
| 去重 | ✅（CAS） | ✅（`content_hash UNIQUE`） | △（需索引表） | △ |
| 与元数据同事务 | ❌ | ✅ | ❌ | ❌ |
| 预签名 | ❌ | ❌ | ✅ | ✅ |
| 版本化 | △（CAS 近似） | ✅（版本表） | ✅ | ✅ |
| 外部 S3 消费者 | ❌ | ❌ | ✅ | ✅ |
| 容器数影响 | 0 | 0（少一个数据目录） | +1 | 0（外部） |

**结论：默认 `fs`；PG 只接小工件；Silo 仅在需要 S3 API/预签名/版本化时启用；S3 仅作为未来远端实现。**

### 2.3 文档解析候选

| 能力 | 单机推荐组合（pypdfium2 + pdfplumber + MarkItDown） | Tika（fallback CLI） | COA 对照（unstructured + Textract） |
|---|---|---|---|
| PDF 文字层 | ✅（pypdfium2） | ✅（PDFBox，中文 CID 乱码概率高） | ✅（pdfminer，fast 模式） |
| 表格 | ✅（pdfplumber） | △ | ✅（Textract TABLES，云依赖） |
| DOCX/PPTX/XLSX | ✅（MarkItDown） | ✅ | △（仅 docx） |
| HTML | ✅（MarkItDown） | ✅ | ❌ 不支持 |
| 扫描件 OCR | △（默认关闭，`--profile parse` + `ocr.enabled=true`） | ✅ | ✅（Textract，云依赖） |
| 常驻成本 | 低（纯库） | 高（1–2 GB JVM、5–15 s 冷启动） | 依赖外部服务 |
| 许可 | Apache/MIT | Apache-2.0 | — |

**结论：** 主链路用 pypdfium2 + pdfplumber + MarkItDown；OCR 默认关闭；Tika 只做冷门格式的一次性 CLI；**避开 PyMuPDF（AGPL）**。COA 的 Textract 链路可作对照，但依赖外部服务，需进白名单（见 03 §3.4.7、§9）。

### 2.4 PG 能不能承担图存储（摘要）

| 维度 | Oxigraph | PG+AGE | PG+CTE |
|---|---|---|---|
| 属性图遍历 | 高 | 中 | 中 |
| RDF 保真 | 高 | 低 | 低 |
| SPARQL 1.1 | 高 | 低 | 低 |
| GSP/named graph | 中（named graph 有；GSP 未核实、契约不启用） | 低 | 低 |
| OWL DL 前置 | 高 | 低 | 低 |
| 生态工具 | 高 | 低 | 低 |

**结论：** 用 PG 承担图 = 放弃 SPARQL/OWL 与 COA 兼容性；`graph.provider=age` 仅作 P2 降级（`sparql=false, gsp=false, owl=false`）。详见 03 §5.6。

### 2.5 LLM 与 Embedding 候选

| 候选 | 协议 | 单机自部署 | 默认 | 工具调用 | 结论 |
|---|---|---|---|---|---|
| **外部 OpenAI 兼容 API**（DeepSeek / 火山方舟 coding plan / OpenAI / vLLM 网关） | OpenAI Chat Completions | 无需（远程） | ✅ **默认**（`llm.provider=openai_compatible`） | 支持（按厂商实测） | 零 GPU、零模型盘；数据出机需白名单 |
| Anthropic 原生 | Messages API | 无需 | 否 | `input_schema` 需 adapter | 有兼容网关时统走兼容端点 |
| Ollama（本地） | OpenAI 兼容 `/v1` | ✅ | 否（`--profile local-llm`） | 视模型，多数需提示词模拟 | 离线/无外网时启用 |
| vLLM / llama.cpp server | OpenAI 兼容 | ✅ | 否（profile） | 视模型 | 有 GPU 时可选 |
| 远程 embedding API | `/v1/embeddings` | 无需 | 仅显式 `provider=openai_compatible` | — | 文本出机；第二个 key/维度漂移 |
| 本地 BGE-M3（独立小服务） | 本地 HTTP | ✅ | **默认 `provider=local-bge`** | — | 1024 维；离线可用；模型盘 2.3 GB |

**结论：** 默认 **本地 BGE-M3**（`local-bge`，1024 维）；LLM 默认外部 API + 无 GPU；本地 LLM 只作 `local-llm` 可选 profile。旧 `auto`（外部优先）**已取消**（见 03 §3.5、D11）。

## 4. 何时必须换 Neo4j / Neptune / 其他图库

| 触发条件 | 判断依据 | 建议 |
|---|---|---|
| 三元组 > 1000 万且复杂查询频繁 | 有基准：P95 延迟超 SLA | 先 Oxigraph 调优（内存/预计算/限流）；仍不够再评估 **Neo4j（自托管）** 或 **Neptune Analytics**（若已上 AWS） |
| 需要 PageRank/社区发现/Louvain | 产品明确要求图算法 | 导出到 NetworkX/GDS；或 Neptune Analytics |
| 需要多机高可用/读写分离 | 有可用性要求 | Neptune（托管）或 Neo4j 集群；Oxigraph 单机不承诺 |
| 需要原生向量 + 图混合的超大规模 | 亿级向量 + 深图 | Neptune Analytics / Neo4j + 向量索引；本项目 P2 |
| 需要完整 RDF 保真 **且** 托管 | 合规/运维约束 | Neptune（唯一同时满足）；但**放弃单机自足** |

**硬约束：**

1. **Neptune 出局**：只能托管，违背“单机优先”；除非未来整体上 AWS。
2. **Neo4j 不是 RDF 原生**：n10s 映射为 LPG 会丢 named graph / blank node 语义；只能作为“外部图算法/向量服务”，不能当本体权威。
3. **换库不改端口**：`GraphStore` 的 SPARQL-first 契约保留；换库即新增适配器 + 迁移作业。

**Oxigraph 规模口径（估算，需基准）：**

| 三元组 | 预期 | 行动 |
|---|---|---|
| ≤ 100 万 | 舒适 | 默认配置 |
| 100 万–1000 万 | 可用，需调优 | 加内存、限流、预计算闭包 |
| > 1000 万 | 不承诺 | 基准 + 评估外部图库（P2） |

## 5. 推荐与切换

| 项 | 结论 |
|---|---|
| **主候选** | **C**（Oxigraph 容器 + platform + PG；`reasoner`/`embedding` learn 档常驻） |
| **备选** | **A**（纯 Python；DL 弱或可外部化时） |
| **不推荐默认** | B（双栈重）、D（非生产） |
| **切换成本** | **低**：改 `graph.provider`（`oxigraph-http` ↔ `pyoxigraph`/`pyoxigraph-memory`）、改 compose profile、改 `reasoning.engine`；业务代码不变 |
| **切换前提** | 端口契约与模板（T1–T8）保持不变；契约测试覆盖两种实现 |

**一句话：** 单机不是“一个实现”，而是“一组可换实现 + 同一组端口”。C 是默认装法，A 是轻装法，B 是 JVM 团队装法，D 是试用装法。

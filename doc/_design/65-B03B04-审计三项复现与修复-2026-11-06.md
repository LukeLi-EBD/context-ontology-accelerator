## 1. 实体页超时（B-03）

### 复现（改前）

真实 IRI：`urn:platform:synthetic/investment_InvestmentObjective-00175`

```
GET /ui/api/entity?iri=urn:platform:synthetic/investment_InvestmentObjective-00175
run=1 timeout  (客户端 30s 未返回；审计报告为 15s)
run=2 timeout
run=3 timeout
```

直连 Oxigraph 执行同形状 SPARQL：`>25s` 未返回，即服务端本身挂起，不是前端或网关超时。

### 根因

`entity_view._triples_query` 使用：

```sparql
VALUES ?g { <...> } GRAPH ?g { { BIND(<iri> AS ?s) ?s ?p ?o } UNION { ?s ?p <iri> } }
```

与已修复的 `webui.neighbors` 504（`a4d493e` / `6ca8561`，E-01）为**同一根因**：Oxigraph 对「变量图 + UNION」挂起。该形状此前只从 `webui.neighbors` 移除，`entity_view` 漏改。

### 修法

改为两条普通一跳查询，不再生成 UNION：

```sparql
# 出边
SELECT ?g ?s ?p ?o WHERE { VALUES ?g { ... } GRAPH ?g { BIND(<iri> AS ?s) ?s ?p ?o } } LIMIT 200
# 入边
SELECT ?g ?s ?p ?o WHERE { VALUES ?g { ... } GRAPH ?g { BIND(<iri> AS ?o) ?s ?p ?o } } LIMIT 200
```

`entity_detail` 分别执行后合并，并按 `(graph,s,p,o)` 去重（自环会同时命中两侧）。推理图沿用同样的两条查询。

### 修后实测（重建镜像后）

```
run=1 status=200 ms=135
run=2 status=200 ms=32
run=3 status=200 ms=29
```

响应体正常包含 `classes[].chain`、`properties[]`、`neighbors.nodes/edges`；`label=InvestmentObjective-00175`。页面 `/ui/entity.html?iri=...` 由该端点供数，修后返回正常。

## 3. `orphanInstances` SPARQL 400（B-04）

### 复现（改前）

`GET /health/dashboard` 返回：

```
orphanInstances.error = "error at 1:318: expected one of ... "
```

直接执行 healthboard 生成的原文，Oxigraph 返回 HTTP 400（同一 1:318 位置）。

### 根因

查询由 Python f-string 拼接，闭合 `FILTER NOT EXISTS` 组需要两个字面量 `}`，但源码写作 `}}`；f-string 中 `}}` 只产生一个 `}`，导致内层 `GRAPH ?g2` 关闭后 `FILTER NOT EXISTS {` 未关闭，语法树在位置 318 处报错。与 Oxigraph 版本无关。

### 修法

将该处 `}}` 改为 `}}}}`（产出两个字面量 `}`）。生成的查询随即为合法 SPARQL，语义与其他查询保持一致，未改动任何过滤条件。

### 修后实测

```
orphanInstances.count = 0
orphanInstances.error = ""
```

在 `abox:synthetic` 上直接执行修正后的查询：0.9s 返回 `0`，印证该图中所有带类型实例都有边。

## 7. 推理链是否处理过 A-Box：实测（2026-11-06 追加）

### 7.1 三组数字

请求级参数 `POST /reasoning/materialize {"profile":"EL","force":true,"aboxGraphs":[...]}`，未改配置、未改引擎默认值。

| 输入 | 结果 | 耗时 | 明细 |
| --- | --- | --- | --- |
| 空 A-Box（`abox:main`，0 三元组） | **1,171** 条推断 | 3,165ms | RDFS 253（1,009ms）+ OWL/EL 918（2,071ms）；SHACL 跳过 |
| `abox:synthetic`（304,919 三元组 / 60,525 实例） | **无输出，413 拒绝** | 46,114ms | `E_REASONING_INPUT_TOO_LARGE`：**stage-2 组装输入** 67,459,727 bytes > `reasoning.max_input_bytes=52,428,800`；未进入 ELK。该值 = T-Box 549,219 + A-Box 导出 41,755,655 + 分隔符 1 + 去重闭包差 25,154,852（拆解见 12.3） |
| 库中当前那份（验收开始时） | **等同空 A-Box** | — | 1,171 条、494 个空白节点；`inferred_pointer.inputHash=927a80f2…` 与空 A-Box 运行的 inputHash **完全一致** |

结论：
- **当前 `urn:platform:inferred:ont-11f92ebb3326` 的 1,171 条全部由 T-Box 公理推出，没有任何 A-Box 派生。** inputHash 相等是决定性证据（推理输入字节完全相同）。
- 全量 A-Box 物化在当前限额下**连提交都做不到**：stage-2 组装输入 64.3MiB 超过 50MiB 上限，46 秒后 413，ELK 从未收到数据。注意闸门比的是**组装后**的输入（T-Box + A-Box + 去重闭包差），不是 A-Box 原始导出（39.8MiB，本身低于上限）。

### 7.2 物化预算

- 全量 ELK 耗时/峰值内存：**无法给出**。平台在进入 ROBOT/ELK 前就 413 拒绝；要测必须把 `reasoning.max_input_bytes` 调高（属配置修改，按约束未做），不能编造数字。
  - **2026-11-07 更新**：已获授权用一次性容器单独实测。第 9 节喂未去重全闭包（上界，36s / 1.89GiB）；12.5 用精确 stage-2 payload 复测（32s / 1.25GiB / 输出 607,416 三元组）。本节保留当时的平台侧观测。
- 仅组装输入的代价：API 容器峰值 **1,798MiB**（导出并拼接 304,919 三元组）；reasoner 峰值 284MiB（该样本不含本次数据）。

### 7.3 一致性门禁的“空过”影响范围

- 代码：`ontology_pg.py:2559-2602` `_gate_consistency(include_abox=True)` 会导出 `self._abox_graphs`；`publish` 的两个调用点（`2721`、`2778`）均使用默认 `include_abox=True`。
- 本部署 `reasoning.abox_graphs=[abox:main]`，`abox:main` 实测 **0 三元组**。
- 证据库统计：**1,187 条 publish 事件、990 个版本**带有 `gates.consistency={profile: EL, consistent: true}`（时间跨 2026-11-05 05:47 至 2026-11-06 23:49）；其中 **0 条**记录 A-Box 图名或三元组数。
- 当前 13 个 `status=published` 版本的最新发布事件全部为 `{EL, consistent: true}`，同样无 A-Box 证据。
- 影响定性：这些一致性结论**对 T-Box 公理可满足性有效**（ROBOT 仍会检出 T-Box 内不可满足类），但**对 A-Box 数据冲突是空过**——门禁实际只看到 T-Box。由于证据包不记录本次校验用了哪些 A-Box 图、各多少三元组，事后无法区分“带真实数据校验通过”与“空 A-Box 空过”。因此不能把这些 `consistent: true` 当作“真实实例数据一致”的证据。
- 限制：历史版本的配置取值未留痕，无法逐版本还原当时的 `abox_graphs`；只能确定当前部署与本次可观测窗口内该值为 `abox:main`（空）。

## 8. 一致性门禁证据补齐（2026-11-07）

### 8.1 改了什么

`OntologyRegistry._gate_consistency`（`platform/src/platform_core/adapters/ontology_pg.py`）在调用 reasoner 前先把**实际送检输入**算出来，并随 `gates.consistency` 一起写进证据包：

| 字段 | 含义 |
| --- | --- |
| `aboxGraphs` | 本次校验使用的 A-Box 图 IRI 列表；`include_abox=False` 时为 `[]`（显式空，不是缺省） |
| `aboxGraphTriples` | 每个图的三元组数（按实际导出的 N-Triples 行计数） |
| `aboxTriples` | A-Box 总三元组数 |
| `tboxTriples` | T-Box 三元组数 |
| `emptyAbox` | `aboxTriples == 0` |
| `aboxGraphsUnavailable` | 配置了但读不出来的图及错误码；**不当作空图**，不计入 0 |
| `inputHash` | `sha256(tbox_nt + 0x00 + abox_nt)`，即送检字节的指纹 |

覆盖范围：
- `publish` 的两个门禁调用点（implicit / governed）都走同一函数，自动带证据；
- 导入校验走 `include_abox=False`，会明确写 `aboxGraphs: []` + `emptyAbox: true`；
- 门禁**失败**时，`PortError.details.input` 同样携带上述证据，失败证据不会丢输入。

用例：`platform/tests/test_o04_evidence.py` 新增 `ConsistencyGateEvidenceTests` 4 例（真实数据 / 显式空 / 图不可读 / 失败保留证据），该文件 12 例全部通过。

### 8.2 真实 publish 验证

为验证“新发布能否自证看到了多少数据”，在运行平台上做了一次真实发布（未改配置）：

1. 部署探针命名空间 `urn:audit:gateprobe` 的 SHACL（`sv-e29fd6e41632`）；
2. 导入 5 三元组探针 T-Box（`imp-e34387c39d06`）；
3. 发布 `ont-feec3aea707e`（`acknowledgeBreaking=true`，随后立即回滚）。

发布返回与证据包落库的 `gates.consistency`（逐字）：

```json

 "aboxGraphTriples": {"urn:platform:graph:abox:main": 0},
 "aboxTriples": 0, "tboxTriples": 5, "emptyAbox": true,
 "aboxGraphsUnavailable": [],
```

## 9. 受控 ELK 物化实测（2026-11-07 00:07–00:08）

### 9.3 结论

**可承受。** 预算数字：

- ELK 在 304,919 条 A-Box 三元组上 **36s** 完成，峰值 **1.89GiB**（`-Xmx2g`），远低于 reasoner 容器 4GiB 上限；
- 加 RDFS 闭包与格式转换，全链 **46s**，低于服务端 `reasoning.timeout_ms=300000`；
- 真正的限制不在 ELK，而在平台提交前的 `reasoning.max_input_bytes=52,428,800`：2026-11-06 23:50 的失败 job（`rsn-70ae8ee5c4b6`）测的是 **stage-2 组装输入 67,459,727 bytes**（T-Box + A-Box + 去重闭包差），46s 后 413；`abox:synthetic` 的原始导出是 41,755,655 bytes（39.8MiB），它不是被拒绝的那个量。**413 是确定性的门槛，由固定导出 + 闭包增量的组装结果决定，不是“数据内容浮动”，也不是引擎能力上限**（完整复核见第 12 节）。

未测：闭包差集在 API 进程内的内存峰值（`_closure_diff` 对 114 万行的集合运算），以及 4GiB 上限下“闭包 JSON + ELK”叠加的最坏情况；本次顺序执行下未触及。

## 10. 结论：推理只覆盖 T-Box，A-Box 从未参与（供产品文档引用）

### 10.1 决定性证据

- 空 A-Box 物化输出 **1,171** 条推断，`inputHash=927a80f2d932ec74f36c95c8f9544d2f77cbc07650938049a0bc17bc1612d8fd`；
- 库中当前推断图指针的 `input_hash` 与之**逐字节相同**，推断条数同为 1,171；
- `inputHash` 是送检字节的 `sha256(tbox + 0x00 + abox)`，相等即**输入完全相同**。因此当前推断图 100% 由 T-Box 公理推出，**没有任何一条来自 A-Box**。

### 10.2 门禁空过的范围

- 2026-11-05 05:47 至 2026-11-06 23:49：**1,187 条 publish 事件 / 990 个版本**带 `gates.consistency={EL, consistent:true}`，其中 **0 条**记录校验用了哪些图、多少三元组；
- 当前 13 个 published 版本的最新发布事件同样如此；
- 这些 `consistent:true` 只对 **T-Box 可满足性**有效，对 **A-Box 数据冲突是空过**；
- 2026-11-07 起的新发布已能自证输入（第 8 节），但历史事件无法回溯。

### 10.3 字节数与门槛

- 2026-11-06 实测：**stage-2 组装输入 67,459,727 bytes（64.3MiB）** > 上限 52,428,800（50MiB），**46,114ms 后 413**，ELK 未执行；
- 该 67,459,727 由 `T-Box 549,219 + A-Box 导出 41,755,655 + 分隔符 1 + 去重闭包差 25,154,852` 精确组成；A-Box 导出本身 41,755,655 bytes（39.8MiB）从未超过上限。两个数字测的是不同量，**不存在“同一份数据这次能过、下次过不了”的浮动**（见 12.3、12.4）；
- 同一数据重跑会**确定性 413**（导出字节可复现、input_hash 一致）；
- 门槛之上 ELK 本身可承受（第 9 节 36s / 1.89GiB；精确 payload 见 12.5：32s / 1.25GiB）。

### 10.4 对外能说什么、不能说什么

**能说：**
- T-Box 一致性门禁在该窗口内通过（ROBOT/ELK 对 T-Box 可满足性有效）；
- 当前推断图（1,171 条）全部由 T-Box 公理推出，可复现（inputHash 一致）；
- A-Box 数据可浏览、可计数（`abox:synthetic`，60,525 实例），看板/实体页读取已修复；
- 受控实测证明 ELK 可处理 304,919 条 A-Box（32–36s、峰值 1.25–1.89GiB）；当前 413 的成因是 stage-2 组装输入（67.46MB）超过 `max_input_bytes`（50MiB），不是引擎能力上限（第 12 节）。

**不能说：**
- 不能说“A-Box 数据已通过一致性校验”——门禁从未把业务 A-Box 送进 reasoner；
- 不能说“实例级推理已生效”——推断图中没有 A-Box 派生三元组；
- 不能说“物化覆盖了业务数据”——物化只覆盖 T-Box；
- 不能把历史 `consistent:true` 当作“真实实例数据一致”的证据。

## 12. 导出稳定性与 413 归因复核（2026-11-07）

针对“同一图两次导出字节数差 25,703,072（38%），三元组数却都是 304,919，所以门槛随数据内容浮动”的质疑，本节逐项给证据。结论先行：**导出是确定性的，413 也是确定性的；67,459,727 与 41,755,655 测的不是同一个量。** 因此不需要“让导出稳定”（它已经稳定），需要决定的是门槛语义。

### 12.1 两次的序列化格式与参数

- 平台只有一条导出路径：`OxigraphHttpStore.export_graph` 固定 `Accept: application/n-triples`（自 `4d1cf87` 起未变）；`POST /reasoning/materialize` 的请求参数只有 `profile` / `force` / `aboxGraphs`，没有格式、前缀或 pretty-print 参数。
- 2026-11-06 23:50 的失败 job（`rsn-70ae8ee5c4b6`）与今天的复核走同一函数、同一参数。N-Triples 本身没有前缀声明、没有 pretty-print、没有缩进，不存在“前缀/排版导致体积变化”的机制。
- 决定性证据不是“三元组数相同”，而是**输入哈希相同**：该 job 的 `input_hash=eb6f7ed8af40e1051099d1337a681e7b338563837ee48f3bbfaf98a72cd507e4`；用今天的 `tbox.nt` + `abox.nt` 按 `_input_hash` 公式（`sha256(tbox + "\n--abox--\n" + abox + "\n--materialize:EL:robot--\n")`）重算，结果逐位相同。推理输入字节完全相同，格式与参数自然相同。
- 对照实验（同一图、同一时刻）：`Accept: application/n-triples` 得 41,755,655 bytes；`Accept: text/turtle` 得 26,546,740 bytes，且该 Turtle 输出不含任何 `@prefix`。这证明格式确实会显著改变字节数——正因如此，平台把导出格式钉死在 N-Triples 是必要的；当前没有格式漂移。

### 12.2 304,919 的来源（是否截断）

两条独立口径一致：

| 口径 | 结果 |
| --- | --- |
| SPARQL `SELECT (COUNT(*))`（`GRAPH <urn:platform:graph:abox:synthetic>`） | 304,919，`truncated=false` |
| 导出文件行数 / 去重后行数 | 304,919 / 304,919（无重复、无空行） |

导出接口返回完整 41,755,655 bytes（HTTP 200）；413 发生在平台侧、闭包计算之后、调用 reasoner 之前，与导出是否截断无关。因此“三元组数两次都是 304,919”不是截断造成的误判。

### 12.3 两个字节数分别是什么

| 量 | 值 | 说明 |
| --- | --- | --- |
| A-Box 原始导出（N-Triples） | **41,755,655** | 304,919 行，sha256 `edfecb7c…c342` |
| T-Box 原始导出 | 549,219 | 3,625 行 |
| RDFS 闭包输出（riot） | 162,034,444 | **1,140,079 行**，rdflib 解析后仅 **481,454** 个唯一三元组（riot 输出含大量重复行） |
| 去重后的闭包差（不在源图中的三元组） | **25,154,852** | 173,163 个三元组 |
| **stage-2 组装输入** | **67,459,727** | `549,219 + 41,755,655 + 1（分隔换行）+ 25,154,852`，与失败 job 的 `error_message` 完全一致 |

即：41,755,655 是 **A-Box 导出**；67,459,727 是 **stage 2 交给 ELK 的组装输入**（T-Box + A-Box + 去重闭包差）。两者不是“同一图名的两次导出”；相差的 25,703,072 bytes = 闭包差 25,154,852 + T-Box 549,219 + 分隔符 1，不是数据漂移。

装配算术已用保留文件独立复算：`tbox.nt 549,219` + `abox.nt 41,755,655` + `merged2.ttl 67,459,726`（少 1 个分隔换行）→ 闭包差 `25,154,852`；按平台公式补 1 字节即 `67,459,727`。

### 12.4 原始文件比对：同一批三元组

- 23:50 的导出是临时文件，未落盘保留；但 `input_hash` 相同已证明那次的 `tbox_nt` / `abox_nt` 与今天**逐字节相同**。
- 今天在 API 容器内直连 Oxigraph 对同一图再次导出：41,755,655 bytes、304,919 行、304,919 个唯一行、sha256 `edfecb7c6edfbf0ec95b7a11355f57ff6935dd31cb20213e6a3b73fff1cec342`，与保留文件完全一致；重复导出字节与顺序均一致（N-Triples 逐行哈希相同）。
- 谓词分布稳定：共 133 个不同谓词（`rdf:type` 60,525、`rdfs:label` 60,420、`core:hasParty` 41,715、`core:agreementId` 16,820……）。不存在“昨天多/少了某些谓词”的情况。

### 12.5 用精确 stage-2 payload 复跑 ELK

第 9 节首轮实验喂的是**未去重的全闭包**（204,339,318 bytes），属上界。这里改用平台实际会发送的精确 payload（67,459,726 bytes / 481,707 行，仅少 1 个分隔换行）在一次性容器中复跑：

| 项 | 数值 |
| --- | --- |
| 输入 | 67,459,726 bytes / 481,707 行 |
| `robot reason` 退出码 / 耗时 | `0` / **32s**（30 分钟上限未触发） |
| 输出 | **607,416** 三元组 / 68,240,499 bytes（ROBOT 写出文件）；转 N-Triples 后 607,416 行 |
| cgroup 峰值内存 | **1,342,251,008 bytes ≈ 1.25GiB** |
| 总墙钟 | 48s |

与第 9 节（36s / 1.89GiB）一致，精确 payload 反而更省。ROBOT 日志有 4 条 `owl:onDatatype` 解析告警，未影响退出码。

### 12.6 归因与处置

- **导出没有不稳定**：固定 NT、固定端点、固定参数，多次导出字节级一致；固定序列化/前缀/顺序这一项当前已满足。
- **413 是确定性的**：只要 `abox_graphs` 包含 `abox:synthetic`，stage-2 组装输入必然约 67.46MB > 52,428,800，必然 413；与“这次导出多大”无关。同一数据重跑结果可复现。
- 因此把 `max_input_bytes` 调大不是治愈手段：它只是把同一条确定性阈值线挪到更大的图上才触发，且掩盖“门槛到底在量什么”的问题。
- 真正的设计问题是**门槛语义不一致**：`max_input_bytes` 同时约束 stage 1 的源输入（42,304,874，通过）与 stage 2 的组装输入（67,459,727，拒绝），两个量含义不同。若要让 30 万级 A-Box 进入物化，应在产品/架构层面决定：把门槛显式定义为“源输入字节”，或为两段分别定义阈值，并把每段字节数与输入哈希写入 job 证据——而不是单纯调大单一阈值。本次未实施任何代码或配置改动。

# 外部算力跑自建 BGE-M3 可行性（"只借算力、不借模型"）

- 报告时间：2026-11-05（Asia/Shanghai）
- 探测方式：**只查公开文档与标价**，未申请账号、未开通付费、未上机部署、未改动任何本地配置
- 目标：确认是否存在"能跑自建 BGE-M3（1024 维、与本地同模型）且公网可达"的算力产品，使向量产出后本地直接复用、建完解耦

## 1. 一句话结论

**有。** 火山引擎「机器学习平台（MLS）在线服务 / 弹性容器实例 VCI / GPU 云服务器 ECS」、阿里云「PAI-EAS」、AWS「SageMaker / EC2 g 系列」都能把 `ghcr.io/huggingface/text-embeddings-inference` 以自建方式跑起来，并暴露公网 HTTPS 的 `/v1/embeddings`；**BGE-M3 是 XLM-RoBERTa 架构，TEI 官方明确支持**，输出正是 dense 1024 维。一次性成本在 **10 元量级**（单卡 A10 跑 1 小时内），远低于"借方舟模型"带来的耦合代价。

## 3. TEI 部署要点（技术可行性三条硬约束）

### 3.1 模型支持：开箱可用 ✅

- TEI 官方支持列表含 **XLM-RoBERTa**（BGE-M3 的底座正是 XLM-RoBERTa-large），直接 `--model-id BAAI/bge-m3` 即可。
- 输出：dense **1024** 维。**sparse / colbert 多向量不输出**——TEI 只做 dense（+ 可选 SPLADE 的 masked-LM 模型）；若现有检索链路只用了 dense 1024，则完全兼容；若用了 sparse/colbert，需要额外服务，不能靠 TEI。
- 硬件镜像必须选对：A10 属 Ampere 8.6 → `ghcr.io/huggingface/text-embeddings-inference:86-1.9`；T4 属 Turing → `turing-1.9`（实验性，FlashAttention 默认关闭）。

### 3.2 部署命令（A10 档）

```bash
docker run --gpus all -p 8080:80 \
  -v $PWD/models:/data \
  --pull always \
  ghcr.io/huggingface/text-embeddings-inference:86-1.9 \
  --model-id BAAI/bge-m3 \
  --dtype float16 \
  --api-key "$EMBED_API_KEY" \
  --max-client-batch-size 32 \
  --max-batch-tokens 16384
```

- 服务端口：镜像内默认 `80`（TEI 原生默认 `3000`，容器镜像做了映射，`-p 8080:80` 是官方示例）。
- 接口：`POST /v1/embeddings`（OpenAI 兼容，`model` 字段填 `text-embeddings-inference` 或 `--served-model-name` 指定值）；原生批量为 `POST /embed {"inputs":[...]}`。
- 健康检查：`GET /health`（TEI 自带）；另有 `GET /info` 可查模型与最大输入长度，`--prometheus-port 9000` 可出指标。
- 鉴权：`--api-key` 已够用，校验 `Authorization: Bearer <key>`，无需额外网关。

### 3.3 显存与批处理

| 项 | 数值/建议 |
|---|---|
| 权重大小 | BGE-M3 ≈ 568M 参数：**fp16 ≈ 1.1 GB，fp32 ≈ 2.3 GB**（HF 上 `pytorch_model.bin` 2.27 GB 是 fp32 落盘体积，不等于 fp16 显存占用） |
| 运行开销 | + KV/attention 与激活、CUDA context ≈ 1.5–3 GB（随 `max-batch-tokens` 与序列长变化） |
| 最小显存建议 | **≥ 8 GB 舒适**（T4 16GB / A10 24GB 均充裕）；6 GB 可跑但 `max-batch-tokens` 需下调到 8192 以内 |
| 关键参数 | `--max-client-batch-size` 默认 32（可上调）；`--max-batch-tokens` 默认 16384（显存紧则下调）；`--auto-truncate` 默认 true |
| 长文本 | BGE-M3 训练长度 8192；TEI 会按模型最大长度截断，入库侧仍应自行按 512–1024 token 切 chunk |

### 3.4 必须验证的一致性（否则"同模型"不等于"同向量"）

1. **pooling**：BGE-M3 用 **CLS pooling**；TEI 会读模型 `1_Pooling/config.json`，建议显式 `--pooling cls` 防漂移。
2. **归一化**：若本地链路对向量做 L2 normalize，TEI 侧也须一致（TEI 按 sentence-transformers 配置处理）；**必须实测**：同 20 条文本，本地与远端向量 cosine ≥ 0.999。
3. **维度**：远端 1024 = 本地 1024，**不需要 1024→2048 全量重建**，这正是"只借算力"的核心收益。

## 4. 与"方舟借模型"的对比

| 维度 | 方舟借模型（doubao-embedding-vision） | 外部算力跑 BGE-M3（本方案） |
|---|---|---|
| 模型 | 不同模型（vision 系） | **与本地完全相同（BAAI/bge-m3）** |
| 维度 | 2048 | **1024（与现有库一致）** |
| 是否需全量重建 | 需要（维度变更），旧分区保留 | **不需要**；向量可直接与本地混合/替换 |
| 建完是否可离线 | 不可，持续依赖方舟 | **可**，一次性产出后本地完全自足 |
| 持续性 | 增量入库长期依赖外部 | 增量可回退本地 CPU（慢但可用），批量再外租 |
| 成本 | 计费口径未确认（coding plan 是否含 embedding 未核实） | **10 元量级一次性**，公开标价可预算 |
| 权益风险 | 仅 1 个模型可用，plan 调整即失效 | 无，任何 GPU 都能跑 |
| 数据出网 | 每篇文档文本长期外发 | 仅批量建库期间外发 |
| 主要风险 | 计费不明、模型不可控、维度不匹配 | 运维成本（起服务、传数据、验一致性）、Spot 可能被抢占 |

## 5. 建议

1. **首选火山 MLS `ml.gni2.3xlarge`（10.09 元/h）或 VCI `gni2`（≈9.05 元/h）**：同一云、同一实名主体、公共网关免备案心智负担最低；按小时起停，跑完即释放。
2. 若要压到极限成本：阿里云 **EAS Spot（≤2.88 元/h）** 最便宜，但可能被抢占，需支持断点续跑（本项目已有 import 断点能力可复用）。
3. **本地第二台 GPU 机器是唯一真正零边际成本路径**：如用户已有 ≥8GB 显存的机器，优先用它，连出网风险都省掉。
4. 落地前必须做完两件事：① 用 20 条样本做"本地 vs 远端"向量一致性校验；② 用 1000 chunk 子集实测吞吐，替换本报告的 100/500 chunk/s 假设。
5. **不建议**为此改动检索语义：本次只是换算力，不换模型、不换维度、不换 pooling。

## 11. 迁移器版本号行为与断档分析（只读结论）

**历史背景**：合并前 `luke` 曾为 `SUPPORTED_SCHEMA_VERSION = 34`，当时 V35（已撤回的 C2 配额分支）与 V36（空号）都不存在，因此出现过 `V34 → 37` 的断档讨论。主线随后推进到 V41，本迁移按主线口径改为 **42**；当前迁移链为 `V1–V42`，V35/V36 永久退休，升序无缺口。

### 11.1 结论

| 问题 | 结论 |
|---|---|
| 是否要求版本号连续 | **否**。迁移器按注册表执行“版本号 > 当前库版本”的条目，不校验连续性 |
| 缺号时行为 | 只执行注册表中大于当前库版本的条目，不报错、不静默跳过后续迁移 |
| 是否有 V1..VN 无空号校验 | **原本没有任何校验**；验收脚本、`/readyz`、健康看板均不检查空号。本轮已新增启动守卫 `E_DB_MIGRATION_GAP`（见 11.4） |

因此，启动不会因为号段不连续而失败。真正需要防的不是“启动失败”，而是“后续补号的迁移被静默跳过”（见 11.3）。

### 11.2 代码位置与行为

- `platform/src/platform_core/adapters/metadata_pg.py`
  - L19：`SUPPORTED_SCHEMA_VERSION = 42`（本分支已提升）。
  - L21–L64：`MIGRATIONS` 注册表，37–42 依次追加在 V34 之后。
  - L193–L198：`current = MAX(version)`，即当前库版本。
  - L199–L211：仅当 `current > SUPPORTED_SCHEMA_VERSION` 时报 `E_DB_MIGRATION_MISMATCH`（防降级）；`current < SUPPORTED` 不报错。
  - L212–L213：`for version, ... in MIGRATIONS: if version <= current: continue`，只按“大于当前值”判断，**没有** `expected_next = current + 1` 之类的连续性检查。
  - L215–L225：执行 SQL 文件，并 `INSERT ... ON CONFLICT DO NOTHING` 记录该版本；执行完即完成，不要求中间号存在。
  - L187–L189：整个迁移在 `pg_advisory_xact_lock('platform:migrate')` 事务锁内执行。
- 注意一个实现细节：L193 的 `current` 只在循环前计算一次，循环内不推进。因此在一个“停在 34”的库上，注册表中所有 `> 34` 的条目都会被执行，执行顺序是 **MIGRATIONS 列表顺序**，不是版本号排序。
- `platform/src/platform_core/api.py` L1667–L1699：`/readyz` 只检查 `metadata.health()`、`graph.ask` 与存储磁盘空间，**不检查迁移版本**。
- `platform/src/platform_core/healthboard.py` L278–L287：健康看板只比较 `MAX(version)` 与 `SUPPORTED_SCHEMA_VERSION` 是否相等（`consistent`），空号不可见；本迁移后 `42 == 42`，结果为一致。
- `platform/tests/acceptance.ps1` / `acceptance-s14.ps1`：全文 grep 不到 `schema_version`、`schemaVersion`、`SUPPORTED`，不校验迁移号。
- `platform/src/platform_core/bundle.py` L907–L915：这是唯一的“精确版本相等”检查，但对象是**导入的 bundle 清单**：`manifest.schemaVersion` 必须等于代码版本，否则 `E_BUNDLE_SCHEMA_MISMATCH`。它不检查迁移空号；但意味着 schema 34 导出的 bundle 不能用 schema 42 的代码导入。

### 11.3 真正的风险：后补低号迁移会被静默跳过

`if version <= current: continue` 是单向的。假设某个环境已经通过代码迁移到 42，之后 V35（C2 复活）再合入：

- 该环境的 `current = 42`，V35 满足 `35 <= 42`，**永远不会执行，也不会有任何提示**；
- 新建库（从 0 开始）会顺序执行 V35，于是“已有环境缺 V35、新环境有 V35”，形成环境漂移。

这不是断档导致的启动问题，而是断档 + 后补号叠加后的数据/结构漂移。合并前需要确认的不是“V35/V36 是否必须存在”，而是“**V35 是否确定永久废弃**”。

### 11.4 决策与工程约束（2026-11-06，方案 C）

已决定采用方案 C：**V35、V36 永久退休，不回收、不改号。** 并把“后补低号被静默跳过”从流程风险升级为启动即报错的工程约束：

- **退休登记**：`adapters/metadata_pg.py` 在 `MIGRATIONS` 之后新增 `RETIRED_MIGRATION_VERSIONS = (35, 36)`。注释写明：35 属于已撤回的 C2 配额分支，36 从未使用；**回收号段会导致已升级环境静默跳过**（`if version <= current: continue` 是单向的）。
- **启动守卫**：`migrate()` 读取 `platform.schema_version` 的全量版本行，凡“注册表中 `version <= current`、不在退休清单、且历史表没有该行”的版本，一律抛 `E_DB_MIGRATION_GAP`；错误信息包含缺口版本号、当前版本、退休清单，以及“该迁移不会被自动执行，请人工确认”；`exit_code = EXIT_CONFIG`（启动失败，而不是静默跳过）。
- **检查顺序**：先执行既有降级检查 `E_DB_MIGRATION_MISMATCH`（`current > SUPPORTED_SCHEMA_VERSION`），再做缺口检查，因此“库版本高于代码版本”仍报 MISMATCH，语义不被新守卫覆盖。
- **无历史表时的退化检查**：`platform.schema_version` 不存在时只能拿到高水位（全新库 `current = 0`），退化规则是“注册表中 `0 < version < current` 且未退休的条目即缺口”。**能力边界**：全新库 `current = 0` 时该检查证明不了任何事，固定返回空；也就是说，退化检查只能挡住“已有高水位但没有逐版本记录”的环境，无法替代历史表。好在这种环境在同一事务内顺序执行所有 `> current` 的迁移，不产生跳过。
- **单测**：`platform/tests/test_migration_gap.py`，7 例全部通过（以假连接运行，未连库、未执行任何 DDL）：正常升序升级不触发；注册表插入低于当前的未退休版本触发 `E_DB_MIGRATION_GAP`；退休号 35/36 不触发；库版本高于代码版本仍报 `E_DB_MIGRATION_MISMATCH`；无历史表全新库返回空；退休与已应用版本被排除；注册表版本号唯一且不含退休号。
- **集成契约**：`54-并行开发与集成契约.md` §2 已加一行“号段不可回收；退休号必须登记在 `RETIRED_MIGRATION_VERSIONS`”。
- **对共享库的影响**：本轮只改代码与文档，未对共享库执行任何 DDL 或迁移（含本迁移重跑）。守卫在下次正式 `migrate()` 时才生效。

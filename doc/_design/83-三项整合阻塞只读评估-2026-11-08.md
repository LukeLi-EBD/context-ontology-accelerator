### 1.3 升级实测矩阵（2.10.4 vs 2.13.4）

在同一临时 venv（Python 3.12）里切换 pydantic 版本，`PYTHONPATH=platform/src`，直接调用 platform 代码：

| 用例 | 2.10.4 | 2.13.4 |
|---|---|---|
| `class M(BaseModel): s: str`，输入 `False` | `ValidationError` | `ValidationError` |
| `load_config(platform.example.yaml)` | 失败：`Input should be a valid string (got False)` | 失败：同左 |

关键发现（不是升级引入，而是既有问题）：`platform/platform.example.yaml:24` 的 `provider: off` 是未加引号的 YAML 标量，PyYAML 按 YAML 1.1 解析为布尔 `False`，pydantic 2.10.4 与 2.13.4 **都拒绝**。仓库示例文件因此不能原样 `load_config` 成功；实际部署配置是否写了引号，仓内无法判断（`D:\agentABC\data\platform.yaml` 属数据目录，本轮未读）。部署侧核对点：`canvas.provider` 必须是带引号的 `"off"` 或 `"simple"`/`"full"`。

FastAPI 0.115.6 的声明范围实测为：`pydantic!=1.8,!=1.8.1,!=2.0.0,!=2.0.1,!=2.1.0,<3.0.0,>=1.7.4`；`TestClient` 冒烟在 2.13.4 下通过，说明不加 `pydantic-settings` 的 pydantic 升级不会被 FastAPI 版本挡回。

- 首选：`pydantic==2.13.4`，两处（`platform/pyproject.toml:13`、`platform/requirements.txt:3`）。

- 不建议 `pydantic>=2.13.4` 无上界。

回归范围（数值来自实测计数）：

- platform 测试树：54 个文件、12,841 行。

### 1.5 相邻耦合（不属于 pydantic，但入 workspace 时必须一起决策）

### 3.2 uv 行为实测（本机 uv 0.12.7）

本机 uv 版本低于仓库要求，`uv` 在仓库根任何命令都直接拒绝：`Required uv version '>=0.13.4' does not match the running version '0.12.7'`。因此以下为临时目录内的等价探针（uv 0.12.7）：

| 探针 | 结果 |
|---|---|
| 显式 member 目录缺失、且无人依赖它，`uv lock` | 成功，缺失项被忽略 |
| 已生成锁、删除 member 目录后 `uv sync --frozen` | 失败：`Distribution not found at: file:///.../sub` |
| 依赖方写 `sub = { workspace = true }`，把 `sub` 从 members 移除后 `uv lock` | 失败：`` `sub` references a workspace in `tool.uv.sources` ... but is not a workspace member `` |

第三行与 `action.yml:6-7` 的上游报错原文一致，说明「只删 members」在本仓必然失败：4 个包用 `workspace = true` 指向 `coa-control-plane-server`。

### 3.3 两种改法对比

| 维度 | A. 条件加载（保持 members，生成前置） | B. 标为 optional（移除成员 + 依赖降级） |
|---|---|---|
| 具体做法 | 不改根 pyproject；`make setup`（已有）或从 CI/他机取回两个生成目录放入 `smithy-generated/`（gitignored） | `pyproject.toml:60-61` 删 2 行；4 个包的 `dependencies` 与 `tool.uv.sources` 各改 1 行（共 8 行）；178 行导入改为延迟导入或 optional extra |
| 仓内改动行数 | 0（可选：文档 1 行说明） | 10 行元数据 + 178 行导入 + `uv.lock` 重写（2 个 editable 块 + 4 个依赖方） |
| 对 `uv sync` 的实际效果 | 生成物不存在时失败（等价报错见 3.2）；生成物存在后按 `Makefile:5-8` / `action.yml:4-8` 的既定顺序执行 sync。成功路径未在本机等价探针复现（0.12.7 临时包缺构建后端，失败与 workspace 解析无关），仓内依据是既有 CI 流程与 `make setup` | 无生成物也能解析安装；但 control-plane/metric-service/ontology-engine/sources 在 import 生成模型时失败 |
| 单机可行性 | 需要 JDK/Gradle/pnpm（`scripts/smithy-generate.sh`）或一次性搬运生成物 | 不解决运行问题，只把失败点从安装期移到导入期 |

## 0. 结论摘要

| # | 结论 | 一句话理由 |
|---|---|---|
| 1 | **两档运行模式**：`runtime.mode=learn`（P0 默认，能力常驻且全开）/ `lean`（作业化、按需） | 用户要边用边学、随时看日志与状态；功能优先于内存节省 |
| 2 | **能力分三类运行形态**：一次性作业、间歇/定时作业、常驻服务 | 本体初始化/物化/校验本质是批处理；learn 档把它们常驻化只为便于观察 |
| 3 | **逐能力开关保留；learn 档默认全开** | `reasoning=off`、`embedding=disabled` 时仍可 CRUD + SPARQL + FTS；lean 才按需关 |
| 4 | **两档功能等价，只差常驻/按需** | 切换只改 `runtime.mode` + compose profile，不改代码、不改数据 |
| 5 | **推理主推组合：RDFS 闭包（默认）+ ELK（EL 物化）+ HermiT（DL 一致性校验）** | EL 快、DL 准；learn 档常驻、lean 档按作业启动 |
| 6 | **推理产物只写独立命名图，绝不覆盖源图** | 可回滚、可对账、可标记 stale |
| 7 | **OWL DL 必须有，但不是在线查询代理** | 物化后查询零推理开销；不物化就明示不支持 |

## 1. 生命周期与运行形态

### 1.1 三类运行形态

| 形态 | 典型任务 | 生命周期 | 是否常驻 | 资源特征 |
|---|---|---|---|---|
| **(a) 一次性作业** | T-Box 导入、R2RML/RML 实例加载、推理物化、一致性校验、embedding 全量构建、导入导出、快照/迁移 | 跑完退出；按内容哈希可重跑 | 否 | 短时高 CPU/内存，允许分钟级 |
| **(b) 间歇/定时作业** | 增量抽取、增量推理、索引重建、备份、对账、清理 | cron/触发；可重叠禁止 | 否（由调度触发短进程） | 中等，夜间窗口 |
| **(c) 常驻服务** | 查询 API、ContextResolver、在线 embedding、在线 LLM、在线推理（**仅当需要在线问答蕴含**） | 长驻；healthcheck | 是 | 稳定内存；首查低延迟 |

**关键判断：** 本体/实例本身是**一次性或间歇**的；只有“问答/检索/查询”是常驻。把推理常驻是**可选项**，不是默认。

### 1.2 每个能力一个开关

| 配置项 | 取值 | 语义 | 关闭时的降级 |
|---|---|---|---|
| `runtime.mode` | `learn` \| `lean` | 两档运行模式（§1.6）：learn=能力常驻全开；lean=作业化按需 | 只影响常驻/按需，**功能等价** |
| `ontology.init_mode` | `off` \| `once` \| `watch` | 一次性导入 / 启动时检查并导入 / 监听目录增量 | 只读已有图；不自动导入 |
| `ontology.init_source` | 路径/对象 key | 初始本体来源 | — |
| `reasoning.mode` | `off` \| `rdfs` \| `materialize` \| `on-demand` \| `validate`（默认 `materialize`；`on-demand` 枚举可读，运行时返回 `E_REASONING_ON_DEMAND_NOT_IMPLEMENTED`）<br>Q8-a 已放开枚举（见 23 号文档） | 见 §2.1 | `off`：无蕴含，仅显式三元组；`rdfs`：只做 subClassOf/subPropertyOf 闭包 |
| `reasoning.service_enabled` | bool | 是否有常驻推理服务 | learn 默认 `true`；lean `false`：只能离线批处理 |
| `reasoning.engine` | `robot` \| `hermit` 已装配；`elk` \| `konclude` 枚举可读但报 `E_PROVIDER_NOT_IMPLEMENTED`<br>Q8-a/b 已放开（见 23 号文档） | 选推理器；`robot`=ROBOT/ELK（materialize），`hermit`=ROBOT/HermiT（一致性/分类） | `elk`/`konclude`：无独立 adapter（ELK 经 robot） |
| `reasoning.schedule` | cron | 间歇物化 | 无 schedule 则只手动/事件触发 |
| `llm.provider` | `openai-compatible` \| `ark` \| `disabled`（无 `anthropic`/`local`；`llm.preset` 已由 Q8-a 落地）<br>已按代码对齐（原文档值=`openai_compatible` \| `anthropic` \| `local`） | 见 §3 | 无配置 → 抽取退规则 |
| `embedding.provider` | `local-bge` \| `openai_compatible` \| `disabled` | 默认 `local-bge`（BGE-M3/1024 维，见 03 §3.5）；取消 `auto` | `disabled`：语义检索退化 FTS |
| `embedding.service_enabled` | bool | 是否允许在线 embedding 调用 | learn 默认 `true`；lean 按需 |
| `ocr.enabled` | bool | 扫描件 OCR | 默认 `false`（D22）；关闭时无文字层文档返回 `NO_OCR_ENABLED` 告警 |
| `search.enabled` | bool | FTS/混合检索 | false：只做精确/前缀匹配 |
| `jobs.workers` | int | 本地并发（**平台当前不消费 `jobs.*`**，无 `JobsConfig`）<br>已按代码对齐（原文档值=参与调度，0 则同步执行） | 当前无效果 |

**统一规则：**

1. **learn 档默认全开**：`ontology.init_mode=watch`、`reasoning.service_enabled=true`、`embedding.service_enabled=true`、`search.enabled=true`；`lean` 档默认 `once`/`false`/按需。
2. **关闭必须显式降级**，启动日志打印 `DEGRADED` 清单（`reasoning=off` → `NO_OWL_DL`；`embedding=disabled` → `SEMANTIC_SEARCH=false`）。
3. **不允许静默降级**：响应元数据带 `degraded=true` 与原因。
4. **开关只影响能力，不影响数据**：关闭推理不删除已有推理图，只是不再更新；重新打开后按哈希重算。

### 1.3 Compose profiles 落地

```yaml
# 常驻集由 runtime.mode 决定：learn → platform+postgres+oxigraph+reasoner+embedding；lean → 前三个
# 实现：runtime.mode=learn 时 .env 写 COMPOSE_PROFILES=learn
services: [platform, postgres, oxigraph]

profiles:
  learn:     # P0 默认：reasoner + embedding 常驻（与 platform 并行，须 healthcheck）
    - reasoner
    - embedding
  init:      # 一次性：本体导入 + 实例加载 + 首次物化
    - init-job        # 跑完退出（restart: "no"）
  reasoning: # lean 档：`docker compose run --rm reasoner`
    - reasoner
  embedding: # lean 档：手动拉起本地 BGE（`docker compose --profile embedding up -d embedding`）
    - embedding
  llm:       # 旧名（保留别名）→ local-llm
    - ollama
  local-llm: # 可选、非默认：离线本地 LLM（Ollama）
    - ollama
  graph-fuseki: # 备选图后端（D25）：启 fuseki 前必须停 oxigraph；两者互斥，不得双写
    - fuseki
  silo:      # 对象存储（P1）
    - silo
  parse:     # 重型解析（含 OCR）
    - tika
  full:      # 全功能（显式开启全部可选件）
    - init-job, reasoner, embedding, ollama, silo, tika
```

> **learn（P0 默认）**：启 `learn` profile，`reasoner` 与 `embedding` 常驻，`init` 以 `once` 启动后转 `watch`；Silo/OCR 仍关闭。
> **lean（熟练后）**：不启 profile，3 容器常驻；推理/初始化用 `docker compose run --rm`，embedding 用 `--profile embedding` 按需拉起。

**启动顺序与依赖：**

```text
postgres(healthy) ─┐
oxigraph(healthy) ─┼─> init-job（一次性，成功后退出）
                   │        │
                   │        └─> reasoner（learn 档常驻；读 init 产物）
                   └─> platform（等 init-job 成功，或在 init=off 时直接起）
ollama / silo / tika：独立，platform 启动后异步可用
```

| 规则 | 说明 |
|---|---|
| `init` 必须在 `api` 前完成 | `platform` 用 `depends_on: init-job: condition: service_completed_successfully` |
| init 失败阻断 | **T-Box 缺失 → 不启动 platform（69）；schema migration 失败 → 不启动（78）**（已按代码对齐，原文档值=78/69 未区分）；实例为空 → 不阻断，标 `DEGRADED` |
| init 幂等可重跑 | 按 `version + contentHash` 跳过；重复跑不重复写 |
| init 失败不污染 | 写入独立命名图；失败则清理该 graph，保留旧版本 |
| 低频任务常驻与否 | **learn 档 reasoner 常驻（watch 自动触发）；lean 档不启 profile，用 `docker compose run --rm reasoner`** |
| 资源隔离 | 推理容器限制 `mem_limit`/`cpus`；OOM 不影响 platform |

### 1.4 作业状态与幂等

```text
表 platform.ontology_job（PG）
  id / kind(init|materialize|validate|embed|reindex|backup)
  ontology_version / input_hash
  graphs[]（涉及的命名图）
  target_graph（物化目标）
  state(queued|running|succeeded|failed|skipped)
  started_at / finished_at / attempt
  error_code / error_message
  result_summary（inferred 数、耗时）
```

| 策略 | 做法 |
|---|---|
| 幂等键 | `kind + ontology_version + input_hash + target_graph` |
| 跳过 | 同键且 `succeeded` 且输入哈希未变 → `skipped`，不重复计算 |
| 并发 | 同 `target_graph` 的单飞锁（PG advisory lock）；不同目标可并行 |
| 失败 | 清理半成品（drop/clear `target_graph`），状态记 `failed`，可重试 |
| 回滚 | 发布是“切换读指针”（当前版本 → 上一版本命名图），不是删除；旧图保留 N 个版本 |
| 观测 | 每次作业记录 `inferred/ms/peakMem`；用于后续容量判断 |

### 1.5 两种运行模式的成本差异

| 模式 | 常驻容器 | 启动时间 | 常驻内存（空载） | 首查延迟 | 适合 |
|---|---|---|---|---|---|
| **`learn`（P0 默认）** | **5**（platform+postgres+oxigraph+reasoner+embedding） | 首次：分钟级（导入+物化）；之后秒级 | 4.5–6.5 GB（含本地 BGE）；16 GB 档见 03 §16.5 | 毫秒级（已物化、已建索引） | 学习/观察平台、日常使用、演示 |
| **`lean`（熟练后）** | **3**（前三个） | 首次：分钟级；每次推理/embedding 需按需拉起（秒级冷启动） | 3–4 GB | 同左（查询不依赖 reasoner） | 资源紧张、低频批处理 |

**推荐：** P0 默认 `learn`（能力全开、便于观察）；熟悉后切 `lean`。两档功能等价，切换只改 `runtime.mode` 与 `COMPOSE_PROFILES`。

### 1.6 两档运行模式（`runtime.mode`）

| 维度 | `learn`（默认） | `lean` |
|---|---|---|
| 常驻组件 | platform + postgres + oxigraph + **reasoner** + **embedding**（本地 BGE-M3） | platform + postgres + oxigraph |
| `init` | `once` 启动导入 → 转 `watch`（监听本体变更并自动物化/校验） | `once`（手工重跑） |
| 推理 | 常驻，watch 自动触发 | `docker compose run --rm reasoner` 作业型 |
| embedding | 本地 BGE 常驻，在线可用 | 按需（本地 BGE 手动拉起；不可用时退 FTS 并标 `degraded`） |
| 能力开关 | 全开 | 按需关 |
| 功能 | **完全等价** | **完全等价** |
| 切换 | 改 `runtime.mode` + `COMPOSE_PROFILES`，不改代码/数据 | 同左 |

**启动顺序（learn）：** `postgres`+`oxigraph` healthy → `init`（once）→ `platform`；`reasoner`/embedding 可与 platform **并行**，但必须自身 healthcheck 通过才算 ready。
**阻断规则：** T-Box 缺失 → **阻断启动**（69，`E_ONTOLOGY_TBOX_MISSING`）；schema migration 失败 → **阻断启动**（78，`E_DB_MIGRATION_FAILED`）（已按代码对齐，原文档值=78/69 未区分）；实例数据为空 → **不阻断**，标 `DEGRADED`。

**推荐：** 默认“一次初始化 + 常驻 platform/PG/Oxigraph/reasoner”；`local-llm` 按需 profile；真正冷启动只作为低配模式。

## 2. OWL DL 推理架构

### 2.1 三种推理模式

| 模式 | 做法 | 查询开销 | 增量性 | 与 T-Box 变更 | 适合 |
|---|---|---|---|---|---|
| **① 物化（materialize）** | 推理器算出蕴含三元组，写入独立命名图 `urn:platform:inferred:<version>` | 零（普通 SPARQL 即可命中） | 差（多数推理器不支持增量，需重算） | T-Box 变 → 全量重物化 | 单机、低频变更、查询要快 |
| **② 查询时重写（query rewriting）** | 把查询改写成等价并集（UCQ），由引擎执行 | 中（查询膨胀） | 好（不物化） | T-Box 变 → 重写规则更新 | OWL 2 QL / 轻量本体、查询多样 |
| **③ 仅校验（validate-only）** | 只做一致性/可满足性检查，不产生新三元组 | 零 | 好 | 每次变更跑 | 治理/发布门禁 |

**推荐：** ①为主（EL/DL 都物化到命名图）、③为发布门禁；②仅在本体是 QL/轻量且不想物化时启用（P2）。

### 2.2 推理器候选对比

| 推理器 | Profile | 语言/部署 | 可进程内 | 性能量级 | License | 与 SPARQL store 耦合 | 结论 |
|---|---|---|---|---|---|---|---|
| **HermiT** | OWL 2 DL | Java；独立 JVM 容器或 CLI | 否（Python 需 JVM；owlready2 可拉起） | DL 一致性/分类慢于 EL，中等本体分钟级 | LGPL（经 owlready2 使用时注意） | 读 T-Box/ABox 文件 → 输出推断三元组文件 | **DL 一致性校验主选** |
| **ELK** | OWL 2 EL | Java；独立容器/CLI | 否 | **极快**（EL 分类秒级） | Apache-2.0 | 文件/OWL API 交换；输出推断公理 | **EL 物化主选** |
| **Konclude** | OWL 2 DL | C++；独立容器/CLI | 否 | 强（DL 优于 HermiT，部分场景显著） | 开源（需核实具体许可） | CLI/HTTP 包装 | DL 备选（HermiT 不够时） |
| **Openllet/Pellet** | OWL 2 DL | Java | 否 | 中等 | AGPL/商业双许可（需核实） | 同 HermiT | 不选（许可与维护成本） |
| **Jena 内置 reasoners** | RDFS / OWL mini / OWL micro | Java | 否（JVM 内） | 快但表达力弱 | Apache-2.0 | 与 Fuseki/TDB2 天然一体 | 仅 B 方案（JVM 栈）用 |
| **owlready2（内嵌 HermiT）** | OWL 2 DL | Python + JVM | 可（进程内拉起 JVM） | 受 JVM 启动/内存影响 | LGPL-3.0 | Python 对象 ↔ 文件/三元组 | 仅 A 方案（纯 Python）；**稳定性待实测** |
| **ROBOT** | OWL 2 DL/EL（封装 OWL API + reasoners） | Java CLI | 否 | 与所调推理器一致 | BSD-3（需核实） | 文件输入输出（ODK 工作流） | **批处理/发布工具链主选** |
| **RDFox** | Datalog/规则（可模拟部分 OWL） | C++；商用 | 否 | 极快（增量物化强） | 商业 | 自有 store + SPARQL | 不选（商用/成本）；P2 评估 |
| **Ontop** | OWL 2 QL（OBDA 重写） | Java | 否 | 查询期重写 | Apache-2.0 | 虚拟 RDF over SQL | 仅“不物化 A-Box”时评估；本项目默认物化 |

### 2.3 语义覆盖度（关键：能不能满足）

| 能力 | HermiT | ELK | Konclude | Jena(RDFS/OWL mini) | owlready2(HermiT) | ROBOT | 说明 |
|---|---|---|---|---|---|---|---|
| 类表达式（交/并/补）蕴含 | ✅ | ✅（EL 限交/存在） | ✅ | ❌ | ✅ | ✅ | EL 不支持并/补/全称 |
| 不相交性推导 | ✅ | △（EL 有限） | ✅ | ❌ | ✅ | ✅ | EL 的不相交支持需实测 |
| 等价类 | ✅ | ✅ | ✅ | △ | ✅ | ✅ | — |
| 属性链（property chain） | ✅ | △（部分支持，**待实测**） | ✅ | ❌ | ✅ | ✅ | EL 对 chain 的支持需按版本核实 |
| 逆属性 | ✅ | ❌（EL 一般不支持） | ✅ | ❌ | ✅ | ✅ | EL profile 本身不含逆属性 |
| 个体推断 | ✅ | △（部分） | ✅ | ❌ | ✅ | ✅ | 个体类型/属性断言 |
| 增量推理 | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | 都不支持；靠重算 + 哈希跳过 |

**缺口结论：** 用 ELK 做 EL 物化时，**逆属性/并补/部分属性链**会缺；需要这些语义时必须 `OWL2DL` + HermiT/Konclude。**不要用 EL 结果冒充 DL 结论。**

### 2.4 与 Oxigraph 的配合

```text
命名图布局（GSP / SPARQL Graph Store 管理）
  urn:platform:tbox:<version>         T-Box（本体公理）
  urn:platform:abox:<version>         实例/事实（含 provenance）
  urn:platform:inferred:<version>     推理产物（只由推理作业写）
  urn:platform:staging:<jobId>        导入/抽取临时区（成功后 swap）
```

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 产物写回同一 Oxigraph 的独立命名图** | 推理器输出三元组 → `inferred` graph | 查询一条 SPARQL 即可联合；无第二套存储 | 需保证不覆盖源图；需版本管理 | **采用** |
| B. 独立推理库副本（另一 Oxigraph/Fuseki） | 推理与查询分离 | 隔离 | 双存储、双备份、双一致性 | 不采用（除极端规模） |

**查询时的图组合：** `FROM <tbox> FROM <abox> FROM <inferred>`，由平台模板固定，不允许业务自行拼接。

**命名图白名单（Q7-b 代码现状）：** `graph_oxigraph.py` 只允许 `FROM`/`FROM NAMED`/`GRAPH <iri>` 命中 `allowed_graphs` 精确集合或 `urn:platform:` 前缀；域外 IRI 返回 `PermissionDenied` / `E_GRAPH_GRAPH_NOT_ALLOWED`。取舍：**按平台命名空间前缀收口，未做“跨版本硬拒”**——`urn:platform:graph:tbox:<任意版本>` 仍可读，因为 publish/diff/export/context 需要按显式版本图读取；若要只允许当前指针版本，需要先改这些调用方，否则会打断发布链。

### 2.5 集成接口

独立容器时走 04 §4.5 `ReasoningService`（HTTP 或 CLI 包装）：

```text
materialize(tboxGraph, aboxGraphs[], profile, targetGraph) -> {inferred, consistent, skipped, ms}
checkConsistency(tboxGraph, aboxGraphs[], profile) -> {consistent, unsatClasses[], violations[]}
classify(tboxGraph, profile) -> {subClassOf[], equivalentClasses[], disjointClasses[], unsatisfiable[]}
```

**失败与降级：**

| 情况 | 行为 |
|---|---|
| 超时 | 返回 `DeadlineExceeded`；不阻塞查询；`reasoningStale=true` |
| 服务不可用 | `Unavailable`；查询继续用旧 `inferred` graph 或纯 RDFS |
| 不一致 | `consistent=false`；**不物化**；发布门禁拒绝 |
| 中途失败 | 清理 `targetGraph`，不留半成品 |
| T-Box 变更 | 旧 `inferred` 标 `stale`，新版本重算后再切读指针 |

### 2.6 推荐组合

| 场景 | 组合 | 开关 |
|---|---|---|
| **默认（P0）** | RDFS 闭包（进程内，`rdflib`/Oxigraph 规则） | `reasoning.mode=rdfs`（代码默认是 `materialize`；此行为推荐值，非默认值） |
| **需要 EL 蕴含（多数业务本体）** | **ELK 物化**到 `inferred` graph | `reasoning.mode=materialize` + `engine=robot`（ROBOT 内部调 ELK；代码无独立 `engine=elk`） |
| **需要 DL 一致性/分类** | **HermiT**（或 Konclude）离线校验 + 可选物化 | `reasoning.mode=validate`/`materialize` + `engine=robot`（ROBOT 内部调 HermiT；代码无独立 `engine=hermit`） |
| **本体发布门禁** | ROBOT（`robot reason`/`robot validate`） | `init`/CI profile |
| **必须在线蕴含** | 预物化 + 常驻 `reasoner` 做增量补算（仍非查询代理） | `reasoning.service_enabled=true` |

**JVM 容器资源（估算，需实测）：**

| 项 | ELK | HermiT | ROBOT |
|---|---|---|---|
| 堆 | 1–2 GB | 2–4 GB（DL 大本体更多） | 2–4 GB |
| 冷启动 | 3–10 s | 5–20 s | 5–15 s |
| 常驻内存 | 1–2 GB | 2–4 GB | 不常驻（CLI） |

**结论：** learn 档 `reasoner` 常驻（默认，`-Xmx` 见 03 §16.5）；lean 档用 `reasoning` profile 按需起。ELK 做 EL 物化、HermiT 做 DL 校验，是“快 + 准”的分工，不是二选一。

## 3. LLM Provider 预设（默认外部 API：DeepSeek / 火山方舟）

**默认：`llm.provider=openai-compatible`，无预设机制。** 已按代码对齐（原文档值=`provider=openai_compatible` + `preset=deepseek`）：代码无 `llm.preset` 字段，`base_url` / `model` 为空即“未配置”（抽取退规则）；实际默认 `timeout_ms=30000`、`max_retries=1`。下表是三组推荐三元组，需显式写进配置，不自动套用。

| 预设 | `base_url` 形态 | `api_key_env` | 默认 `model` | 流式 | tool-calling | JSON 模式 | 上下文上限 |
|---|---|---|---|---|---|---|---|
| **DeepSeek（默认）** | `https://api.deepseek.com/v1` | `DEEPSEEK_API_KEY` | `deepseek-chat` | ✅ SSE | ✅ OpenAI tools schema（并行调用**待实测**） | ✅ `response_format={"type":"json_object"}` | 128K（V3 系列，**待实测**；`deepseek-reasoner` 不支持参数化 tools） |
| **火山方舟 coding plan** | `https://ark.cn-beijing.volces.com/api/v3` | `ARK_API_KEY` | `ep-xxxx`（endpoint id，**不是模型名**；具体模型名按控制台，待实测） | ✅ SSE | 按模型而异（**待实测**） | ✅（部分模型，**待实测**） | 32K–256K（按模型，**待实测**） |
| **Ollama（仅降级）** | `http://ollama:11434/v1` | 无（本地） | `qwen2.5:7b-instruct`（**按实测选**，中文优先） | ✅ SSE | 模型相关，多数需提示词模拟（**待实测**） | ✅ `format=json` | 8K 默认，`num_ctx` 可调 |

**DeepSeek vs 豆包（火山方舟）关键能力差异（P0 需知）：**

| 维度 | DeepSeek | 豆包 / 火山方舟 | 影响 |
|---|---|---|---|
| tool-calling | 原生支持（`deepseek-chat`）；reasoner 不支持 | 依模型/endpoint 而定，需实测 | 抽取管线**不依赖原生 tools**（用 JSON 输出），因此两者都可跑 |
| 流式 | SSE，字段兼容 OpenAI | SSE，字段基本兼容 | 统一 `ChatEvent` |
| 结构化输出 | `json_object`；严格 schema 需自行校验 | 部分模型支持 `json_schema`（待实测） | 一律**本地 schema 校验 + 一次重试**，不信任网关 |
| 最大上下文 | 128K（待实测） | 32K–256K 按模型（待实测） | 长文档必须分块；chunk 预算取两者最小值 |
| 配额/限流 | 按账户 | coding plan 有配额/限流 | 429 → `ResourceExhausted`，退避尊重 `retryAfterMs` |
| 数据出机 | 是 | 是 | 属白名单；响应标 `degraded=true` |

**不支持 tool-calling 的降级策略（写死）：**

1. **默认：提示词内嵌 JSON 协议**（prompt 约定 `{"tool":"name","args":{...}}`，解析后转 `toolCall` 块）；解析失败**只重试一次**（`temperature=0`）；仍失败 → `Internal`，不循环、不猜参数。
2. **拒绝该能力**：若任务把它列入 `requirements.llm_tools_native` 且 `degradation.deny` → **启动自检 fail-fast**，错误样例 `E_LLM_NO_TOOLS`（见 04 §10.3 / §11.5，exit 78）。
3. P0 抽取/归一/回答**均不要求原生 tools**，因此默认走 1，不阻断启动；响应元数据保留 `tools=simulated, degraded=true`。

**Ollama（`local-llm` profile，仅降级路径）：**

- 启动：`docker compose --profile local-llm up -d ollama`；模型盘挂 `./data/models:/root/.ollama/models`（约 4–8 GB/模型，估算）。
- 默认模型建议：`qwen2.5:7b-instruct` 或 `qwen3:8b`（中文可用，**按实测选**）；内存 8–16 GB 量级（CPU/GPU 相关，估算）。
- **定位：离线/无外网时的降级路径，不承诺与云端同等质量**；抽取质量下降时标 `degraded=true`，重要任务应回到 DeepSeek。

**降级链：** 外部 LLM 不可用 → 退避重试（仅幂等）→ 抽取降级为规则 + 模板回答；不静默产出“无来源答案”。

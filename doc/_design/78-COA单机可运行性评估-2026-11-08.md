# COA 单机可运行性评估（2026-11-08）

> 评估对象：`packages/` 下的 COA 上游源码，问题不是「COA 有什么功能」，而是**在单机、无 AWS 的前提下，这些 package 能不能真的跑起来**——因为二开必须在 COA 上做，不能另建一套。
> 方法：只读源码核实（文件 + 行号）。**未安装依赖、未启动任何服务、未接触 8080 权威栈。**
> 判定口径：`能起进程` = 静态确认 import 链上无 AWS 网络调用、无必填 AWS 环境变量；`能提供服务` = 至少一条业务路径在没有 AWS 的情况下返回有效结果。后者全部为否定。

---

## 0. 结论（先看这段）

**一句话：COA 上游在「单机、无 AWS」下没有任何端到端可用路径。10 个包里只有 3 个能起进程（`ontology-engine`、`mcp-server`、`web-app`），而起起来的这 3 个一条业务路径都走不通；`vkg` 是唯一接近「本地真能算」的组件，但要绕开它在 entrypoint 里的 S3 强依赖。**

| package | 形态 | 无 AWS 能起进程 | 无 AWS 能提供服务 | 第一硬门槛 |
| --- | --- | --- | --- | --- |
| `ontology-engine` | FastAPI 容器，`:8001` | 能（`/health` 返回 ok） | 否 | Neptune（`NDB_ENDPOINT` 未设即 RuntimeError） |
| `context-manager` | AgentCore Runtime 容器，`:8080` | 能（本地 uvicorn 起 `/ping`） | 否 | Neptune + AOSS + Bedrock |
| `metric-service` | API Gateway Lambda handler | 否（无 HTTP 入口） | 否 | DynamoDB + Neptune + AOSS |
| `sources` | Lambda handlers + 流水线 | 否 | 否 | DynamoDB + Glue/Athena + DataZone |
| `mcp-server` | FastMCP，`:8000` | 能（关鉴权后） | 否（6 个工具全是转发） | Lambda invoke + AgentCore Runtime |
| `mcp-proxy` | Node stdio 桥 | 否（启动即解析配置） | 否 | SSM / Cognito / AgentCore ARN |
| `web-app` | Vite SPA，`:5173` | 能（dev server 起得来） | 否（登录需 OIDC） | OIDC issuer + clientId |
| `vkg` | ECS 容器（Ontop + H2） | 否（`ONTOLOGY_BUCKET`/`NAMESPACE` 必填 + `aws s3 cp`） | **改后可** | S3（唯一可低成本替代项） |
| `data-layer` | Lambda | 否（模块级必填环境变量） | 否 | AgentCore Runtime |
| `control-plane` | Lambda authorizer + handlers | 否 | 否 | API Gateway + DynamoDB + Cognito |

**对二开的直接判断：**「跑 COA 原样」不可行；「保留 COA 的接口契约与语义、换实现」可行，但替换面等价于重写一遍 `platform/`（5 个托管后端 × 4 个服务）。详见 §6、§7。

## 1. 先于 AWS 的一层门槛：构建期

这一层与 AWS 无关，但会挡住所有实测，必须先说清楚。

| 事实 | 证据 |
| --- | --- |
| `smithy-generated/` 在当前检出中不存在 | `Test-Path coa/smithy-generated` → `False` |
| 该目录被 gitignore | `.gitignore:45`、`.gitignore:161` |
| 但它是 uv workspace 的成员 | 根 `pyproject.toml:60-61`：`smithy-generated/control-plane-python-server`、`.../data-layer-python-server` |

结论：**单机实测的前置条件是「联网 + JDK21 + Gradle」，不是 AWS 凭证。** 这一步不通，往后所有判断都只能停在静态分析。

## 5. 单机最小路径

### L0 构建（无 AWS，但要联网 + JDK21 + Gradle）

```bash
# 仓库根 D:\agentABC\coa
make generate          # 生成 smithy-generated/（当前缺失，且被 gitignore）
uv sync --all-packages # 之后 workspace 才可解
```

不做这一步，后面任何命令都会卡在「缺 `coa-control-plane-server` / `coa-data-layer-server`」。

### L1 只证明「进程能起、不碰 AWS」（3 个，均无业务价值）

```bash
# 1) ontology-engine
uv run uvicorn coa_ontology.main:app --port 8001
curl -s localhost:8001/health      # {"status":"ok"}
curl -s localhost:8001/readiness   # status=degraded；graph_store/vector_store/bedrock 全 error
# 一调 /ontologies 即 RuntimeError("NDB_ENDPOINT not set")

# 2) mcp-server（关鉴权）
SCL_AUTH_ENABLED=false uv run python -m coa_mcp    # :8000 起来
# 6 个工具：discovery 走 Lambda invoke，execution 走 CM_RUNTIME_ARN，全部失败

# 3) web-app（npm install 在仓库根执行，见 web-app/README.md:33-35）
npm install && cd packages/web-app && npm run dev  # :5173
# 不配 authority/clientId 则登录页起不来；配了也要后端在跑
```

### L2 单包「真能算」（唯一低成本项：`vkg`）

```bash
# 原样（要求 S3 里有 artifacts）
docker build -t vkg-local packages/vkg/
docker run --rm -p 8080:8080 \
  -e ONTOLOGY_BUCKET=local -e NAMESPACE=default -e VERSION=latest vkg-local
# 无 S3 → 起在 degraded：/sparql/translate 返 503，进程仍活（entrypoint.sh:53-57）

# 改本地（推荐）：把 entrypoint.sh:36-57 的 S3 下载段换成目录挂载
docker run --rm -p 8080:8080 -v ./local-artifacts:/app/ontology vkg-local
curl -s -X POST localhost:8080/sparql/translate -d '{"sparql":"..."}'
```

最短验证命令：`docker run` 后 `curl -sf localhost:8080/health`；翻译能力用 `/sparql/translate` 直接验，不依赖任何 AWS。

### L3 端到端（「导入本体 → 问答」）

**不存在的路径。** 即便把 H6/L1–L5 全部低成本绕掉，剩下 H1–H4 四项仍需要改 6+ 个文件、补齐两个适配层（GraphStore 17 个方法、VectorStore 10 个方法，见 `stores/base.py:55-183,203-487`）。这已经不是「让 COA 跑起来」，而是「用 COA 的契约重写实现」——与本项目 `platform/` 已经做的事重合。

## 7. 对「二开在单机上是否可行」的结论

**可行，但不是「把 COA 改到能单机跑」这条路线。**

1. **不建议原地改造。** 5 个托管后端 × 4 个服务，替换面与 `platform/` 已有的 PG + Oxigraph + 本地 embedding + 本地 reasoner 实现高度重合；在 COA 里改等于把同一件事做第二遍，还要额外背上 Lambda/AgentCore 形态的壳。
2. **建议的复用边界（按投入产出排序）：**
   - `models/src/main/smithy/*.smithy` —— 纯契约，零 AWS 耦合，直接可复用（这也是 76/77 号文档对照所依赖的接口语义）。
   - `ontology-engine` 的纯校验逻辑：`validation/`（pyshacl + owlready2/HermiT）、`sqlglot` 相关校验 —— 不依赖 AWS，可直接搬（注意 `validation/shapes/nl_generator.py:53` 一处 SSM 调用要摘掉）。
   - `context-manager` 的分层策略编排（tier1/tier2/tier3 的判定顺序、deadline/预算、SQL firewall）—— 逻辑价值最高，但必须先剥离 8 个 AWS client。
   - `metric-service` 的 `osi_parser.py` / `validator.py` / `validate_soft.py` —— 纯文本解析与语义校验，可复用。
   - `mcp-server` 作为**协议适配层范式**（6 工具 → 2 后端），最适合照抄成「平台版 MCP server」。
3. **不建议复用：** `sources`（Glue/DataZone 管道）、`control-plane`（API Gateway authorizer 形态）、`metric-service` 的 API Lambda 层 —— 形态即 AWS，挪到单机等于重写。
4. **一个务实的中间态：** 若二开只需「本体 + 指标 + 问答」三件事，`platform/` 已经是单机可跑的等价物；把 COA 的 Smithy 契约、`mcp-server` 的工具面、`vkg`（本地 Ontop 翻译）三者接上 `platform` 的后端，比改 COA 本体便宜一个数量级。

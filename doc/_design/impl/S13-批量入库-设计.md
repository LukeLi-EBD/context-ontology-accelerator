# S13 · 批量入库（目录导入）（设计）

> 文档编号：impl/S13 · 版本：v1.0 · 日期：2026-11-05
> 范围：只新增“目录批量入库”入口与进度/状态可视化，不改解析、分块、检索语义。
> 关联：OQ-16（CAS 去重）、OQ-19（坏文件不落半成品）、OQ-21（大文件读取）、OQ-26（BGE-M3）。

---

## 1. 目标与边界

现状只有 UI 单文件上传与 `seed` 两份示例，几十 GB 资料无法进入平台。S13 增加：

- `platform import <dir>`：递归扫描目录，按白名单入库；
- `platform imports`：查看批次与单文件状态/失败原因；
- 只读 HTTP 与文档库页“导入进度”区块。

边界：

- 不新增第三方依赖；解析仍走 `LocalDocumentParser`（pypdfium2 / MarkItDown），分块与嵌入仍由 `DocumentService` / `SearchService` 完成；
- 不做定时扫描、文件监听、上传队列管理（P2）；
- 不改变 `document_id = sha256` 与检索/分块语义。

---

## 2. 命令与批次身份

```
platform import <dir> [--dry-run] [--retry-failed]
                      [--parse-concurrency 2] [--embed-concurrency 2]
                      [--progress-seconds 30]
platform imports [--batch <id>] [--status pending|parsing|chunked|indexed|failed] [--limit 20]
```

- **批次身份 = 解析后的根目录绝对路径**，`import_batch.root_path UNIQUE`。同一目录再次执行即续跑同一批次；换目录 = 新批次。
- `platform import` 在 `pg_try_advisory_lock('platform:import:<batch_id>')` 下执行；同一批次不允许并发跑两遍。
- 批次状态 `running → completed`；收到 `KeyboardInterrupt` 时置 `interrupted`，退出码 130。

## 3. 扫描与去重

`scan_directory()` 规则：

| 规则 | 行为 |
|---|---|
| 扩展名白名单 | 仅 `.pdf/.docx/.txt/.md`；其余计入 `unsupported` |
| 隐藏文件/目录 | 名称以 `.` 开头直接跳过（隐藏目录整棵剪枝） |
| 软链接 | `os.walk(followlinks=False)`，文件级 `is_symlink()` 跳过 |
| 平台自身目录 | 跳过 `storage.root` 自身（除非它就是导入根），并跳过其下 `blobs/tmp/backups/exports/ontology/owl/shapes/jobs/models` |
| 0 字节 | 扫描期即判 `failed/E_DOC_EMPTY` |
| 超限 | 超过 `documents.max_upload_bytes` 判 `failed/E_DOC_TOO_LARGE` |
| 不可读 | 扫描/哈希 `OSError` 判 `failed/E_IMPORT_UNREADABLE` |

去重：

- 每个文件流式计算 `sha256`（1 MiB 分块）；同 `rel_path` 且 `size/mtime` 未变化时直接复用库里的 sha，避免重复读盘。
- 同 sha 的多个路径归为一组，**组内只解析一次**；`document_id` 即 sha，CAS 天然把“改名同内容”识别为同一对象。
- 批次内某 sha 若已存在 `platform.document`，直接标记 `indexed, deduplicated=true`，不解析、不嵌入。
- dry-run 语义：
  - `toImport` = 去重后、且尚不存在的文档数（唯一内容数）；
  - `toImportFiles` = 其中包含组内重复文件的行数；
  - `skipped` 分 `duplicate/unsupported/empty/tooLarge/unreadable/hidden` 六类；
  - `willFail` 仅统计扫描期可判定的失败（空/超限/不可读），解析期失败无法预知。

## 4. 状态机与断点续跑

单文件状态：

```
pending ──▶ parsing ──▶ chunked ──▶ indexed
   ▲            │            │
   │            └──── failed ┘
   └── 崩溃残留 parsing 在下次执行时重置为 pending
```

- 写入 `parsing` 时 `attempts += 1`；解析成功转 `chunked` 并回填 `document_id/deduplicated/degraded`。
- 嵌入成功转 `indexed`；异常转 `failed` + `failure_code/failure_message`。
- 续跑时：
  - 已 `indexed` 的项不进入队列；
  - `chunked` 且有 `document_id` 的项**跳过解析，直接 `index_document`**（汇总里记为 `resumedChunked`）；
  - 残留 `parsing` 重置 `pending`；
  - `--retry-failed` 只重置 `status='failed' AND sha256 IS NOT NULL` 的项（0 字节/不可读没有 sha，不重试）。
- 因此“中断后再次执行”处理的是剩余项，不是整批重来。

---

## 5. 失败隔离与失败码

每个 sha 组独立 `try/except`，单文件失败只影响本组：

| 码 | 触发 |
|---|---|
| `E_DOC_EMPTY` | 0 字节（扫描期） |
| `E_DOC_TOO_LARGE` | 超过 `documents.max_upload_bytes`（扫描期） |
| `E_IMPORT_UNREADABLE` | 读取/哈希失败（扫描期） |
| `E_DOC_FORMAT_UNSUPPORTED` | 引擎拒绝的 MIME |
| `E_DOC_PARSE_FAILED` | 损坏/无法解析（保留引擎消息） |
| `E_DOC_PDF_ENCRYPTED` | 加密 PDF（尾部 `/Encrypt` 预检 + 引擎 password 提示） |
| `E_EMBED_*` / `E_VECTOR_*` | 嵌入或向量写入失败 |
| `E_IMPORT_UNEXPECTED` | 兜底，带异常类型 |

失败原因落 `import_item.failure_code/failure_message`，CLI `platform imports --status failed` 与 `GET /imports/items?status=failed` 均可列；`--retry-failed` 只重跑失败项。

---

## 6. 并发、限流、进度与汇总

- 两阶段流水：解析池（`--parse-concurrency`）+ 嵌入池（`--embed-concurrency`），默认均 2，避免打满 CPU。
- **PDFium 非线程安全**：`parsers.py` 用模块级 `_PDFIUM_LOCK` 串行化 PDF 打开/取文本/关闭；并发只在解析池的调度层，不在引擎临界区。实测并发调 PDFium 会 native segfault（见 §11）。
- 进度线程每 `--progress-seconds`（默认 30s）打印：`已处理/总数、processed/indexed/failed、files/s、MB/s、elapsed`。
- 结束汇总字段：`total/alreadyDone/processed/parsed/resumedChunked/indexed/failed/failedThisRun/documentsAdded/skipped/elapsedSeconds/bytesProcessed/throughputMbPerSec/peakRssMb/failures/exitCode`。峰值内存取 `/proc/self/status` 的 `VmHWM`。

## 8. 实测（2026-11-05）

### 8.1 语料构成

`/data/corpus-s13`（**256 个文件、1,517,229 字节**）：

| 构成 | 数量 | 说明 |
|---|---|---|
| 生成的合法单页 PDF `generated/bench-*.pdf` | 220 | 3.6 KB/个，各 3 chunks；覆盖 ≥200 文件门槛 |
| 改名副本 `generated/renamed-copy-1..5.md` | 5 | 与 bench-0001..0005 内容相同，验证 CAS 改名去重 |
| 仓库真实文档 `real/*.md|txt` | 28 | 全部 `_design/` 设计文档 + `_impl` README/OPEN-QUESTIONS，45–75 chunks 的大文档 |
| 坏文件 `bad/` | 3 | 0 字节 `empty.txt`、损坏 `corrupted.pdf`、加密 `encrypted.pdf`（pypdf RC4-128） |

另建干净语料 `/data/corpus-s13-clean`（120 个新 PDF + 4 个改名副本 = 124 文件、455,452 字节），用于严格验证 dry-run 与真实入库数一致（不含不可预知的解析失败）。

### 8.2 dry-run

`/data/corpus-s13`：

```

skipped=8 (duplicate=7, empty=1)  alreadyIndexed=2  willFail=1
```

`/data/corpus-s13-clean`：


### 8.3 断点续跑（真实崩溃）

第一次导入在并发调用 PDFium 时 native segfault（已修复，见 §11），库里留下 `indexed=2 / failed=3 / chunked+parsing=251` 的混合断点。随后执行同一命令续跑：

```
total=256 alreadyDone=5 processed=251 parsed=244 resumedChunked=4
indexed=251 failed=3 documentsAdded=244 elapsed=1792.87s
peakRssMb=120.7 exitCode=0
```

- 4 个已 `chunked` 的文档没有再次解析，直接嵌入；
- 最终该批次 248 个文档、1,139 chunks，失败 3 个。

### 8.4 重复执行（②）

同一目录再跑一次：

```
total=256 alreadyDone=256 processed=0 parsed=0 resumedChunked=0
indexed=0 documentsAdded=0 failed=3 elapsed=0.54s
```

0 新增、0 重复解析。

### 8.5 干净语料（①）

```
processed=124 parsed=120 indexed=124 documentsAdded=120
elapsed=276.31s bytesProcessed=440,760 peakRssMb=118.3 exitCode=0
```

`dry-run.toImport=120` 与 `documentsAdded=120` 逐数一致；`toImportFiles=124` 与 `indexed=124` 一致（4 个改名副本记为 `deduplicated`）。

### 8.6 失败隔离与 --retry-failed（④）

首次导入混入 3 个坏文件，整批仍完成（exit 0）：

```
bad/empty.txt        E_DOC_EMPTY           document is empty (0 bytes)
bad/corrupted.pdf    E_DOC_PARSE_FAILED    cannot open PDF: Failed to load document (PDFium: Data format error).
bad/encrypted.pdf    E_DOC_PDF_ENCRYPTED   PDF is encrypted (password required); decrypt it before import
```

随后 `--retry-failed`：

```
retryFailed=true processed=2 parsed=2 indexed=0 documentsAdded=0 elapsed=0.59s
failures: corrupted.pdf=E_DOC_PARSE_FAILED, encrypted.pdf=E_DOC_PDF_ENCRYPTED, empty.txt=E_DOC_EMPTY
```

只重试 2 个有 sha 的失败项；0 字节项不进入解析流水，失败码保持不变。

### 8.7 吞吐与峰值内存（⑤）

| 语料 | 文件/文档 | chunks | 耗时 | 吞吐 | 峰值 RSS |
|---|---|---|---|---|---|
| clean（120 新 PDF） | 124 / 120 | 360 | 276.31s | 0.45 files/s；**1.30 chunks/s**；0.0015 MB/s | 118.3 MB |
| corpus 续跑（真实混合） | 251 / 244 | 1,133 | 1792.87s | 0.14 files/s；**0.63 chunks/s**；0.0008 MB/s | 120.7 MB |

MB/s 偏低是因为语料以短文本 PDF/文档为主（单文件 3–70 KB），瓶颈在 CPU 上的 BGE-M3 嵌入而非磁盘 I/O。

## 11. 已知边界

- **PDFium 串行化**：并发解析 PDF 会 native segfault（实测），S13 用模块锁把 PDFium 临界区串行；代价是 PDF 解析吞吐受单核限制。解决方向见 OQ-55。
- **dry-run 不能预测解析失败**：`willFail` 只覆盖扫描期可判定的空/超限/不可读；损坏或加密 PDF 只有在解析时才暴露，因此 ① 的严格等号只在干净语料上成立。
- **批次身份依赖路径**：目录改名/移动会生成新批次，旧批次状态仍按原路径保留（OQ-56）。
- **吞吐瓶颈是 CPU 嵌入**：本机 BGE-M3 约 1.3 chunks/s（短文本），几十 GB 全量嵌入的时间与“换外部 embedding”的决策见 S3 设计（OQ-57）。
- **批次的 running 状态无心跳**：进程被杀后批次仍是 `running`，直到下一次执行才被改写；不引入定时任务（P2）。

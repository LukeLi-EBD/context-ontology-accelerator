# COA 二开路线评估（修正版）

> 本文是对 78 号《COA 单机可运行性评估》的对质与修正，不重复其源码证据。
> 78 的结论是：COA 上游在单机无 AWS 下没有端到端可用路径，10 个包中 3 个能起进程但业务全不通，硬门槛 6 条，且不建议原地把 COA 改到单机可跑。
> 本文回答四个问题：工作量是否上修、切片 1 是否可执行、路线 2 是否才是务实解、修正后的推荐与首切片。

---

## 0. 修正结论（先看这段）

**一句话：真二开（COA 包当运行时宿主）在单机场景下不推荐。工作量从 L 上修为 XL：最小范围 1.5–2×，全能力对齐 3–5×。推荐改为「路线 2′：以 COA 契约为准绳、纯逻辑回流、platform 做单机宿主」。**

| 问题 | 结论 |
| --- | --- |
| Q1 工作量是否上修 | **是**。L→XL；最小范围 1.5–2×，全对齐 3–5×。Neptune 强制 https+SigV4 本身只值 40 行左右，真正上修的是 AOSS 唯一实现 + tier3 绑 `graphrag-lexical-graph`，以及 H5 结构化数据面 |
| Q2 切片 1 是否不可执行 | **不是不可执行**。`metric-service` 的 Lambda 形态不影响切片，因为切片只 import `osi_parser`/`validator` 纯逻辑；`uv sync` 阻塞可用「独立 venv + PYTHONPATH」绕开，不安装 workspace |
| Q3 抽纯逻辑接进 platform 是否就是路线 2 | **是，确切地说是路线 2 的「契约优先」变体（2′）**。我原来否定路线 2 的两条理由中，成本理由被 78 证伪并撤回；定义理由仍然成立 |
| Q4 修正推荐 | **路线 2′**。首切片：`metric-service` 的 Smithy 指标契约 + OSI 解析/校验纯逻辑接入 platform，独立 venv 运行，不碰 `uv sync`、不碰 AWS、不写 8080 |

**必须说清的口径问题：** 路线 2′ 不是严格字面的「在 COA 上二开」——运行时宿主仍是 `platform/`，COA 上游包不参与运行。它是「以 COA 的接口契约和语义为准绳，在单机宿主上做二开」。这两个口径不能混为一谈，必须由需求方拍板。若坚持「COA 包必须当运行时宿主」，则只剩「接受 AWS 运行面」或「XL 重写」两条路，单机都不推荐。

## 1. 与 78 的关系

### 1.1 接受的事实

- 构建期门槛：`smithy-generated/` 缺失且被 gitignore，`uv sync --all-packages` 在 codegen 前必然失败；codegen 需要联网 + JDK21 + Gradle。
- 运行期门槛：H1 AgentCore Runtime 协议、H2 Bedrock、H3 Neptune（context-manager 强制 https + SigV4 且无开关）、H4 AOSS（唯一向量实现 + tier3 绑 `graphrag-lexical-graph`）、H5 Glue/Athena/DataZone、H6 DynamoDB 8 张表。
- 端到端结论：无 AWS 下没有任何「导入本体 → 问答」的可用路径。

### 1.2 我此前判断中被证伪的部分

| 此前判断 | 78 证据 | 修正 |
| --- | --- | --- |
| 「Protocol 边界齐全，真二开只是 L」 | `context-manager` Neptune 无免签开关；AOSS 是唯一向量实现；tier3 全量绑 `graphrag-lexical-graph` | 低估了运行面，不只是「包一层适配器」 |
| 「Route 2 的解耦成本接近 Route 1」 | 78 列出的可复用面（Smithy 契约、pyshacl/HermiT/sqlglot 校验、分层策略、MCP 范式、vkg）恰好是 AWS-free 或低改动面 | 对「有界复用集」不成立，撤回该理由 |

## 2. Q1：工作量上修区间

### 2.1 分项

| 上修项 | 78 证据 | 代码量级 | 对总工作量 |
| --- | --- | --- | --- |
| context-manager Neptune 强制 https + SigV4，无开关 | `clients/neptune.py:156-165` | 1 文件约 40 行 + `/sparql` 路径映射代理 | +0.1–0.2 L；风险在方言/错误码差异，不在行数 |
| AOSS 是唯一向量实现 | `stores/opensearch_vector.py:82-91` | ontology-engine 新 `VectorStore` 适配器 300–400 行（10 个方法） | +0.2–0.3 L |
| tier3 全量绑 `graphrag-lexical-graph` | `context-manager/pyproject.toml:38-44` | 实现 llama-index VectorStore 或替换 tier3 策略，800–1,500 行 | **+0.5–1.0 L，主上修项** |
| Bedrock 三协议（converse / invoke_model / guardrail） | 78 §4 H2 | 本地 shim 300–500 行，或改 6 处客户端 | +0.2–0.3 L |
| AgentCore Runtime 调用协议 | 78 §4 H1 | 3 个 client 约 150 行 + SSE 帧约定替换 | +0.1–0.2 L |
| Glue / Athena / DataZone | 78 §4 H5 | 若保留结构化源接入：`sources` 73 个 boto 文件中一大半要换；若砍掉：tier1/tier2 指标路径仍需换成本地观测库 | +1.0–2.0 L（保留）；+0.3–0.5 L（砍掉） |
| DynamoDB 8 张表 | 78 §4 H6 | 0 行代码 + 表结构 seed + DynamoDB Local 覆盖实测 | +0.1–0.2 L |
| 构建期 smithy codegen | 78 §1 | JDK21 + Gradle + Maven Central 网络 | 前置条件，约 +0.1 L |

### 2.2 区间

- **最小范围（本体 + 指标 + 问答，砍掉 sources 结构化接入、砍掉 tier3 agent）**：约 **1.5–2×** 我此前的 L，即 L→XL 下沿。
- **全能力对齐（保留 tier3、sources、control-plane、多组织）**：约 **3–5×**，即 XL 上沿。
- 结论：**不是「L 但可行」，而是「XL 且必须砍范围才可行」**。

**直接回答 Q1：** Neptune 那一条本身不会让工作量显著上修；真正上修的是 AOSS/tier3 与 H5。区间如上。

## 4. Q3：抽纯逻辑接进 platform 是不是路线 2

### 4.1 定性

**是。** 而且它不是路线 2 的泛化说法，而是其中更严格的一支：

- **路线 2A（弱）**：把 COA 某个包当库，platform 调它；
- **路线 2B（本文推荐，记作 2′）**：以 COA 的 Smithy 契约和语义为准绳，只把 AWS-free 的纯逻辑（校验、解析、分层策略、工具协议）回流进 platform，platform 仍是唯一运行时宿主。

### 4.2 我原来否定路线 2的理由，逐条状态

| 原理由 | 状态 | 说明 |
| --- | --- | --- |
| 「路线 2 仍是 platform 当宿主，不满足‘在 COA 上二开’」 | **成立** | 这是目标定义问题，不会因工程量变化而消失 |
| 「路线 2 的解耦成本接近路线 1」 | **撤回** | 78 证明路线 1 的运行面成本远高于我此前估计；而有界复用集（Smithy/pyshacl/HermiT/sqlglot/分层策略/MCP 范式/vkg）恰好是 AWS-free 或低改动面 |
| 「路线 2 会保留 B 类重叠」 | **成立但可收敛** | 重叠仍在，但可以按 COA 契约逐步收敛，不必一次重写 |

**直接回答 Q3：** 是路线 2（2B）。我的成本理由动摇并撤回；定义理由没有动摇。因此结论取决于需求方选哪个口径：要「COA 包当宿主」，路线 2 不满足；要「COA 契约当准绳、单机可跑」，路线 2′ 是唯一务实解。

## 5. 修正后的推荐

### 5.1 推荐：路线 2′（契约与纯逻辑回流的迁移融合）

**理由：**

1. **单机可运行**：platform 已经是单机可跑的 PG + Oxigraph + 本地 embedding + 本地 reasoner 宿主；不需要重建 H1–H6。
2. **功能优先**：COA 提供的是语义与契约上限（Smithy 模型、分层策略、校验规则、MCP 六工具范式），platform 提供的是单机实现底座；两者组合比任何一套单独都更全。
3. **易用可用**：结束态仍是一套 API、一套 UI、一份 T-Box 真相；不引入 Lambda/AgentCore 的运行形态。
4. **资产保留**：platform 43,775 行中无需废弃 B 类；COA 的复用面是有界、可验证的，不是「整包搬运」。

### 5.2 为什么不选路线 1（真二开）

- 78 已证明单机无端到端路径；最小可用也要 1.5–2× 此前工作量，全对齐 3–5×。
- 替换面与 `platform/` 已有实现高度重合：等于把同一件事做第二遍，还要额外背 Lambda/AgentCore 形态的壳。
- 只有一种情况应选路线 1：组织能提供 AWS 运行面，或明确接受 XL 重写并且不以单机为交付形态。

### 5.3 为什么不选路线 3（双栈）

- 没有任何二开成果；COA 123k 行源码继续做参考资料；两套真相分叉。
- 只能作为迁移期临时态，不能作为终态。

### 5.4 必须承认的代价

路线 2′ 的结束态不是「COA 上游包在运行」，而是「COA 契约在约束 platform 的实现」。如果对外表述必须写成「基于 COA 运行」，那是不准确的，不能这么写。文档与验收口径应统一为：**以 COA 契约为准绳的单机二开**。

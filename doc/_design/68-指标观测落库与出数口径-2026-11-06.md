> 任务：`D:\agentABC\coa`，分支 `luke`。目标是回答“平台为什么一条指标都出不了数”，并用真实批量计算把 `metric_observation` 落满，给出可复核的对外口径。

> 本文只记录事实、代码依据和实算结果。未改任何指标定义公式；未对共享库执行 DDL；未 `git push`。

## 0. 结论摘要

1. `platform.metric_observation` **不是指标结果缓存**，而是按“指标 × 定义版本 × 实体 × 窗口”存储**分子/分母观测值**的输入层。指标值在读取时由 `formula_expr` 现算。
2. 平台此前“一条都出不了数”的直接原因：观测表 0 行。`/metrics/{id}/output?compute=true` 只读 `metric_observation`；此前从未有任务把编译器/投影器算出的分子分母写进去。编译器路径 `/metrics/{id}/compute` 能直算，但它**不落库**，且与审计调用的 `/output?compute=true` 不是同一条读取路径。
3. 本轮用现有编译器 + 投影器做了真实全量计算：
   - **74 条** `structurally_computable` = **62 条数值指标 + 12 条规则型指标**；
   - 数值指标：**54 条实算成功并落库**，**8 条失败**（7 条无数据行、1 条读取路径拒绝）；
   - 规则型：**12 条**通过 `/rules` 实算，**0 条失败**（其中 FIN-BANK-002 只出规则命中，不出数值）；
   - `metric_observation` 实际落库 **37,471 行 / 55 条指标**，全部 `data_source=synthetic`、`fixture=false`，无编造值。
4. 对外口径（可被外部 `?compute=true` 调用）：**41 条**数值指标可返回真实值；另有 **13 条**数值指标只能内部（`internal=true`）出数，因 `publishable=false` 对外返回 403。
5. 旧的“82 条可算”= 85 − 3 条 `blocked_external`，**把 8 条 `blocked_semantics` 也算进去了**；按 `computability_tier='structurally_computable'` 的真实口径是 **74**，从 74 再按“数值/规则”和“成功/失败”拆分，才是可审计的最终数字。
6. `FIN-BANK-002` 不是“缺绑定”的数值指标，而是 `output_mode=rule_set` 的分档规则；它**不能出数值**，但 `/rules` 在 2025-12-31 触发 9,581 条。按“不可出数值”降级，不能留在数值可算清单里。
7. `FIN-INS-021`（原“4 条可发布出数”之一）在当前事实数据下**永远算不出**：V20 事实函数要求 `installment_no=13`，而 `ins_payment_record` 只有 `installment_no=1`。必须数据侧补 13 期数据或从可出数清单移除。
8. 45 / 48 两份文档关于“MetricService 写 metric_observation”“观测行=算出的值”的描述与代码不符。本文第 4 节给出错误定位与正确表述，供回写线引用。

## 1. `metric_observation` 的设计定性

### 1.1 结论

**观测层 = 分子/分母输入层，不是结果缓存。**

- 一张观测行 = 某个指标、某个定义版本、某个实体、某个窗口下，已按事实层口径聚合好的 `numerator` 与 `denominator`；
- 观测行**没有 `value` 列**，也不应该存公式结果；
- 读取时，`MetricService.compute` 对观测行做跨实体合成，再用 `formula_expr` 算值；
- 因此“出数”的正确动作是：**把分子/分母写进观测表**，而不是把编译器的 `value` 写进去。

### 1.2 代码依据

| 事实 | 代码位置 |
|---|---|
| 表结构只有 numerator/denominator，无 value | `platform/src/platform_core/sql/V19__metric_observation.sql:28-50` |
| 唯一键是指标+版本+实体+窗口 | 同上 `:49` |
| 外部导入只写 numerator/denominator | `platform/src/platform_core/metric_loader.py:1-8` |
| 事实投影只写 numerator/denominator | `platform/src/platform_core/metric_facts.py:523-640` |
| 读取时从观测表取分子分母 | `platform/src/platform_core/metrics.py:340-380` |
| 读取时用 formula_expr 算值 | `platform/src/platform_core/metrics.py:382-434` |
| 编译器直接读事实表，不写观测 | `platform/src/platform_core/metric_compiler.py:281-316` |
| 编译器测试明确“no observation row is produced” | `platform/tests/test_metric_facts_v7.py:1-5` |
| API 注释明确“direct fact-table aggregation, no observation cache” | `platform/src/platform_core/api.py:3774` |

### 1.3 为什么文档会误写成“结果缓存”

`doc/_design/45` 的时序图把 `MetricService` 画成 `metric_observation` 的写入方；`doc/_design/46` 把观测行描述成“某口径在某时间窗口算出的值”。实际实现里：

- 写观测的是 `MetricLoader`（外部导入）和 `MetricProjector`（事实函数投影），**不是 MetricService**；
- 观测行存的是分子/分母，**不是值**；
- `MetricCompiler` 是第三条路径，只直算、不落库。

因此文档描述的是一个“值缓存”，而代码实现是“分子分母观测层”。二者不是同一设计。

## 2. 平台此前为什么一条都出不了数

审计实测路径是：

```
GET /metrics/{id}/output?compute=true&asOf=... 或 periodStart/periodEnd
  → MetricService.compute
  → SELECT ... FROM platform.metric_observation
  → 0 行
  → 400 E_METRIC_NO_DATA
```

而平台此前真正能“算”的路径是：

```
GET /metrics/{id}/compute?dataSource=fixture   （dataSource 必填，无默认值）
  → MetricCompiler.execute
  → 直接 SELECT 事实表
  → 返回 rows，但不 INSERT 观测表
```

所以“公式编译通过、字段绑定齐全”（结构可算）与“观测表有值、端点能出数”是两件事。缺的是**批量计算并将分子分母落库**这一环，不是缺编译器，也不是缺表。

## 3. 本轮改动

### 3.1 读取路径补齐（`metrics.py`）

1. **补齐聚合取值**
   - `_AGGREGATES` 增加 `count`、`count_distinct`（`metrics.py:46`）。
   - 关键语义修正：观测行是**按实体预聚合**的，跨实体合成不能再套一遍原始聚合。因此 `sum / count / count_distinct` 一律合成 `SUM(column)`；`max/min/avg` 才用对应聚合（`metrics.py:66-72`）。
   - 如果不这样处理，`count_distinct` 会变成“对每个实体的去重计数再去重”，例如 FIN-BANK-017 会算出 75.0%，而正确的加权迁徙率是 40.0384%。本轮已实测纠正。
2. **补齐数值类指标类型**
   - 原白名单只有 `ratio/duration/sum`，导致 `count/amount/period_value` 指标（如 CUST-002、CUST-003、FIN-INS-002、CUST-013）直接 `E_METRIC_NOT_DRIVABLE`。
   - 新增 `_DRIVABLE_KINDS = ("ratio", "duration", "sum", "count", "amount", "period_value")`（`metrics.py:50`）。`band/index/rule_set` 仍走专用路径。
3. **分母聚合按公式需要生成**
   - 原实现只在 `kind='ratio'` 时生成 denominator SQL，导致 `period_value` 的 `numerator / denominator` 公式因缺 denominator 被判“not drivable”。
   - 改为“公式里出现 denominator 就生成分母聚合”（`metrics.py:305-316`）。
4. **dataSource 如实返回**
   - 原实现按 `fixture` 布尔值硬编码 `dataSource="fixture"`，会把合成数据再次标成 fixture。
   - 改为从观测行 `MIN(data_source)` 读取并返回（`metrics.py:363, 434`）。当前实测返回 `dataSource="synthetic", fixture=false`。

### 3.2 `MetricProjector` 接受 synthetic（`metric_facts.py`）

- 数据源校验扩为 `fixture|business|synthetic`（`metric_facts.py:568`）。
- `fixture` 不再由 data_source 推导，而是取事实函数返回行中的 `fixture` 值；当前事实行为 `false`（`metric_facts.py:601-604`）。
- 这样观测行保留 `data_source=synthetic`、`fixture=false`，不会把合成数据伪装成 fixture。

### 3.3 V37 迁移（原编号 V41；集成期已注册并并入 `luke`）

- 文件：`platform/src/platform_core/sql/V37__metric_observation_synthetic.sql`
- 内容：
  1. 幂等检查 `metric_observation.data_source` 的 CHECK，缺 `synthetic` 时替换；
  2. 给表/列加注释，写明“观测行是分子/分母输入，不是结果缓存”“合成数据不得标为 fixture”；
  3. 不写数据、不改指标定义。
- 现状说明：V26 的循环 DDL 已经把包括 `metric_observation` 在内的 `data_source` CHECK 扩成 `fixture|business|synthetic`（当前库实测已允许 synthetic）。因此 V37 在当前库上是**幂等 no-op**，它的价值是把这一契约显式化，供新建库/未执行 V26 的库使用。

## 4. 45 / 48 文档错误（供回写线引用）

### 4.1 `doc/_design/45-产品架构介绍.md`

**错误位置**：指标计算时序图把 `MetricService` 画成 `metric_observation` 的写入方。

**错在哪**：代码中 `MetricService` 只读观测表（`metrics.py:340-380`），没有任何 INSERT。写观测表的是 `MetricLoader` 和 `MetricProjector`（`metric_facts.py`），`MetricCompiler` 则不写。

**正确表述**：

> `MetricCompiler` / `MetricProjector` 从事实表或事实函数产出**分子/分母**，写入 `metric_observation`；`MetricService` 只读取观测行，在读取时用 `formula_expr` 现算指标值。`metric_observation` 不是结果缓存。

### 4.2 `doc/_design/48-技术说明书.md`

**错误位置**：观测行被描述为“某口径在某时间窗口算出的值”。

**错在哪**：V19 表结构没有 `value` 列（`V19__metric_observation.sql:28-50`），只有 `numerator`、`denominator`。把观测行说成“值”会让人以为可以直接查询结果，掩盖了公式现算和跨实体合成这两步。

**正确表述**：

> 观测行是某指标/版本/实体/窗口下的**分子与分母**；指标值由 `MetricService.compute` 在读取时对观测行做跨实体合成后，按 `formula_expr` 计算。观测表本身不存指标结果。

## 5. 74 / 82 两套口径逐条对账

### 5.1 总量拆解

当前库共 **85** 条指标定义：

| Tier | 条数 | 含义 |
|---|---:|---|
| `structurally_computable` | **74** | 公式可编译、绑定/函数齐全，本轮实算对象 |
| `blocked_semantics` | 8 | 公式不可翻译、需业务裁定、或缺 regulatory source |
| `blocked_external` | 3 | 缺外部监管数据/实体，永远不可由平台闭环 |

**82 的来源**：`85 − 3 条 blocked_external = 82`，等价于 `74 + 8 条 blocked_semantics`。也就是说，旧的“82 条可算”把 8 条**语义阻塞**指标也算了进去，这 8 条并没有通过“结构可算”。

8 条 `blocked_semantics` 逐条：

- CUST-004 RFM 分档（五分位）
- FIN-BANK-019 30→90 累计迁徙率
- FIN-BANK-020 迁徙率（户数口径变体）
- FIN-BANK-021 迁徙率（期末余额口径变体）
- FIN-BANK-036 不良处置率/处置回收率
- FIN-INS-012 两年综合成本率（2003）
- FIN-INS-022 13 个月保费继续率
- FIN-INS-023 25 个月继续率

3 条 `blocked_external`：CUST-011、FIN-INS-029、FIN-INS-030。

### 5.2 74 条内部拆分

| 分类 | 条数 | 说明 |
|---|---:|---|
| 数值指标（可通过 observation 出数） | **62** | 53 条字段绑定 + 9 条事实函数 |
| 规则型指标（`output_mode=rule_set`） | **12** | 走 `/rules`，不产生 observation 数值；含 FIN-BANK-002 |

> 因此，“74 条结构可算”不能直接等于“74 条可出数值”。可出数值的起点是 **62**，从 62 再减失败。

### 5.3 最终对外口径

| 口径 | 条数 | 说明 |
|---|---:|---|
| 结构可算 | 74 | 审计起点 |
| 数值指标 | 62 | 74 − 12 规则型 |
| 数值实算成功 | **54** | 62 − 8 失败 |
| 其中 `publishable=true`（外部可调） | **41** | 外部 `?compute=true` 可返回真实值 |
| 其中 `publishable=false`（仅内部） | 13 | `internal=true` 可出数，外部 403 |
| 规则型实算成功 | 12 | `/rules` 可出规则命中；10 条 publishable |
| **业务结果实算成功（数值 + 规则）** | **66** | 54 + 12 |

**对外数字建议**：不要再说“82 条可算”。准确说法是：

> 74 条结构可算；其中 62 条数值指标，54 条在当前合成数据上实算成功，41 条可对外出数值；其余 8 条数值指标失败原因见第 7 节；另 12 条为规则型指标，经 `/rules` 实算成功。

## 11. 契约变更影响（2026-11-07）

### 11.1 计算端点：拒绝退化窗口、`dataSource` 无默认值

| 请求 | 变更前 | 变更后 |
|---|---|---|
| `period` 指标 + 仅 `asOf` | 200，悄悄按 `start=end=asOf` 算 1 天窗口（`min_window_days=0` 放行） | 400 `E_METRIC_WINDOW_INSUFFICIENT`，`period metric requires a full window` |
| `period` 指标 + `periodStart == periodEnd` | `/compute` 200 单点；`/output?compute=true` 400 `E_METRIC_NO_DATA`（两端不一致） | 两端均 400 `E_METRIC_WINDOW_INSUFFICIENT`，同码同文案 |
| `/compute` 不传 `dataSource` | 200，按 `fixture` 读取；无匹配时返回空 `rows` + `E_METRIC_DATASOURCE_MISMATCH` | 400 `E_METRIC_DATA_SOURCE_REQUIRED`，`details.allowedDataSources = ["fixture","business","synthetic"]`；OpenAPI `required: true` |
| `/output?compute=true` 不传 `dataSource` | 200，参数被静默忽略，多个来源的观测被混在一起汇总 | 400 `E_METRIC_DATA_SOURCE_REQUIRED`，`details` 与 `/compute` 相同；传入值真正过滤观测行 |
| `MetricCompiler.compile/execute` 不传 `data_source` | 默认 `fixture` | Python 层直接报缺参（无默认值） |

**这是契约收紧，不是回归。** 第三方 QA 用例 `q_S14` / `q_M01` 在新契约下会返回 400：`q_S14` 的默认 `/compute` 调用从“200 空结果、原因不可见”变成“不传参数直接拒绝并列出允许值”；`q_M01` 的 8 条 period 指标用 `asOf` 单点，从“能出 1 天数”变成 400 窗口错误。两者都必须按新契约改写用例，**不得引用 `doc/_qa/evidence/` 里的旧快照作为当前行为证据**。`doc/_qa/` 由对应 owner 分派，本线未改动。

### 11.2 计算溯源：不进 PROV，用 `source_ref_registry` 承载

- 调查结论：`/output`、`/compute` **从不写 PROV**；PROV 的 `KINDS` 只有 `decision / rule_trigger / refusal`，且仅由 `/answer` 与规则执行写入。计算不是裁决，本轮没有把它塞进 PROV。
- 替代载体：成功出数时写一条 `ref_kind=metric_computation` 的 `source_ref_registry` 记录，并在响应返回 `computationRef`（`src://computation/<id>`）。locator 含：`metricId`、`definitionVersion`、`window`、`dataSource`/`fixture`、`factTables`（直算）或 `observationRef`（观测）、`rowCount`/`sampleCount`/`sampleRows`、`value`、`computedAt`、`endpoint`、`caller{actor,client,userAgent,requestId}`。
- 入口：`GET /metrics/{id}/computations?limit=` 列出记录；`GET /source/resolve?ref=src://computation/<id>` 解析单条。
- 边界：平台无认证，“谁调的”只能是 `X-Actor` / client / UA / requestId，缺失时明确记为 `anonymous`；`/compute` 记录不含原始 SQL，靠 `factTables` + 窗口 + `dataSource` 可复算。

### 11.3 已知限制

- `/metrics/{id}/computations` 用 `locator->>'metricId'` 过滤，当前 registry 量小，未加索引，查询为全表扫描。**若该入口被频繁调用，需补 `(ref_kind, locator->>'metricId')` 的表达式索引**（属于 DDL，按约定由集成方在迁移中应用）。
- 计算记录只在成功出数时写：`/compute` 要求 `rows` 非空，`/output?compute=true` 要求 `value` 非空；空结果不产生审计行。

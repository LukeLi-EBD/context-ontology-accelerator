## 1. 一句话定位 + 仓库事实核查

**它是一个只做 Amazon Redshift 方言、只做到语法树为止的 ANTLR4 Go 解析器**：喂一段 SQL，拿回一棵 ANTLR `ParseTree`（`IRootContext`）。它不产出归一化 AST，不做语义分析、name resolution、血缘、格式化或改写。

它**解决**：离线、不连库地判断一段 Redshift SQL 在语法上是否成立，并把语句结构暴露成可按规则类型遍历的树。

它**不解决**：

- 方言之外的 SQL（这是单方言仓，不是 `parser/` 那种多方言集合）；
- 语义正确性（表/列是否存在、类型是否匹配、函数签名）；
- Redshift 的完整语法面（实际只补了少量列属性，见下）；
- 代码生成的可重现性保障（ANTLR 版本未锁定，`build.sh` 里没有版本号）。

**事实核查（逐条给证据）**：

1. **生成物已提交进仓，跑测试不需要装 ANTLR。** 6 个 `*.go` 生成文件（合计约 6.5 MB）+ 2 个 `.tokens` + 2 个 `.interp` 都在根目录；`go test` 实测可过（§10）。
2. **没有独立 AST 层。** 根目录没有 `ast/`、`semantic/`、`rewrite/`、`format/`；树就是 `antlr.ParserRuleContext`，节点类型是生成出来的 `XxxContext`。
3. **单方言，不是多方言框架。** 全仓只有一对 `RedshiftLexer.g4` / `RedshiftParser.g4`；没有方言注册表、没有公共 Node 接口。
4. **Redshift 专属语法极少。** 语法侧与 Redshift 相关的只有 `rs_colattributes` 的 7 个分支（`RedshiftParser.g4:678-686`）：`DEFAULT`、`IDENTITY_P(...)`、`GENERATED BY DEFAULT AS IDENTITY(...)`、`ENCODE StringConstant`、`DISTKEY`、`SORTKEY`、`COLLATE (CASE_SENSITIVE | CASE_INSENSITIVE)`。对应的新 token 只有 `ENCODE`（`RedshiftLexer.g4:2696`）、`DISTKEY`（`:2700`）、`SORTKEY`（`:2704`）、`CASE_SENSITIVE`（`:2708`）、`CASE_INSENSITIVE`（`:2712`）。注意 `columnDef` 里是 `rs_colattributes?`（单次可选，`:675`），7 个分支互斥，**同一列写两种属性（如 `IDENTITY(1,1) ENCODE lzo`）解析不了**。
5. **表级 `DISTKEY(col)` / `SORTKEY(col)` / `DISTSTYLE` 不在本仓语法里。** `createstmt`（`RedshiftParser.g4:631-637`）在 `opttableelementlist` 之后只接 `optinherit? optpartitionspec? table_access_method_clause? optwith? oncommitoption? opttablespace?`；`DISTKEY`/`SORTKEY` token 在 parser 里只出现在 `rs_colattributes`（`:683-684`）。所以 `README.md:36-40` 的 Quick Start（表级 `DISTKEY(id) SORTKEY(name)`）按语法**应当解析失败**——这是静态核对结论，未实际编译运行该段示例。
6. **212 个样例没有一个用到 Redshift 扩展。** 在 `examples/` 里 grep `DISTKEY|SORTKEY|ENCODE|DISTSTYLE` 为 0 命中；样例文件名（`aggregates.sql`、`brin.sql`、`amutils.sql`、`combocid.sql` …）与 PostgreSQL `src/test/regress/sql/` 高度一致，**推测直接取自 PG 回归套件**。README 的 “200+ test cases” 指数量对得上（212），但覆盖的是 PG 语法而非 Redshift 语法。
7. **`.g4` 规则规模**：parser 818 条规则（生成常量 `RedshiftParserRULE_*` 共 818 个，最大编号 817）；lexer 684 个具名 token 常量（最大编号 686）；`stmt` 的顶层语句分支 **124 个**（`RedshiftParser.g4:32-156`），而不是 README 说的 “200+ statement types”。

**生成命令（唯一权威写法）**

```bash
antlr -Dlanguage=Go -package parser -visitor -o . RedshiftLexer.g4 RedshiftParser.g4
```

即 `build.sh:2`。要点：

- `-package parser`：所有 Go 文件都是 `package parser`，与目录名 `redshift-parser` 不同，import 后标识符是 `parser`；
- `-o .`：生成物落回仓库根，与 `.g4` 同级；
- `-visitor`：同时生成 listener（默认开启）与 visitor；
- **没有锁定 ANTLR 版本**：脚本只写 `antlr`。生成物头写的是 4.13.2，换一个 4.13.x 重新生成可能产生整文件级 diff，这是本仓最大的可重现性风险（§12）。

**生成器与手写代码的耦合点**（读代码时最容易漏的一半行为）：

1. `RedshiftParser.g4:5` → 生成的 `RedshiftParser` 结构体内嵌 `RedshiftParserBase`（`redshift_parser.go:17-19`），所以 `p.ParseRoutineBody(...)`、`p.GetParsedSqlTree(...)` 这类调用实际落到手写方法。
2. `RedshiftLexer.g4:37` → `RedshiftLexer` 内嵌 `RedshiftLexerBase`（`redshift_lexer.go:17-22`），`.g4` 里的 `{l.pushTag()}`, `{p.isTag()}?` 等 action/predicate 由手写基类实现。
3. `RedshiftParser.g4:1916` 的 `p.ParseRoutineBody(localctx)` 是**内联 action**：它会被原样抄进 `redshift_parser.go:84540`，所以“手写逻辑”其实是靠 `.g4` 里的一行调用挂上去的。

## 4. 端到端主链路：从输入 SQL 到 AST

以 `CREATE TABLE t (id INT IDENTITY(1,1))` 这条 Redshift 语句为例；调用链与入口行号如下。

```
antlr.NewInputStream(sql)                              // parser_test.go:52
  └─ NewRedshiftLexer(input)                           // redshift_lexer.go:3573
       └─ NextToken()（按需拉取，非全量扫描）
            └─ NewCommonTokenStream(lexer, 0)          // parser_test.go:56
                 └─ NewRedshiftParser(stream)          // redshift_parser.go:6372
                      └─ p.Root()                      // :7999
                           ├─ p.Stmtblock()            // :8235
                           │    └─ p.Stmtmulti()       // :8385
                           │         └─ p.Stmt()        // :10652
                           │              AdaptivePredict(..., decision)
                           │              └─ p.Createstmt()      // :30580
                           │                   └─ p.ColumnDef()   // :32298
                           │                        └─ p.Rs_colattributes() // :32588
                           └─ p.Match(RedshiftParserEOF)          // :8009
```

### 步骤 1：读入文本，构造字符流

- 生产/测试入口一致：`antlr.NewInputStream(string(data))`（`parser_test.go:52`）。
- 产出 `antlr.CharStream`；lexer 的 `LA(k)`、`Seek()` 都基于它（`redshift_lexer_base.go:32`、`:41`）。

### 步骤 2：词法分析

- 入口：`NewRedshiftLexer`（`redshift_lexer.go:3573`），`RedshiftLexerInit()`（`:3567`）先装载 ATN/DFA。
- `RedshiftLexer.g4:36-39` 打开 `caseInsensitive = true`，因此 `select`/`SELECT` 落到同一个 token；但标识符片段 `IdentifierStartChar` 显式关掉大小写折叠（`:2720`），避免把 `[a-zA-Z_]` 折成同一类。
- 4 个 mode（`RedshiftLexer.g4:2983`、`:3017`、`:3032`、`:3051`）：
  - `EscapeStringConstantMode` / `AfterEscapeStringConstantMode` / `AfterEscapeStringConstantWithNewlineMode`：`E'...'` 里的转义与反斜杠续行；
  - `DollarQuotedStringMode`：`$tag$...$tag$`。
- 手写钩子在 `.g4` 内联调用：
  - `Operator` 规则末尾 `{l.HandleLessLessGreaterGreater();}`（`RedshiftLexer.g4:187-189`），把 `<<`/`>>` 改回 `LESS_LESS`/`GREATER_GREATER`（`redshift_lexer_base.go:47`）；
  - `BeginDollarStringConstant` → `{l.pushTag();}` + `pushMode(DollarQuotedStringMode)`（`:2838-2841`）；结束规则用 `{p.isTag()}?` 谓词 + `{l.popTag();}` + `popMode`（`:3061-3065`）；标签栈实现在 `string_stack.go`；
  - `NumericFail` → `{l.HandleNumericFail();}`（`:2889-2892`），回退 2 个字符并改判为 `Integral`（`redshift_lexer_base.go:41`）；
  - `charIsLetter` / `CheckIfUtf32Letter` 作为标识符谓词（`RedshiftLexer.g4:2727`、`:2730`）。
- 空白、换行、行注释、块注释全部 `-> channel(HIDDEN)`（`:2919-2938`），parser 在默认通道上看不到它们；psql 元命令 `\d` 走 `MetaCommand`（`:2960-2962`），并由 `plsqlconsolecommand` 规则接住（`RedshiftParser.g4:159-161`）。
- 产出：惰性的 `antlr.TokenSource`。

### 步骤 3：装填 token 流

- `antlr.NewCommonTokenStream(lexer, 0)`（`parser_test.go:56`），第二个参数 `0` = 只取默认通道。
- `CommonTokenStream` 支持任意位置 `LT(k)`，这是 `stmt` 上 124 路 `AdaptivePredict` 能回溯的前提。

### 步骤 4：语法分析入口

- `Root()`（`redshift_parser.go:7999`）由 `RedshiftParser.g4:15-17` 的 `root : stmtblock EOF ;` 生成：`EnterRule` → `Stmtblock()` → `Match(EOF)` → `ExitRule`；`errorExit` 分支统一做 `ReportError` + `Recover`（`:8016-8024`）。
- 必须匹配 `EOF`，所以“尾部有垃圾”不会静默放过；测试还会额外断言树的首尾 token 索引（`parser_test.go:74-89`）。
- 空输入也能过：`stmtmulti : (stmt SEMI?)*`（`RedshiftParser.g4:27-29`）允许 0 条语句，`root` 只要求 `EOF`。同时 `SEMI?` 意味着**分号可省略**，`SELECT 1 SELECT 2` 这类输入不会被语法层拒绝。

### 步骤 5：语句分派（ALL(*)）

- `Stmt()`（`redshift_parser.go:10652`）对 124 个分支做一次 `AdaptivePredict`（`:10661`），然后 `switch` 到具体规则，例如 `p.Createstmt()`。
- 这是 ANTLR 的 ALL(*) 自适应预测：不是 LL(k) 的固定前瞻，遇到 SQL 这种强歧义输入会在运行时模拟 ATN 决定分支；`RedshiftParserParserStaticData`（`redshift_parser.go:21-30`）里的 `serializedATN` + `decisionToDFA` 就是它的数据底座。

### 步骤 6：语句内部（CREATE TABLE 路径）

- `Createstmt()`（`:30580`）→ `Opttableelementlist()`（`:31292`）→ `Tableelementlist()`（`:31582`）→ `ColumnDef()`（`:32298`）→ `Rs_colattributes()`（`:32588`）。
- `ColumnDef` 的规则体是 `colid typename create_generic_options? rs_colattributes? colquallist`（`RedshiftParser.g4:674-676`），所以 Redshift 列属性只在这一处生效，且**一次只能挂一个**（`rs_colattributes?` 不是 `*`），`IDENTITY` 与 `ENCODE` 不能同时出现；`Rs_colattributesContext` 带 `seed`/`step` 两个标签字段（`redshift_parser.go:32399-32403`），对应 `IDENTITY(seed, step)` 里的具名参数。
- `typename` 的 `generictype` 允许任意标识符当类型（`RedshiftParser.g4:3221-3223` → `type_function_name : identifier | ...` `:4031-4036`）。因此 `SUPER`、`VARBYTE`、`GEOMETRY` 这类 Redshift 类型**没有专门规则，但能作为泛型类型名通过**——这是“容忍式支持”，不是精确建模。

### 步骤 7：函数体二次解析（树中树）

- 触发点：`createfunc_opt_list` 规则尾部的内联 action（`RedshiftParser.g4:1913-1920`），生成后是 `redshift_parser.go:84507` 的 `Createfunc_opt_list()`，在 `:84540` 调 `p.ParseRoutineBody(localctx)`。
- `ParseRoutineBody`（`redshift_parser_base.go:36`）流程：
  1. 在 `createfunc_opt_item` 列表里找 `LANGUAGE` 项，取 `nonreservedword` 下的 `Identifier` 文本作为 `lang`（`:43-78`）；
  2. 找带 `AS` 的项，取 `Func_as` → 第 0 个 `sconst` → `GetRoutineBodyString()`（`:83-116`）；
  3. 用 `getRedshiftParser(text)` 新建一套 lexer/parser（`:185-194`），并按 `lang` 调 `Plsqlroot()` 或 `Root()`（`:118-123`），把结果赋给 `Func_asContext.Definition`（`:120-122`；字段声明见 `RedshiftParser.g4:1956` 的 `func_as locals[antlr.ParserRuleContext Definition]`，生成字段在 `redshift_parser.go:85484`）。
- 这是全仓唯一的“树中树”，也是遍历时最易踩空处：`Definition` 可能为 nil（`redshift_parser_base.go:95-106` 的多个 `return`）。
- **语言名识别很窄**：只读 `nonreservedword → Identifier`，因此 `LANGUAGE 'plpgsql'`（字符串形式）和 `LANGUAGE sql`（`sql` 被词法成关键字 token `SQL_P`，`Identifier()` 返回 nil）都不会进入二次解析。实测 `examples/alter_generic.sql:29-32`（`LANGUAGE sql` + 单引号函数体）没有产生任何内层报错，而 `examples/triggers.sql:938`（`LANGUAGE plpgsql` + 单引号函数体）产生了 1 条内层报错——与上述代码路径一致。

### 步骤 8：错误处理与产物

- 外层 parser/lexer 默认用 ANTLR 的 `DefaultErrorStrategy`；测试与 `ParseService` 会换 listener、并可用 `antlr.NewBailErrorStrategy()` 首错即停（`parser_test.go:131`）。
- 测试的 `CustomErrorListener`（`parser_test.go:15`）只统计**外层**错误（`:71-72`）；内层 parser 的错误由 `RedshiftParserErrorListener` 先收进内层 `parseErrors`（`redshift_parser_error_listener.go:12`），再由 `ParseRoutineBody` 复制回外层 `receiver.parseErrors`（`redshift_parser_base.go:124-132`）。外层同样**没有导出的 getter**，测试也不读它。
- 产物就是 `IRootContext`；消费方用 `RedshiftParserListener` 或 `RedshiftParserVisitor` 下钻，或直接对 `*XxxContext` 做类型断言。

## 7. 关键设计点

**设计 1：单方言 + 单 `.g4` 对，不做“统一 AST”。**
Redshift 与 PostgreSQL 的差异集中在 DDL（分布键、排序键、编码）与少数函数；抽公共 Node 接口的收益低、维护成本高。本仓选择“一份 PG 语法 + 少量 Redshift 补丁”，代价是 **Redshift 覆盖非常浅**：表级 `DISTKEY`/`SORTKEY`/`DISTSTYLE` 按 Redshift 写法根本无法解析；`SUPER`/`VARBYTE` 等类型、`GETDATE`/`DATEADD` 等函数则因为 `generictype` 与“任意函数名可作标识符”而能**碰巧通过语法**，但没有任何专门规则或语义。

**设计 2：生成物提交进仓，`./build.sh` 是开发者动作而非构建动作。**
消费方不必装 Java/ANTLR，`go get` 即用；代价是语法与生成物可能不同步，且 ANTLR 版本未锁（§12）。`CLAUDE.md:104` 用全大写强调“Always run `./build.sh` before tests”，说明这是踩过的坑。

**设计 3：用 `superClass` 把 ANTLR 表达不了的东西下放到 Go。**
`$tag$` 需要标签栈、`<<`/`>>` 需要按上下文改 token 类型、`E'...'` 需要 mode 切换——`.g4` 没有可变状态，只能在 `RedshiftLexerBase` 里写命令式代码，再用 predicate/action 挂钩（`RedshiftLexer.g4:181`、`:188`、`:2840`、`:3063`）。读词法必须同时读 `.g4` 与 `redshift_lexer_base.go`，否则漏一半行为。

**设计 4：函数体二次解析是“树中树”，但只在很窄的条件下发生。**
`ParseRoutineBody` 只识别**裸标识符**形式的 `LANGUAGE`（且 `sql` 因是关键字 token 而识别不到），只处理 `plpgsql`/`sql` 两种；单引号函数体会经 `TrimQuotes`（`redshift_parser_base.go:135-140`）裁剪。该函数 `return s[1 : len(s)-2]` 的上界比正确值少 1，**会多裁掉最后一个字符**：`examples/triggers.sql:938` 的 `AS 'begin RETURN NULL; end'` 被裁成 `begin RETURN NULL; en`，内层 parser 因此在 `1:21` 报 `mismatched input '<EOF>' expecting {'=', ':='}`——这与 `go test` 全量运行时 stderr 出现的同一条报错完全吻合。单文件复跑 `triggers.sql` 可稳定复现 1 条。

**设计 5：测试即规范，但只验证“能解析”，不验证“解析对不对”。**
`TestRedshiftParser`（`parser_test.go:40`）遍历 `examples/` 的 212 个文件，对每个文件断言 lexer/parser 错误数为 0，并断言树的首尾 token 索引（`:74-89`）。它**没有**任何“树形状”断言；`:90` 那句被注释掉的 `require.Equal(t, string(data), stream.GetTextFromTokens(...))` 是曾想做 token 往返校验又放弃的痕迹。更关键的是：内层 `ParseRoutineBody` 的错误不进外层 listener，所以**函数体解析失败不会让测试变红**。

**设计 6：错误处理分两层，但内层不可观测。**
外层错误用标准 listener 统计（可替换为 `BailErrorStrategy`）；内层错误先进内层 `parseErrors`，再复制回外层（`redshift_parser_base.go:124-132`），全程没有导出 getter。`getRedshiftParser`（`redshift_parser_base.go:185-194`）新增了 `RedshiftParserErrorListener` 但**没有移除默认 `ConsoleErrorListener`**，于是同一批内层错误既落 `parseErrors` 又打到 stderr；测试只看外层 listener，所以函数体解析失败不会让测试变红——这就是 `go test` 输出里那 10 条 `line x:y ...` 的来源。

### 8.2 新增一个“AST 节点”

本仓没有节点注册表：**新增 Context 类型 = 新增语法规则 = 改 `.g4` 再生成**。不要手写 Context 类型，生成物会被覆盖。若需要在节点上挂额外数据，用 ANTLR 的 `locals[...]`（参考 `func_as locals[antlr.ParserRuleContext Definition]`，`RedshiftParser.g4:1956`），生成器会产出同名字段（`redshift_parser.go:85484`）。

这是本仓最值得补的缺口。标准做法：

1. 新增规则 `rs_table_attributes : DISTSTYLE (AUTO|EVEN|KEY|ALL) | DISTKEY OPEN_PAREN colid CLOSE_PAREN | (COMPOUND|INTERLEAVED)? SORTKEY OPEN_PAREN columnlist CLOSE_PAREN | ... ;`（可参考 workspace 内 `parser/redshift/RedshiftParser.g4:785-788` 的成熟写法）；
2. 在 `createstmt` 的三条分支后各接 `rs_table_attributes*`（`RedshiftParser.g4:632-636`）；
3. `./build.sh`；
4. 加 `examples/` 用例（现有 212 个样例一个都没覆盖）。

### 8.4 新增 token / 关键字

- 在 `RedshiftLexer.g4` 里加大写 token 规则，再生成；
- 如果它还要能当标识符用，必须把它加进 `unreserved_keyword`（`RedshiftParser.g4:4067`）或 `col_name_keyword`（`:4370`）等规则，否则会变成保留字，破坏现有 SQL；
- **`keywords.go` 不参与解析**：`IsReservedKeyword`（`redshift_lexer_base.go:436`）只被 `IsIdentifier`（`:75`）调用，而 `IsIdentifier` 在仓内没有任何调用点。改 `keywords.go` 只影响对外字典与消费方，不会改变 parser 行为。

### 8.5 新增手写钩子

- 词法：在 `RedshiftLexerBase` 加方法，在 `.g4` 用 `{l.xxx();}`（action）或 `{p.xxx()}?`（predicate）调用；
- 语法：在 `RedshiftParserBase` 加方法，在 `.g4` 规则尾部用 `{p.xxx(localctx);}` 调用（`createfunc_opt_list` 就是这么挂 `ParseRoutineBody` 的）。
- 重新生成后手写文件不会被覆盖，但**方法名必须与 `.g4` 里写的一致**，否则生成代码编译失败。

### 8.6 接入下游

- **只要语法校验**：照 `parser_test.go:52-72` 的写法，装自己的 listener，看计数；
- **要遍历结构**：嵌 `BaseRedshiftParserVisitor`，按 `*XxxContext` 覆写 `VisitXxx`；或嵌 `BaseRedshiftParserListener`；
- **要列级血缘/审核**：本仓只给树，需要自己在上层做 catalog 与语义规则；
- **要复用 parser 提升吞吐**：照 `ParseService`（`parser_test.go:95-139`）做 `Reset` + `SetInputStream` + `SetTokenStream`，并注意它用的是 `BailErrorStrategy`。

## 12. 未覆盖 / 存疑

1. **README/CLAUDE 与实际代码不一致（事实）**：
   - `README.md:12` 称 “Full support for ... DISTKEY, SORTKEY”，但语法只有列级 `rs_colattributes`，没有表级 `DISTKEY(col)`/`SORTKEY(col)`；
   - `README.md:11` 称 “200+ SQL statement types”，实际 `stmt` 只有 124 个分支；
   - `CLAUDE.md:28-31` 仍写 `EnginePostgreSQL`/`EngineRedshift`，`CLAUDE.md:71` 仍要求“用 `GetEngine()` 区分 Redshift/PostgreSQL”；Go 代码里 grep `GetEngine|EnginePostgreSQL|engine_specific` 为 0 命中，`engine_specific_test.go` 也不存在——最后一次 commit 正是 `chore: remove the engine switching logic (#1)`；
   - `CLAUDE.md:22` 称 “600+ keywords”，`keywords.go` 实际 843 条。
2. **ANTLR 版本未锁定（事实 + 风险）**：`build.sh` 只写 `antlr`，没有 `4.13.2`、没有 jar、没有 `.antlr-version`。生成物头是 4.13.2，运行时是 4.13.0。换版本重新生成会产生整文件级 diff，这是本仓最大的可重现性风险。
3. **`TrimQuotes` 疑似 off-by-one（已复现）**：`redshift_parser_base.go:139` 返回 `s[1 : len(s)-2]`，正确上界应为 `len(s)-1`。`examples/triggers.sql:938` 的单引号 plpgsql 体因此被裁掉末字符 `d`，内层 parser 报 `1:21 mismatched input '<EOF>' expecting {'=', ':='}`；全量测试 stderr 共 10 条同类报错，但测试仍 PASS。该实现与 `parser/redshift/redshift_parser_base.go:139` 完全相同，属继承缺陷。
4. **`LANGUAGE` 识别过窄（代码推断，有现象支持）**：`ParseRoutineBody` 只取 `nonreservedword → Identifier`（`redshift_parser_base.go:56-71`），所以 `LANGUAGE 'plpgsql'` 不解析、`LANGUAGE sql` 因 `sql` 是关键字 token `SQL_P` 也不解析。`alter_generic.sql` 的单引号 `LANGUAGE sql` 函数体没有任何内层报错，可作旁证；**未逐条验证所有写法**。
5. **内层错误不可观测（事实）**：`parseErrors` 未导出、无 getter（`redshift_parser_base.go:12`）；`RedshiftParserErrorListener` 的 `grammar` 字段也未导出（`redshift_parser_error_listener.go:5-7`）；`getRedshiftParser` 未移除默认 `ConsoleErrorListener`（`:190-192`），错误会同时落到 `parseErrors` 与 stderr。测试只统计外层 listener，函数体解析失败不会失败。
6. **212 个样例不覆盖 Redshift 扩展（事实）**：grep `DISTKEY|SORTKEY|ENCODE|DISTSTYLE` 为 0 命中；样例名与 PG 回归套件一致（**推测来源为 `src/test/regress/sql/`**，未逐文件比对）。因此“Redshift 支持”在本仓没有测试证据。
7. **大量对外符号在仓内无调用点（事实）**：`IsIdentifier`（`redshift_lexer_base.go:75`）、`IsReservedKeyword`（`:436`）、`GetParsedSqlTree`（`redshift_parser_base.go:21`）、`GetBuiltinFunctions`（`builtin_function.go:831`）在仓内均只有定义、无调用。它们是给消费方的 API，不是解析流程的一部分；不要误以为关键字表参与 token 归类。
8. **`StringStack` 行为与命名不符（事实）**：`Pop()` 取 `items[0]`（`string_stack.go:19-26`），是 FIFO 而非 LIFO；当前 dollar-quote 用法不会暴露，但若未来支持嵌套标签需改成真正的栈。
9. **无 LICENSE 文件（事实）**：`README.md:182-184` 声称 MIT，根目录没有 `LICENSE`；`RedshiftLexer.g4:6-30` 保留了 Tunnel Vision 的 MIT 头。
10. **无 CI / 无 Makefile（事实）**：没有 `.github/workflows`，只有 `build.sh`；`parser_test.go` 的全量断言是否在提交前被强制执行，仓内无法保证。
11. **空输入与缺分号可通过（事实）**：`stmtmulti : (stmt SEMI?)*`（`RedshiftParser.g4:27-29`）+ `root : stmtblock EOF` 意味着空串合法、`SELECT 1 SELECT 2` 也合法；做“SQL 合法性门禁”时必须在上层另加约束。

## 在你的数据栈里的位置

`redshift-parser` 处在**“Redshift SQL 文本 → 语法树”**这一环，刻意只做语法、不做语义。
它与 workspace 里的 `parser`（多方言集合）是**并列的两种组织方式**：`parser` 用“每方言一个目录 + 统一工程约定”覆盖 16 个方言，本仓则把 Redshift 单独抽成一个可 `go get` 的 module，并保留 PG 回归样例作为验收基线。
向下游看，它输出的是 ANTLR `ParseTree`；`MetricFlow` 的表达式解析走 Python 侧 `sqlglot`（`metricflow/converters/expression_utils.py:5`），`dbt` 仓内也没有对本仓 Go 包的引用。所以本仓的价值不在“被谁 import”，而在**“不连 Redshift 也能确认这段 DDL/DML 在语法上成立，并能按规则类型取到结构”**——这是整条链里唯一的纯离线 Redshift 语法能力；若需要完整 Redshift 语法（表级分布/排序键、`ALTER DISTKEY`、`DISTSTYLE`），应优先用 workspace 内的 `parser/redshift`，或按 §8.3 给本仓补齐。

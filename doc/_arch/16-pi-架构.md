## 1. 一句话定位

pi 是一个**在终端里运行的编码智能体（coding agent）**：它把「用户输入 → 组装上下文与系统提示 → 调用任意 LLM 提供方 → 让模型发起工具调用 → 在本机执行 bash/edit/write/read → 把结果写回会话文件 → 决定是否再跑一轮」这条闭环做成一个**可嵌入、可扩展、可回放的运行时**；CLI、TUI、print、JSON、RPC、TypeScript SDK 六种入口共享同一套 `AgentSession` 与 `Agent` 内核。

它**解决**：

- 让模型真正能读写仓库、执行命令，并把每次改动落到磁盘；
- 会话持久化与分叉（树状 JSONL），可恢复、可回退、可压缩；
- 多家模型提供方 / 协议的统一接入（40+ provider 目录，含 OAuth、自建代理）；
- 扩展生态：第三方以 TypeScript 模块的方式注册工具、命令、provider、UI 与事件钩子；
- 把「模型写的 JS」放进受限沙箱执行（codemode），只把脚本输出回灌给模型。

它**不解决**：

- 不是通用工作流调度器（没有 DAG、没有跨机任务编排）；
- 不做容器/网络隔离：**扩展代码与工具执行都在 pi 进程的 OS 权限下运行**（`packages/coding-agent/docs/how-pi-works.md:47-49`）；
- 不托管模型推理；token/费用只做统计，不做配额治理。

一句话：**pi 是「单进程、可扩展的终端编码智能体运行时」，不是调度系统，也不是安全沙箱。**

要点：

- **单进程、无守护进程**：TUI、扩展、工具、会话写入都在同一 OS 进程内（`docs/how-pi-works.md:47-49`）。
- 只有三类「跨边界」：LLM 的 HTTPS、bash 子进程、MCP server 子进程；codemode 另起 worker thread。
- `AgentSessionRuntime` 是「cwd 变更」的分界：切目录/新建/fork 时销毁旧 runtime 再建新 runtime（`src/core/agent-session-runtime.ts:74`、`:196`、`:226`、`:262`）。

  - 若最后一条是 assistant，先 `_checkCompaction(...)`（`:1893-1896`）；
  - `extensionRunner.emitBeforeAgentStart(...)`（`:1899`）——扩展可改系统提示、工具清单、注入消息；
  - 组装 `messages`（用户消息含图片规范化、nextTurn 消息、扩展 custom 消息）（`:1908-1936`）；
  - `_preparePromptAndToolLoadout(...)`（`:1937`）应用本轮系统提示与工具装载；
- 然后 `await this.agent.prompt(messages)`（`:1863`），进入「后置轮循环」：`_handlePostAgentRun()` 决定是否 `agent.continue()`（`:1864-1873`）。

`Agent.prompt`（`packages/agent/src/agent.ts:373`）→ `runPromptMessages`（`:432`）→ `runWithLifecycle`（`:507`）→ `runAgentLoop(...)`（`packages/agent/src/agent-loop.ts:102`）。

### 步骤 8：`runLoop` 的单轮结构

`packages/agent/src/agent-loop.ts:163`：

```
while (true) {                        // 外层：follow-up 可能再开一轮
  while (hasMoreToolCalls || pending) { // 内层：工具调用 + steering
    prepareNextTurn / prepareRequest    // 每轮前的模型、思考等级、上下文重算
    streamAssistantResponse(...)        // 见步骤 9
    if stopReason === error/aborted → turn_end + agent_end，返回
    toolCalls = message.content.filter(type === "toolCall")
    executeToolCalls(...)               // 见步骤 10
    finishTurn(...)                     // 可返回 end/continue
    pendingMessages = getSteeringMessages()
  }
  followUpMessages = getFollowUpMessages()
  if (没有更多消息) break
}
emit({ type: "agent_end", ... })
```

### 步骤 9：`streamAssistantResponse` 组装请求并流式消费

`agent-loop.ts:381`：

1. `config.transformContext?.(messages)` —— 对应 `AgentSession` 注入的 `extensionRunner.emitContext(...)`（`sdk.ts:436`）；
2. `await config.convertToLlm(messages)` —— `AgentMessage`（含 system/custom/bashExecution）→ LLM 兼容 `Message`（`sdk.ts:297`、`src/core/messages.ts`）；
3. `streamFunction(config.model, llmContext, {...})`（`:403`）—— 即 `ModelRuntime.streamSimple`（`src/core/model-runtime.ts:723`）；
4. 逐个消费流事件：`start` / `text_*` / `thinking_*` / `toolcall_*` / `done|error`，同步更新 `context.messages` 并 `emit({type:"message_start"| "message_update"})`（`:414-451`）。

`ModelRuntime.streamSimple`（`model-runtime.ts:723`）内部：解析鉴权 → 选 provider → 交给 provider 的 `streamSimple`（`model-runtime.ts:747`）→ 落到 `packages/ai/src/models.ts:907` 的统一实现。

### 步骤 10：工具批次执行

`executeToolCalls`（`agent-loop.ts:508`）：

- 只要有一个工具声明 `executionMode === "sequential"`，或全局 `toolExecution === "sequential"`，走串行（`:516-522`）；
- 串行路径：`emit(tool_execution_start)` → `prepareToolCall` → `executePreparedToolCall` → `finalizeExecutedToolCall` → `emit(tool_execution_end)` → 生成 `ToolResultMessage`（`agent-loop.ts:541-577`）；
- `executePreparedToolCall` 调用 `prepared.tool.execute(id, args, signal, onUpdate)`（`:832`）；
- 并行路径 `executeToolCallsParallel`（`:586`）同构，只是并发发起。

`bash` 工具的实际执行（`src/core/tools/bash.ts:434` → `src/core/bash-executor.ts:48` `executeBashWithOperations`）：

- 逐块解码 stdout/stderr、剥 ANSI、替换二进制乱码（`bash-executor.ts:76-111`）；
- 超过 `DEFAULT_MAX_BYTES` 时把全量输出落到临时文件（`:84-88`、`:132-135`）；
- `truncateTail(...)` 截断后把可读片段返回模型，完整输出路径放在 `fullOutputPath`（`:132-145`）。

`read`/`edit`/`write` 直接走文件 IO，`edit` 还经 `withFileMutationQueue`（`src/core/tools/file-mutation-queue.ts:32`，由 `tools/index.ts:20` 重导出）串行化同文件改动。

### 步骤 11：事件回灌 → 持久化 → 自动压缩

`Agent` 产生的事件由 `AgentSession._handleAgentEvent`（`agent-session.ts:1104`）处理：

1. 先发扩展（`_emitExtensionEvent`，`:1144`），再通知公开订阅者（`:1145`）；
2. `message_end` 时按角色持久化：custom → `appendCustomMessageEntry`，system/user/assistant/toolResult → `appendMessage`（`:1148-1167`）；
3. assistant 消息记入 `_lastAssistantMessage`，并重置重试/溢出恢复标志（`:1171-1188`）；`turn_end` 时补发挂起的 custom 消息（`:1196-1199`）；
4. 每轮结束后由 `_handlePostAgentRun()` 触发 `_checkCompaction(...)` 估算 token：`shouldCompact(contextTokens, contextWindow, settings)`（`:3111`，实现 `compaction/compaction.ts:267`），命中则 `_runAutoCompaction("threshold", false)`（`:3127`），内部 `prepareCompaction` + `compact(...)`（`compaction.ts:965`）生成摘要条目。

### 步骤 12：循环终止与 settle

- 无工具调用且无 steering/follow-up → `runLoop` 发 `agent_end`（`agent-loop.ts:320`）；
- `_startRun` 的 finally 里 `_emitAgentSettled()`（`agent-session.ts:1880`），UI 回到可输入态；
- 该轮所有消息已增量写入 JSONL 会话文件（`SessionEntry` 带 `parentId`，`session-manager.ts:57-67`）。

## 7. 典型场景分步

### 7.1 场景 A：交互模式下的「读文件 → 改文件」

1. TUI 提交文本 → `InteractiveMode` 调 `session.prompt(text)`（`agent-session.ts:2058`）。
2. `prompt` 通过 input handler / 模板展开后 `_startRun`（`:2138`）。
3. `_prepareRun` 触发 `before_agent_start`，把系统提示与工具装载定稿（`:1890-1937`）。
4. `agent.prompt` → `runAgentLoop`（`agent-loop.ts:102`）→ `streamAssistantResponse`（`:381`）→ 模型返回 `toolCall{name:"read", path}`。
5. `executeToolCalls` 串/并行执行（`:508`）；`read` 工具读盘并把带行号的内容作为 `ToolResultMessage` 回灌。
6. 下一轮模型返回 `toolCall{name:"edit"}`；`edit` 走 `withFileMutationQueue` 保证同文件串行（`file-mutation-queue.ts:32`，经 `tools/index.ts:20` 重导出）。
7. `_handleAgentEvent` 每条 `message_end` 即写入 JSONL（`agent-session.ts:1148-1167`）。
8. 模型不再发起工具调用 → `agent_end` → `_emitAgentSettled`，TUI 刷新并等待下一次输入。

### 7.2 场景 B：RPC 模式（外部程序驱动）

1. `pi --mode rpc` → `runRpcMode(runtime)`（`rpc-mode.ts:54`）。
2. stdin 逐行读 JSON 命令，`switch` 分发：`prompt`（`:394`）、`steer`（`:416`）、`abort`（`:426`）、`new_session`（`:435`）、`set_model`（`:470`）、`compact`（`:533`）、`bash`（`:561`）、`fork`（`:611`）…
3. 每个命令调用同一 `runtime.session`，事件以 JSONL 写 stdout——与 TUI 走完全相同的 `AgentSession`，只是渲染层不同（`docs/how-pi-works.md:35-39`）。

### 7.3 场景 C：恢复 / 分叉 / 压缩

- 恢复：`createSessionManager` 打开已有 JSONL（`main.ts:696`）；`createAgentSession` 用 `buildSessionContext()` 取活动分支消息（`sdk.ts:210`），并从 `model_change`/`thinking_level_change` 条目恢复模型与思考等级（`sdk.ts:219`、`:256-260`）。
- 分叉：`AgentSessionRuntime.fork(...)`（`agent-session-runtime.ts:262`）复制选中历史到新文件；分支摘要由 `BranchSummaryEntry` 承载（`session-manager.ts:106`）。
- 压缩：`_checkCompaction` → `shouldCompact(...)`（`agent-session.ts:3111`）→ `_runAutoCompaction(...)`（`:3127`）→ `prepareCompaction` + `compact(...)`（`compaction.ts:965`）→ 写入 `CompactionEntry`；**原始 entry 不删除**，只在重建上下文时被摘要替换（`docs/how-pi-works.md:31`）。

### 7.4 场景 D：codemode 嵌套工具调用

1. 模型发起 `codemode` 工具调用（`CODEMODE_TOOL_NAME`，`extensions/codemode/tool.ts:39`）。
2. 脚本在 Worker Thread 的 QuickJS(WASM) 中运行（`packages/codemode/README.md:9-12`；WASM 路径 `config.ts:494`）。
3. 脚本内部 `tools.<name>(...)` 通过宿主注入的桥回调进入 `NestedToolCallRunner`（`agent-session.ts:120` 引入，`:737` 懒创建）。
4. 嵌套调用仍走 `tool_call`/`tool_result` 钩子（`tool.ts:8-10` 注释所述语义），但其结果**不进入 LLM 上下文**，只有脚本输出/返回值回灌。
5. `store()` 写入以 `codemode-store` 自定义条目落会话（`tool.ts:41-42` 的 `CODEMODE_STORE_ENTRY_TYPE`）。

## 8. 扩展点与二次开发

### 8.1 扩展（首选方式）

一个扩展就是一个 TypeScript 文件，默认导出 `ExtensionFactory`：

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerTool({ name: "my_tool", /* TypeBox parameters、execute */ });
  pi.registerCommand("hello", { handler: async (args, ctx) => { /* ... */ } });
  pi.on("tool_call", async (event) => { /* 可返回阻断/改写 */ });
}
```

放置位置与加载：

- 用户级：`~/.pi/agent/extensions/*.ts`（`packages/coding-agent/docs/extensions.md:17`，示例 `examples/extensions/hello.ts`）；
- 项目级：`<cwd>/.pi/extensions/`（本仓库自用示例见 `.pi/extensions/tps.ts` 等）；
- CLI：`-e/--extension <path>`（`main.ts:783` 的 `additionalExtensionPaths`）；
- pi 包（npm/git 分发多资源）：`src/core/package-manager.ts:818` `class DefaultPackageManager`，文档 `docs/packages.md`。

加载机制：`jiti` 直接解释 `.ts`，无需编译（`extensions/loader.ts:2`、`:12`）；loader 还会注入 `@earendil-works/pi-*` 与 `typebox` 的别名，使扩展与宿主共用同一份类型/实例（`loader.ts:101-122`）。

可注册项（`ExtensionAPI`，`types.ts:1592-1914`）：

| 类别 | API | 用途 |
|---|---|---|
| 工具 | `registerTool`（`:1671`） | 新工具（可设 `exposure` 控制是否直接可见/仅 codemode 可达） |
| 命令 | `registerCommand`（`:1680`） | `/xxx` 斜杠命令 |
| 快捷键/参数 | `registerShortcut`、`registerFlag`（`:1683`、`:1692`） | TUI 按键、CLI 扩展参数 |
| 模型 | `registerProvider`（`:1858`）、`registerVirtualModel`（`:1911`） | 自建 provider、别名/路由模型 |
| 渲染 | `registerMessageRenderer`（`:1715`）、`registerEntryRenderer`（`:1721`）、`registerToolRenderer`（`:1724`） | 自定义消息/工具输出样式 |
| 会话 | `setSessionName`、`sendUserMessage`（`:1754`、`:1741`） | 会话命名、主动注入消息 |
| UI | `setWidget`、`setStatus`、`setFooter`、`setHeader`、`setEditorComponent` 等（`:166-281`） | 终端组件与状态区 |

## 11. 未覆盖 / 存疑

1. **`durable` / `chord` / `env` 与主产品的运行时关系**：编码代理的 `package.json` 依赖中**没有** `durable`/`chord`/`env`（`packages/coding-agent/package.json:43-47`），只有 `durable`、`env` 声明依赖 `chord`。因此推断它们是「面向服务端/持久化/远端执行的平行产品线」，**当前 CLI 不使用**。依据：依赖声明 + 源码中未见 import。

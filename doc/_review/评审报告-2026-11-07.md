## 2. 方向四问

### 2.1 “本体为核心 + 单机可运行 + 功能优先”是否站得住

**站得住的部分**：85 条指标、159 类 / 139 属性、15,218 个文档片段对单机单域是合理规模；Oxigraph + PG + 本地 BGE-M3 的组合在这套规模下没有出现技术性塌陷。
**站不住的部分**：平台的“可出数”不取决于技术，而取决于业务事实与术语确认。
- 观测 100% synthetic（`SELECT data_source, count(*) → synthetic|37477`）。
- A-Box 事实账本 `fact_assertion=0`，而 `fact_event=10,146` 主要来自 `urn:platform:test:*` / smoke 图，且含 3,566 条 `purged_test_graph`——生产 A-Box 治理表是测试残留。
- 术语别名 0/18、`term_check=1`，术语层“门禁在、内容空”。
- 生成器修复（doc 59）能救回 5 条零观测指标，本身就是“供给问题而非算法问题”的证明。

**结论**：规模不是瓶颈，**知识/数据供给是瓶颈**。继续加指标、加端点不会提高“可出数”。

### 2.2 对标/赶超 AWS COA 的差距

- 该仓库是 AWS COA 的 fork（`origin=https://github.com/aws/context-ontology-accelerator.git`）。仓库根 `README.md:1-13` 仍是上游 AWS 版叙事（namespace/RBAC/MCP/Scan→Model→Serve），与单机产品不是同一形态。
- “赶超”从未转成验收口径：[09-需求对照与一致性复查.md](file:///d:/agentABC/coa/doc/_design/09-需求对照与一致性复查.md#L15) 标为“部分匹配”，:74 明确列为“待用户决策：需确认对标清单”。
- **可补且已局部领先**：治理工作流（提案/审批/supersede/门禁/证据包）、口径注册与三分可算性、验收证据链与可复现批次、T-Box/A-Box 命名图隔离、离线本地模型。
- **结构性不可能（在单机定位下）**：多租户与 IAM/RBAC、Glue/Athena/Databricks 连接器生态、Neptune/图集群规模、托管 SLA 与 SaaS 运营、商业支持。
- **差距的本质**不在功能点多少，而在“生态位 + 规模 + 运营”。用“赶超”作为对外话术会持续制造不可兑现承诺。

### 2.4 技术选型是否结构性错误/过早优化

**无结构性错误。** Oxigraph 0.5.7 + SPARQL 1.1 + ROBOT/ELK + PG18/pgvector + TEI/BGE-M3 均在本规模实测可用。
**真正的设计风险（非选型）**：
1. **同指标双计算路径**：`/metrics/{id}/compute` 走 `MetricCompiler`（事实表 SQL，[metric_compiler.py:142-169](file:///d:/agentABC/coa/platform/src/platform_core/metric_compiler.py#L142-L169)），`/metrics/{id}/output?compute=true` 走 `MetricService.compute`（读 `metric_observation` 聚合，[metrics.py:266-380](file:///d:/agentABC/coa/platform/src/platform_core/metrics.py#L266-L380)）。两条路径可对同一指标给出不同数值，却共用“可出数”话术。
2. **`/metrics-readiness` 是静态 registry**：20 行由迁移 V34 播种（`metric_readiness` 表，`checkedAt=2026-11-06`），16 executed / 3 not_executable / 1 registered_only。它是“人工断言”，不是运行时验证结果，但接口语义容易被读成“实测”。
3. **`metrics.py` 头注释“平台没有 metric fact store”已过时**：`metric_facts.py` 就是事实投影层（fact_function → observation）。头注释与实现自相矛盾。

**过早优化/冗余**：Fuseki 双实现（8080/8082 都在跑，但默认 profile 不启用）、`canvas_full` 端口占位、bundle 强 schema 匹配、数据字典 79 条绑定/297 条列注释全部落在静态 SQL（无运行时维护入口）。这些不致命，但增加维护面。

**对“可复现”意味着什么**

1. **tag 不是身份**：`73` 已记录 `merged-r02` 曾被 `docker commit` 临时件顶替；判断运行版本必须看 **容器 image id**。
2. **三套数据互不等价**：8080 是 57 条有观测 / 37,477 行；8082 是 39 文档 / 8,540 三元组；qa-fill 与 8087 无现场。同一端点在不同栈会给出不同数量级，**数字不可互换**。
3. **仓库只复现到“代码 + 默认配置（off）”**：8080 的 `full` + `synthetic` + 37,477 行全部依赖仓库外文件与卷；换机后无法重建，因此“可复现”目前只到**同机同卷**。
4. **死栈制造了幻影证据**：322,021（probe）、74/62/12（8087）都仍是文档里的“能力证明”，但已无法重跑；必须降级为“历史快照”。
5. **可复现应分五层**：代码 ✅ / 镜像 ✅ / 配置 ❌ / 数据 ❌ / 运行态 ❌。本轮只把第 1、2 层做实；后三层是本日变更暴露的最大结构性缺口。

**“单一一套权威栈”定义建议（评审意见）**

1. **唯一性**：同一时间只有 `AS-8080` 有权产生对外数字与验收结论；其他栈一律标注用途，不得混用口径。
2. **身份五元组**：`commit SHA + image id + schema max + 数据快照 id + 生效配置 sha256`，缺一项即视为不可复现；容器 id 与启动时间作为部署锚点单独登记。
3. **配置入仓**：生效配置脱敏后进仓库（`platform/config/authoritative.yaml` 或等价形态），密钥只经 env 注入；仓库外 override 不得作为唯一入口。
4. **数据契约**：快照必须带六项计数（docs/chunks/obs/facts/triples/A-Box）与校验和，可导出/导入；仅有 Docker 卷不算数据可复现。
5. **换栈票**：每次替换记录旧/新容器 id、image id、startedAt、迁移列表、换前后计数；R3 的缺口由此关闭。
6. **一条验证命令**：`stack verify` 一次性校验上述五元组与 manifest 关键数（85/74/57/56/35、schema 42、aboxGraphs 两图），不一致即失败。
7. **收缩与保留**：保留 3 个镜像（当前 `canvas-full-48c4840`、回退 `merged-42`、回归 `merged-r02`）；qa-fill / 8087 / probe 卷归档后删除；8082 可改为按需启动。
8. **引用纪律**：对外文档禁止引用 8082/8087/probe 的数量级结论；确需交叉校验时，必须同段写明“仅交叉校验、不可复算”。

### 9.6 剩余优先级（按“解决当前最痛缺口”排序）

1. **权威栈可校验（P0-A）**——配置脱敏入仓 + V43 + 五元组台账 + 换栈票 + `stack verify`。
   - 为什么第一：本日所有数字都建立在 8080 运行态上，而该运行态无法由仓库重建；换机即失去全部证据。它也是成本最低、能立刻止住“多套栈”扩散的一步。
2. **B 线闭环（P0-B）**——在 AS-8080 跑一次 A-Box 离线全量并留快照；溯源从档 1 推进到档 2/3（路径归因、L2 展开、解析器读标记）。
   - 为什么第二：值级溯源是 `76` 矩阵唯一“领先项”，但路径格 28.5% / raw 61.19% 不足以支撑“领先”话术；A-Box 推理不落在权威栈，B 线就仍是“能力证明”而非“当前状态”。
3. **知识供给（P1-A）**——33 题 7 confirmed / 21 assumed / 5 undecidable；术语别名 0/18；业务数据 0 条。
   - 为什么第三：这是“可出数”的真实瓶颈，但需要业务方决策，不是工程单方面能补；不解决，42 条对外可出数永远只是 synthetic。
4. **门禁可信度（P1-B）**——G06 重设计后重跑 R02；否则“8/10”与“24 PASS”都不可信。
5. **文档残留与栈收缩（P2）**——`45:460` 的 82/5、`52:263` 的 schema 34、`45` 模块表、根 README；清理死栈与多余镜像。

**结论一句话**：先做 1，不是因为它最显眼，而是因为不做它，2–5 的结论都无法被别人复算；2 可与 1 并行，3 需另起业务窗口。
